# Time Pilot — how the machine actually works

A model of Konami's Time Pilot (`timeplt`, 1982) derived from the program's own routines and
checked against the real ROM running under MAME. Its companion, `gameplay.md`, describes the same
game from the outside using only the public record; this document explains what the code does to
produce that game, and says plainly where the code does not settle something.

**Every claim carries a confidence tag, carried from the cell or routine's entry in `names.js`.**

- **`[seen]`** — the role was observed on the real ROM under MAME: a write, a read, a value change or
  a dispatch that only that role explains.
- **`[code]`** — read from the routines that touch it. The mechanics are exact; the role is an
  inference the machine has not yet been watched confirming.
- **`[guess]`** — plausible and unconfirmed. Not to be relied on.

A wrong role stated confidently is worse than no name at all, so where the code leaves a question
open this document says so, and §9 collects those questions.

---
## §2 The frame: one interrupt, four modes
Time Pilot's main processor has one heartbeat: a non-maskable interrupt at every vertical blank. Nearly all of the game runs inside that interrupt. The foreground program, once power-on is finished, does one thing forever: it takes drawing commands off a ring buffer and executes them. Every decision (reading the panel, counting coins, choosing what the screen is doing, flying the ship, sending a sound) happens in the vertical-blank service. The service does it by running one arm of a two-level **sequence machine**, whose outer level is the machine's mode. There are four modes: the power-on wipe, the attract presentation, the "credit on the board, press start" screen, and the round engine. The round engine is shared by the attract demo and real play. This part covers power-on, the frame service, coins and sound, the machine itself and the first three modes up to the moment a game starts, and then the round engine (mode 3) that both the demo and a real game run.

### Power-on: from the reset vector to a running frame

The Z80 starts at address zero, and the first thing Time Pilot does there is leave: trampolineToProbeExpansionThenSettleControlLatch [seen] is a bare jump to the real power-on code, probeExpansionThenSettleControlLatch [seen]. That routine first asks whether an expansion board is fitted. It reads EXPANSION_SOCKET_PROBE 0x6000 [seen], one byte past the end of the program ROM, and only a board answering 0x55 would take control. An empty socket floats high, so on a normal cabinet the question always comes back "no" and power-on carries on. It seats the stack at SPRITE_RAM_BASE 0xB000 [seen], so the stack grows down into the top of work RAM, and then kicks the watchdog through WATCHDOG_RESET 0xC200 [seen]. The board resets the processor unless this address is written often enough, and the value written does not matter, which is why every long stretch of the boot that follows is dotted with these kicks. Next it writes zero across the control latch from NMI_ENABLE_LATCH 0xC300 [seen]. That latch takes its data from the low bit and its line number from the address, two addresses to a line, so the walk drives its first four lines low: the frame-interrupt enable, the flip-screen line, the audio-interrupt line and the audio-mute line. The most important of these is line 0, the frame-interrupt enable: with it low, no vertical blank can interrupt the cold start. Finally the routine turns the picture on by copying DISPLAY_ON_VALUE 0x2D4B [seen], a program byte holding 1, into VIDEO_ENABLE_LATCH 0xC308 [seen]. The value comes from the image rather than an immediate, so a patched image can leave the screen dark.

The cold start is a chain of routines that each jump into the next, and none of them ever returns. clearWorkRamAndSpriteBank1ThenColdInit [seen] zeroes two overlapping runs of the sprite bank at SPRITE_BANK1_BASE 0xB410 [seen] and SPRITE_BANK1_SLOT0_Y 0xB411 [seen], then all 2 KB of work RAM from PLAYER_STATE 0xA800 [seen]. The first sprite bank, SPRITE_BANK0_BASE 0xB010 [seen], is not cleared here. From here on every game-state cell starts at zero, and everything later in the boot only sets the few structures that must not. It closes with the first of the game's many image checks: it adds up the 256 program bytes that begin at the frame-service entry, and a total other than a genuine image's does not halt the machine. Instead it runs one whole frame service early, out of band, which quietly corrupts the boot rather than refusing it.

clearScreenRamAndVerifyImageThenColdInit [seen] comes next. It fills the colour plane with attribute 0x10 and the character plane with the blank glyph 0xF1, so the screen starts in one known pattern. Even the two plane bases are read from program words, COLOUR_RAM_BASE_WORD 0x2581 [seen] and VIDEO_RAM_BASE_WORD 0x4A37 [seen], not written as immediates. It then folds every byte of the 24 KB program ROM into an eight-bit total, kicking the watchdog once per byte because the loop is long enough to trip it. The byte at address zero is counted twice, because it seeds the total and is also added as the first term. A genuine image lands on 0xAF. Any other total jumps into a velocity table and runs it as code, so control is destroyed rather than reported.

initColdStartRamThenSeedConfig [seen] fills the command ring at COMMAND_RING 0xAC00 [seen] with 0xFF. The ring treats a set high bit as "empty", so a zeroed ring would read as a backlog of pending commands, and this fill is what lets the foreground start idle. It then seeds the random register (seedRandomRegister [seen]), loads the default high-score table (loadDefaultHighScores [seen]) and parks both deferred cell lists on empty (emptyBothDeferredCellLists [seen]), with a watchdog kick after each.

### Settings: the switches read once, and the two defaults

seedGameConfigFromDipSwitches [seen] is where the operator's choices first reach RAM. Two fixed defaults come out of the image first. HIGH_SCORE_HI 0xA98D [seen] takes 1 from DEFAULT_HIGH_SCORE_HI 0x08C9 [seen], so the displayed high score starts at 10,000. KILL_QUOTA 0xA9CD [seen] takes 0x38 (56) from DEFAULT_KILL_QUOTA 0x0874 [seen], which is the quota every round copies when it starts, and matches the 56 enemies per era in gameplay.md. Both switch banks read active-low, so each read is complemented before use.

The coinage bank, DSW0_PORT 0xC360 [seen], goes into COINAGE_SETTINGS 0xA9B1 [seen], and unpackCoinage [seen] turns its two nibbles into the per-slot rates. Each nibble is looked up in the 16-entry COINAGE_VALUE_TABLE 0x4B95 [seen]. The low nibble ("Coin A") lands in COIN_SLOT_1_RATIO 0xA9C9 [seen] and the high nibble ("Coin B") in COIN_SLOT_2_RATIO 0xA9CC [seen]. Each result byte holds coins-required-minus-one in its high nibble and credits paid in its low. A nibble of 15 means free play: it raises FREE_PLAY 0xA9C0 [seen] to all ones before the lookup, and either slot alone is enough to raise it.

The gameplay bank, DSW1_PORT 0xC200 [seen], is the read side of the watchdog address. The routines of the chain share it out, each peeling off its bits and rotating the rest on. seedGameConfigFromDipSwitches turns the low two bits into a lives count of 3, 4 or 5. The fourth setting, which would compute 6, is stored as 0xFF, and since each lost life takes one off that means 255 lives. gameplay.md reports this setting as "256". A bonus life taken while the count reads 0xFF wraps it to 0, and the next lost life takes it back to 0xFF, so play goes on; the reserve strip shows its six-emblem clamp throughout. unpackTheFirstThreeSwitchSettings [seen] stores that count in STARTING_LIVES 0xA9C1 [seen], bit 2 in UPRIGHT_CABINET 0xA9C2 [seen] (1 for upright, 0 for cocktail), and bit 3 in BONUS_LIFE_SETTING 0xA9C3 [seen], which picks the bonus-life mark list and the attract captions that announce it. finishBootSelfTestAndColdStart [seen] takes bits 4–6 into DIFFICULTY_SETTING 0xA9C4 [seen] (0 to 7, in the order MAME labels 1 (Easiest) to 8 (Difficult)) and bit 7 into DEMO_SOUNDS_ENABLE 0xA9C6 [seen], the attract-sound gate. These cells are written once per boot. The frame service mirrors the gameplay bank every frame as well, but into a different cell, DIP1_MIRROR 0xA9AD [seen], which nothing reads. Moving a gameplay switch therefore has no effect until the next reset.

finishBootSelfTestAndColdStart then drives FLIPSCREEN_LATCH 0xC302 [seen] from FLIPSCREEN_INIT_BYTE 0x0C3E [seen] and paints the power-on picture, a lattice of boxes across the character plane (tileCharPlaneWithBoxLattice [seen]). It sums 256 bytes from BOOT_SELFTEST_CHECKSUM_BASE 0x27DE [seen] against 0xC5. Like the RAM-clear check, a mismatch runs a frame service out of band and then cold-starts anyway. petWatchdogThroughStartupDelayThenStartMachine [seen] holds the lattice on screen for a fixed delay: twelve passes counted down in SEQUENCE_DELAY 0xA9EB [seen], each pass a run of watchdog kicks, so the delay never lets the board reset under it. It leaves that cell at zero, sends sound command 0 straight to the audio processor to quiet it, and jumps to enableInterruptAndEnterForegroundLoop [seen] with NMI_ENABLE_BYTE 0x4C87 [seen], a program byte holding 1.

That routine is the hinge between boot and the running game. It writes the byte to NMI_ENABLE_LATCH 0xC300 [seen], which switches the frame interrupt on for the first time since power-on, kicks the watchdog, and jumps into the foreground loop runCommandRingDrainLoop [seen] for good. From this point the machine has exactly two lives. The foreground loop takes drawing and scoring requests off the command ring whenever it has time. The frame interrupt, once per vertical blank, does everything else.

### The vertical-blank service: the game's heartbeat

0x0066 is the Z80's non-maskable-interrupt vector. The board raises that interrupt at vertical blank while latch line 0 is set, so enterVblankInterrupt [seen] runs once a frame. It jumps to enterVerticalBlankService [seen], which leads straight into serviceVerticalBlankInterrupt [seen]. The same entry is what the boot-time image checks call on a tampered image. Every frame's work runs in a fixed order, and the order matters.

The display comes first, because the beam is between pictures. publishSpriteShadow [seen] copies the sprite shadow in work RAM into the two hardware sprite banks. drainBothDeferredCellLists [seen] then blanks the character cells painted on the previous pass and paints the ones now pending. Next the service closes its own gate by writing 0 to NMI_ENABLE_LATCH 0xC300 [seen], so a second vertical blank cannot land in the middle of this frame's work, and it kicks the watchdog.

It then settles the picture's orientation. SCREEN_UNFLIPPED 0xA987 [seen] is cleared only when ACTIVE_PLAYER 0xAD32 [seen] is nonzero and UPRIGHT_CABINET 0xA9C2 [seen] reads 0, which is player two's turn on a cocktail table. Every other case leaves it at 1, and the cell is copied into FLIPSCREEN_LATCH 0xC302 [seen], so the screen turns round for the second player at a table and never on an upright.

Next the inputs are latched. Each port is read and complemented, so in the mirror a set bit means "pressed" or "switch on". DSW1_PORT 0xC200 [seen] goes to DIP1_MIRROR 0xA9AD [seen]. IN0_PORT 0xC300 [seen] (coins, service and the two start buttons) goes to IN0_MIRROR 0xA9AE [seen]. IN1_PORT 0xC320 [seen] (player one's stick and fire) goes to IN1_MIRROR 0xA9AF [seen], and IN2_PORT 0xC340 [seen] (the cocktail player-two controls) goes to IN2_MIRROR 0xA9B0 [seen]. The coinage bank is also re-read into COINAGE_SETTINGS 0xA9B1 [seen] every frame, although the per-slot rates unpacked from it at boot are never recomputed. Every write is unconditional, so each mirror shows exactly what the panel asserts on this frame. Outside the boot-time settings unpack, which reads both switch banks straight from their ports, game code reads the mirrors, never the ports.

The clocks step next. FRAME_TICK 0xA980 [seen] is a byte counter stepped here every frame and zeroed again at the start of every attract demo (below), and its low bit is what makes the copyright line flash. BCD_FRAME_COUNTER 0xA9CE [seen] is a two-digit packed-decimal counter running 00 to 99 and round again, stepped with the processor's decimal adjust. The countdown timers then wind one step toward zero and stop there: BANK_LAUNCH_COOLDOWN 0xA817 [seen], WAVE_CLAIM_TIMER 0xA812 [seen] and ATTACKER_SPAWN_COOLDOWN 0xA8F4 [seen]. They are play timers, but the service ticks them in every mode.

The coin inputs are serviced every frame, whatever the game is doing (next part). The service then runs one arm of the sequence machine and closes the frame through sendOneQueuedSoundThenReopenFrameInterrupt [seen]. That routine sends one waiting sound byte and only then reopens the interrupt gate, writing NMI_REENABLE_BYTE 0x1600 [seen], again a program byte holding 1, to NMI_ENABLE_LATCH. Reopening last is what keeps any frame's work from being cut in half.

### Coins, credits and the mechanical counters

serviceCoinInputs [seen] runs the whole coin pipeline once a frame. Each input is debounced the same way: the line's bit from IN0_MIRROR 0xA9AE [seen] is shifted into the bottom of a history byte, one sample per frame. Only the pattern 001 in the low three bits counts, meaning idle, idle, then asserted. So a coin that holds the switch for several frames, or a button held down, is counted exactly once, on its first frame.

The inputs are taken in a fixed order. awardOneCreditOnDebouncedInputEdge [seen] watches IN0 bit 2, the service input, through SERVICE_CREDIT_DEBOUNCE 0xA983 [seen]. Each clean press is worth exactly one credit, whatever the coinage switches say. tallyCoinSlot1AndAwardCredit [seen] watches coin slot 1 (IN0 bit 0) through COIN_SLOT_1_DEBOUNCE 0xA9C7 [seen]. meterCoinageTowardCreditOnEdge [seen] does the same for coin slot 2 (IN0 bit 1) through COIN_SLOT_2_DEBOUNCE 0xA9CA [seen].

Every accepted coin asks for the coin chime through requestCoinSound [seen], whose code is the program byte COIN_SOUND 0x322E [seen]. The coin is also counted as one pulse owed to that slot's mechanical counter, in COIN_COUNTER_PULSES_OWED 0xA981 [seen] or COIN_COUNTER_PULSES_OWED_SLOT_2 0xA982 [seen], and then metered against the coinage. Each slot keeps an accumulator, COIN_SLOT_1_ACCUMULATOR 0xA9C8 [seen] or COIN_SLOT_2_ACCUMULATOR 0xA9CB [seen], that climbs by 0x10 per coin, so the coin count sits in the high nibble. Each slot also has a rate byte unpacked from the coinage switches, COIN_SLOT_1_RATIO 0xA9C9 [seen] or COIN_SLOT_2_RATIO 0xA9CC [seen], holding the coins required less one in its high nibble and the credits bought in its low nibble; the coinage table gives one coin for one credit as 0x01 and two coins for one credit as 0x11. While the slot's rate byte is still at or above the accumulator, the coins so far are not enough. A two-coin setting, for example, waits on the first coin and pays on the second. Once the accumulator passes the rate byte, the full price (the rate's high nibble plus 0x10) is taken back out, any overshoot carries toward the next purchase, and the rate's low nibble is the number of credits awarded.

The award goes through awardCoinCreditThenPulseCoinCounter [seen] (slot 1's metering falls straight through into it at 0x496E; slot 2 and the service input jump to it). Outside free play it decimal-adds the credits into CREDIT_COUNT 0xA986 [seen], a packed-BCD byte that saturates at 99, and repaints the two-digit readout at CREDIT_COUNT_READOUT_CELL 0xA47F [seen] through paintCreditCountPanel [seen]. With FREE_PLAY 0xA9C0 [seen] raised, that add and the repaint are skipped, so on a free-play cabinet the credit count never moves.

The output side pays off the owed pulses. pulseSlot1CoinCounter [seen] and pulseSlot2CoinCounter [seen] are the same routine with different cells. While a slot owes pulses, an idle timer (COIN_PULSE_TIMER 0xA984 [seen], COIN_PULSE_TIMER_SLOT_2 0xA985 [seen]) is loaded with 48 and the counter's latch line (COIN_COUNTER_0_LATCH 0xC30A [seen], COIN_COUNTER_1_LATCH 0xC30C [seen]) is driven high. The timer then counts down one step a call. It drops the line at exactly 24 and takes one off the debt at zero, so the next pulse begins on the following call and two quick coins give two distinct clicks. The operator's meter keeps counting coins on free play too, because the pulse runs whether or not a credit was banked. One quirk: every crediting path ends by falling into slot 1's pulse driver, whichever input paid, and the service then calls that driver again. On a frame that completes a credit (banked, or under free play merely reached), slot 1's driver therefore runs twice. If slot 1 still owes a pulse, its timer advances two steps that frame and that click comes out shorter. Slot 2's driver is never reached from that tail.

### The sound queue

The main processor never waits on the audio processor. A sound request is appended to a small queue in work RAM, and at the very end of every vertical-blank service, sendOldestQueuedSoundCommand [seen] sends one byte from its head. SOUND_QUEUE_COUNT 0xAC43 [seen] holds how many codes are waiting, and the codes follow it from SOUND_QUEUE_HEAD 0xAC44 [seen]. The append body at 0x562A has no entry of its own: enqueueSoundUnconditional [seen] falls into it, and the two gated entries branch into it. It steps the count on and stores the code at the count cell plus the new count, so codes line up in arrival order. The drain lowers the count, sends the head byte, and slides every remaining byte one place toward the head. Neither end checks for room, and the count wraps at a byte. The result is that a burst of requests is heard one per vertical-blank service over that many services, oldest first.

The byte reaches the second Z80 through sendSoundCommand [seen], the only routine that writes the sound latch. It puts the byte in SOUND_COMMAND_LATCH 0xC000 [seen] and pulses AUDIO_IRQ_LATCH 0xC304 [seen] high and back low, and that edge is what makes the audio processor look. Power-on is the one sender that goes around the queue, when it sends command 0 directly.

Producers reach the queue through one of three gates, which differ only in when they let a request through. enqueueSoundUnconditional [seen] always queues. enqueueSoundIfGameInProgress [seen] queues only while PLAY_ACTIVE 0xAD30 [seen] is set. enqueueSoundIfGameOrDemoSoundsOn [seen] queues while PLAY_ACTIVE is set or, failing that, while DEMO_SOUNDS_ENABLE 0xA9C6 [seen] is set. A request the gate refuses is simply discarded, not deferred. PLAY_ACTIVE is the only thing that separates real play from the attract demo, so sounds behind the in-play gate are silent in the demo whatever the switch says. The coin chime takes the ungated entry, because coins normally arrive while no game is running. enqueueTransitionSoundStops [seen] also takes the ungated entry, queuing six fixed codes, each fetched from its own program byte, followed by a seventh code formed from ERA_INDEX 0xAD04 [seen] plus 0x8C, the one code of the seven that differs from era to era. All seven have bit 7 set, and the audio processor takes a code with bit 7 set as a stop: it clears the channel playing the sound numbered by the low seven bits. The routine therefore silences sounds at a transition rather than starting any.

### The sequence machine

After the coins, the service runs one arm of a two-level sequence machine. SEQUENCE_PHASE 0xA9AB [seen] is the outer level, the machine's mode, and its low two bits pick one of the four dispatchers in the service's inline table. Phase 0 is the power-on wipe, phase 1 the attract sequence, phase 2 the credit / push-start screen, and phase 3 the round engine, where both real play and the attract demo run. SEQUENCE_SUBSTEP 0xA9AC [seen] is the inner level: each dispatcher reads it and jumps through its own word table to the arm it selects. Phase 0 masks the index to three bits. Phases 1 and 2 use it raw, except that the doubling to a word offset wraps at eight bits.

An arm either returns, and then runs again next frame, or moves the machine on. advanceSequenceSubStep [seen] steps the inner index by one so the next frame runs the following arm. advanceSequencePhase [seen] steps the outer phase and zeroes the inner index in one move, because a new mode only makes sense from its first arm. Direct seats write the pair outright: seatSequencePhase3AndResetSubStep [seen] sets phase 3 with sub-step 0, and other entries load the phase from a program byte. This one-arm-per-frame rule is what spreads every screen transition over time. A wipe blanks one line per frame, a hold counts SEQUENCE_DELAY 0xA9EB [seen] down by at most one per frame, and a pen draws one leg per frame, all simply by returning until the job is done.

Phases 1, 2 and 3 each run a tail of their own after every arm; phase 0 has none. Phase 1's tail is advanceSequenceElseStartFreePlayGame [seen]. With any credit in CREDIT_COUNT 0xA986 [seen] it steps the phase on, so a coin pulls the machine out of attract into phase 2 on the very next frame. With no credit, a free-play cabinet with a start button held in IN0_MIRROR 0xA9AE [seen] hides every sprite and starts a game through startGameOnFreePlay [seen]. Phase 2's tail, noOpSequencePhase2Tail [seen], does nothing. Phase 3's tail, advanceAttractTowardGameStart [seen], is how a coin interrupts the demo: when PLAY_ACTIVE is clear and a credit is present, it zeroes the sub-step and reloads the phase from SEQUENCE_PHASE_ON_CREDIT 0x1736 [seen], a program byte holding 2. With no credit it takes the same free-play branch as phase 1's tail, so on a free-play cabinet a start button pressed during the demo hides every sprite and starts a game at once.

Nearly every arm of phases 0–2 also carries an image check. These checks are woven into the sequence rather than run once: each folds a fixed span of the program into a total and compares it with a genuine image's value. On a mismatch they mostly do not stop. They step the phase when they should step the sub-step, blank the display, or jump into data run as code. On a genuine image none of those arms is ever taken, and the narration below follows the genuine path.

### Phase 0: the power-on wipe

Work RAM was zeroed, so the first frame after the interrupt opens finds phase 0, sub-step 0. dispatchSequencePhase0SubStepArm [seen] has only two real arms in its table. The first is startTheWholePlaneWipeAndFoldAnImageBlockIntoThePhase [seen]. Through armWholePlaneWipeThenDerailOnATamperedImage [seen] it seats the wipe cursor BLANK_LINE_CURSOR 0xA989 [seen] on CHAR_PLANE_BASE 0xA400 [seen] with BLANK_LINES_LEFT 0xA988 [seen] at 32, which is the whole 32 × 32 character plane. It then reads the next sub-step, 6, from WIPE_SUBSTEP_SEED 0x1749 [seen], the low byte of a call operand reused as data. Last, it folds 256 bytes from SEQUENCE_PHASE_TAMPER_SPAN_BASE 0x5648 [seen] into the phase itself, a fold that leaves phase 0 standing on a genuine image and moves it anywhere else on a patched one.

Sub-step 6 is armAttractScreenShowingHighScore [seen]. Each frame it first calls blankNextLine [seen], which blanks one line of the plane and returns until the line count reaches zero. The lattice left by the boot is erased one line per frame, so the wipe takes 32 frames, and the new screen is drawn only once the old one is clean. On that frame the arm posts captions 5, 6 and 7 and a pictogram command to the command ring. It writes the digit-0 glyph into PLAYER1_SCORE_READOUT_TENS_CELL 0xA701 [seen] and PLAYER1_SCORE_READOUT_ONES_CELL 0xA6E1 [seen], seeds six work-RAM cell pairs, five of them the tamper witnesses described below, from the witness seed table WITNESS_SEED_TABLE 0x163F [seen], and paints the high-score digits (paintHighScoreReadout [seen]). It then seats phase 1 directly at sub-step 2. On a free-play cabinet it posts one extra caption. The end of a demo and the end of a game both restart at phase 1, not here. The genuine path reaches phase 0 again in one corner only. A credit banked on the same frame that phase 1's last arm runs meets the phase-1 tail after the arm has already written phase 3, and the tail steps the phase to 4. Its low two bits select phase 0, so the machine runs the power-on wipe again: the phase fold leaves a value whose low bits are still 0, and slot 6 then seats phase 1 at sub-step 2. From there phase 1's tail sees the credit and moves on to phase 2, after the wipe has held the machine for 32 frames.

### Phase 1: the attract sequence

dispatchSequencePhase1SubStepArm [seen] runs one arm from PHASE1_SUBSTEP_DISPATCH_TABLE 0x1659 [seen] and then the credit-watching tail. The first two arms belong to the restart path. When a demo or a game ends, restartAttractSequence [seen] seats phase 1 at sub-step 0, and armPenRouteInColour5ThenAdvanceStep [seen] sets PEN_GLYPH 0xAD0B [seen] to the blank 0xF1, the glyph every era's pen already holds, and PEN_COLOUR 0xAD0C [seen] to 5, and re-arms the pen at its route start. It plots nothing itself. advancePenRunAnimationStep [seen] then retraces the route in colour 5 one leg per frame and steps on when the drawer reports a run that reseats to row zero. On its way out it parks a checksum verdict in BANK_LAUNCH_COOLDOWN 0xA817 [seen], the play timer borrowed outside play. When the pen colour already held 5 on arrival, the first arm steps twice and the retrace is skipped. After power-on, phase 0 hands over at sub-step 2, so these two arms do not run.

showCreditLine [seen] puts up the credit line. On free play it only steps on. Otherwise it repaints the credit readout from CREDIT_COUNT 0xA986 [seen] and posts caption 8, the CREDIT caption, beside it. It requires the banked verdict in BANK_LAUNCH_COOLDOWN to be zero, stamps the copyright strip in sprites (stampCopyrightStrip [seen]) and requests the copyright line (flashCopyrightLine [seen]). It then steps on through advanceSequenceUnlessImageTampered [seen], which passes only when the 20 bytes from COPYRIGHT_CAPTION_RECORD 0x086B [seen], the seventeen-byte record and the three bytes after it, sum to the genuine total. buildCopyrightScreenThenVerifyImage [seen] posts the copyright screen's captions in one burst and steps on after an XOR check of 24 bytes at COPYRIGHT_IMAGE_CHECKSUM_BASE 0x176A [seen].

The next arm is a hold. holdCopyrightThenEraseTheCoinInvitation [seen] re-stamps the copyright strip and re-requests its line every frame, which makes the line flash on FRAME_TICK's low bit, and counts SEQUENCE_DELAY 0xA9EB [seen] down. A cell holding zero on arrival wraps to 255. The startup delay left it at zero, and it is zero again whenever the attract sequence restarts after a demo, so this hold lasts 256 frames. When it expires the arm copies the copyright line's N glyph and its colour (COPYRIGHT_SAMPLE_GLYPH_CELL 0xA63C [seen]) into TAMPER_GLYPH_KONAMI 0xACC7 [seen], erases the coin-invitation captions 3 and 4, and steps on. paintReadoutsThenSampleWitnessOrDerail [seen] checks that the copyright line's cells still hold one of the line's two colours (checkTheCopyrightLineColoursOrDerail [seen]) and that TAMPER_GLYPH_SOURCE_CELL 0xA67C [seen] still holds its glyph. It then posts a caption, paints the five labelled numeric readouts (paintFiveLabelledNumericReadouts [seen]), and copies the glyph at TAMPER_SAMPLE_GLYPH_CELL 0xA5DC [seen] and its colour into TAMPER_GLYPH_READBACK 0xADFB [seen] and TAMPER_COLOUR_READBACK 0xADFC [seen].

holdCopyrightThenVerifyGlyphAndSeatWitnessOrDerail [seen] is a second hold on the same SEQUENCE_DELAY. Nothing reseeds the cell between the two holds, so it too runs the long way round from zero. It ends by checking the line colours again and checking the copyright N through a pointer built from a program byte, then seats another witness pair in TAMPER_GLYPH_COPY 0xAB43 [seen].

The arms that follow do nothing visible. guardBlockOrBlankDisplay [seen] and guardBlockOrDerailSequence [seen] each fold a span of code and step on. foldImageBlockIntoSignatureThenAdvanceSequence [seen] banks a fold into TAMPER_IMAGE_SIGNATURE 0xAA6F [seen] (setting slot 7's scenery shape byte, SCENERY_SPRITE_CODE_SLOT7 0xAA3F [seen], to 0xFF on the way). stepSequenceUnderChecksum [seen] compares a fold of SEQUENCE_CHECKSUM_SPAN_BASE 0x0BCC [seen] against EXPECTED_CHECKSUM_TOTAL 0x1A50 [seen], and trampolineToAdvanceSequenceSubStep [seen] spends a frame doing nothing but stepping.

The last arm, verifyImageSignatureThenStartAttractDemoOrDerail [seen], requires the banked signature to read 0x76 and then starts the demo. It parks the caption sprites (hideCaptionSprites [seen]) and seeds the autopilot script (seedDemoAutopilotScript [seen]). It clears TWO_PLAYER_GAME 0xAD31 [seen], PLAYER_TWO_LIVES 0xAD20 [seen], PLAY_ACTIVE 0xAD30 [seen] and the sub-step, gives PLAYER_ONE_LIVES 0xAD10 [seen] a single life, and seats phase 3. Because PLAY_ACTIVE is left clear, the round engine that runs next is the demo, not a game. At every arm along the way the tail is watching CREDIT_COUNT, so a coin cuts the whole sequence short.

### Phase 2: credit on the board, waiting for start

Phase 2 is entered with a credit banked, either from the phase-1 tail or from the demo's tail. dispatchSequencePhase2SubStepArm [seen] runs its arms with a tail that does nothing (noOpSequencePhase2Tail). The first, parkSpritesAndArmLineWipeThenAdvanceSequence [seen], hides every sprite at once (hideAllSprites [seen]). It copies the glyph and colour at LINE_WIPE_SAMPLED_CELL 0xA5FC [seen] into LINE_WIPE_SAMPLE_RECORD 0xACBE [seen], and arms a shorter wipe through armLineWipeFromFifthLine [seen]: BLANK_LINE_CURSOR 0xA989 [seen] at BLANK_LINE_START_CELL 0xA404 [seen], so the first four lines are spared, and a line count read from the program byte BLANK_LINES_COUNT 0x0CCD [seen], which holds 27. blankOneLineThenGuardBlockOrDerailSequence [seen] then blanks one line per frame, so the wipe takes 27 frames and clears lines 4 to 30, leaving the first four lines and the last one untouched. When the last line is done, it XOR-folds 1024 bytes from IMAGE_GUARD_BLOCK_4980_BASE 0x4980 [seen] and steps on.

postPushStartScreenCaptions [seen] lays out the information screen in one burst of caption requests. It picks the bonus-life caption pair by BONUS_LIFE_SETTING 0xA9C3 [seen], so the screen states the score marks the operator chose. It also picks the credit line by CREDIT_COUNT. With two or more credits it posts caption 25 and steps twice, straight to the two-credit wait. With exactly one it posts caption 23 and steps once.

stepCopyrightScreenAwaitingStart [seen] is the one-credit wait. Every frame it re-stamps and flashes the copyright line and samples COPYRIGHT_GLYPH_SAMPLE_CELL 0xA61C [seen] into TAMPER_GLYPH_STRIP 0xABFE [seen]. That witness is checked later, during play, not here. A press of the one-player start (IN0_MIRROR bit 3) starts a game. If a second credit arrives instead, the arm posts caption 25 and steps on. stepTwoCreditCopyrightScreenAwaitingStart [seen] is the two-credit wait. It keeps the same screen alive and tests the two-player start (bit 4) first, so with both buttons held two players win. It never steps the sequence itself; leaving is entirely the job of the start routines.

Both starts end at seatSequencePhase3AndResetSubStep [seen]. startOnePlayerGame [seen] parks the copyright sprites. It clears TWO_PLAYER_GAME and PLAYER_TWO_LIVES, and player two's zero lives are what later make a hand-over impossible. It raises PLAY_ACTIVE 0xAD30 [seen] to all ones, loads PLAYER_ONE_LIVES from STARTING_LIVES 0xA9C1 [seen], takes one credit off CREDIT_COUNT with a decimal subtract, repaints the readout, and copies three tilemap cells, glyph and colour, aside again (copyThreeTilemapCellsFromBothPlanes [seen]): the copyright line's N at COPYRIGHT_SAMPLE_GLYPH_CELL 0xA63C [seen] into TAMPER_GLYPH_KONAMI 0xACC7 [seen], TAMPER_GLYPH_SOURCE_CELL 0xA67C [seen] into TAMPER_GLYPH_COPY 0xAB43 [seen], and LINE_WIPE_SAMPLED_CELL 0xA5FC [seen] into LINE_WIPE_SAMPLE_RECORD 0xACBE [seen]. startTwoPlayerGame [seen] raises PLAY_ACTIVE and TWO_PLAYER_GAME, stocks both players' lives, runs checkTamperGlyphCopyElseRunAwardLabelStep [seen], and takes two credits. The free-play start, startGameOnFreePlay [seen], makes the same flag and lives stores without any charge, choosing one or two players by the held button; it does not copy those three cells aside again or run checkTamperGlyphCopyElseRunAwardLabelStep. From the next frame on, phase 3, the round engine, owns the frame.

### Starting a game

A game begins when the sequence machine is moved, by a constant store rather than a step, into its last outer phase. seatSequencePhase3AndResetSubStep 0x172A [seen] writes 3 into SEQUENCE_PHASE 0xA9AB [seen] and zeroes SEQUENCE_SUBSTEP 0xA9AC [seen], so the next vertical blank enters the round engine at its first arm. Every way into a game ends there; what differs is who is playing and what it costs.

Free play bypasses the credit. Every phase-3 arm returns into advanceAttractTowardGameStart 0x0F54 [seen], which does nothing while PLAY_ACTIVE is raised. During the demo it watches for a coin: a nonzero CREDIT_COUNT zeroes the sub-step and reloads the phase from the ROM byte SEQUENCE_PHASE_ON_CREDIT 0x1736 [seen], which holds 2, so the next frame shows the push-start screen instead of the demo. With no credit but FREE_PLAY 0xA9C0 [seen] raised and a start button held, it parks every sprite (hideAllSprites 0x15B6 [seen]) and jumps to startGameOnFreePlay 0x1690 [seen], which stocks one or both player blocks by the held button (two-player tested first) and charges nothing. advanceSequenceElseStartFreePlayGame 0x167B [seen] is the same decision for phase 1, the attract sequence (phase 2's tail is a bare return), except that it has no PLAY_ACTIVE guard and leaves a credit by stepping the phase rather than reloading it.

### Phase 3: the round engine

Phase 3 belongs to both real play and the attract demo. dispatchSequenceSubStepArm 0x0F1F [seen] masks SEQUENCE_SUBSTEP to its low nibble and runs one arm from PHASE3_SUBSTEP_DISPATCH_TABLE 0x0F29 [seen] each time the vertical-blank service runs. An arm that has finished its job calls advanceSequenceSubStep 0x0F1A [seen], so the next service runs the arm after it; an arm that must jump elsewhere stores the sub-step directly, usually from a byte in the program image. The arms fall into three runs: getting play going (arms 0 to 7, ending in the round engine itself; arm 0 opens a game or demo, a life after a lost one or a turn pass re-enters at arm 1, and a won round re-enters at arm 3), the end of a game (arms 8 to 11), and the round-won animation (arms 13 and 14), with the attract restart at arm 12.

**Arm 0, opening a game.** armNewGameThenStepSequence 0x27B1 [seen] asks for the game-start sound, seats the enemy aim anchor (ENEMY_AIM_ANCHOR_Y 0xAC64 [seen] and ENEMY_AIM_POINT_TABLE 0xAC65 [seen]) on the ship's fixed screen position, and resets both players' saved blocks to the opening state. Each player starts on round 1 in era 0, with no bonus-life latch, no Mother-Ship armed, the round-intro-pending flag set, the mid and high places of its saved life-tick counter cleared, and a kills-remaining count copied from KILL_QUOTA 0xA9CD [seen]. ACTIVE_PLAYER 0xAD32 [seen] and PEN_COLOUR 0xAD0C [seen] are zeroed. From here the arm splits on PLAY_ACTIVE. In a credited game it zeroes both three-byte scores and posts command 4 with argument 0 so the score labels are drawn. It then loads the difficulty record the DIP switches chose (loadDifficultyRecord 0x0F7B [seen], indexed by DIFFICULTY_SETTING 0xA9C4 [seen]), starts both players on that record's rounds 1–5 rung (START_RUNG_ROUNDS_1_5 0xA9D3 [seen]), and arms SEQUENCE_DELAY 0xA9EB [seen] at 0x96 (150), the hold the fly-in counts down on odd frames only (below). In the demo it cycles ATTRACT_STAGE_COUNTER 0xA9D0 [seen] through 1, 2 and 3 and starts player one in that era and round. That is why the demo shows 1940, 1970 and 1982 but never 1910 or 2001. The demo also zeroes FRAME_TICK 0xA980 [seen], the packed-decimal frame counter and the script round-robin, reseeds the random generator, wipes the player-shot and object-state blocks, always plays difficulty record 2, sets the standoff aim block to 0x80, and arms the delay at 0x5A (90). Every demo therefore starts from the same generator state on the same fixed difficulty. Both paths fold a program block into a guard on the way out, as described below.

**Arms 1 and 2, the era's pen.** seatCaptionPenFromEraFoldingTamperIntoPhase 0x335E [seen] reads the active player's era, looks up a glyph-and-colour record in ERA_PEN_TABLE 0x0F8D [seen], and stores it into the player's saved pen (PLAYER_ONE_PEN_GLYPH 0xAD1B / PLAYER_TWO_PEN_GLYPH 0xAD2B [seen]) and onto the live pen, PEN_GLYPH 0xAD0B [seen] and PEN_COLOUR. If the colour it stores is the one the live pen already held, it steps the sub-step one extra time. That skips arm 2, so the pen route is redrawn only when the incoming era's colour differs from the live pen. That happens at the first round of a game or demo, where arm 0 zeroed the pen colour. It happens again when the ship dies after the Mother-Ship has fallen, so that the next life opens in the next era, and at a two-player hand-over between players in different eras or after a filed score, which leaves the pen in colour 0 (arm 8, below). A death in the same era does not redraw it. A won round never reaches arm 1 at all, because the round-won animation re-enters the sequence at arm 3 (below). Either way it re-arms the pen route at its start (armThePenRouteThenColdStartOnATamperedImage 0x01E1 [seen]). Arm 2, blankKillMeterThenAdvancePenRunStep 0x5BD7 [seen], blanks the fourteen kill-meter cells (blankFourteenCharCells 0x07D2 [seen]) and draws one leg of the interpolated pen route (drawInterpolatedPenRun 0x0201 [seen]) each frame, stamping PEN_GLYPH and PEN_COLOUR along a line from one point of the route, a rectangle of start points near the playfield's edge, to the one fixed target cell 0xA611. It steps on only once the last leg is drawn, when the next start point it loads is the route table's closing entry, the one with row 0. On the glass the route is a sweep of the sky colour over the whole playfield, its leading edge a staircase, which replaces the attract screen; phase 1's erase arm runs the same route with the blank glyph in colour 5 and sweeps the sky away again.

**Arm 3, whose turn.** loadActivePlayerContextAndPostRoundHud 0x4C75 [seen] copies the active player's sixteen-byte saved block (from PLAYER_ONE_LIVES 0xAD10 or PLAYER_TWO_LIVES 0xAD20) over the live context that begins at LIVES_REMAINING 0xAD00 [seen]. That live block carries ROUND_NUMBER 0xAD01, KILLS_REMAINING 0xAD02, BONUS_LIFE_LATCH 0xAD03, ERA_INDEX 0xAD04, the life-tick counter, START_RUNG 0xAD0A, the pen, MOTHER_SHIP_ARMED 0xAD0D and ROUND_INTRO_PENDING 0xAD0E (all [seen]). Each player therefore keeps their own era, round, quota progress and difficulty ladder in a two-player game. In play it then posts the round pictograms (command 6, with the round number) and the reserve-ship emblems (command 5, with LIVES_REMAINING less one, since the ship in play is not shown in reserve).

**Arm 4, captions and a clean field.** postLifeStartCaptionsAndResetPlayfield 0x0774 [seen] posts the life-start captions. The demo gets only "READY". A game gets "PLAYER 1" or "PLAYER 2" by ACTIVE_PLAYER, followed by "READY" when ROUND_INTRO_PENDING is clear, or by the stage-number caption (command 7) when it is set. A fresh round therefore announces its stage, and a restart after a death in the same round just says READY. The arm then repaints the kill meter and calls resetPlayfieldForLifeStart 0x19F0 [seen], the reset that runs at every life start. That reset zeroes both world-scroll words (WORLD_SCROLL_Y 0xA808, WORLD_SCROLL_X 0xA80A [seen]) and the life's base-sixty tick counter. It clears MOTHER_SHIP_ARMED, PARACHUTIST_RUNG 0xA8F7 [seen], SHOT_BURST_PENDING 0xAA81 [seen] and ROUND_TRANSITION_HOLD 0xACC6 [seen]. It reseats the difficulty rung (ERA_RUNG 0xACC0 [seen] from START_RUNG, ERA_RUNG_TIMER 0xA9D7 [seen] from ERA_RUNG_PERIOD 0xA9D6 [seen]). It sets the ship to heading 0x80 with PLAYER_STATE 0xA800 [seen] at 0xFF and its sprite pinned at the screen centre, frees the shot slots, retires and renumbers every object record, and seeds the era's scenery. Finally it scatters the current era-and-rung settings row into the spawner cells (the same copy applyEraRungSettings performs, below).

**Arms 5 and 6, the fly-in.** flyLifeStartHoldThenEraseLifeStartCaptions 0x16AF [seen] runs at every life start and lets the ship fly over the scenery with no enemy or collision service. It counts SEQUENCE_DELAY down on odd frames only, and while ROUND_INTRO_PENDING is raised it repaints the era's year caption in one of three shades on three of every sixteen frames, so the year flashes. When the delay expires it erases the life-start captions (records 9, 0x0E and 0x1A), clears ROUND_INTRO_PENDING, re-arms the delay at 0x2A (42) and steps on. flyEnemyFreeLeadInThenStepSequence 0x5694 [seen] adds the player's shots to that player-side service, counts the delay down on every pass rather than every other one, and steps into the round engine when it expires. The result is a short enemy-free lead-in during which the player can already turn and fire.

**Arm 7, the round engine.** serviceRoundThenResolvePlayerState 0x1199 [seen] is the pass of real play, run once per service while the sub-step is 7. In a fixed order it services the enemy re-aim tick, the player's frame (dispatchPlayerFrameByState 0x1EDF [seen]), the player's shots, the wave driver, the parachutist, the Mother-Ship, the craft slots, the era's scenery, the era-object bank from era 2 on, the 1940 bomber and its companion fixed slot, the actor slots, the 1910 ballistic bank, the collision pass, and a request, from the third era on, on one frame tick in 32 and only while none of the era-object bank's three slots is live, that sound 6 stop. It interleaves sprite-multiplex passes between these groups so more objects can be shown than the sprite hardware holds. It then does the bookkeeping that belongs to this section: the bonus-life check, the hit-chain timer, the difficulty escalation tick and the kill meter. Finally it reads PLAYER_STATE. At 0xFF (alive) it hands to advanceRoundWhenFieldCleared 0x1271 [seen]. Any other nonzero value means the ship is still dying, so it simply returns. At 0 the ship is dead, and it falls into loseLifeAndHandOver 0x11ED [seen]. The sub-step stays at 7 until the ship is lost or the round is won.

**Winning a round.** advanceRoundWhenFieldCleared acts only when KILLS_REMAINING is zero, ROUND_TRANSITION_HOLD has been raised by the Mother-Ship's destruction (0xFE at its field sweep, 0xFF when its wreck finishes), and the fifteen object records from ACTOR_RECORD_SLOT0 0xA810 [seen] to 0xA8F0 are all empty. In other words, the round ends once the field has emptied after the Mother-Ship falls, not at the moment it falls. It queues the transition sound stops. In the demo it then restarts attract (phase from ATTRACT_SEQUENCE_START_PHASE 0x16D3 [seen], which reads 1). In a game it parks every non-player sprite and calls startNextRound 0x2DB8 [seen]. That routine steps ROUND_NUMBER, which keeps counting past five, and steps ERA_INDEX, wrapping from 4 back to 0 so the second loop replays the same eras. It picks the round's opening rung from one of three difficulty-record cells by round bracket (rounds 1–5, 6–10, 11 and up: START_RUNG_ROUNDS_1_5 0xA9D3, START_RUNG_ROUNDS_6_10 0xA9D4, START_RUNG_ROUNDS_11_UP 0xA9D5, all [seen]). It refills KILLS_REMAINING from KILL_QUOTA, which is not keyed by era or loop, so every round asks for the same quota, and it clears the Mother-Ship flag and the transition hold and raises ROUND_INTRO_PENDING. advanceRoundWhenFieldCleared then saves the live context back into the active player's block and sets the sub-step from NEXT_ROUND_START_SUBSTEP 0x4A35 [seen], which holds 0x0D. Arm 13, armRoundWonBandAnimationThenStepSequence 0x4A0F [seen], builds the warp band in the character plane in the current pen colour, seeds the animation's control block, and sets the player's saved pen from the new era. Arm 14, stepRoundWonBandAnimation 0x1323 [seen], plays it on alternate pairs of frames: the ship flashes white, the scripted band animations run, the ship's colour cycles, and the colour plane floods. When the animation finishes, arm 14 arms the delay at 90, hides every sprite, reloads the active player's context, and sets the sub-step from INTRO_SUBSTEP_RELOAD 0x2750 [seen] (3). The next round therefore resumes at arm 3, after the pen arms, because arm 13 already re-seeded the pen. Slot 15 of the table is a bare return, loc_15b5 [code]: arm 14 overwrites the sub-step in the same frame it steps it to 15, so nothing dispatches there.

**Losing a life.** loseLifeAndHandOver hides every sprite. If ROUND_TRANSITION_HOLD is already raised, the Mother-Ship was destroyed before the ship died, and startNextRound banks the round so the next life opens in the next era. It queues the transition sound stops, takes one off LIVES_REMAINING, and saves the live context to the active player's block. With lives left, ACTIVE_PLAYER flips if the other player still has lives, so in a two-player game the turn passes on every death until the other player has no lives left, and from then on the survivor plays every life. SEQUENCE_DELAY is armed at 90 and the sub-step is set from NEXT_LIFE_SUBSTEP_SEED 0x4B52 [seen] (1), so the next life replays the opening arms from the pen arm onward. With no lives left it jumps to postGameOverBanner 0x1253 [seen]. In a game that routine posts "PLAYER n" and "GAME OVER", arms a 180-frame hold and steps to arm 8. In the demo it jumps to restartAttractSequence 0x12FB [seen] instead, which clears PLAY_ACTIVE and ACTIVE_PLAYER, reloads phase 1 and recomputes the sub-step from an image fold that lands on zero for the genuine program.

**The end of a game.** Arm 8, fileScoreAfterGameOverHoldElsePassTurn 0x330B [seen], holds GAME OVER until the 180-frame delay runs out and then tries to file the active player's score into the high-score table (below). If the score ranks nowhere, the arm erases the PLAYER and GAME OVER captions, sets the sub-step from SKIP_INITIALS_SUBSTEP_SEED 0x0843 [seen] (0x0B) and jumps to passTurnToOtherPlayerIfLivesElseStepSequence 0x12E7 [seen]. That routine hands play to the other player if they have lives (handPlayOverToOtherPlayer 0x1226 [seen] flips ACTIVE_PLAYER, arms the delay at 90 and seats the hand-over sub-step) and otherwise steps on to arm 12, the attract restart. If the score was filed, arm 8 asks for the filed-score sound and sets the pen to colour 0 and the blank glyph 0xF1, so the pen route's next trace repaints its blank tiles in colour 0 instead of the era's, before stepping to the initials arms 9 and 10. When initials entry finishes it arms the delay at 60 and steps to arm 11, holdThenPassTurnToOtherPlayerIfLivesElseStepSequence 0x12E2 [seen]. Arm 11 counts that delay out and then makes the same pass-or-restart decision. In a two-player game, the first player to run out therefore goes through GAME OVER and possibly initials, and then the other player carries on.

### Scoring, bonus lives and the high score

Nothing adds to a score directly. Every scoring event posts command 4 with an award index on the command ring (postCommand 0x0038 [seen]), which silently drops the pair if the ring's next cell is still occupied, and the foreground drain hands command 4 to awardScoreToPlayer 0x0C90 [seen]. That routine does nothing at all while PLAY_ACTIVE is clear, so the demo never scores. Index 0 is not an award but a request to redraw the score labels: in a two-player game both labels and both scores, in a one-player game player one's label (caption 6, "1-UP") and score, with the second label erased and the second score blanked. Any other index selects a three-byte packed-decimal entry from SCORE_AWARD_TABLE 0x0D27 [seen]. Indices 1 to 8 are 100 to 800 and 9 is 900. Then come 1,000, 1,500, 2,000, 3,000, 4,000 and 5,000 for indices 10 to 15. The entry is added with decimal carry into the active player's score, PLAYER1_SCORE_LO/MID/HI 0xAD33–0xAD35 or PLAYER2_SCORE_LO/MID/HI 0xAD36–0xAD38 (all [seen]), low byte first. Every entry has a zero low byte, so a score always ends in 00. The carry out of the top byte is discarded, so the score rolls over from 999,900 to zero. The routine then compares the new score, most significant byte first, against the single displayed high score, whose top byte is HIGH_SCORE_HI 0xA98D [seen] with the lower bytes at 0xA98C and 0xA98B. Only a strictly greater score is copied over it and repainted (paintHighScoreReadout 0x0D6B [seen]). Last, it repaints whichever player's score changed.

The award indices map onto the game's targets. A common kill goes through postChainedHitScore 0x51DE [seen]. When CHAIN_WINDOW 0xA99D [seen] is empty the hit pays index 1 (100). While the window is open it steps CHAIN_STEP 0xA99E [seen] and pays the step folded to 1–8, so hits in quick succession pay 100, 200 and so on up to 800, then wrap back to 100. Every hit reloads the window to 30. expireHitChain 0x5205 [seen] takes one off it each round-engine pass. On every pass that finds the window already empty it clears CHAIN_STEP, so the next hit starts at the bottom of the ladder. The clear comes one pass late, though: the pass that empties the window leaves the step alone. A hit on the very next pass pays 100 and reopens the window with the old step still in place, so the hit after it carries on up the old ladder. This climbing chain disagrees with gameplay.md's flat "100 per common enemy"; the code wins. The 1940 bomber pays index 11 (1,500) from advanceHitSoakingObjectThenAnimateDeath 0x3B94 [seen]. A wiped-out formation pays index 12 (2,000) from driveObjectAppearanceByPhaseBand 0x2C31 [seen], which also clears CLAIM_TOKEN 0xA821 [seen] so it pays once. The Mother-Ship pays index 13 (3,000) from loc_43f0 [seen]. Rescued parachutists go through postNextParachutistBonus 0x4831 [seen], which reads the slot's rung (PARACHUTIST_RUNG 0xA8F7) before incrementing it. Rungs 0 to 3 index PARACHUTIST_BONUS_ARG_TABLE 0x484F [seen] (1,000, 2,000, 3,000, 4,000), and every rung after that pays index 15 (5,000). The rung is cleared at every life start, so the ladder restarts on a death or a new round.

Extra ships come from awardBonusLifeAtScoreMark 0x4DDE [seen], which runs once per round-engine pass in a credited game. BONUS_LIFE_SETTING 0xA9C3 [seen] picks one of two length-prefixed mark lists: BONUS_LIFE_MARK_TABLE_BIT0_CLEAR 0x4E1B [seen] holds 10, 60, 110 … 960 thousand, and BONUS_LIFE_MARK_TABLE_BIT0_SET 0x4E30 [seen] holds 20, 80, 140 … 980 thousand. Each mark is a single packed-decimal byte matched against the top byte of the active player's score, the hundred-thousands and ten-thousands digits. A match is honoured only if bit 0 of BONUS_LIFE_LATCH 0xAD03 [seen] is clear. The award sets the latch, adds one to LIVES_REMAINING, posts the new reserve count to the emblem strip (command 5) and asks for the bonus sound. Any pass whose top byte matches no mark clears the latch again. Because the latch lives in the per-player context, each player has their own. Because the match is on the score's top byte alone, a score that rolls over past 999,900 passes the same marks again and pays again. The lists stop at 960,000 and 980,000; past the last mark nothing is paid until the score wraps. This bears on gameplay.md's "extra lives up to 960,000": the code has the ceiling, but it applies to each trip round the score counter, not for ever.

### The high-score table and initials entry

The table is five eight-byte records in work RAM from HIGH_SCORE_TABLE_BASE 0xAB08 [seen] to HIGH_SCORE_TABLE_END 0xAB2F [seen]. Each record holds a rank byte at +0, three packed-decimal score bytes at +1 to +3 (most significant at +3, e.g. HIGH_SCORE_REC0_SCORE_HI 0xAB0B [seen]) three initials glyphs at +4 to +6, and a 0xF1 pad byte at +7. At cold start loadDefaultHighScores 0x4BA5 [seen] copies the whole block from DEFAULT_HIGH_SCORE_TABLE 0x4BB1 [seen]. The default scores are 10,000, 8,800, 8,460, 6,520 and 4,300, with the initials K.O, N.A, M.I, O.O and Y.A, and since the table lives only in RAM a power cycle restores them. Its top entry, 10,000, matches the displayed high score that seedGameConfigFromDipSwitches seeds from DEFAULT_HIGH_SCORE_HI 0x08C9 [seen]. The table and the single displayed high score are separate: the displayed one is promoted live during play, and the table changes only at game over. Nothing copies the table into the displayed high score: that score's only writers are the power-on wipe of work RAM, the boot seed from DEFAULT_HIGH_SCORE_HI and awardScoreToPlayer's promotion.

fileScoreIntoHighScoreTable 0x4CC3 [seen] walks the records from the top. isScoreBelow 0x4D2B [seen] compares three bytes most significant first, and the walk stops at the first record the candidate is not below. A tie therefore files above the record it ties. If the score is below all five, the table is untouched and the caller is told so. Otherwise the records beneath the slot slide down eight bytes, with a copy that runs backward from the table's last byte toward the slot (source HIGH_SCORE_SLIDE_SRC 0xAB27 [seen], destination HIGH_SCORE_TABLE_END) so the old fifth record drops off. The slot's three initials cells are filled with the blanking glyph 0xF1 and the score is copied in. Two cursors are parked: SCRATCH_PTR_A 0xA991 [seen] on the record's first initials byte, and SCRATCH_PTR_B 0xA993 [seen] on the matching on-screen cell, found by adding twice the rank the slot used to hold to HIGH_SCORE_INITIALS_CELL_BASE 0xA531 [seen]. Finally the rank column is renumbered 0 to 4 from the top.

Arm 9, erasePenRouteThenOpenInitialsEntry 0x08B4 [seen], first runs the colour-0 pen route one leg a frame until it is back at row zero. It then checks a program block (below), posts the entry screen's captions, and paints the five table rows (paintFiveLabelledNumericReadouts 0x4BDC [seen], one column each from HIGH_SCORE_REC0_CURSOR 0xA711 to HIGH_SCORE_REC4_CURSOR 0xA719 [seen], each rank in its own colour). It empties the four press histories and the letter index from INITIALS_BACK_PRESS_HISTORY 0xA995 [seen] onward, sets INITIALS_SLOTS_LEFT 0xA99A [seen] to 3, draws letter 0 at the cursor from INITIALS_LETTER_GLYPH_TABLE 0x12C7 [seen], and remembers the colour already under the cursor in INITIALS_LOCKED_LETTER_COLOUR 0xA990 [seen].

Arm 10, stepHighScoreInitialsEntry 0x18C3 [seen], runs every frame and splits on frame parity. On odd frames the only entry work is the cursor blink: INITIALS_CURSOR_FLASH_TIMER 0xA99C [seen] counts up and its bit 4 picks colour 0x14 or 0x10. On even frames it samples the player controls (readPlayerControls 0x1ED1 [seen]) into four press histories, one bit per sample, newest in bit 0. A control acts only when its low three samples read "not, not, pressed", which is the leading edge of a press. A fresh press on either commit control locks the letter: INITIALS_COMMIT_PRESS_HISTORY 0xA997 [seen] holds FIRE, and INITIALS_ALT_COMMIT_PRESS_HISTORY 0xA998 [seen] holds bit 0x20 of the panel word, which no control on either panel drives (the panel has one button), so on the cabinet only fire commits; the unwired one is tested first. Commits take priority over everything else. The locked glyph is written both into the table record and onto the screen in the remembered colour, both cursors advance, the slot count drops, and the next slot starts again from letter 0. Otherwise a fresh forward press (INITIALS_FORWARD_PRESS_HISTORY 0xA996 [seen]) steps INITIALS_LETTER_INDEX 0xA999 [seen] round its 27-entry ring of A to Z and one final mark, and a fresh back press steps it the other way. A held control saturates its history so the leading-edge pattern cannot recur; when the history reads saturated, rearmHeldControlRepeat 0x1980 [seen] empties it, so the next sample counts as a fresh press and a held stick auto-repeats. The back history is emptied at 0x7F, one sample sooner than the forward one at 0xFF. Each letter change redraws the cursor and restarts its blink.

The entry has a time limit. SEQUENCE_DELAY arrives at zero from arm 8's hold and is decremented once every eighth frame, so its first tick wraps it to 255 and the player gets 256 ticks of eight frames. If it runs out, the cell still waiting for an initial is blanked. Either a third commit or the timeout finishes the entry: the delay is re-armed at 60, the transition sound stops are queued, and the sequence steps to arm 11. On every frame that does not finish the entry, the arm also lets a new game start without waiting, but only once neither player has lives left. On free play either start button begins a free game. With one credit only the one-player button alone is accepted. With two or more, the one-player button alone starts one player and any other held start begins two.

### The random generator

The game's randomness is a seventeen-byte shift register at RANDOM_REGISTER 0xAB30 [seen]. Each draw, drawRandomByte 0x4B4B [seen] shifts the register one byte toward its tail and drops the oldest byte. It writes the exclusive-or of the bytes at offsets 7 and 16 into the vacated head, and returns that feedback plus the free-running FRAME_TICK. Mixing in the frame counter means the same register state gives different draws on different frames. What a draw returns therefore depends on the frame it is taken on as well as on how many draws came before it, although the frame counter never enters the register itself. seedRandomRegister 0x4B67 [seen] reloads the register from the fixed run at RANDOM_REGISTER_SEED_SOURCE 0x4B84 [seen]. That happens at cold start, and again at the start of every attract demo, where FRAME_TICK is also zeroed, so each demo round replays from the same seed. A real game is not re-seeded; it inherits whatever state the attract cycle left.

The draws feed the enemy waves: the wave driver, the free-slot spawner and the wave spawner all take draws. pickScriptAtRandomOrInTurn 0x382D [seen] shows the pattern most clearly. A draw at or above SCRIPT_PICK_THRESHOLD 0xACC4 [seen], which the difficulty row sets, is folded to one of four random movement scripts (5–8). A draw below it is thrown away and the next script is taken in turn from SCRIPT_CYCLE_COUNTER 0xA9CF [seen] (0–4, wrapping). The threshold therefore sets how often enemy behaviour is random rather than ordered.

### ROM self-checks and anti-tamper witnesses

Running alongside the game logic is a layer of checks whose only purpose is to make a modified program image misbehave rather than fail cleanly. They take three forms, and the round engine is full of them.

The first form folds a block of program bytes into a total and compares it with a constant. On a mismatch, the check either steps the sequence phase (advanceSequencePhase 0x0F11 [seen]), throwing the machine into the wrong mode, or sends control somewhere it does not belong, such as a cold start, the middle of the frame interrupt handler, or an address outside the program image. On a genuine image the check passes by construction. Examples in phase 3 include the XOR fold over LIFE_START_CAPTIONS_CHECKSUM_BASE 0x4C99 [seen] in arm 4, the XOR fold over IMAGE_GUARD_BLOCK_0BDD_BASE 0x0BDD [seen] in arm 2, and the sum over HIGH_SCORE_FILED_CHECKSUM_BASE 0x01F1 [seen] in arm 8. Others are the XOR fold over INITIALS_ENTRY_CHECKSUM_BASE 0x4880 [seen] in arm 9, which derails on a mismatch, and the sum over PEN_ROUTE_CHECKSUM_BASE 0x0E33 [seen] inside armThePenRouteThenColdStartOnATamperedImage, which cold-starts the machine. seedRandomRegister has its own guard over three program bytes, the whole word at RANDOM_SEED_GUARD_WORD0 0x086D and only the low byte of the word at RANDOM_SEED_GUARD_WORD1 0x0870 [seen], and on any nonzero total it jumps to 0x6000, outside the program image. The phase-1 guards stepSequenceUnderChecksum 0x4B19 [seen] and guardBlockOrDerailSequence 0x3252 [seen] follow the same pattern. A phase step is worse than it sounds in phase 3: it makes the phase 4, whose low two bits select phase 0, so a tampered image restarts the attract cycle from the power-on wipe in the middle of a game. From phases 1 and 2 the same step only moves the machine one phase on.

The second form is quieter: a fold that rewrites SEQUENCE_PHASE itself and cancels out on a genuine image. Arm 0's demo path subtracts the block at SEQUENCE_PHASE_CHECKSUM_BASE 0x3310 [seen] from the phase and XORs the result with 0x90. Arm 1 adds the bytes at CAPTION_PEN_CHECKSUM_BASE 0x178C [seen] plus a bias. Arm 2, blankKillMeterThenAdvancePenRunStep 0x5BD7 [seen], adds the twenty program bytes at advancePenRunAnimationStep_ADDR 0x1734 [seen] to the phase plus a bias of 0x77. Arm 5 folds LIFE_START_HOLD_CHECKSUM_BASE 0x4D9F [seen] every frame of the fly-in. Arm 6 folds LEAD_IN_CHECKSUM_BASE 0x0831 [seen] every frame and LEAD_IN_EXPIRY_CHECKSUM_BASE 0x12A7 [seen] on expiry. With the right bytes the phase comes out unchanged; with any edit the machine silently lands in another phase in the middle of play. A related family drives the picture-enable latch. Arm 0 writes the XOR of the block at DISPLAY_LATCH_CHECKSUM_BASE 0x1550 [seen] plus one to VIDEO_ENABLE_LATCH 0xC308 [seen], and arm 3 writes the XOR of TAMPER_CHECKSUM_SPAN_BASE 0x5B50 [seen] less one. The latch takes only data bit 0, with 1 meaning picture on, and the genuine folds come to 0x4C and 0x52, both even, so the values written are 0x4D and 0x51, both odd. Both therefore produce the latch's "on" value for the genuine program, and a patched block whose fold comes out odd blanks its own screen at the start of a game or a life. guardBlockOrBlankDisplay 0x17B9 [seen] blanks the display outright with DISPLAY_OFF_VALUE 0x4C89 [code] on a mismatch. It also overwrites the witness pair TAMPER_WITNESS with a cell copied from the display (TAMPER_WITNESS_SAMPLE_CELL 0xA65C [code], the O of the copyright line), and it leaves the sub-step where it is, so the attract sequence repeats this arm with the picture off until a credit or a free-play start moves the machine on.

The third form, the witnesses, checks the screen rather than the program. The attract screen's witness seeding (armAttractScreenShowingHighScore 0x15FE [seen], reading WITNESS_SEED_TABLE 0x163F [seen]) first seeds each witness pair with its expected glyph and colour 0x05. During the attract and credit screens, routines then overwrite several of the pairs with the glyph and colour actually found in chosen caption cells, with sampleCellGlyphAndColour 0x1AFC [seen] doing the copy where a routine does not do it inline. stepCopyrightScreenAwaitingStart samples COPYRIGHT_GLYPH_SAMPLE_CELL 0xA61C [seen] into TAMPER_GLYPH_STRIP 0xABFE and TAMPER_COLOUR_STRIP 0xABFF [seen]. holdCopyrightThenEraseTheCoinInvitation 0x1748 [seen] samples the N of the copyright line (COPYRIGHT_SAMPLE_GLYPH_CELL 0xA63C [seen]) into TAMPER_GLYPH_KONAMI 0xACC7 [seen]. holdCopyrightThenVerifyGlyphAndSeatWitnessOrDerail 0x178C [seen] copies TAMPER_GLYPH_SOURCE_CELL 0xA67C [seen] into TAMPER_GLYPH_COPY 0xAB43 [seen]. paintReadoutsThenSampleWitnessOrDerail 0x176A [seen] fills TAMPER_GLYPH_READBACK 0xADFB and TAMPER_COLOUR_READBACK 0xADFC [seen]. startOnePlayerGame [seen] re-samples two of the pairs at every credited one-player start, through copyThreeTilemapCellsFromBothPlanes 0x4B30 [seen]: TAMPER_GLYPH_KONAMI from COPYRIGHT_SAMPLE_GLYPH_CELL and TAMPER_GLYPH_COPY from TAMPER_GLYPH_SOURCE_CELL, each with its colour; its third copy refreshes LINE_WIPE_SAMPLE_RECORD from LINE_WIPE_SAMPLED_CELL, a pair the witness seed table also seeds but no code reads back. Much later, often in the middle of play, other routines read these pairs back and require the expected glyph with one of two accepted colours, 0x10 or 0x05. The player's death animation, advancePlayerAnimationStrip 0x2010 [seen], checks the strip pair and on failure falls into loc_1f2e [code], a table executed as code. The Mother-Ship's closing sequence in loc_43f0 [seen] checks TAMPER_GLYPH_COPY and on failure runs derailIntoMotherShipWreckCountdown 0x459B [code] from a misaligned entry. The scenery seed, seedSceneryEntriesThenRunScenery 0x3117 [seen], checks TAMPER_WITNESS 0xAD39 [seen] and on failure diverts through trampolineToLoc_307f 0x3114 [code] into the caption bytes at loc_307f [code]. The era-4 scenery seat checks TAMPER_GLYPH_KONAMI the same way and on failure runs a packed table as code. The demo autopilot, seedDemoAutopilotScript 0x210E [seen], checks the readback pair and on failure drops into loc_2251 [code]. The two-player start's checkTamperGlyphCopyElseRunAwardLabelStep 0x460E [seen] is the odd one out. It compares only the glyph in TAMPER_GLYPH_COPY with its source cell and returns at once when they agree, as they do on a genuine image. On a mismatch it stamps the Mother-Ship's '3000' label into whatever slot is at hand and pays the Mother-Ship's 3,000 award. One more banked value is a fold of program bytes rather than a screen sample: TAMPER_IMAGE_SIGNATURE must read 0x76 before the demo starts, and on a mismatch control transfers to 0x2530, a 256-sample velocity table with a peak of 281. Two stubs load it as a table, `ld hl,0x2530` at 0x585A and at 0x595F, but nothing in the program transfers to either stub.

The KONAMI pair shows how far a witness can travel from its check. Until the first copyright hold expires, TAMPER_GLYPH_KONAMI holds the literal 0x3B and 0x05 that the power-on witness seed table seeds; the hold then replaces them with the glyph and colour actually on screen. The attract arms that follow already derail when that caption cell's glyph is not 0x3B, or when any of the copyright line's thirteen colour cells is not 0x10 or 0x05. A two-player or free-play game started before that hold expires plays with the literal pair, and one started after it, but before the later attract checks have run, plays with the patched copy and dies on reaching 2001. A credited one-player start never keeps the literal pair: startOnePlayerGame re-samples it from the screen as the game starts, so that game plays with whatever the caption cell then shows.

A cheaply patched copyright line therefore survives the attract screen and fails only once the game is being played, far from the edit that caused it.

Beyond the explicit checks, many values the sequence needs are fetched from program bytes rather than written as immediates. Among the sub-steps fetched this way, the one a won round jumps to comes from NEXT_ROUND_START_SUBSTEP 0x4A35 (13), the one a lost life jumps to from NEXT_LIFE_SUBSTEP_SEED 0x4B52 (1), and the one at the end of the round-won animation from INTRO_SUBSTEP_RELOAD 0x2750 (3). The attract restart and the coin-in jump take their phases from ATTRACT_SEQUENCE_START_PHASE 0x16D3 (1) and SEQUENCE_PHASE_ON_CREDIT 0x1736 (2). None of these five is a stored table entry; each is a byte inside an instruction. NEXT_ROUND_START_SUBSTEP is the operand of the `ld b,0x0d` at 0x4A34, NEXT_LIFE_SUBSTEP_SEED is the opcode byte of the `ld bc,0x0010` at 0x4B52, INTRO_SUBSTEP_RELOAD is the operand of the `ld a,0x03` at 0x274F, ATTRACT_SEQUENCE_START_PHASE is the operand of the `and 0x01` at 0x16D2, and SEQUENCE_PHASE_ON_CREDIT is the high byte of the `call 0x0201` at 0x1734. Other fetched values are instruction bytes as well. ROUND_TRANSITION_HOLD_SEED 0x07D1 [seen] (0) is the high byte of a jump's target, SKIP_INITIALS_SUBSTEP_SEED 0x0843 (11) is the high byte of a call's target, and ROUND_WON_ANIMATION_STEP_SEED 0x3213 [seen] (0) is an instruction's immediate operand. Six of the seven codes in the transition sound stops are also fetched from the program image, four of them from instruction bytes and two from data tables. A patch near any of them misroutes the machine.

A bad copy therefore boots only if the whole-image sum and the boot block agree. It may then play normally for a while before it restarts from the wipe, freezes on a jump into data, blanks its picture, lands in the wrong attract step, or asks for the wrong sounds. Which of these happens, and when, depends on which bytes were changed.

## §3 The world moves, not the ship

Time Pilot's ship never goes anywhere. Its sprite is placed once at the middle of the picture and stays there. What the joystick changes is the ship's *heading*, and each frame that heading is turned into a velocity which is applied, negated, to everything else on the screen. So the camera is simply the ship's velocity reversed, and every other moving thing in the game (clouds, enemies, shots, the Mother-Ship, parachutists) picks up that reversed velocity, or for the clouds a scaled copy of it, as part of its own motion. This section follows that chain from the stick to the heading, from the heading to the scroll, and from the scroll to the scenery. It then covers the three separate counters the game uses where the manual only says "round": the era, the round number and the difficulty rung.

### The pinned ship and the camera

Time Pilot's ship never moves on the glass. Every life starts in resetPlayfieldForLifeStart 0x19F0 [seen], which puts the player's sprite entry at a fixed spot: PLAYER_ENTRY 0xAA10 [seen] (the entry's native-X byte) takes 0x84 and PLAYER_SPRITE_Y 0xAA41 [seen] takes 0x78. Neither the steering nor the scrolling code ever writes that entry's coordinates. The ship faces 0x80 on PLAYER_HEADING 0xA802 [seen], PLAYER_STATE 0xA800 [seen] is set to its alive value 0xFF, and both world-scroll words are zeroed. The same point, 0x78 across and 0x84 down, is where armNewGameThenStepSequence 0x27B1 [seen] seats the enemy aim anchor, ENEMY_AIM_ANCHOR_Y 0xAC64 [seen] and ENEMY_AIM_POINT_TABLE 0xAC65 [seen]. That is why enemies can aim at a fixed screen point and still be aiming at the ship.

So flying means moving everything else. The ship has a heading but no position. Each frame its velocity is worked out from that heading, negated, and stored as two 16-bit words: WORLD_SCROLL_Y 0xA808 [seen] and WORLD_SCROLL_X 0xA80A [seen]. Both are 8.8 fixed point: a high byte of whole pixels over a low byte of fraction. They are named for the board's native raster axes. The board is mounted ROT90, so native Y runs across the displayed picture and native X runs up and down it. Every world object drawn as a sprite stores each coordinate split in two; player shots, drawn in the character plane, keep each coordinate whole in their own slot. The whole part is in its sprite entry (+0x31 for native Y, +0x00 for native X), and the fraction is in its object record (+3 and +5). The scroll word is added to that split coordinate as one 16-bit number, so the fraction carries into the whole and a sub-pixel speed builds up across frames instead of being lost.

driftWithWorldScroll 0x2B60 [seen] is the plainest consumer: it adds the two scroll words to an object and nothing more, so a world-fixed thing such as a parachutist once its slot has left the live 0xFF state (runParachutistSlot 0x47B3 [seen]; a live parachutist flies on its own stored velocity through flyAlongStoredVelocity 0x3E05 [seen]) or the Mother-Ship's wreck while its countdown runs (loc_43f0 [seen]) streams past the ship at exactly the ship's speed. Movers with a speed of their own fold the camera into the same addition. flyAlongHeading 0x58BC [seen] adds its own velocity component plus the scroll word to each coordinate. flyAlongStoredVelocity 0x3E05 [seen] does the same with a velocity banked in the record at +0x0A..+0x0D. Neither drifts the object a second time. Player shots work the same way. fireAndSweepPlayerShots 0x23E3 [seen] seeds a new shot's velocity as minus four times the current scroll words, which is four times the ship's own velocity. Each pass it then adds that velocity plus the current scroll, so a shot always flies straight out of the nose wherever the camera is heading: it crosses the screen at three times the ship's velocity while travelling through the world at four times it.

The ship's frame is the second service of the round engine, so everything that moves afterwards reads the scroll the ship has just set. Only reaimEnemyCraftByFlightScriptOnPhaseTick 0x31B4 [seen] runs before it. When the low place of the life tick counter reads 00–06 or 30–36 it steps the flight script of the one craft whose slot the units digit names, if that slot is live (head 0xFF), and, unless that craft is holding its aim, re-aims it: it rewrites the craft's aim heading (+1), which the craft's own handler then turns its heading (+2) toward a step at a time. On a value whose tens digit is neither 0 nor 3 and whose units digit is 7, it instead lays out the enemy aim points around the ship's centre from the heading as it stood before this pass's turn. Neither branch moves any object. Nothing is clamped either: a byte coordinate simply wraps at 256.

### From stick to heading

dispatchPlayerFrameByState 0x1EDF [seen] is the player's per-pass handler. It leaves at once when PLAYER_STATE reads zero. It plays the death animation (advancePlayerAnimationStrip) when the state is any value other than 0xFF. While the ship is alive it decides who is flying. When PLAY_ACTIVE 0xAD30 [seen] is clear, the attract demo's autopilot flyDemoShipByScript 0x214B [seen] flies the ship from a script. In a live game, readPlayerControls 0x1ED1 [seen] returns the control byte of whichever panel faces the picture (see *Cabinet and flip* below), and only its low nibble, the four stick directions, is kept. A centred stick goes straight to the world scroll at the current heading. An off-centre stick goes through turnShipTowardTargetHeading 0x1F01 [seen] first.

PLAYER_HEADING is a whole byte, so a full turn is 256 steps and heading arithmetic wraps for free. The stick nibble does not set the heading. It indexes STICK_HEADING_TABLE 0x1F2E [seen] through fetchTableByte 0x0008 [seen], which gives the heading the ship *wants*. The table's entries are multiples of 0x20. The two bits of each opposite pair map to headings half a turn apart (0x00 and 0x80, 0xC0 and 0x40), the four diagonals map to the headings midway between, and combinations a stick cannot make read zero, the same target as left. The panel's bits are left 0x01, right 0x02, up 0x04 and down 0x08, and the eight targets run left 0, down-left 0x20, down 0x40, down-right 0x60, right 0x80, up-right 0xA0, up 0xC0 and up-left 0xE0. Heading therefore increases anticlockwise on the glass, and the 0x80 seated at life start faces right. The live heading then turns toward the wanted one. It takes the short way round: if the live heading minus the wanted one is 0x80 or more the step is added, otherwise it is subtracted, so a target exactly opposite is always approached the increasing way. The step is three heading steps a pass of the player's handler, or four once ERA_INDEX 0xAD04 [seen] (its low nibble) reaches 3. Four divides the 0x20 spacing exactly, but three does not: across 0x20 a walk of threes comes up two short of the target and then overshoots it by one, and across 0x40 it stops one short. That is why the routine has a third arm, snapHeadingOntoTheTurnTarget 0x1F3E [seen]. When the live heading is one step either side of the target (difference 0xFF or 0x01), the target is written outright and the turn ends exactly on a stick direction. Turning only happens while the stick is held off centre. Release it mid-turn and the ship keeps whatever intermediate heading it has reached and flies on along it, because the centred path scrolls at the heading as it stands.

So the ship cannot flip round instantly. Reversing course is an ordinary turn of 0x80 steps: 44 passes of the player's handler at the slow step (42 steps of three bring the heading two short, one more overshoots by one, and a snap lands it) and 32 at the fast one. The heading sweeps through the half-circle between the two targets, and the ship is drawn at every sector along the way. This settles the "can it about-face?" disagreement in gameplay.md: the code only allows a sweep round, never a flip.

Enemy craft turn on a separate rule. Their step comes from TURN_RATE_BY_ERA_TABLE 0x2C1D [seen], which holds 1, 1, 2, 2 and 5 by era, through steerTowardAimHeading 0x2BEF [seen]. In the fifth era, when a craft's native-Y byte is within 72 of either reference value 120 or 132, steerEra4CraftTowardAimHeadingThenFly [seen] overwrites ERA_INDEX with 0 around the turn to select the slow rate, and then writes 4 back; outside that window the craft turns at the fifth era's own rate of 5. That is safe only because the fifth era's craft handler is its sole caller, but for the length of that turn every reader of "the era" sees era 0.

The heading is also the only visible sign of which way the ship faces. negateVelocityIntoWorldScrollThenDressSprite 0x1F55 [seen] ends by calling dressPlayerSpriteForHeading 0x20AF [seen]. That routine rounds the heading to the nearest of thirty-two sectors (it adds half a sector, then keeps the top five bits) and copies the matching entries of PLAYER_HEADING_SHAPE_TABLE 0x20CE [seen] into PLAYER_SPRITE_CODE 0xAA11 [seen] and, from the parallel column thirty-two bytes on, into PLAYER_SPRITE_ATTRIBUTE 0xAA40 [seen]. The shape column uses sixteen drawings, codes 0xE8-0xF7: 0xF0 at both horizontal headings and 0xE8 at both vertical ones. 0xF1-0xF7 fill the sectors on the downward side of the horizontal and 0xE9-0xEF those on the upward side, each run toward the vertical and then back. The attribute column supplies the flip bits that complete the circle: 0x40 from straight up round through left to just short of straight down, 0x80 at straight down itself, and 0xC0 from just past straight down round through right to just short of straight up. The life-start reset calls the same routine, so a new ship is drawn facing 0x80 before it has moved.

### From heading to velocity, at the era's pace

Every steering path ends in scrollWorldAtTheEraPace 0x1F42 [seen]: the centred stick, a stepped turn, the snap, and the demo autopilot. This routine reads the heading but never decides it. It picks one of three velocity tables from ERA_INDEX alone: OPENING_ERA_VELOCITY_TABLE 0x5E00 [seen] for era 0, SECOND_FASTEST_VELOCITY_TABLE 0x2E3E [seen] for eras 1 and 2, and VELOCITY_TABLE_08FA 0x08FA [seen] for eras 3 and 4. It hands that table and the heading to velocityForHeading 0x596E [seen].

Each velocity table is 256 signed 16-bit samples, one per heading step. velocityForHeading reads the sample at the heading for one component and the sample a quarter turn (0x40 steps) back for the other. The two samples are a quarter-circle apart, so together they make a pair of perpendicular components, and the table's size is the speed. The three player tables have the same shape at three sizes. Their peak samples are 256, 306 and 331, and in 8.8 fixed point 256 is exactly one pixel per pass. Other movers choose their speed the same way, by choosing a table. SLOWEST_VELOCITY_TABLE 0x59D7 [seen] and VELOCITY_TABLE_5C00 0x5C00 [seen] are smaller versions of the same curve, peaking at 206 and 231. Together the peaks run 206, 231, 256, 306, 331, a ladder in steps of 25 with no 281 among the tables any reachable routine loads; a 281-peak table does sit at 0x2530, and two entry stubs load it (ld hl,0x2530 at 0x585A and at 0x595F), but nothing in the program calls or jumps to either stub. So "faster" and "slower" in this game mean a different table rather than a scaled value, apart from the two doublings described at the end of this paragraph. Across the circle the length of a table's vector stays within about 4–5% of its peak (4.0% in the opening-era table, about 4.4% and 4.6% in the two faster ones). The diagonals are within 1% of it, about 254 against 256 in the opening-era table, and the low points are a few irregular samples, such as headings 51 and 243, where the length is about 246. doubledVelocityForHeading 0x59A0 [seen] does the same lookup and shifts both components left once, giving twice the table's length. flyAlongHeadingAtDoubleVelocity 0x58FE [seen] doubles inside the step instead: it adds each looked-up component twice and the world scroll once.

There is no throttle. The only thing that changes the ship's speed is the era: 1910 flies at the slowest pace, 1940 and 1970 faster, and 1982 and 2001 fastest. The pair then goes to negateVelocityIntoWorldScrollThenDressSprite 0x1F55 [seen]. It negates each component as a 16-bit two's-complement word and stores the results in WORLD_SCROLL_Y and WORLD_SCROLL_X. Apart from bulk clears, the only other writer of those two words is the life-start reset, which zeroes them. Because the stored value is the negated velocity, everything that adds it moves opposite to the ship's travel, and that opposite movement is the camera.

The axis names need care. scrollWorldAtTheEraPace passes the sample at the heading on as the component that lands in WORLD_SCROLL_Y and its perpendicular partner as the one that lands in WORLD_SCROLL_X, and those names refer to the board's native raster axes, not the player's view. On the ROT90 board native Y is the display's horizontal axis, mirrored (display_x = 239 − native_y), and native X is the display's vertical axis (display_y = native_x). Check this against heading 0, which is stick-left. The first component is +256 along native Y, which is leftwards on the glass, and WORLD_SCROLL_Y gets −256, which slides the world rightwards. At heading 0x40 (down) the second component is +256 along native X, which is downwards, and the world slides up. In each case the world moves against the stick, as gameplay.md describes. Reading WORLD_SCROLL_Y as a vertical scroll gets the axis wrong; reading it as horizontal gets the axis right but the sign mirrored.

The era is read three different ways in this part of the machine. The turn rate splits it {0,1,2} | {3,4}, the pace splits it {0} | {1,2} | {3,4}, and the scenery (below) splits it {0} | {1,2,3} | {4}. The pace depends only on the era, and the era wraps after 2001, so the second loop's 1910 scrolls and turns exactly like the first. Whatever the manual's "speed … gradually increased" refers to, it is not the ship.

### Scenery and depth

The clouds of the sky eras and the asteroids of 2001 do not move at the world's own speed. They live in eight sprite slots of their own: records from SCENERY_RECORD_SLOT0 0xA900 [seen] and sprite entries from SCENERY_ENTRY_SLOT0 0xAA30 [seen]. runSceneryForEra 0x2CBC [seen] drives them once per pass of the round engine, and it is also called from the life-start hold and lead-in arms, and is reached from the life-start reset too. It seats a record cursor and an entry cursor on the first scenery slot. It then calls a fixed running order of steps, and each step drifts one object and hands both cursors on, advanced past every slot that object used. advanceToNextSlot 0x309B [seen] keeps the two cursors on the same slot index by stepping the record cursor 16 bytes and the entry cursor 2.

Depth comes from three drift fractions. driftAtHalfWorldScroll 0x2DF4 [seen] moves an object by half the scroll, through displaceByHalf 0x304D [seen]. driftAtThreeQuartersWorldScroll 0x2D93 [seen] moves it by three quarters, through displaceByThreeQuarters 0x303E [seen]. driftAtFiveQuartersWorldScroll 0x2D6E [seen] moves it by five quarters, through displaceByFiveQuarters 0x2E31 [seen]. All three build their fraction from an arithmetic right shift of the scroll word, which rounds toward the negative whichever way the ship flies. The five-quarter drift adds that rounded-down quarter to the whole, so it rounds down; the half and three-quarter drifts subtract a rounded-down half or quarter from the whole, so they round up. Half-pace objects trail the world furthest and read as the farthest layer. Three-quarter-pace objects read as a nearer layer behind the playfield. A five-quarter-pace object moves further than the world and so reads as passing in front of it.

Objects wider than one sprite are built afresh on every scenery run. Only the head tile drifts. placeAbuttingTile 0x3058 [seen] puts a further tile in the next slot one sprite pitch (16) along the entry's +0x31 coordinate, with the same +0x00 coordinate. placeDiagonallyAbuttingTile 0x308A [seen] steps 16 back on +0x31 and 16 on along +0x00, treating the pair as one 16-bit number so a carry from the low axis reaches the high one. Because the extra tiles are rebuilt from the head tile on every run, an object can never come apart.

The era chooses the running order, and each order fills all eight slots:

- **Era 0 (1910):** driftThreeTileSceneryAtFiveQuarters 0x2D15 [seen] lays a near object as a straight strip of three tiles. Then two calls of driftTwoTileSceneryAtThreeQuarters 0x2D36 [seen] lay two two-tile objects in the middle layer, and driftOneTileSceneryAtHalf 0x2D68 [seen] lays one single tile in the far layer.
- **Eras 1-3:** the same order, except that the near object is driftNearestSceneryTriTile 0x2D21 [seen]. It places one tile abutting the head and a third diagonally off that one, so the three tiles fill three corners of a square.
- **Era 4 (2001):** two near two-tile objects from stepTwoTileSceneryAtFiveQuarters 0x2D2D [seen], two single middle-layer tiles from driftOneTileSceneryAtThreeQuarters 0x2D62 [seen], and two single far tiles from driftOneTileSceneryAtHalf.

Any era value other than 0 and 4 gets the middle order.

### Seating the scenery for an era

The life-start reset seats the scenery through a chain of routines that each hand straight on to the next; the last, runSceneryForEra, returns to the reset, which then falls into the rung copy described under *The difficulty rung*. seatEraSceneryCodesThenSetAttributesAndRunScenery 0x30A5 [seen] copies the current era's eight-byte row of ERA_SCENERY_ROW_TABLE 0x3176 [seen] into the shape byte of each scenery sprite, from SCENERY_SPRITE_CODE_SLOT0 0xAA31 [seen] at a stride of two. The row is selected as table + 8 × era, using offsetAddress 0x0018 [seen]. This is how the same slots become clouds in one era and asteroids in another. Before the copy it sums the first sixteen bytes of COPYRIGHT_CAPTION_RECORD 0x086B [seen], all but its terminator, against 0x22 and discards the result.

It then passes an attribute byte to setSceneryAttributesThenRunEraScenery 0x30D1 [seen]: 0xCC for eras 0-3, or 0x28 for era 4, which is fixed by the two-instruction entry setFinalEraSceneryAttributesThenRunEraScenery 0x3156 [seen]. That byte is written into all eight scenery attribute bytes, starting at SCENERY_SPRITE_ATTRIBUTE_SLOT0 0xAA60 [seen], so the whole scenery layer takes one colour per era group.

The starting positions differ by era:

- **Eras 0-3:** seedSceneryEntriesThenRunScenery 0x3117 [seen] walks four packed rows of SCENERY_SEED_TABLE 0x316E [seen]. Each row seats two adjacent slots: the first byte goes to the +0x31 coordinate of the first slot and, 0x10 higher, to the second; the second byte goes to the +0x00 coordinate of both.
- **Era 4:** setSceneryAttributesThenRunEraScenery itself copies eight two-byte pairs from ERA4_SCENERY_SEED_TABLE 0x315E [seen] into the eight entries, one pair per slot, so the asteroid field starts scattered rather than paired.

Either way the chain ends in runSceneryForEra, so the first frame of a life already has its scenery drifted and tiled. Because the positions come from fixed tables, the sky starts from the same layout on every life.

Nothing retires a scenery object when it leaves the picture. Both of its byte coordinates just wrap round the 256-wide space, in every era, and its slot keeps its shape byte. The shape bytes change only when a playfield reset seats a new era row [seen], in a game and in the attract demo alike, with two exceptions outside play. The boot clear zeroes them. And foldImageBlockIntoSignatureThenAdvanceSequence [seen] overwrites slot 7's shape byte, SCENERY_SPRITE_CODE_SLOT7 0xAA3F [seen], with 0xFF among the attract sequence's image checks, each time the attract cycle passes them, including the attract that follows a game, with no reset. The same routine then banks its image signature into TAMPER_IMAGE_SIGNATURE 0xAA6F [seen], which is slot 7's native-Y byte. The next playfield reset seats the era row and fresh positions over both [seen].

Both seed paths are guarded by the anti-tamper witness bytes. Era 4 needs TAMPER_GLYPH_KONAMI 0xACC7 [seen] to read 0x3B with 0x05 or 0x10 after it, or control goes through loc_315b 0x315B [code] into the scenery row table executed as code. Eras 0-3 need TAMPER_WITNESS 0xAD39 [seen] to read 0x68 with 0x10 or 0x05 after it, or control goes through trampolineToLoc_307f 0x3114 [code] into caption bytes at 0x307F executed as code.

### Era, round and rung counters

The active player's progress lives in a sixteen-byte live context starting at LIVES_REMAINING 0xAD00 [seen]. Two counters there record the player's position in the loop, and they mean different things. ROUND_NUMBER 0xAD01 [seen] is an ordinal that keeps counting across loops instead of wrapping with the eras (it is one byte, so it wraps only after 255 rounds, as described below), and the round readout is posted from it. ERA_INDEX 0xAD04 [seen] runs 0-4 and wraps, and it picks which era is played. No writer stores anything above 4: the direct stores are the round wrap in startNextRound and the 0 and 4 around the fifth era's turn, and the context copies bring in per-player era cells that are only ever set to 0, to the demo's 1–3, or from ERA_INDEX itself. Other context bytes in the same block include KILLS_REMAINING 0xAD02 [seen], the life tick counter LIFE_TICKS_LOW/MID/HIGH 0xAD05-0xAD07 [seen], START_RUNG 0xAD0A [seen], MOTHER_SHIP_ARMED 0xAD0D [seen] and ROUND_INTRO_PENDING 0xAD0E [seen].

Each player keeps a saved copy of the block: PLAYER_ONE_LIVES 0xAD10 [seen] onward and PLAYER_TWO_LIVES 0xAD20 [seen] onward. loadActivePlayerContextAndPostRoundHud 0x4C75 [seen] copies the active player's saved block into the live one when that player's turn starts. advanceRoundWhenFieldCleared 0x1271 [seen] writes it back when a round ends, and loseLifeAndHandOver 0x11ED [seen] writes it back on every lost life.

When a credited game starts, armNewGameThenStepSequence 0x27B1 [seen] sets both players' saved copies to the same starting values. Era and Mother-Ship flag start at 0. Round number and the round-intro-pending flag start at 1. Kills remaining starts from KILL_QUOTA 0xA9CD [seen], which the boot code filled from DEFAULT_KILL_QUOTA 0x0874 [seen], a ROM byte of 0x38 (56). The start rung is filled from the difficulty record, described below.

The attract demo takes a different branch of the same arm. It cycles ATTRACT_STAGE_COUNTER 0xA9D0 [seen] through 1, 2, 3, then starts the demo in that era with round number era + 1. The demo therefore shows only 1940, 1970 and 1982.

When a round is won and the field is clear, advanceRoundWhenFieldCleared calls startNextRound 0x2DB8 [seen]. That routine increments ROUND_NUMBER and steps ERA_INDEX, wrapping from 4 back to 0, so 2001 is followed by 1910 again. It refills KILLS_REMAINING from KILL_QUOTA; the quota does not depend on the era, so every round asks for the same number of kills. It clears MOTHER_SHIP_ARMED and ROUND_TRANSITION_HOLD 0xACC6 [seen] and raises ROUND_INTRO_PENDING to 0xFF. Before those refills, straight after stepping the era, it reloads START_RUNG according to how far the ordinal has reached: START_RUNG_ROUNDS_1_5 0xA9D3 [seen] below round 6, START_RUNG_ROUNDS_6_10 0xA9D4 [seen] for rounds 6-10, and START_RUNG_ROUNDS_11_UP 0xA9D5 [seen] from round 11 on. This is where the loop gets harder. The second lap replays the same five eras because ERA_INDEX wraps, but it starts on a higher rung because ROUND_NUMBER has kept counting.

### The difficulty rung

Within an era, difficulty is the rung ERA_RUNG 0xACC0 [seen], from 0 to 15. Each (era, rung) pair has its own row of tuning bytes. ERA_RUNG_SETTINGS_POINTER_TABLE 0x1B04 [seen] holds a pointer to each row, indexed by (era << 4) + rung and fetched with fetchTableWord 0x0010 [seen]. applyEraRungSettings 0x1A9A [seen] copies the selected ten-byte row into the cells the spawners and launchers read. The first four bytes tune the bank launcher: how many records it scans for a free slot (BANK_LAUNCH_SLOT_COUNT 0xA844 [seen]), how close a craft's heading must lie to the ship's (BANK_LAUNCH_HEADING_HALF_WIDTH 0xA837 [seen]), the half-width of the zone around the ship inside which a launch is refused (BANK_LAUNCH_NEAR_HALF_WIDTH 0xA827 [seen]), and how long it rests between launches, one byte written to both BANK_LAUNCH_COOLDOWN_PERIOD 0xA814 [seen] and the live BANK_LAUNCH_COOLDOWN 0xA817 [seen]. The next two set the wave size, CRAFT_SPAWN_SLOT_COUNT 0xACC1 [seen], and SCRIPT_PICK_THRESHOLD 0xACC4 [seen], which weighs the choice of flight script between a random pick and a fixed cycle. The last four tune the era-weapon launch the same way: the era-object slot count, which also picks the era-1 bomber shot's seat (ATTACKER_SPAWN_SLOT_COUNT 0xA8C6 [seen]), the window that decides whether a launch goes ahead (ATTACKER_SPAWN_WINDOW_HALF 0xA8D6 [seen]), the final window an era-0 launch must fall inside, which also seeds the 2001 weapon's approach countdown (ATTACKER_SPAWN_AIM_WINDOW_HALF 0xA8E6 [seen]), and one cooldown byte written to both ATTACKER_SPAWN_COOLDOWN_PERIOD 0xA8F6 [seen] and the live ATTACKER_SPAWN_COOLDOWN 0xA8F4 [seen]. Three of these also serve the era-1 bomber's shot, fireBomberShotWhenClearOfPlayer 0x3D25 [seen]: it needs a non-zero era-object slot count, fires only when one of its two tiles lies outside the 0xA8D6 window round the ship, and shares the cooldown, which it re-arms after each shot. The slot count is also the loop bound of sweepEra2PlusObjectBank 0x40D6 [seen].

Because each cooldown's live countdown is reloaded together with its period, applying a row also restarts both cooldowns at the new rate. So difficulty means how many craft come, how often, and from how wide a window. It never affects how fast the world or the ship moves.

This copy is also the last part of the life-start reset. resetPlayfieldForLifeStart seats ERA_RUNG from the player's START_RUNG, reloads ERA_RUNG_TIMER 0xA9D7 [seen] from ERA_RUNG_PERIOD 0xA9D6 [seen], and zeroes the life tick counter and PARACHUTIST_RUNG 0xA8F7 [seen]; once the scenery is seated it runs the same ten-byte copy, which begins at 0x1A9A.

A death therefore drops the rung back to where the round started.

During a life the rung climbs. escalateDifficultyRungOnCounterWrap 0x4D3A [seen] runs once each time serviceRoundThenResolvePlayerState 0x1199 [seen] services the round. It advances the life tick counter, three packed-decimal places that each roll over at 60, using advanceSexagesimalDigit 0x4D67 [seen]. Only on a roll-over of the lowest place does it go on to count ERA_RUNG_TIMER down. When the timer goes from one to zero, it is rearmed from ERA_RUNG_PERIOD, ERA_RUNG climbs by one but is held at 15, and the routine jumps straight into applyEraRungSettings so the harder row takes effect immediately. A timer already at zero stays idle. So the rung climbs once every ERA_RUNG_PERIOD × 60 services, and a long life ends up on its era's hardest row. A timer loaded with zero would never climb, but no difficulty record supplies zero.

The life tick counter is not a clock. It counts round-engine passes, and the pass rate varies with how much work each pass does, so the same number of steps takes a varying number of frames [seen].

### The DIP ladder

The operator's difficulty switches choose the shape of this ladder, not a single setting. At power-on seedGameConfigFromDipSwitches 0x52AA [seen] reads both DIP banks complemented, because the switches are active-low. DSW0_PORT 0xC360 [seen] is the coinage bank; it goes to COINAGE_SETTINGS 0xA9B1 [seen] and on to unpackCoinage 0x4ACC [seen]. DSW1_PORT 0xC200 [seen] is the gameplay bank, and its bits are split up as follows:

- **Bits 0-1, lives:** the two bits plus 3. The fourth setting, which would give 6, is stored as 0xFF instead. This goes to STARTING_LIVES 0xA9C1 [seen], written by unpackTheFirstThreeSwitchSettings 0x2E19 [seen].
- **Bit 2, cabinet:** goes to UPRIGHT_CABINET 0xA9C2 [seen], also in 0x2E19.
- **Bit 3, bonus-life list:** goes to BONUS_LIFE_SETTING 0xA9C3 [seen], also in 0x2E19.
- **Bits 4-6, difficulty:** go to DIFFICULTY_SETTING 0xA9C4 [seen], written by finishBootSelfTestAndColdStart 0x49A8 [seen]. The value runs 0-7.
- **Bit 7, attract sound:** goes to DEMO_SOUNDS_ENABLE 0xA9C6 [seen], also in 0x49A8.

The five gameplay cells are written once per boot. The frame service also copies the gameplay bank into DIP1_MIRROR 0xA9AD [seen] every frame, but that mirror is a separate cell. The coinage bank is treated differently: the frame service recopies it into COINAGE_SETTINGS every frame, though unpackCoinage runs only at power-on.

When a credited game starts, armNewGameThenStepSequence passes DIFFICULTY_SETTING to loadDifficultyRecord 0x0F7B [seen]. That routine copies a four-byte record from DIFFICULTY_RECORD_TABLE 0x186A [seen] into four cells: START_RUNG_ROUNDS_1_5, START_RUNG_ROUNDS_6_10 and START_RUNG_ROUNDS_11_UP, followed by ERA_RUNG_PERIOD. Both players' saved start rungs, PLAYER_ONE_START_RUNG 0xAD1A [seen] and PLAYER_TWO_START_RUNG 0xAD2A [seen], take the first of these. One switch setting therefore fixes four things: the rung each bracket of rounds opens on, and how quickly the rung climbs within a life.

The table runs from gentle to harsh:

| DIP setting | start rung, rounds 1–5 | rounds 6–10 | rounds 11+ | rung period |
|---|---|---|---|---|
| 0 (easiest) | 0 | 2 | 6 | 13 |
| 1 | 0 | 3 | 7 | 12 |
| 2 | 0 | 4 | 8 | 11 |
| 3 | 2 | 6 | 10 | 10 |
| 4 | 4 | 8 | 12 | 9 |
| 5 | 7 | 10 | 13 | 7 |
| 6 | 11 | 13 | 14 | 5 |
| 7 (hardest) | 15 | 15 | 15 | 5 |

A harder setting starts higher and climbs sooner. The loop escalation is only the move from one starting-rung column to the next at rounds 6 and 11, so a lap is harder than the one before only because each life starts higher on the same per-era rows. At the hardest setting every column is already 15, so the rung is at its maximum from the first ship and there is no escalation during a life or between laps at all. The attract demo ignores the switches and always loads record 2: rungs 0, 4 and 8, climbing every 11. gameplay.md's quoted manual line ("the number of planes attacking you, the speed and number of shots and grenades are gradually increased") is these spawn and launch parameters, stepped by rung within a life and by round bracket across loops.

### Cabinet and flip

A cocktail table has two control panels facing each other, and the picture is turned round for the second player. Once a frame, serviceVerticalBlankInterrupt 0x00D9 [seen] recomputes SCREEN_UNFLIPPED 0xA987 [seen]. The cell is 0 only when it is player two's turn (ACTIVE_PLAYER 0xAD32 [seen] non-zero) on a cocktail cabinet (UPRIGHT_CABINET zero), and 1 otherwise. That value is written to FLIPSCREEN_LATCH 0xC302 [seen]. Before the first frame service runs, the boot code drives the latch from FLIPSCREEN_INIT_BYTE 0x0C3E [seen], a ROM byte holding 1.

The same service copies each input port into a complemented mirror. IN1_MIRROR 0xA9AF [seen] holds the main panel and IN2_MIRROR 0xA9B0 [seen] the cocktail panel. readPlayerControls returns the cocktail mirror when SCREEN_UNFLIPPED is zero, and the main one otherwise, so whoever is facing the picture steers the ship. The two panels use the same bit layout, and because the picture is turned round along with the panel, STICK_HEADING_TABLE serves both players unchanged.

The orientation is also applied to the sprites, as they are copied out. publishSpriteShadow 0x0365 [seen] runs first in the frame service. It copies the sprite shadow into SPRITE_BANK0_BASE 0xB010 [seen] (native X and shape) and SPRITE_BANK1_BASE 0xB410 [seen] (attribute and native Y). Each byte goes through an orientation transform on the way:

- **Upright:** only the native Y changes, becoming 241 − Y.
- **Turned round:** native X becomes 240 − X, the shape passes through unchanged, the attribute has its top two bits toggled, and native Y becomes Y + 1.

Because the publish runs before the service rewrites SCREEN_UNFLIPPED, each frame's sprites use the orientation from the frame before. One other routine reads the cell. floodColourPlaneWithSavedPlayerColour 0x13CC [seen] paints its colour rectangle backwards from the far corner when the picture is turned round. It covers the same cells either way.

### The fixed tables this part of the machine reads

All of the behaviour above is driven by constants in the program image:

- **Steering and drawing the ship:** STICK_HEADING_TABLE 0x1F2E [seen] turns a stick position into a wanted heading. PLAYER_HEADING_SHAPE_TABLE 0x20CE [seen] gives the ship's shape and attribute for each heading sector.
- **Speed:** OPENING_ERA_VELOCITY_TABLE 0x5E00 [seen], SECOND_FASTEST_VELOCITY_TABLE 0x2E3E [seen] and VELOCITY_TABLE_08FA 0x08FA [seen] set the pace for each era group. SLOWEST_VELOCITY_TABLE 0x59D7 [seen] and VELOCITY_TABLE_5C00 0x5C00 [seen] are the two smaller tables, and most of their readers double them (doubledVelocityForHeading 0x59A0 [seen], flyAlongHeadingAtDoubleVelocity 0x58FE [seen]). 0x59D7 runs at its own size, peak 206, only through flyAtSlowestSpeed 0x5840 [seen] and velocityForHeadingAtSlowestSpeed [seen], and at 412 elsewhere. Every use of 0x5C00 the program reaches is doubled, to 462, faster than any era's scroll pace: the era-0 craft's shots (fireCraftShotWhenAimedNearPlayer [seen]) and the Mother-Ship's shots in eras 2-4 (MOTHER_SHIP_SHOT_VELOCITY_ARM_BY_ERA_TABLE 0x478B [seen]). TURN_RATE_BY_ERA_TABLE 0x2C1D [seen] gives the enemies' per-era turn rates, through steerTowardAimHeading 0x2BEF [seen].
- **Scenery:** ERA_SCENERY_ROW_TABLE 0x3176 [seen] dresses the scenery for each era. SCENERY_SEED_TABLE 0x316E [seen] and ERA4_SCENERY_SEED_TABLE 0x315E [seen] place it.
- **Difficulty:** DIFFICULTY_RECORD_TABLE 0x186A [seen] and ERA_RUNG_SETTINGS_POINTER_TABLE 0x1B04 [seen] make up the two levels of the difficulty ladder.
- **Single bytes:** DEFAULT_KILL_QUOTA 0x0874 [seen] and FLIPSCREEN_INIT_BYTE 0x0C3E [seen].

Several of these tables are also traps for a patched image: a failed check jumps into their bytes and runs them as code, and on a genuine image none of those jumps is taken. STICK_HEADING_TABLE is entered as loc_1f2e 0x1F2E [code] only through the derail jump at 0x2063, and a relative jump at 0x1F37 inside the table aims at loc_1f99 0x1F99 [code], bytes past the table's end, but that path never takes it. VELOCITY_TABLE_08FA is entered as loc_08fa 0x08FA [code] only on a checksum mismatch. SECOND_FASTEST_VELOCITY_TABLE is the landing of a guard jump in showCreditLine [seen], and SLOWEST_VELOCITY_TABLE the landing of the whole-image checksum in clearScreenRamAndVerifyImageThenColdInit [seen]. ERA_SCENERY_ROW_TABLE is run through loc_315b only when the scenery witness fails.

## §4 Objects: one array, two tables, and two ways onto the screen

### The slot array: one array, two tables

Everything that moves on Time Pilot's screen apart from the text and the player's shots lives in one fixed array of twenty-four slots, and every slot is split across two tables that sit in different places in work RAM. The first table holds sixteen-byte object records, one per slot, running from PLAYER_STATE 0xA800 [seen] up to PLAYER_STATE_BLOCK_END 0xA97F [seen]: this is the object's state, its heading and the fractional parts of its position. The second table is the sprite shadow, two bytes per slot, and it holds what the sprite hardware will be told: the screen position, the shape and the attribute. Slot *n* owns the record at 0xA800 + 16·*n* and the sprite entry at 0xAA10 + 2·*n*, so any routine that walks the slots carries two cursors and steps them together, sixteen bytes on one and two on the other. advanceToNextSlot 0x309B [seen] is that step written once, and the scenery steps end in it; the bank sweeps described below write it inline.

The array is carved into fixed bands, and a slot's band decides who drives it. Slot 0 is the player, with record PLAYER_STATE 0xA800 [seen] and entry PLAYER_ENTRY 0xAA10 [seen]. Slots 1-4 are the enemy shots, ACTOR_RECORD_SLOT0 0xA810 [seen] through ACTOR_RECORD_SLOT3 0xA840 [seen] with entries from ACTOR_ENTRY_SLOT0 0xAA12 [seen]; an enemy craft fires into them through fireCraftShotWhenAimedNearPlayer 0x3ED6 [seen]. Slots 5-11 are the seven enemy-craft slots, CRAFT_RECORD_SLOT0 0xA850 [seen] onward with entries from CRAFT_ENTRY_SLOT0 0xAA1A [seen]. The sixth and seventh craft slots double as the Mother-Ship's pair: slot 10 is MOTHER_SHIP_STATE 0xA8A0 [seen] with MOTHER_SHIP_ENTRY 0xAA24 [seen], slot 11 is CRAFT_RECORD_SLOT6 0xA8B0 [seen] with CRAFT_ENTRY_SLOT6 0xAA26 [seen]. Slots 12-14 are the three-slot era-object bank, ERA_OBJECT_RECORD_SLOT0 0xA8C0 [seen] onward with entries from ERA_OBJECT_ENTRY_SLOT0 0xAA28 [seen]; it holds the era's special objects (the 1910 bombs, the 1940 bomber, the later missiles). Slot 15 is the parachutist, PARACHUTIST_RECORD 0xA8F0 [seen] with PARACHUTIST_ENTRY 0xAA2E [seen]. Slots 16-23 are the scenery band, SCENERY_RECORD_SLOT0 0xA900 [seen] with entries from SCENERY_ENTRY_SLOT0 0xAA30 [seen], driven by runSceneryForEra 0x2CBC [seen] as the parallax layer behind the action.

The shadow is itself two parallel halves 0x30 bytes apart. The first half, 0xAA10-0xAA3F, holds each slot's native-X coordinate at entry +0 and its shape at entry +1; the second half, 0xAA40-0xAA6F, holds the attribute at entry +0x30 and the native-Y coordinate at entry +0x31. For the player those are PLAYER_ENTRY 0xAA10 [seen], PLAYER_SPRITE_CODE 0xAA11 [seen], PLAYER_SPRITE_ATTRIBUTE 0xAA40 [seen] and PLAYER_SPRITE_Y 0xAA41 [seen]. The two halves map straight onto the two hardware sprite banks, as described under publishing below.

The player's shots are the exception to all of this. They do not live in the slot array and own no sprite entry: they have their own six-record array at PLAYER_SHOT_ARRAY 0xAA80 [seen], ending at PLAYER_SHOT_ARRAY_END 0xAADF [seen], and reach the screen through the character plane instead (the last subsection).

### Coordinates

A position is an 8.8 fixed-point number per axis, and it too is split across the two tables: the whole byte sits in the sprite entry and the fraction byte sits in the record. The native-Y coordinate's whole byte is entry +0x31 and its fraction record +3; the native-X coordinate's whole byte is entry +0 and its fraction record +5. Every mover glues the pair into one sixteen-bit value, adds a displacement and splits it back, so the sum wraps at sixteen bits and a sub-pixel velocity accumulates in the fraction instead of vanishing. driftWithWorldScroll 0x2B60 [seen], flyAlongHeading 0x58BC [seen] and flyAlongStoredVelocity 0x3E05 [seen] all work this way. Keeping the whole byte in the entry is what lets a move show up on screen with no further copy: the moment the sum is stored, the sprite entry holds the new screen position.

These are the board's native raster axes. The cell names say X and Y after the hardware, and the vertical-monitor cabinet turns the picture on its side, so native Y runs across the glass. Positions are always screen positions. The player's ship never moves on screen: resetPlayfieldForLifeStart 0x19F0 [seen] pins its entry at native X 0x84 (PLAYER_ENTRY 0xAA10 [seen]) and native Y 0x78 (PLAYER_SPRITE_Y 0xAA41 [seen]), and nothing that flies the ship touches those bytes again. Instead every other object except the scenery, which takes a fixed share of it (below), gains WORLD_SCROLL_Y 0xA808 [seen] and WORLD_SCROLL_X 0xA80A [seen], the negated ship velocity, on top of its own motion each frame. That is the camera, and it is why the edge tests below are taken on screen bytes and not on any world position: the world has no edge, only the screen does.

### The record, byte by byte

A record's meaning is partly shared and partly up to the family that owns the slot. The bytes every family agrees on come first.

Byte +0 is the head byte, and it is the slot's whole life state. Zero means the slot is free, and every sweep, spawner and launcher tests for zero before it takes a slot. 0xFF means a live object, the value a spawner writes when it claims a slot. Anything else means the object is in some timed state, and the value is usually its own countdown: a craft that has just been hit carries the collision sweeps' mark 0xF0, which stepDyingObjectState 0x2B93 [seen] turns into a death countdown starting at 0x3B; a one-shot animation counts its head down to zero in runOneShotAnimatedObjectSlot 0x406C [seen]; and a craft parked waiting to launch holds 0xFE, which releaseHeldObject 0x2B52 [seen] steps to 0xFF when its delay runs out. Because the head carries the state, a whole dispatch is one byte read: dispatchObjectSlotByHeadByte 0x3E63 [seen] and serviceSlotByHeadByte 0x3DEB [seen] are three-way splits on zero, 0xFF and everything else.

Byte +2 is the current heading, a byte that divides a full turn into 256 steps. velocityForHeading 0x596E [seen] turns it into a velocity, and the dressers turn it into a shape. Byte +1 is the heading the object is steering toward. spawnEnemyIntoFreeSlotElseStepSearch 0x37D6 [seen] seeds both +1 and +2 half a turn from PLAYER_HEADING 0xA802 [seen], so a new craft starts out facing the ship. Bytes +3 and +5 are the two coordinate fractions described above.

Byte +0x0E is the slot's delay. It is what lets a slot be emptied without being free at once. The retire helpers that arm it are described below. releaseHeldObject 0x2B52 [seen] counts it down for a held craft and sets it to 0x80 on release, a mark rather than a new delay. armBomberSlotWhenTimerFires 0x3C25 [seen] counts it down only on passes that find FRAME_TICK 0xA980 [seen] even. In the era-2-plus bank sweep outside the last era, a slot with a 0xFF marker flies while its +0x0E count is non-zero and chases its aim point once the count is spent. A fresh craft from the spawner starts with it clear. The other delays have readers too: the Mother-Ship's idle arm in loc_43f0 [seen] counts down the 0x5F that retireEntryPairIntoCooldown leaves, and armBomberSlotWhenTimerFires counts down the 0x80 that retireObjectAndHold leaves. The 0x80 that releaseHeldObject loads is read differently: its top bit marks the craft as a formation member, and countTheKillAndGrantTheSharedToken 0x2BBA [seen] tests it when the craft dies (§6).

Byte +0x0F is the slot's identity stamp. freeAndNumberEveryObjectSlot 0x1AE4 [seen] writes each record's position in the run into it, starting from one at ACTOR_RECORD_SLOT0 0xA810 [seen], so the stamp equals the slot's array index. Code then selects by it. launchAttackerIntoFreeSlot 0x4243 [seen] lets a craft launch only when FRAME_TICK 0xA980 [seen]'s low three bits plus five equal its stamp, which hands each craft slot one frame in eight. chaseOneAimPointAndRetireAtTheLine 0x4117 [seen] re-aims only on a pass whose FRAME_TICK low nibble equals the stamp. countTheKillAndGrantTheSharedToken writes a record's own stamp, with its top bit set, into the shared cell CLAIM_TOKEN 0xA821 [seen] to mark which object a timed claim belongs to.

The bytes in between belong to whichever family runs the slot. An enemy craft keeps a scripted triple at +8, +9 and +0x0A, stepped by stepCraftFlightScript 0x323A [seen]: +9 is the script position and +0x0A selects a 32-byte script through CRAFT_FLIGHT_SCRIPT_TABLE 0x3438 [seen]. Each step counts +9 down by one and loads +8 with that script's byte at the new count, so the script plays backwards and stops on its first byte when the position reaches zero. +8 is filled from a script one step per call, but the reader that consumes it for craft, reaimEnemyCraftByFlightScriptOnPhaseTick [seen], uses it as an aim-point selector and never as a sprite code: it indexes ENEMY_AIM_POINT_TABLE 0xAC65 [seen] by it, treats 0x10 as "keep the current aim", and treats 0x11 as "aim at the table base, turn the aim half a turn away, then hold". On a craft this "animation" is therefore a flight script, not a picture. turnFiveCraftAway [seen] sets +8 to 0x11 and clears +9 in the first five craft records, but only while LIFE_TICKS_LOW 0xAD05 [seen] reads zero; its one caller, driveEnemyWaveForLifePhase [seen], calls it at life phase 7, which sends those craft into the break-away. Objects that fly on a fixed velocity keep it as two words at +0x0A and +0x0C instead (flyAlongStoredVelocity 0x3E05 [seen]). The ballistic object keeps the sign of its fixed step in +1 and a growing speed word at +7/+8. The final-era approach handler keeps a countdown at +4. The Mother-Ship's dresser reads +4, which on that record is MOTHER_SHIP_HITS_TO_ABSORB 0xA8A4 [seen], as a damage stage, and +6 as a flash counter. The parachutist keeps its rung count at +7. These offsets mean nothing outside their family, which is why the same byte can be a steering order in one slot and half a velocity word in another.

Some bytes inside these records are not per-object state at all. A record band is also a convenient place to keep single shared cells, and several named cells fall inside particular records. PLAYER_HEADING 0xA802 [seen] is the player record's +2, and the player record holds WORLD_SCROLL_Y 0xA808 [seen] and WORLD_SCROLL_X 0xA80A [seen] at +8 and +0x0A. WAVE_KILL_COUNTDOWN 0xA811 [seen] and WAVE_CLAIM_TIMER 0xA812 [seen] sit inside enemy-shot slot 0's record, and CLAIM_TOKEN 0xA821 [seen] inside slot 1's. The round's settings row, which resetPlayfieldForLifeStart 0x19F0 [seen] scatters at the start of every life, lands inside the enemy-shot, era-object and parachutist records: BANK_LAUNCH_COOLDOWN_PERIOD 0xA814 [seen], BANK_LAUNCH_COOLDOWN 0xA817 [seen], BANK_LAUNCH_NEAR_HALF_WIDTH 0xA827 [seen], BANK_LAUNCH_HEADING_HALF_WIDTH 0xA837 [seen] and BANK_LAUNCH_SLOT_COUNT 0xA844 [seen] at +4 and +7 of enemy-shot records, ATTACKER_SPAWN_SLOT_COUNT 0xA8C6 [seen], ATTACKER_SPAWN_WINDOW_HALF 0xA8D6 [seen] and ATTACKER_SPAWN_AIM_WINDOW_HALF 0xA8E6 [seen] as the +6 bytes of the era-object bank, and ATTACKER_SPAWN_COOLDOWN 0xA8F4 [seen] and ATTACKER_SPAWN_COOLDOWN_PERIOD 0xA8F6 [seen] at +4 and +6 of the parachutist record. MOTHER_SHIP_AIM_SIDE_TOGGLE 0xA8B4 [seen] is +4 of the slot after the Mother-Ship's. Those cells are always read and written by their absolute address, never through a record cursor, so an address inside 0xA800–0xA97F is not automatically "field n of object i". The parachutist's rung, PARACHUTIST_RUNG 0xA8F7 [seen], has a name of its own but is a true field: the reset zeroes it by address, and the rescue award reads and steps it as +7 of the parachutist record.

### The slot life cycle

A slot starts each life free and numbered. resetPlayfieldForLifeStart 0x19F0 [seen] runs at every life start. It first retires particular slots on purpose: it takes the era-object bank's first pair out with retireObjectAndHold 0x3C0D [seen], retires its third slot with retireSlotIntoSharedCooldown 0x3DFB [seen], holds the parachutist off with retireSlotIntoCooldown 0x48AD [seen], and then runs retireSlotAndSubPixel 0x2BDE [seen] over the parachutist record and the six scenery records after it, zeroing each one's head byte, both fractions and both sprite coordinates. Then freeAndNumberEveryObjectSlot 0x1AE4 [seen] walks the run from ACTOR_RECORD_SLOT0 0xA810 [seen] to the end of the scenery band, clearing each head byte and restamping +0x0F. The order matters because the free touches only those two bytes: every delay armed at +0x0E a moment earlier survives it, so a freed slot can still be held off its next spawn. (Apart from the cold-start wipe of all work RAM, clearWorkRamAndSpriteBank1ThenColdInit 0x0069 [seen], only the attract demo's round start, in armNewGameThenStepSequence 0x27B1 [seen], zeroes the whole record block and the whole shot array outright.)

A slot is claimed by finding a zero head and writing 0xFF into it. For ordinary enemy craft the search is gateTheFreeSlotSearchAndPickItsRun 0x37BD [seen]. It opens only on two values of the counter it is pointed at, then chooses where to look. While KILLS_REMAINING 0xAD02 [seen] is non-zero it seats on the top craft slot, CRAFT_RECORD_SLOT6 0xA8B0 [seen], and searches as many slots as CRAFT_SPAWN_SLOT_COUNT 0xACC1 [seen] allows. Once the quota is spent it seats on CRAFT_RECORD_SLOT4 0xA890 [seen] for a fixed five, which keeps the search off the two records the Mother-Ship takes. The search walks downward. spawnEnemyIntoFreeSlotElseStepSearch 0x37D6 [seen] looks at one slot and, if the head is taken, hands off to closeOneTurnOfTheFreeSlotSearch 0x3847 [seen], which backs both cursors off one slot and comes round again. The first free slot it meets is claimed and stocked: a start position comes from the spawn tables ENEMY_SPAWN_DIRECTION_INDEX_TABLE 0x39FB [seen] and ENEMY_SPAWN_RECORD_TABLE 0x3A3B [seen], indexed by the ship's heading jittered at random, and the headings, fractions, flight script and delay are seeded. At most one slot is filled per search. The era-object bank has its own walk, upward, in launchAttackerIntoFreeSlot 0x4243 [seen], bounded by ATTACKER_SPAWN_SLOT_COUNT 0xA8C6 [seen].

While it is live, a slot is moved, dressed and tested by whatever handler its band runs, every frame. It leaves play by being retired, which ends the cycle by zeroing the head byte again, possibly with a delay armed so that the slot sits out a while before the next claim.

### Retiring and hiding

Retiring is the record-aware way out, and it always does two things at once: it zeros the head byte, so every handler reads the slot as free, and it zeros both whole coordinates in the sprite entry (+0 and +0x31), which takes the sprite off the picture. The helpers differ only in what else they do, and each family uses its own.

retireSlot 0x40AB [seen] is the plain form: it makes exactly those three stores and leaves the fractions standing. retireSlotAndSubPixel 0x2BDE [seen] also clears the two fractions at +3 and +5, and it is how the craft services and the dying-craft countdown let go of a slot. The remaining helpers also arm the delay at +0x0E, so that the freed slot sits out a while. retireSlotIntoCooldown 0x48AD [seen] is retireSlot's three stores plus 0xF0 into that delay, and the parachutist leaves play this way; spawnAtEdgeAhead [seen] counts that delay down, on passes that find FRAME_TICK odd, before placing it again. retireSlotIntoSharedCooldown 0x3DFB [seen] calls retireSlot and then copies ATTACKER_SPAWN_COOLDOWN_PERIOD 0xA8F6 [seen] into the delay, so every slot it retires waits the same shared, per-round interval. retireObjectAndHold 0x3C0D [seen] frees the caller's record and the record one stride on (zeroing both head bytes), zeros the caller's sprite and the fixed entry ERA_OBJECT_ENTRY_SLOT1 0xAA2A [seen], and arms the caller's delay with 0x80. retireEntryPairIntoCooldown 0x46DB [seen] is the version for one record that shows two sprites: it zeros the head and both coordinates of two neighbouring entries and arms the delay with 0x5F, and armMotherShipOrStep 0x43B7 [seen] and the Mother-Ship's dresser use it on MOTHER_SHIP_STATE 0xA8A0 [seen]. A retired slot's record keeps whatever else it held.

The one-shot animation retires itself through retireSlot 0x40AB [seen]. When runOneShotAnimatedObjectSlot 0x406C [seen] counts its head down to zero, the head is already the free value, so the only bytes that change are the two sprite coordinates.

Hiding is a separate and blunter tool that ignores the records entirely. hideAllSprites 0x15B6 [seen] zeros the native-Y byte of all twenty-four entries, from PLAYER_SPRITE_Y 0xAA41 [seen] in steps of two, and touches nothing else. A sprite with a zero native-Y byte is off the picture, but its record, shape and attribute all survive, so an object hidden this way is still alive. It is simply invisible until something rewrites its native-Y byte. The scene changes use it: life loss, the round-won sweep, a demo round's end, the push-start screen, a free-play start, and a game started from the initials screen. hideCaptionSprites 0x0B2B [seen] is the same idiom over the first four entries only, which is where the attract screens stamp the copyright caption as sprites. It runs when a credited game or the demo begins; a free-play start parks every sprite with hideAllSprites instead.

### Retire lines and edge tests

Because positions are screen bytes that wrap at 256, "has this object left the field?" is asked as "has a coordinate arrived in a narrow window near some line?". Each window is a wrapped distance (bias, then one unsigned compare), and each is a few values wide, so an object moving several pixels a frame lands inside it instead of stepping over it.

The common test is hasReachedRetireLine 0x2B83 [seen]. It answers yes when the native-Y byte is within one of 0xF8 or, failing that, the native-X byte is within one of 0x04. Those two lines are exactly half the coordinate range away from the ship's pinned position (0x78 + 0x80 and 0x84 + 0x80), the point on screen farthest from the player in a world that wraps. Each era's craft service, the parachutist, the enemy-shot handler, the era-2-plus bank's flying arms and serviceSlotByHeadByte 0x3DEB [seen] all ask it after moving (the era-0 ballistic arc and the era-1 bomber use bounds of their own), and the callers that act on a yes retire the slot at once.

A second family serves objects whose way out depends on their direction. hasReachedBoundaryBandSelectedByHeading 0x3CC4 [seen] splits the compass by adding a quarter turn to the heading at record +2 and looking at the top bit. One half tests the native-Y byte for 0xED-0xEF. The other half hands over to hasDriftedOffTheField 0x3CD9 [seen], which tests the band just past it, 0xF0-0xF2. Whichever band misses, the question falls through to hasReachedNativeXEdgeWindow 0x3CE1 [seen], a four-wide window on the native-X byte that straddles the wrap, 0xFE through 0x01. So the answer is always the OR of a heading-chosen native-Y band and the native-X window. flyBomberThenTryAimedShot 0x3B77 [seen] and dressSpriteForHeadingOrRetireAtEdge 0x4447 [seen] use this family. The player's shots have their own bounds, given in the last subsection.

### Dressing sprites

Moving an object changes its coordinate bytes. Dressing it means writing the other two bytes of its entry, the shape at +1 and the attribute at +0x30 (flip bits plus colour), so that the sprite points the way the object is heading. Every dresser rounds the heading at record +2 to the nearest sector, by adding half a sector before truncating, so headings just short of a full turn wrap into sector 0 and the circle closes. It then looks that sector up in ROM for a shape and an attribute, and the mirroring bits in the attribute let a handful of drawn shapes cover the whole circle. The dressers differ in resolution, in how their tables are laid out and in which objects they serve.

The ship is dressed by dressPlayerSpriteForHeading 0x20AF [seen], from PLAYER_HEADING 0xA802 [seen] at 32 sectors, out of PLAYER_HEADING_SHAPE_TABLE 0x20CE [seen] with its attribute table 32 bytes on. It writes PLAYER_SPRITE_CODE 0xAA11 [seen] and PLAYER_SPRITE_ATTRIBUTE 0xAA40 [seen] directly. negateVelocityIntoWorldScrollThenDressSprite 0x1F55 [seen] calls it on every pass of the live ship's handler, and the life reset calls it once.

Each era's craft have a dresser of their own. The first two eras share spriteForHeading 0x2A57 [seen], which works at 16 sectors from SPRITE_SHAPE_BY_SECTOR_TABLE 0x2A77 [seen] and SPRITE_MIRROR_BY_SECTOR_TABLE 0x2A87 [seen] and returns the pair without storing it. It adds eight to the shape whenever bit 1 of FRAME_TICK 0xA980 [seen] is set, so each direction alternates between two poses every two frames. refreshSpriteFromHeading 0x2A3C [seen] stores that pair as it is for the first era's craft. refreshSecondEraSpriteFromHeading 0x2A47 [seen] dresses the second era's craft, shifting the shape by 16 into another block of the sprite ROM and the attribute by 53 into another colour. The third era's craft go through dressSpriteForFineHeading 0x2A97 [seen], at 32 sectors and with the same two-frame alternation. Its FINE_HEADING_SHAPE_TABLE 0x2ABC [seen] is a single table of shape-and-attribute pairs, not two parallel tables. The fourth era's craft go through dressSpriteForCoarseHeading 0x2AFC [seen], at 16 sectors from COARSE_HEADING_SHAPE_TABLE 0x2B18 [seen] with the attribute table 16 bytes on and no alternation. The chased era weapons are dressed the same coarse way by dressSpriteShapeAndAttributeForHeadingSector 0x3FAF [seen], from HEADING_SECTOR_SHAPE_TABLE 0x3FCA [seen] with its attribute table 16 bytes on.

The Mother-Ship is two sprites wide, and dressSpriteForHeadingOrRetireAtEdge 0x4447 [seen] dresses both entries of its pair at once: the shapes at +1 and +3, the attributes at +0x30 and +0x32. It first asks the heading-chosen edge test, and on a yes it retires the pair through retireEntryPairIntoCooldown 0x46DB [seen] instead of dressing it. Otherwise, outside the last era, it builds an index into MOTHER_SHIP_SHAPE_PAIR_TABLE 0x44F1 [seen] from ERA_INDEX 0xAD04 [seen], bit 1 of FRAME_TICK 0xA980 [seen] and a damage stage folded from record +4, and takes a colour from ERA_SPRITE_COLOUR_TABLE 0x4531 [seen] by era alone. The routine's only caller runs the Mother-Ship record, so +4 there is MOTHER_SHIP_HITS_TO_ABSORB 0xA8A4 [seen], folded as ((7 − hits) >> 1) & 3: the Mother-Ship wears its damage. The heading then only chooses a compass half. Facing one half, the two shapes are laid into the entries in swapped order. Facing the other, they keep table order and both attributes gain 0x80, which flips a mirroring bit, so the same pair of tiles reads as facing the other way. In the last era the pair gets attribute 0x70 and the two-pose flutter of dressSpriteFlutterShapesByFrameTickBit 0x44DC [seen], which picks shapes 0xD5/0xD4 or 0xD7/0xD6 from bit 2 of FRAME_TICK 0xA980 [seen] and so holds each pose for four steps of that counter, one per frame service. Once +4 has dropped below 7, the counter at +6 runs there as a flash cycle: for a few passes of each cycle both attributes are 0x51 instead of 0x70, and the cycle shortens as +4 falls, so a damaged Mother-Ship flashes.

One-shot animations are not dressed by heading. runOneShotAnimatedObjectSlot 0x406C [seen] picks a shape from ONE_SHOT_OBJECT_SHAPE_TABLE 0x4094 [seen] by how far its countdown has run, holds each shape for four of its countdown steps (round-engine passes, not frames), and uses the fixed attribute 0x0E. A few objects are animated from FRAME_TICK alone. animateFixedShapeCycle [seen] and animateFixedShapeCycleFromShape50 [seen] step through eight consecutive shape codes from FRAME_TICK bits 1–3, one shape every two frames, starting at shape 0x40 with attribute 0x44 or at shape 0x50 with attribute 0x0A, so everything drawn through them animates in step. animateSelectedShapeCycle [seen] uses the record's +4 to pick a block of four shapes and FRAME_TICK bits 2–3 to pick one within the block.

### Screen output: two ways onto the screen

No object handler writes to the display hardware. Objects reach the screen by two routes, and both are deferred to the next vertical blank. Objects in the slot array are sprites: their handlers write the shadow at 0xAA10-0xAA6F, and the shadow is copied into the hardware sprite banks. The player's shots are character cells: the shot engine appends cell edits to a pending list, and the list is applied to the character plane. The two copies are the first two things serviceVerticalBlankInterrupt 0x00D9 [seen] does, publishSpriteShadow 0x0365 [seen] and then drainBothDeferredCellLists 0x5286 [seen]. So both routes always show the state the previous frame's logic left behind. Two kinds of write do reach the hardware during the frame, and neither comes from an object handler. The doubling passes described below rewrite the scenery sprites' bytes in the hardware banks while the picture is being scanned out. The character-plane text and the kill meter (§8) are written straight into the plane, as drawKillMeter 0x0809 [seen] does from the round engine's service list.

### Sweeping the banks

Each band is driven by its own pass, and every pass is on the round engine's fixed service list, serviceRoundThenResolvePlayerState 0x1199 [seen], though the player's frame and the scenery are also run from the life-start hold arm, those two and the player's shots from the enemy-free lead-in at the start of every life, and the scenery alone from the life-start reset. The order is: one enemy craft re-aimed on its tick, the player's frame, the player's shots, the wave driver, the parachutist, the Mother-Ship, the seven craft slots, the scenery, the era-2-plus bank, the era-1 bomber and the era-1 fixed slot, the four enemy-shot slots, the era-0 bank, and only then the collision pass. The doubling passes described below are threaded between these. A later pass therefore sees anything an earlier one wrote this frame.

The craft and enemy-shot bands are stepped as fixed lists of slots. stepSevenCraftSlots 0x28A1 [seen] calls seven tiny entries in turn. Each entry seats one slot's record and entry as constants and jumps to dispatchSeatedSlotByEraIndex 0x290E [seen], which chooses that era's craft service from the low three bits of ERA_INDEX 0xAD04 [seen] through ERA_SLOT_DISPATCH_TABLE 0x2914 [seen]. The last two entries, seatMotherShipSlotThenDispatchByEraUnlessArmed 0x28EE [seen] and seatCraftSlot6ThenDispatchByEraUnlessArmed 0x28FE [seen], return at once while MOTHER_SHIP_ARMED 0xAD0D [seen] is set, which is how the Mother-Ship's pair is withheld from the ordinary craft service. The flag is raised when the Mother-Ship is armed and cleared only at round start or life start, so from arming until then, even after the Mother-Ship is destroyed, neither slot runs as a craft. Of the eight words in ERA_SLOT_DISPATCH_TABLE, the first five are the five era services. The sixth and seventh point outside the program image, and the eighth is the round-won band animation of sequence step 14, stepRoundWonBandAnimation 0x1323 [seen]. ERA_INDEX never passes 4, so in play the dispatcher takes only the first five. stepFourActorSlots 0x3E36 [seen] does the same for the enemy-shot slots, running each through dispatchObjectSlotByHeadByte 0x3E63 [seen]. Every per-slot service has the same skeleton (serviceEra0EnemyCraftSlot 0x2927 [seen] is typical): free slots do nothing, timed states are stepped, and a live object is steered, flown, tested against the retire line and dressed, in that order. A slot that retires is never dressed.

The era-object bank is swept by a counted loop, and each era enters it a different way. In the first era, serviceEra0BallisticObjectBank 0x3FEA [seen] seats the cursors on ERA_OBJECT_RECORD_SLOT0 0xA8C0 [seen] and ERA_OBJECT_ENTRY_SLOT0 0xAA28 [seen] with a count of three. It then joins the loop whose head is sweepObjectSlotBankByHead 0x3FF9 [seen]. The loop head branches to two later points in it: sweepObjectSlotBankServicingFirstSlot 0x4008 [seen], used when the current slot is already known to hold a countdown, and advanceSlotThenSweepObjectBankByHead 0x400B [seen], used when the slot is empty or has just been dealt with. Inside the loop a 0xFF head flies a ballistic arc (flyAlongBallisticArc 0x4017 [seen]) and any other non-zero head runs the one-shot animation. From the third era on, sweepEra2PlusObjectBank 0x40D6 [seen] seats the same cursors with a count taken from ATTACKER_SPAWN_SLOT_COUNT 0xA8C6 [seen], and does nothing if that count is zero. Its loop body, serviceSlotByMarkerThenCloseSweepTurn 0x40EA [seen], ends every arm in closeOneTurnOfTheSlotSweep 0x410B [seen], which steps both cursors forward, counts one off and re-enters the body while turns remain. That makes one call cover the whole bank. Within the body, a non-0xFF marker is a drifting countdown object. A 0xFF marker in the last era runs stepSlotApproachThenBreakawayRetire 0x4194 [seen]. In the other eras, a 0xFF marker flies on its stored velocity while its +0x0E count lasts and then switches to chaseOneAimPointAndRetireAtTheLine. In the second era the bank's first two slots, 12 and 13, are one two-tile bomber run by serviceEra1BomberObject [seen]; slot 13's entry is only its second tile, rebuilt from the first tile every step by flyBomberThenTryAimedShot [seen] (by advanceHitSoakingObjectThenAnimateDeath [seen] while it dies), and serviceFixedSlotInEra1 [seen] flies the bank's third slot, slot 14, through serviceSlotByHeadByte 0x3DEB [seen] (§6).

The scenery band is walked by runSceneryForEra 0x2CBC [seen]. It chooses one of three running orders by era and hands the two cursors from step to step, each step drifting one scenery object at its own fixed share of the world scroll, from half up to five quarters of it. A multi-tile object takes one slot per tile: the head tile is drifted, and placeAbuttingTile 0x3058 [seen] (or, for the cornered three-tile shape's third tile, placeDiagonallyAbuttingTile 0x308A [seen]) rebuilds each further tile flush against it on every run, stepping the cursors as it goes, so the object never comes apart. Every running order uses up exactly the eight scenery slots.

### Publishing to the sprite banks

publishSpriteShadow 0x0365 [seen] copies the shadow into the two hardware sprite banks at the top of every vertical blank. Bank 0 at SPRITE_BANK0_BASE 0xB010 [seen] takes the native-X and shape bytes. Bank 1 at SPRITE_BANK1_BASE 0xB410 [seen] takes the attribute and native-Y bytes. Each bank is one continuous forty-eight-byte block, but it is gathered from three runs of the shadow in an order that is not memory order. First come scenery slots 16-18 (from SCENERY_ENTRY_SLOT0 0xAA30 [seen], and SCENERY_SPRITE_ATTRIBUTE_SLOT0 0xAA60 [seen] for bank 1). Next come all of slots 0-15 (from PLAYER_ENTRY 0xAA10 [seen], and PLAYER_SPRITE_ATTRIBUTE 0xAA40 [seen]). Last come scenery slots 19-23 (from SCENERY_ENTRY_SLOT3 0xAA36 [seen], and SCENERY_SPRITE_ATTRIBUTE_SLOT3 0xAA66 [seen]). So hardware sprites 0-2 and 19-23 are exactly the eight scenery sprites, and hardware sprites 3-18 are the player and every active object.

Each byte passes through a transform on the way, chosen by which half of its sprite it is and by which way round the picture is. That orientation comes from SCREEN_UNFLIPPED 0xA987 [seen]. Upright, only the native-Y byte changes, becoming the complement of the value plus 14, that is of (value + 14), which is 241 minus the value. Turned round, the native-X byte becomes the complement of (value + 15), the shape passes through, the attribute has its top two (flip) bits toggled, and the native-Y byte steps on by one. Every transform is byte-wide and wraps. The vertical-blank service rewrites SCREEN_UNFLIPPED 0xA987 [seen] only after this publish, so each frame's sprites follow the orientation the previous frame settled.

After the copy, and only inside one window of the sequence machine, the publish arms the scenery sprites for doubling. The window is SEQUENCE_PHASE 0xA9AB [seen] at 3 with SEQUENCE_SUBSTEP 0xA9AC [seen] from the floor held in the ROM byte SPRITE_RAISE_STEP_FLOOR 0x0832 [seen] (5 on this image) up to 7. Those are the life-start hold arm, the enemy-free lead-in at the start of every life and the round engine itself, exactly the three arms that run the doubling passes. For each of the eight scenery sprites whose bank-1 native-Y byte still has its top bit clear, the publish adds 0x80 to that byte and to the sprite's bank-0 native-X byte. A sprite whose top bit is already set is left alone, so running the raise twice changes nothing.

### Scenery doubling mid-frame

The board has twenty-four sprites, too few for the ship, the enemies and a sky's worth of scenery. So the eight scenery sprites are each shown twice per frame, by moving them while the picture is being scanned out. Bit 7 of a scenery sprite's bank-1 native-Y byte is the request. A doubling pass "trades" a requested sprite: it clears the request, which takes 128 off the native-Y byte, and adds 128 to the partner native-X byte in bank 0. The same sprite then sits half the coordinate range away on both axes. For a sprite the publish raised, the trade simply puts it back where the shadow said it was. So during the early part of the scan it is drawn half the range away, and after the trade it is drawn at its true position: one cloud, two places on the glass.

The trade must not happen before the first appearance has been drawn, so it is gated on the raster. SCANLINE_COUNTER 0xC000 [seen] is read and added to the request byte, and the trade is due once the sum carries out of eight bits, which is a line that depends on where the sprite sits. multiplexSpriteSlotsSkipping 0x0F97 [seen] is the opportunistic pass. It trades every sprite whose line the beam has already passed and leaves the rest armed, and the round engine runs it at five points spread through its service list. multiplexSpriteSlots 0x1098 [seen] is the closing pass that ends the list. Each of its eight blocks spins on the raster until its sprite's line comes and then trades it, so every request is honoured before the frame's work is done. Its stretch for hardware sprites 19-23 is loc_10f8 0x10F8 [seen], reached only by branches inside multiplexSpriteSlots 0x1098 [seen]. The life-start hold arm flyLifeStartHoldThenEraseLifeStartCaptions 0x16AF [seen] and the enemy-free lead-in flyEnemyFreeLeadInThenStepSequence 0x5694 [seen] run the same passes, closing with multiplexSpriteSlots 0x1098 [seen]. Hardware sprites 3-18, the active objects, are never touched by any of this. The ROM also has an entry five bytes into sprite 19's block, spinRemainingSpriteMultiplexSlots 0x10FD [seen], whose only call sits in caption bytes that run as code only on the anti-tamper derail.

### Player shots in the character plane

The player's shots are not sprites at all. fireAndSweepPlayerShots 0x23E3 [seen] keeps them in the six sixteen-byte records of PLAYER_SHOT_ARRAY 0xAA80 [seen], and each record holds its whole position. Byte +0 is the head (0 free, 0xFF live, anything else marked, for instance the 0xF0 a hit writes). +3/+4 is the native-Y coordinate as a full 8.8 word (fraction, then whole), and +5/+6 the native-X one. +0x0A and +0x0C are the two velocity words. Each shot the gun launches seeds its velocity as four times the negated world scroll, which is four times the ship's own velocity. It starts at a muzzle position looked up from PLAYER_SHOT_SPAWN_POSITION_TABLE 0x2771 [seen] by the ship's heading rounded to 32 directions. Each pass the sweep adds that velocity plus the world scroll to both words, and culls a shot whose head has been marked or whose whole byte has entered its edge band: 0xF0-0xFF on native Y, 0xF8-0x0F on native X. Culling clears the head and both whole bytes. freeAllShotSlots 0x2755 [seen] frees every shot at each life start by zeroing each record's head and its native-Y whole byte (+0 and +4), reading its fill byte and stride from program bytes, SHOT_SLOT_FILL_BYTE 0x5C01 [seen] and PLAYER_SHOT_SLOT_STRIDE 0x0861 [seen]. The shot-against-target tests take the shots' whole bytes against the targets' sprite entries (stagePlayerShotSweepAgainstTargetsAndRun 0x4F5D [seen] stages the first of them).

A shot that survives the sweep is drawn by queueTileStampForObject 0x5337 [seen] as a two-by-two block of character cells. Both whole coordinates are biased by seven. The top five bits of each pick the block's top-left cell in a 32-cell-wide grid based at COLOUR_PLANE_BASE 0xA000 [seen]: the native-Y coordinate gives the row and the native-X one the column. The low three bits of each pick one of the 64 eight-byte records of PRESHIFTED_TILE_RECORD_TABLE 0x53D4 [seen]. Each record is four glyph-and-attribute pairs, one per cell, pre-drawn at that sub-cell offset, and that is what lets a shot built from eight-pixel cells move a pixel at a time. A pair whose glyph is zero is skipped, but the cell walk still advances. Each surviving pair is appended as four bytes (cell address low, cell address high, glyph, attribute) behind DEFERRED_WRITE_CURSOR 0xAE00 [seen], whose entries start at DEFERRED_WRITE_LIST 0xAE04 [seen]. The write pointer steps only its low byte, so the list never leaves its page.

At the next vertical blank, drainBothDeferredCellLists 0x5286 [seen] does three things in a fixed order. First, blankCellsPaintedLastPass 0x530E [seen] walks the erase list behind DEFERRED_BLANK_CURSOR 0xAE80 [seen] (entries from DEFERRED_BLANK_LIST 0xAE84 [seen]) and writes the blank glyph 0x20 into the character plane, leaving colour alone. Next, paintDeferredCells 0x52D2 [seen] walks the pending list. For each entry it writes the glyph into the character plane, which sits 0x400 above the colour plane (CHAR_PLANE_BASE 0xA400 [seen]), and writes the attribute back into the colour plane with the low nibble of PEN_COLOUR 0xAD0C [seen] added. Both walks skip any cell whose colour byte has bit 4 set, the mark of a character drawn above the sprites, so a shot never overwrites or erases the HUD. Last, the pending list is copied wholesale onto the erase list, with a top-bit mark on the copied cursor that the blanker masks off, and the pending cursor is parked back on its first entry. If nothing was pending, emptyBothDeferredCellLists 0x526A [seen] parks both cursors instead. The lists are not a double buffer. The copy always runs one way, so whatever is painted on one pass is exactly what gets blanked on the next. A shot cell therefore stays on screen only as long as the sweep keeps queueing it, and a culled shot disappears on the next vertical blank with no erase code of its own.

## §5 The player's ship

### The player record

The ship has no position in the world. It sits at a fixed spot near the centre of the picture, and "flying" means turning it and sliding the world past it the other way. So the ship's state is small. It lives in a record whose head byte is PLAYER_STATE 0xA800 [seen], with the heading two bytes on at PLAYER_HEADING 0xA802 [seen], and in a sprite entry that starts at PLAYER_ENTRY 0xAA10 [seen]. The byte between the state and the heading, PLAYER_RECORD_SPARE_BYTE 0xA801 [seen], is cleared at every life start and nothing reads it. The sprite entry's +0 byte (PLAYER_ENTRY itself) and its +0x31 byte, PLAYER_SPRITE_Y 0xAA41 [seen], are the ship's two coordinates on the board's native axes. They are set at each life start, to 0x84 and 0x78, and no steering code moves them, so they are the fixed point every contact test measures against. Apart from the power-on wipe of work RAM, the only other writers do not move the ship: hideAllSprites [seen] and hideCaptionSprites [seen] zero PLAYER_SPRITE_Y to hide the sprite, and on the attract copyright screen stampCopyrightStrip [seen] reuses the entry for the first piece of the copyright caption strip, writing 216 into PLAYER_ENTRY and 160 into PLAYER_SPRITE_Y. The entry's +1 byte, PLAYER_SPRITE_CODE 0xAA11 [seen], holds the shape, and its +0x30 byte, PLAYER_SPRITE_ATTRIBUTE 0xAA40 [seen], holds the colour, with the mirroring in its top two bits.

PLAYER_STATE 0xA800 [seen] uses the same small alphabet as every object slot. 0xFF means alive. 0xF0 is written by whatever kills the ship. From then on the byte is a countdown that drives the explosion, and it reaches 0 when the ship is gone. Almost everything in this section is a branch on that one byte.

The heading is a whole byte: 256 steps round the circle, so all heading arithmetic simply wraps at eight bits. Each life starts with the heading at 0x80.

### One frame of the ship

The round engine, serviceRoundThenResolvePlayerState 0x1199 [seen], runs the ship's frame second in its service list, straight after the enemy re-aim. The frame runs before the gun and before every mover, so the world scroll the ship sets this pass is the one everything else reads. The ship's frame is dispatchPlayerFrameByState 0x1EDF [seen]. The life-start hold arm and the enemy-free lead-in, which open every life, also call it, so the ship flies during those arms too (see "Round start and each life" below).

dispatchPlayerFrameByState branches on PLAYER_STATE 0xA800 [seen]:

- **Zero:** the ship has been torn down and the frame does nothing.
- **Any value other than 0xFF:** the ship is exploding, and the frame goes to advancePlayerAnimationStrip 0x2010 [seen] (see "The explosion" below).
- **0xFF:** the ship is alive. The routine then checks PLAY_ACTIVE 0xAD30 [seen], the flag that tells a credited game from the attract demo. With the flag clear, nobody is holding the stick and flyDemoShipByScript 0x214B [seen] steers the ship. With the flag set, the routine reads the controls and keeps the low nibble, the four stick bits. An off-centre stick goes to turnShipTowardTargetHeading 0x1F01 [seen]. A centred stick goes straight to scrollWorldAtTheEraPace 0x1F42 [seen], which carries the ship on along whatever heading it already holds.

Every live path, whether the player, the autopilot or a centred stick is in charge, ends in that same scroll routine.

### Controls

readPlayerControls 0x1ED1 [seen] returns the control word for whichever panel faces the picture. The vertical-blank service copies both panels into work RAM every frame, complemented so that a set bit means "pressed": IN1_MIRROR 0xA9AF [seen] for the main panel and IN2_MIRROR 0xA9B0 [seen] for the cocktail panel. SCREEN_UNFLIPPED 0xA987 [seen] reads zero only when the picture is turned round for the second player on a cocktail cabinet. Then the cocktail panel's word is used; otherwise the main panel's. The routine returns the whole byte, and each caller takes what it needs: the ship's frame keeps the stick nibble, the gun keeps bit 4, the fire button, and high-score initials entry shifts bits 0, 1, 4 and 5 into four press histories.

### Turning

turnShipTowardTargetHeading 0x1F01 [seen] turns the stick into a target heading. It indexes STICK_HEADING_TABLE 0x1F2E [seen] by the stick nibble, through fetchTableByte 0x0008 [seen]. Each single direction bit gives one of the four headings 0x00, 0x40, 0x80 and 0xC0. Each legal pair of bits gives the diagonal between its two directions (0x20, 0x60, 0xA0 or 0xE0). So the table names eight compass points, 32 steps apart. Combinations a real stick cannot make, with two opposite bits set, read heading 0.

If the live heading already equals the target, the routine changes nothing. Otherwise it subtracts the target from the live heading, modulo 256, and the size of that difference picks the action:

- **One step either side (0x01 or 0xFF):** the heading snaps exactly onto the target.
- **0x80 or more:** the target is nearer going upward, so the routine adds the turn step.
- **Anything else:** the routine subtracts the step.

Judging by which half of the circle the difference falls in is what makes the ship always turn the short way round.

The step size depends on the era. The ship turns three steps per pass of its handler (one per round-engine pass, not per frame) while the low nibble of ERA_INDEX 0xAD04 [seen] is below 3, and four steps a pass from era 3 on. Targets are 32 apart and three does not divide 32, so a turn made of threes can stop two steps short of the target. The snap arm exists for this case: the next step of three carries the heading to one past the target, and on the following pass the difference reads a single step, so the snap puts the heading on the target exactly. The snap arm has its own entry, snapHeadingOntoTheTurnTarget 0x1F3E [seen], which writes the target into PLAYER_HEADING 0xA802 [seen] and falls into the scroll. The turn routine jumps to it whenever the difference is one step either side. An eighth of a turn at three steps a pass therefore lands two short after ten passes, overshoots on the eleventh and is snapped onto the target on the twelfth; at four steps a pass it takes exactly eight passes. A full reversal is legal and simply takes longer: 44 passes at three steps a pass, 32 at four.

The heading only moves while the stick is held off centre. If the stick is released in mid-turn, the ship keeps whatever intermediate heading it had reached. A reversal is therefore not a flip: the heading sweeps through every step between the old direction and the new one. The ship is not locked to eight headings either. It stays on whatever intermediate heading it reached until the stick is pushed again, so it can hold any of the 256. This contradicts the eight locked facings in gameplay.md.

### Speed and the world scroll

scrollWorldAtTheEraPace 0x1F42 [seen] reads the heading; it never decides it. It picks one of three velocity tables using ERA_INDEX 0xAD04 [seen] alone: the opening era flies on OPENING_ERA_VELOCITY_TABLE 0x5E00 [seen], eras 1 and 2 on SECOND_FASTEST_VELOCITY_TABLE 0x2E3E [seen], and every era from 3 on VELOCITY_TABLE_08FA 0x08FA [seen].

The routine passes the chosen table to velocityForHeading 0x596E [seen]. That routine reads the table as 256 signed 16-bit samples of one curve and takes two of them: the sample at the heading, and the sample a quarter turn back, which is its perpendicular partner. The three tables are the same curve at three sizes. Their peaks are 256, 306 and 331 in 8.8 fixed point, so in the opening era the ship covers a whole pixel a pass and later eras are faster. There is no throttle: the ship's speed changes only when the era changes.

negateVelocityIntoWorldScrollThenDressSprite 0x1F55 [seen] negates both components as 16-bit words. It stores them as this pass's WORLD_SCROLL_Y 0xA808 [seen] and WORLD_SCROLL_X 0xA80A [seen], both in 8.8 fixed point on the native axes. The board is rotated, so "Y" and "X" are field names, not screen directions. World-fixed objects add these cells, or a fraction of them for parallax, to their own coordinates through driftWithWorldScroll 0x2B60 [seen] and its wrappers. Because the stored value is the ship's velocity reversed, the whole world slides against the ship's motion, and that is the camera.

The routine then ends in dressPlayerSpriteForHeading 0x20AF [seen]. A ship pinned in place can show its direction only through its shape, so this routine keeps the shape in step with the heading. It reads PLAYER_HEADING 0xA802 [seen], adds half a sector (4) to that copy without writing it back, and keeps the top five bits, which rounds the heading to the nearest of thirty-two sectors. The wrap closes the circle: a heading just below a full turn rounds up into sector 0. The sector indexes PLAYER_HEADING_SHAPE_TABLE 0x20CE [seen] for the shape, written to PLAYER_SPRITE_CODE 0xAA11 [seen]. A parallel table 32 bytes further on gives the attribute byte, written to PLAYER_SPRITE_ATTRIBUTE 0xAA40 [seen]. Thirty-two sectors therefore stand in for 256 headings, and they need fewer drawings still: the shape table uses only the sixteen codes 0xE8 to 0xF7, each for two sectors, and the attribute's top two bits mirror the shape so that it faces the right way. The attribute's colour field is zero in every entry.

Other systems also read the heading. The enemy spawners and the edge-ahead placement use PLAYER_HEADING to decide where newcomers enter, described with the enemies.

### Firing

The round engine calls fireAndSweepPlayerShots 0x23E3 [seen] immediately after the ship's frame. The enemy-free lead-in arm at the start of every life, flyEnemyFreeLeadInThenStepSequence 0x5694 [seen], also runs the ship's frame before the gun, with a sprite fixup and the era's scenery between them. Because the gun runs after the ship, every shot moves by the scroll the ship has just set. The player's shots are not sprites. Each one is a 16-byte record in the six-record PLAYER_SHOT_ARRAY 0xAA80 [seen]. A record holds a head byte (0 free, 0xFF live, anything else marked), the shot's two coordinates as 8.8 words at +3 and +5, and two velocity words at +10 and +12. Each live shot is drawn as a two-by-two block of character cells through queueTileStampForObject 0x5337 [seen].

The gun samples the fire button only while PLAYER_STATE 0xA800 [seen] reads 0xFF and ROUND_TRANSITION_HOLD 0xACC6 [seen] is clear. Otherwise it skips straight to the sweep, so shots already in flight keep moving while the ship dies or a round closes. When the button is sampled, bit 4 of the control word is shifted into FIRE_BUTTON_EDGE_SHIFT 0xA98E [seen]. The low two bits of that byte read 01 (released at the previous sample, pressed now) only on the pass of a fresh press, and that press loads SHOT_BURST_PENDING 0xAA81 [seen] with 3. One press therefore owes a burst of three shots. Holding the button does not arm another burst; it has to be let go and pressed again.

A shot leaves on a pass only when both of these hold:

- **A shot is owed.** During credited play SHOT_BURST_PENDING must be non-zero. With PLAY_ACTIVE 0xAD30 [seen] clear the burst count is not consulted at all, so the attract demo's ship fires as fast as the cooldown and the free records allow.
- **The cooldown has run out.** SHOT_SPAWN_COOLDOWN 0xAA82 [seen] must read zero.

The gun then takes the first free record, stepping by the 16 held in PLAYER_SHOT_SLOT_STRIDE_WORD 0x0D46 [seen]. If all six records are busy, nothing launches and neither the burst nor the cooldown is spent. SHOT_BURST_PENDING and SHOT_SPAWN_COOLDOWN are bytes 1 and 2 of shot record 0, which the shot records themselves do not use.

A launch does four things:

1. It asks for the shot sound through requestPlayerShotSound 0x567E [seen]. The command code comes from the program byte PLAYER_SHOT_SOUND 0x3270 [seen]. The request goes through enqueueSoundIfGameOrDemoSoundsOn 0x5617 [seen], so the shot can also be heard in the demo when demo sounds are on.
2. It sets the velocity. Each velocity word is minus four times one world-scroll component, which is four times the ship's own velocity.
3. It sets the starting point. The heading is rounded to the nearest of thirty-two directions and used to fetch a word from PLAYER_SHOT_SPAWN_POSITION_TABLE 0x2771 [seen] through fetchWideTableWord 0x018C [seen]. The word's two bytes become the whole parts of the two coordinates, with zero fractions. The table entries trace a small ring around the ship's pinned position: they are muzzle points, one per direction.
4. It makes the head byte live, takes one from the burst, and sets SHOT_SPAWN_COOLDOWN to 6.

The sweep runs on every call, whether or not a shot launched. It first winds the cooldown down by one, so a new shot can leave at most once every six calls. Then, for each record:

- A record whose head is neither 0 nor 0xFF is freed on the spot. This is how a shot that has hit something leaves the field.
- A live record has its velocity word and the current scroll component added to each coordinate as one 8.8 word, so fractions accumulate. The velocity word is four times the ship's velocity and the scroll is the same velocity reversed, so a shot on a steady course moves across the picture at three times the ship's speed, the way the ship is pointing.
- A record whose first whole part reaches 0xF0–0xFF, or whose second whole part reaches 0xF8–0xFF or 0x00–0x0F, has left the field. The sweep frees it by clearing its head and both whole parts.
- Every other record is queued to be painted.

At each life start, freeAllShotSlots 0x2755 [seen] empties the bank. It clears byte +0 and byte +4 of each of the six records. Neither the fill nor the stride is an immediate in the code. The routine reads both from the program image: SHOT_SLOT_FILL_BYTE 0x5C01 [seen] supplies the fill, which is 0 and also serves as the stride's high byte, and PLAYER_SHOT_SLOT_STRIDE 0x0861 [seen] supplies the stride's low byte, 16.

### Being hit

The ship has no shield, and every contact test treats it the same way. Each test first refuses to run unless PLAYER_STATE 0xA800 [seen] reads 0xFF. It then compares the ship's two fixed coordinates, PLAYER_ENTRY 0xAA10 [seen] and PLAYER_SPRITE_Y 0xAA41 [seen], with the other object's sprite-entry +0 and +0x31 bytes. Each axis is a wrapped byte difference plus a slack, and it must fall below a width. Because slack and width are separate, a test box can sit off-centre. A touch writes 0xF0 into PLAYER_STATE and into the other object's state byte, and that one write is the whole of the ship's death at this point. The explosion and the loss of the life follow from that byte in later frames.

The ship's contact tests run only on passes that land on an even FRAME_TICK. dispatchCollisionPassByEra 0x4E4F [seen] sends those passes of eras 0, 2 and 3 to runAllCollisionSweepsThisFrame 0x4E63 [seen]. In era 4, dispatchEra4CollisionByFrameParity 0x4F2A [seen] does the same on an even tick. Era 1 has its own split, splitCollisionWorkByFrameParity 0x4EBC [seen]. A pass on an odd tick, in every era, sweeps only the player's shots. The ship's own contacts are therefore judged only on even-tick passes, on positions that have already moved that pass.

On a ship-contact pass, the sweeps run in address order through the object array:

- **Enemy shots.** destroyPlayerAndObjectsTouchingIt 0x5185 [seen] tests the ship against the four enemy-shot records from ACTOR_RECORD_SLOT0 0xA810 [seen], using a box of five either side. A touch kills both the ship and the shot, and scores nothing. The sweep does not stop at the first touch, so one pass can mark several shots.
- **Enemy craft.** destroySlotsAndPlayerOnContact 0x5152 [seen] continues from where that sweep stopped, through the craft band: seven slots, or five while MOTHER_SHIP_ARMED 0xAD0D [seen] is raised, because the band's last two records then belong to the Mother-Ship. Its box is seven either side on one axis and eight either side on the other. Ramming a craft kills both, and each touch posts a score through postChainedHitScore 0x51DE [seen]. A collision still pays the points for the craft.
- **The Mother-Ship.** While it is armed, destroyPlayerAndMotherShipOnContactByEra 0x50B1 [seen] tests the ship against MOTHER_SHIP_STATE 0xA8A0 [seen]. In eras 0 and 4 it hands the test to destroyPlayerAndMotherShipOnContact 0x50EE [seen], whose first-axis box is eight either side. In the other eras it runs the same test itself with a box of six either side. On both paths the second-axis box is lopsided, accepting a difference from 25 below to 9 above. A touch kills both, zeroes MOTHER_SHIP_HITS_TO_ABSORB 0xA8A4 [seen] so the Mother-Ship is destroyed outright instead of absorbing the hit, and posts the chained score.
- **The era weapons.** In eras 0, 2, 3 and 4, destroyEraObjectsAndPlayerOnContact 0x5121 [seen] tests the ship against the three-record era-object bank from ERA_OBJECT_RECORD_SLOT0 0xA8C0 [seen]. A touch kills both and scores.
- **The era-1 bomber.** In era 1 the bank's slot 0 holds the bomber. destroyPlayerAndBomberOnContact 0x507E [seen] tests ramming it, with a box of six either side on one axis and an off-centre −0x18..+8 on the other. A touch kills both, zeroes BOMBER_HITS_TO_ABSORB 0xA8DC [seen], and scores. A second test, destroyPlayerAndObjectsTouchingIt 0x5185 [seen] on ERA_OBJECT_RECORD_SLOT2 0xA8E0 [seen], covers whatever the bomber launches, and that object can hit the ship.
- **The parachutist.** Every ship-contact pass ends with markObjectsTouchingPlayer 0x51B3 [seen] on the parachutist's record. This is the one contact that leaves the ship alive: it marks only the parachutist's state byte, described with the parachutist.

### The explosion

Once PLAYER_STATE 0xA800 [seen] holds anything other than 0 or 0xFF, dispatchPlayerFrameByState sends each pass to advancePlayerAnimationStrip 0x2010 [seen], aimed at the player's record and sprite entry. The routine uses the state byte as its own clock.

The kill left the byte at 0xF0, which is above the cap of 0xB4, so the first pass of the explosion is recognised as the opening one. On that pass the routine:

- clamps the byte to 0xB4, which means the opening work runs exactly once per explosion;
- writes 0xFF into the sprite entry's +1 byte, PLAYER_SPRITE_CODE 0xAA11 [seen]. Shape 255 in the sprite ROM is empty, so the ship's own sprite disappears and the fireball takes its place;
- asks for requestDestructionSoundBurst 0x56D2 [seen], which queues sound codes 0x15, 0x14 and 0x13 through enqueueSoundIfGameInProgress and then runs on into a further pair, 0x12 and 0x11, offered through enqueueSoundIfGameOrDemoSoundsOn, five requests in all (the Mother-Ship's death sweep asks for the same burst, straight after enqueueTransitionSoundStops [seen]), and also for requestSoundSixStopWhilePlaying 0x5679 [seen] once ERA_INDEX 0xAD04 [seen] has reached 2;
- checks two anti-tamper witnesses. TAMPER_GLYPH_STRIP 0xABFE [seen] must hold 0xA5 and TAMPER_COLOUR_STRIP 0xABFF [seen] must hold 0x05 or 0x10. A genuine image always passes. A patched copyright caption sends the frame into loc_1f2e 0x1F2E [code], where table bytes run as code.

Every pass, the opening one included, the byte is then counted down by one. On seven keyframe values, eight counts apart from 0xB3 down to 0x83, the routine paints a block of character tiles over the ship's pinned screen position at PLAYER_ANIM_VRAM_BASE 0xA5AF [seen]. Each block is PLAYER_ANIM_ROW_COUNT 0x337A [seen] rows (6) of PLAYER_ANIM_COL_COUNT 0x4902 [seen] tiles (5). Both counts are bytes of the program image, not immediates. Each tile's colour cell is filled with ERA_INDEX plus 0xC1, so the fireball's colour follows the era.

The first four keyframes grow the fireball, painting PLAYER_ANIM_STRIP_0 0x1F76 [seen], then PLAYER_ANIM_STRIP_1 0x1F94 [seen], then PLAYER_ANIM_STRIP_2 0x1FB2 [seen], and at its largest PLAYER_ANIM_STRIP_3 0x1FD0 [seen]. The next two shrink it again by repeating strip 3 and then strip 2, and the seventh paints PLAYER_ANIM_STRIP_4 0x1FEE [seen]. That last strip is all glyph 0xF1, the same glyph that surrounds the drawing in the other strips, so the final keyframe paints the explosion out. Between keyframes nothing is drawn, and after the last keyframe the count runs on silently down to zero.

The drawn explosion is visible for 48 round-engine passes, and the count reaches zero 180 passes after the hit. These are passes of the round engine, not frames.

The ship does not steer during the explosion. The scroll routine is not called, and apart from bulk RAM clears (the power-on wipe of work RAM, and the demo's round start, which zeroes 0xA800-0xA97F) only the scroll routine and the life-start reset write the scroll words. So WORLD_SCROLL_Y 0xA808 [seen] and WORLD_SCROLL_X 0xA80A [seen] keep the last velocity the live ship stored, and while the ship is exploding the world keeps drifting at the dead ship's last speed and direction [seen]. Both words keep that velocity until the next life's playfield reset zeroes them, but the drift itself stops when the countdown ends: loseLifeAndHandOver hides every sprite, and from then until the reset the scenery stands still even though the scroll still holds the dead ship's velocity [seen]. The gun is closed for the same reason. The rest of the round engine keeps running throughout the countdown.

### Losing a life and handing over

The explosion never takes the life itself. After running its subsystems, the round engine serviceRoundThenResolvePlayerState 0x1199 [seen] reads PLAYER_STATE 0xA800 [seen]:

- **0xFF:** the ship is alive, and the engine goes on to advanceRoundWhenFieldCleared 0x1271 [seen].
- **Any other non-zero value:** the explosion is still running, and the pass simply ends.
- **Zero:** the engine falls into loseLifeAndHandOver 0x11ED [seen].

loseLifeAndHandOver works through these steps:

1. It parks every sprite with hideAllSprites 0x15B6 [seen].
2. If ROUND_TRANSITION_HOLD 0xACC6 [seen] is raised, the round had already been won, so startNextRound 0x2DB8 [seen] banks it first and the next life opens in the next era.
3. It queues enqueueTransitionSoundStops 0x5634 [seen].
4. It decrements LIVES_REMAINING 0xAD00 [seen], the first byte of the live 16-byte per-player context block, and copies the whole block out to the active player's save block. ACTIVE_PLAYER 0xAD32 [seen] chooses between PLAYER_ONE_LIVES 0xAD10 [seen] and PLAYER_TWO_LIVES 0xAD20 [seen]. The saved copy therefore carries the new count.
5. If the count has reached zero, control passes to postGameOverBanner 0x1253 [seen].
6. Otherwise, if the other player's saved lives are non-zero, ACTIVE_PLAYER flips. In a one-player game PLAYER_TWO_LIVES was zeroed when the game started, so the turn never passes; in a two-player game the turn passes on every death until the other player has no lives left, and from then on the survivor plays every life.
7. Finally it arms the sequence machine: SEQUENCE_DELAY 0xA9EB [seen] gets 90, and SEQUENCE_SUBSTEP 0xA9AC [seen] is loaded from NEXT_LIFE_SUBSTEP_SEED 0x4B52 [seen], which holds 1. The sub-step is reseated at once, so the next life or the other player's turn re-runs the life-start arms from sub-step 1; the 90 is the count for the life-start hold that comes after those arms.

### Round start and each life

Each life, whether it is a new round or a restart after a death, opens with postLifeStartCaptionsAndResetPlayfield 0x0774 [seen]. This is the life-start arm of the sequence machine. It posts the captions: " READY " alone in the demo, or the "PLAYER n" caption chosen by ACTIVE_PLAYER 0xAD32 [seen] in a game, followed by " READY " again or, when ROUND_INTRO_PENDING 0xAD0E [seen] is set, the round-number caption. It then repaints the kill meter and calls resetPlayfieldForLifeStart 0x19F0 [seen].

For the ship, resetPlayfieldForLifeStart is a clean start:

- **The world:** both scroll words are zeroed, so the world begins unscrolled.
- **The gun:** SHOT_BURST_PENDING 0xAA81 [seen] and ROUND_TRANSITION_HOLD 0xACC6 [seen] are cleared.
- **The ship's record and sprite:** PLAYER_HEADING 0xA802 [seen] is set to 0x80, PLAYER_RECORD_SPARE_BYTE 0xA801 [seen] is cleared, and PLAYER_STATE 0xA800 [seen] is set to 0xFF. The ship is then pinned by writing 0x84 to PLAYER_ENTRY 0xAA10 [seen] and 0x78 to PLAYER_SPRITE_Y 0xAA41 [seen].
- **The picture and the bank:** dressPlayerSpriteForHeading 0x20AF [seen] draws the ship facing its new heading, and freeAllShotSlots 0x2755 [seen] empties the shot bank.

The same routine also resets the life's other state. It zeroes the life tick counters, LIFE_TICKS_LOW 0xAD05 [seen], LIFE_TICKS_MID 0xAD06 [seen] and LIFE_TICKS_HIGH 0xAD07 [seen]. It lowers MOTHER_SHIP_ARMED 0xAD0D [seen] and PARACHUTIST_RUNG 0xA8F7 [seen]. It seats this life's difficulty rung ERA_RUNG 0xACC0 [seen] from START_RUNG 0xAD0A [seen] and reloads ERA_RUNG_TIMER 0xA9D7 [seen] from ERA_RUNG_PERIOD 0xA9D6 [seen]. It retires every object slot and loads the era's spawn settings, described with the enemies.

The ship is alive from that frame on, and the arms that follow fly it before any enemy appears. flyLifeStartHoldThenEraseLifeStartCaptions 0x16AF [seen] runs the ship's frame and the era scenery, and on a round's first life it flashes the era-year caption. flyEnemyFreeLeadInThenStepSequence 0x5694 [seen] adds the gun, so the player can steer and shoot over empty sky until the lead-in delay expires and the round engine takes over.

Between eras the ship's own sprite also takes part in the band animation that stepRoundWonBandAnimation 0x1323 [seen] runs after a round is won, described with the end of a round. Its first steps run flashPlayerWhiteOnAlternateCalls 0x1367 [seen]. That routine rewrites the colour bits of PLAYER_SPRITE_ATTRIBUTE 0xAA40 [seen], keeping the two mirroring bits so the ship still faces the same way. It alternates the colour between 62 (white) and 0 on the bit-0 parity of PLAYER_FLASH_TICK 0xA9F1 [seen]. When the tick reads 8, it moves ROUND_WON_ANIMATION_STEP 0xA9F0 [seen] on to 1 and asks for requestPlayerWhiteFlashSound 0x5811 [seen]. That sound's code comes from ROUND_WON_FLASH_SOUND 0x07A9 [seen], and the request goes through enqueueSoundIfGameInProgress 0x560C [seen], so it sounds only in a real game. A later step runs cyclePlayerSpriteColourThenAdvanceStepAtZero 0x1393 [seen]. It drives the same colour field from bit 2 of SPRITE_COLOUR_CYCLE_COUNTDOWN 0xA9F3 [seen], choosing 0x37 or 0x3F, and moves the step on to 3 once the count is found at zero.

### The demo autopilot

The attract demo is the real round engine running with PLAY_ACTIVE 0xAD30 [seen] clear, so a live ship needs a pilot. When the demo starts, verifyImageSignatureThenStartAttractDemoOrDerail 0x2730 [seen] calls seedDemoAutopilotScript 0x210E [seen], which picks one of three byte-coded scripts in ROM. The choice is made by PLAYER_ONE_ERA_INDEX 0xAD14 [seen], which the attract arm reuses as a selector. A selector of 0 or 3 picks DEMO_AUTOPILOT_SCRIPT_FIRST 0x218C [seen], 1 picks DEMO_AUTOPILOT_SCRIPT_SECOND 0x2251 [seen], and any other value picks DEMO_AUTOPILOT_SCRIPT_THIRD 0x22FA [seen].

The demo writes its own era into that cell only after this choice, so each demo's script follows from the era the previous demo left behind. The demo path of the new-game arm advances ATTRACT_STAGE_COUNTER 0xA9D0 [seen] through 1, 2, 3, 1 and writes the new value into PLAYER_ONE_ERA_INDEX, which becomes the era the demo flies. In the steady cycle the script chosen from the previous value therefore pairs the first script with era 1, the second with era 2 and the third with era 3. After power-on the selector is 0, which picks the first script, the same pairing. After a real game the selector is the stale era left in player one's saved block, so the first demo after a game can fly a script with a different era than the steady cycle pairs it with. No script has a terminator: the cursor simply steps on into whatever bytes follow. The first script runs into the second's opening byte at 0x2251, the second into the third's at 0x22FA, and the third into a block at 0x23D4 that nothing seeds, which also opens with four bytes of 60. Each demo is over before its cursor gets far past its own script: the cursor reaches no further than 0x2251, 0x22FA and 0x23D8 respectively [seen]. The routine loads DEMO_SCRIPT_DWELL 0xADF2 [seen] with the script's first byte plus one, and points the cursor DEMO_SCRIPT_POINTER_LO 0xADF3 [seen] / DEMO_SCRIPT_POINTER_HI 0xADF4 [seen] at that byte.

It then checks two tamper readbacks. TAMPER_GLYPH_READBACK 0xADFB [seen] must be 0xFD and TAMPER_COLOUR_READBACK 0xADFC [seen] must be 0x10 or 0x05. On any other value the routine jumps into the second script's data as if it were code, loc_2251 0x2251 [code]. An altered tile image therefore never gets a working demo.

On each pass, flyDemoShipByScript 0x214B [seen] reads the script byte. The low six bits are a pass count and the top two bits are a turn command. While the count is 2 or more, the routine decrements the whole byte. The borrow cannot reach the top bits, so the command survives the countdown. When the count is spent (0 or 1), the routine steps the cursor, reloads from the next script byte plus one, and looks again in the same pass. An entry whose count bits are zero reloads as 1, is spent at once, and is skipped.

The surviving command steers the ship. A command of 00 holds the heading, 01 turns PLAYER_HEADING 0xA802 [seen] down by 3, and 10 or 11 turns it up by 3.

Unlike the player's turn, the autopilot moves the heading directly rather than toward a stick target, at the slower rate in every era. Like every other live path, it ends in scrollWorldAtTheEraPace 0x1F42 [seen], so the demo ship flies at the era's real pace, and like the player's ship it can hold any of the 256 headings. All three scripts open with four bytes of 60 passes with no turn, so the demo flies straight for at least its first 240 passes. The gun ignores the burst count while PLAY_ACTIVE is clear, so the demo ship fires whenever the cooldown and a free record allow.

## §6 Killing, and being killed

### The shared language of a hit

Every object in a round, from the player's ship to the smallest enemy bullet, carries a state byte at the head of its sixteen-byte record, and all the killing in Time Pilot is spoken through that byte. 0xFF means live, 0x00 means free, and 0xF0 means "just hit". No collision test ever removes anything from the screen itself: a test that finds two things touching writes 0xF0 into one or both state bytes, perhaps posts a score, and moves on. Each object's own handler finds the mark on its next turn and turns it into whatever dying looks like for that kind of object. Keeping the two halves apart is what lets one sweep mark several objects in a single pass, and it is why nearly every test below begins by refusing anything that does not read exactly 0xFF.

Positions are compared the same way everywhere. Each object has a sprite entry whose +0x00 byte is one native coordinate and whose +0x31 byte is the other; the player's are PLAYER_ENTRY 0xAA10 [seen] and PLAYER_SPRITE_Y 0xAA41 [seen], and the player's ship never leaves the centre of the screen. A test takes the wrapped byte difference of two coordinates, adds a reach and asks whether the result is below a span, which accepts a difference from minus the reach up to span minus reach minus one. A box can therefore be lopsided, and several are. Below, "in X" is the +0x00 coordinate and "in Y" the +0x31 one (the native axes), the axis on which the two-tile Mother-Ship and bomber seat their second tile 16 further on. The player's own shots are the exception to the sprite-entry rule: each of the six shot records at PLAYER_SHOT_ARRAY 0xAA80 [seen] keeps its whole-part coordinates inside the record itself, at +6 and +4.

### Which sweep runs on which frame

Testing everything against everything on every pass is too much for the CPU, so the work is split by the low bit of FRAME_TICK 0xA980 [seen], the frame counter: a pass that runs on an odd tick does one half, and a pass on an even tick the other. The round engine calls dispatchCollisionPassByEra (0x4E4F) [seen] once per pass, after every mover in its service list, so every contact is judged on positions already moved that pass and every marked object dies on its handler's next turn. It reads ERA_INDEX 0xAD04 [seen] first: the 1940 era (era 1) and the 2001 era (era 4) each go to their own splitter, and the other three eras share one rule. On an odd frame dispatchShotSweepByMotherShipArmed (0x4F35) [seen] tests the player's shots against the enemy craft. On an even frame runAllCollisionSweepsThisFrame (0x4E63) [seen] runs everything else.

The odd-frame craft sweep depends on MOTHER_SHIP_ARMED 0xAD0D [seen]. The craft band is seven records from CRAFT_RECORD_SLOT0 0xA850 [seen], paired with sprite entries from CRAFT_ENTRY_SLOT0 0xAA1A [seen]. Once the Mother-Ship is armed, its two-tile body takes over the band's last two records, MOTHER_SHIP_STATE 0xA8A0 [seen] and CRAFT_RECORD_SLOT6 0xA8B0 [seen]. With the flag clear, the six shots are swept against all seven craft. With it set, sweepShotsOverFiveCraftThenMotherShip (0x4FBF) [seen] sweeps them against only the first five craft, then falls into markMotherShipAndShotHitByShots (0x4FE0) [seen], which tests the same shots against the Mother-Ship's own box.

The even-frame pass is a chain of sweeps, each picking up where the last one stopped. Its first step, stagePlayerShotSweepAgainstTargetsAndRun (0x4F5D) [seen], tests the player's shots against the three-slot era-object bank: records from ERA_OBJECT_RECORD_SLOT0 0xA8C0 [seen], entries from ERA_OBJECT_ENTRY_SLOT0 0xAA28 [seen]. That bank holds the bombs and missiles described below. Every remaining step pits the player's ship against something. One cursor pair, a record cursor at a sixteen-byte stride and a sprite-entry cursor at a two-byte stride, is handed from sweep to sweep, so together they walk the object array in address order. They start at the four enemy-shot slots, ACTOR_RECORD_SLOT0 0xA810 [seen] with its sprite entry ACTOR_ENTRY_SLOT0 0xAA12 [seen]. Four strides on they reach the craft band at 0xA850, seven more bring them to the era-object bank at 0xA8C0, and three more to the parachutist at PARACHUTIST_RECORD 0xA8F0 [seen].

While the Mother-Ship is armed, the craft step covers only five slots. destroyPlayerAndMotherShipOnContactByEra (0x50B1) [seen] then gives the Mother-Ship its own ramming test, and the cursor is reseated at the era-object bank because the craft step stopped short of it.

Era 1 differs because its era-object bank holds the bomber instead of three era weapons. splitCollisionWorkByFrameParity (0x4EBC) [seen] keeps the odd-frame craft sweep. Its even frame begins with markEra1BomberAndShotHitByShots (0x4F7E) [seen], the player's shots against the bomber, and then runs the usual player-against-shots and player-against-craft steps (plus the Mother-Ship ramming test while it is armed). After those it tests the player ramming the bomber, with destroyPlayerAndBomberOnContact (0x507E) [seen], and the player against the bomber's launched object at ERA_OBJECT_RECORD_SLOT2 0xA8E0 [seen], before the parachutist pickup. No sweep in era 1 tests the player's shots against 0xA8E0, so whatever the bomber launches can kill the player but cannot be shot down.

Era 2001 makes its odd frame broader instead. dispatchEra4CollisionByFrameParity (0x4F2A) [seen] runs the full even-frame pass unchanged. On odd frames it sweeps the shots against one run that starts at the enemy-shot slots and continues into the craft band: the four shots plus seven craft while the Mother-Ship is clear, or plus five craft and then the Mother-Ship's own test while it is armed. So the enemy shots can be shot down only in 2001. In the other eras no sweep ever aims the player's shots at those four slots.

### What each sweep tests and what it pays

Every sweep that lets the player's shots hit something, except the Mother-Ship's and the bomber's own tests, is built on destroyTargetsHitByShots (0x5211) [seen]. It takes the six shot records as its outer loop and a run of targets as its inner loop. A shot that is not 0xFF is skipped. A live shot is tested against every target in the run. The target must itself be live, and neither of its sprite coordinates may sit in the narrow band around zero that an unplaced or retired slot leaves behind; that rule keeps a parked entry from ever being hit. On a touch, the shot and the target both take 0xF0 and the hit is paid through postChainedHitScore (0x51DE) [seen]. The inner loop tests targets, not the shot, so a shot already spent in this pass keeps sweeping, and one shot can take several targets and be paid for each one. Between shots the target cursors are reloaded from SCRATCH_PTR_A 0xA991 [seen] and SCRATCH_PTR_B 0xA993 [seen], which every caller stages first, so each shot faces the whole run afresh. The box is 7 either side on both axes for craft, era weapons and, in 2001, enemy shots. The Mother-Ship's box in X is 8 either side in eras 0 and 4 and 6 in the others, and it is lopsided in Y, reaching 23 toward its second tile and 7 the other way, so one box covers both tiles of its body. The bomber's box is 6 either side in X and lopsided in Y in the same way, 23 toward its second tile and 7 the other way.

The ramming tests have the same form, with the player's ship in the place of the shot. destroyPlayerAndObjectsTouchingIt (0x5185) [seen] runs the player against the four enemy-shot slots in a box 5 either side; a touch marks both the player and the shot, and nothing is paid. destroySlotsAndPlayerOnContact (0x5152) [seen] runs the player against the craft, 7 either side in X and 8 in Y, and a touch marks both and is paid at the chained rate. The player's state is tested only once, before that sweep starts, so a ship that hits two craft in one pass takes both with it and is paid twice. Because the craft is left at 0xF0 exactly as a shot would leave it, its death also counts toward the kill quota: ramming a craft is paid and counted as if it had been shot, at the price of the ship. destroyEraObjectsAndPlayerOnContact (0x5121) [seen] runs the player against the era weapons, 6 either side, and it too marks both and pays the chain, so flying into a bomb or a missile scores as if it had been shot, although it still costs the ship.

The Mother-Ship's ramming test, destroyPlayerAndMotherShipOnContactByEra [seen], hands over in eras 0 and 4 to destroyPlayerAndMotherShipOnContact (0x50EE) [seen], which applies a box 17 wide on native X; the other eras use a 13-wide one inline. Both are 35 wide on native Y. Either way a touch marks both, pays the chain, and also zeroes MOTHER_SHIP_HITS_TO_ABSORB 0xA8A4 [seen], so ramming destroys the Mother-Ship outright instead of spending one of its hits. Ramming the bomber in era 1 works the same way through BOMBER_HITS_TO_ABSORB 0xA8DC [seen]: both die and the chain pays. The one contact that leaves the player alive is the parachutist's. markObjectsTouchingPlayer (0x51B3) [seen] writes 0xF0 into the parachutist's state and nothing else, and the parachutist's own handler then pays the rescue ladder.

Every player-side sweep refuses unless PLAYER_STATE 0xA800 [seen] reads 0xFF. A refusing sweep hands its cursors back unmoved, which does no harm because every later sweep in the chain refuses too.

### The chain

postChainedHitScore [seen] does not add to the score itself. It posts command 4 to the command ring, and the ring's scoring handler, awardScoreToPlayer (0x0C90) [seen], later adds entry n of SCORE_AWARD_TABLE 0x0D27 [seen] to the active player's score. Entries 1 to 8 of that table are 100 to 800 points. The ladder lives in two cells. If CHAIN_WINDOW 0xA99D [seen] is empty when a hit arrives, the hit starts over at the first rung and pays 100. If the window is still open, CHAIN_STEP 0xA99E [seen] is stepped and the hit pays the rung the step selects, folded into 1 to 8, so a run of closely spaced hits pays 100, 200 … 800 and then wraps back to 100 instead of capping. Either way the window is reloaded to 30. Because the collision pass runs before expireHitChain in the service block, a hit landing on the first pass after the window has emptied, before any call has cleared CHAIN_STEP, pays 100 but leaves the old step in place, and the next hit climbs on from the old rung.

The other half of the chain is expireHitChain (0x5205) [seen], an entry in the round engine's service block. It takes one off the window on each call, and once the window reads zero it clears the step on every call. The window therefore counts dispatches of the service block, not frames, and expireHitChain is the only thing that ever ends a chain. Because the ring drops a command whose slot is still occupied, a hit that lands while the ring is full is not paid.

### How craft die, and the kill count

An enemy craft dies in its own per-era handler, serviceEra0EnemyCraftSlot through serviceEra4EnemyCraftSlot (0x2927, 0x29D5 and the three between) [seen]. Each one reads the state byte: 0x00 free, 0xFE held, 0xFF flying, and any other value a death in progress, which it passes to stepDyingObjectState (0x2B93) [seen]. That routine turns the 0xF0 mark into a countdown starting at 0x3B and, on the same step, calls countTheKillAndGrantTheSharedToken (0x2BBA) [seen]. This is where a kill is counted. It requests the pair of impact sounds and takes one off KILLS_REMAINING 0xAD02 [seen], stopping at zero rather than wrapping. If the dying craft belongs to a wave whose claim window, WAVE_CLAIM_TIMER 0xA812 [seen], is still open, the kill also ticks WAVE_KILL_COUNTDOWN 0xA811 [seen]. The kill that empties that countdown writes its slot ordinal into CLAIM_TOKEN 0xA821 [seen], and the craft holding the token later posts the 2,000-point formation award (entry 12) as its wreck winds down, through driveObjectAppearanceByPhaseBand [seen].

From 0x3B down, stepDyingObjectState takes one off the count each step and hands the wreck to moveObjectByStateByteThenRunAppearance [seen]. While the count is 32 or more that routine takes a second one off and flies the wreck on at the slowest speed, so the count falls by two a step; below 32 the wreck only drifts with the world and the count falls by one. The same count drives its appearance through driveObjectAppearanceByPhaseBand. From 42 up the wreck keeps its shape and cycles its tint, from 41 down to 10 it steps through OBJECT_PHASE_SHAPE_TABLE 0x2C94 [seen], and once the count falls below 10 every wreck except the formation-token holder is freed at once by retireSlotAndSubPixel [seen]. A count of exactly 0x3C also counts a kill on the way down; the only way a craft reaches that value is the Mother-Ship's sweep below.

The count is taken only on this craft path. Kills of the bomber, the bombs and missiles in the era-object bank, and enemy shots are never counted, and neither is the Mother-Ship. A craft destroyed by ramming is counted like one destroyed by a shot, because the mark is the same.

KILLS_REMAINING is seeded at each round start from KILL_QUOTA 0xA9CD [seen], which boots from DEFAULT_KILL_QUOTA 0x0874 [seen], a ROM byte reading 56. drawKillMeter (0x0809) [seen] draws it as the bar along the bottom of the screen. The routine picks the era's row of KILL_METER_GLYPH_ROW_TABLE 0x087C [seen] and lays one bar cell for every four kills still owed, starting at KILL_METER_BAR_START_CELL 0xA79F [seen]. It caps the bar with an end glyph chosen by the count's low three bits, then blanks the next cell. As kills come in, the bar shortens one cell every four kills and the end glyph slides back with it. This meter is the "time bar" of the public record: it measures kills owed, not time.

### Enemy weapons and special craft, era by era

Enemy craft attack in two ways. The first is a bullet. Every era's craft handler calls fireCraftShotWhenAimedNearPlayer (0x3ED6) [seen], and it fires into a free enemy-shot slot only when a run of conditions all hold. It must be this craft's turn, a pass whose FRAME_TICK low three bits plus five equal its +0x0F stamp, and BANK_LAUNCH_COOLDOWN 0xA817 [seen] must have run out. A slot must be free within the first BANK_LAUNCH_SLOT_COUNT 0xA844 [seen] shot slots. The craft must not already be close to the player's fixed screen position on both axes, as judged by BANK_LAUNCH_NEAR_HALF_WIDTH 0xA827 [seen]. Its heading must lie within BANK_LAUNCH_HEADING_HALF_WIDTH 0xA837 [seen] of PLAYER_HEADING 0xA802 [seen], so it is flying the player's way. Finally, the heading from the craft toward ENEMY_STANDOFF_AIM_MAIN 0xAC7F [seen] must lie within 16 steps of the craft's own, so it is already pointing at a stand-off point offset from the ship's centre along the line of the ship's heading, not at the ship itself.

The bullet starts at the craft and flies straight along that aim. The shot slots are serviced by stepFourActorSlots [seen] and dispatchObjectSlotByHeadByte [seen]. A flying shot moves along its stored velocity and is freed at a retire line. A shot carrying any other state is simply retired where it stands, except in 2001, where runSlotCountdownDriftAndAnimateElseRetire (0x3E8E) [seen] plays it out as a short animated countdown, because only in 2001 can a shot be shot down.

The second way is an era weapon, launched into the era-object bank. In eras 0, 2, 3 and 4 the craft handler also calls launchAttackerIntoFreeSlot (0x4243) [seen]. On the craft's turn, once ATTACKER_SPAWN_COOLDOWN 0xA8F4 [seen] has run out, it finds a free bank slot within ATTACKER_SPAWN_SLOT_COUNT 0xA8C6 [seen], and does not launch on a pass that finds the craft within ATTACKER_SPAWN_WINDOW_HALF 0xA8D6 [seen] of the player on both axes. commissionStagedAttackerByEra (0x42B7) [seen] then fits the new weapon out for the era:

In 1910 (era 0), setTheLaunchFacingInsideOneAimWindow (0x429C) [seen] launches only when the craft sits within ATTACKER_SPAWN_AIM_WINDOW_HALF 0xA8E6 [seen] of the player in X, and it sets the sign of the bomb's sideways drift from which side of the player the craft lies in Y, so the bomb always drifts toward the player. The bomb is seeded with a velocity pointing against its pull, so serviceEra0BallisticObjectBank (0x3FEA) [seen] and flyAlongBallisticArc (0x4017) [seen] throw it up, stall it and bring it down on a parabola, with that fixed sideways drift of one and a half pixels a step. The motion fits the hand grenades gameplay.md describes for 1910.

In 1970 (era 2) the weapon is aimed at the stand-off point, skewed a quarter turn to one side or the other, and begins homing at once. The sweepEra2PlusObjectBank (0x40D6) [seen] body hands it to chaseOneAimPointAndRetireAtTheLine (0x4117) [seen], which re-aims only on passes whose FRAME_TICK low nibble equals its +0x0F stamp, turns one unit a step and flies at double speed. The motion fits gameplay.md's homing missiles. In 1982 (era 3) the weapon leaves a fixed step off the craft's facing with a fixed velocity, flies straight for a countdown, and only then starts to home the same way.

In 2001 (era 4) the weapon is aimed straight at the stand-off point and runs stepSlotApproachThenBreakawayRetire (0x4194) [seen]. It flies at double speed throughout. During its approach, a countdown seeded from ATTACKER_SPAWN_AIM_WINDOW_HALF that ends early once it comes within 16 of its target on both axes, it re-aims, on passes that find FRAME_TICK's low four bits zero, at one of two stand-off points, ENEMY_STANDOFF_AIM_SET 0xAC75 [seen] or ENEMY_STANDOFF_AIM_CLEAR 0xAC79 [seen], turns toward it, and is not freed by a retire line. Once the approach is over it stops turning and flies straight on along its last heading until a retire line frees it.

Any of these weapons that is shot or rammed ends as an animated countdown that drifts with the world and then frees its slot. runOneShotAnimatedObjectSlot (0x406C) [seen] handles this in era 0 and stepDriftingCountdownObjectByEraFrames (0x413C) [seen] from era 2 on.

Era 1 instead has the middle-size bomber, a two-tile craft at 0xA8C0 driven by serviceEra1BomberObject (0x3B5F) [seen]. While the Mother-Ship is not armed, armBomberSlotWhenTimerFires (0x3C25) [seen] launches it from the screen edge the player is heading toward, seating the coordinate pair that HEADING_EDGE_POSITION_TABLE 0x3C84 [seen] holds for that heading (or, when the heading is close to 0 or 128, the pair for a heading a sixteenth of a turn to one side or the other) (the Mother-Ship's launch reads the same table), flying straight in one of two opposite directions, with BOMBER_HITS_TO_ABSORB [seen] seeded to three. A hit is absorbed by advanceHitSoakingObjectThenAnimateDeath (0x3B94) [seen]: one hit is spent, the bomber goes back to live, and the impact sounds play. A hit that finds the count at zero, which is the fourth hit or any ramming, starts its death. The wreck recolours, cycles through DEATH_ANIMATION_SHAPE_TABLE 0x3C09 [seen], and partway down posts entry 11, 1,500 points. That is on top of the chained payment every hit on it already earned. While live, the bomber can fire an aimed shot through fireBomberShotWhenClearOfPlayer (0x3D25) [seen], which seats shape 0x4D and attribute 0x62, the pair the craft's shots carry. That shot is aimed a little to one side of the stand-off point, alternating sides from one launch to the next. It is seated at 0xA8E0 and flown straight by serviceFixedSlotInEra1 (0x3DDA) [seen], or, when the era allows only one era-object slot or 0xA8E0 is busy, it is seated in the last enemy-shot slot and flown there as an ordinary enemy shot. The bomber's kill is never counted toward the quota.

### The Mother-Ship and its hit counter

armMotherShipOrStep (0x43B7) [seen] runs once per service-block dispatch. On one frame in eight, once KILLS_REMAINING is zero and both of the Mother-Ship's records are free, it arms the Mother-Ship. Arming raises MOTHER_SHIP_ARMED, seeds MOTHER_SHIP_HITS_TO_ABSORB with 7, and parks the record in a delay through retireEntryPairIntoCooldown (0x46DB) [seen]. The flag stays up for the rest of the round or life. While it is up, the craft entries for array slots 10 and 11, the Mother-Ship's pair, stand aside (seatMotherShipSlotThenDispatchByEraUnlessArmed [seen] and seatCraftSlot6ThenDispatchByEraUnlessArmed [seen]), the collision sweeps change shape as described above, and no bomber launches. From then on loc_43f0 (0x43F0) [seen] is the Mother-Ship's whole life, with its record's head byte as the phase.

**Idle and launch.** At 0x00 the Mother-Ship counts its delay down and then launches, provided ROUND_TRANSITION_HOLD 0xACC6 [seen] is clear. It appears at the edge HEADING_EDGE_POSITION_TABLE 0x3C84 [seen] gives for the player's heading nudged a sixteenth of a turn to one side or the other, and flies horizontally, heading 0 or 128, announced by the era sound.

**Live.** At 0xFF it moves by its own velocity plus the world scroll, which lets the player overtake it. While BANK_LAUNCH_COOLDOWN is clear and one of its tiles is on the picture but outside the band around the player, it fires an aimed shot into whichever of the last two enemy-shot slots, ACTOR_RECORD_SLOT2 0xA830 [seen] and the one after it, is free. Successive shots are swung to alternating sides of the aim by MOTHER_SHIP_AIM_SIDE_TOGGLE 0xA8B4 [seen]. If it reaches the edge of the field, dressSpriteForHeadingOrRetireAtEdge (0x4447) [seen] returns it to idle with a fresh delay and leaves the hit counter untouched.

**Hit.** A shot sweep marks the Mother-Ship 0xF0 and pays the chain for that hit. On the next step, if MOTHER_SHIP_HITS_TO_ABSORB is non-zero, the Mother-Ship spends one hit, returns to 0xFF, plays the impact sounds and flies on the same frame. A hit that finds the counter at zero starts its death. A fresh Mother-Ship therefore absorbs seven hits and dies on the eighth. The sweeps test its state only once per pass, so several shots that land together are each paid even though they share one mark. At launch the counter has a floor: any value below 6 is set to 5. A Mother-Ship that went idle after two or more hits therefore comes back needing six more, while one that went idle after a single hit keeps a counter of 6 and needs seven more.

**Death and the round's end.** On its first dying step the Mother-Ship counts down to 0xEF. On the next it sweeps the whole field: every one of the fifteen records from 0xA810 to 0xA8F0 that reads 0xFF receives a dying code, staggered 10 apart so the objects go down one after another, and posts entry 2, 200 points. Records held at 0xFE are freed. Every swept craft receives a code of 0x3C or more, so it passes through the kill-count step on its way down. A bomber caught live in the sweep finds BOMBER_HITS_TO_ABSORB already cleared by the sweep and plays its full death, 1,500 points included. A parachutist caught in flight is taken as a rescue and pays its ladder rung. The sweep also sets ROUND_TRANSITION_HOLD to 0xFE and restarts the head at 0xE4. From there the wreck drifts with the world through MOTHER_SHIP_WRECK_SHAPE_TABLE 0x461B [seen]. At 0xB4 it switches to one fixed shape pair, 0xFE/0xFD with attribute 0x6C, which shows a '3000' label, and posts entry 13, 3,000 points; requestMotherShipAwardSound 0x580B [seen] asks for the award sound only if the player is alive, but the award is posted either way. At 0x5A its sprites are hidden. At zero it returns to idle and raises ROUND_TRANSITION_HOLD to 0xFF. That same step checks an anti-tamper witness pair, TAMPER_GLYPH_COPY 0xAB43 [seen], which must hold glyph 0x7C, and the colour byte after it, which must be 0x10 or 0x05: a genuine image returns, and a patched one derails into derailIntoMotherShipWreckCountdown [code]. Once the quota is spent, the hold is raised and all fifteen records read free, advanceRoundWhenFieldCleared (0x1271) [seen] starts the next round. A Mother-Ship destroyed by ramming enters the same death; nothing in it asks whether the player survived except the award sound.

A Mother-Ship destroyed on its first launch therefore pays a chained payment for every shot that marks it, at least eight, then 200 for each live object swept (plus the bomber's 1,500 and the parachutist's rung when either is caught), and 3,000 at the award label. One that went idle and relaunched after two or more hits needs six more hits after the relaunch, on top of the ones it took before. Ramming it pays one chained contact in place of the hits it still owed, then the same sweep and the same 3,000.

### Parachutists

runParachutistSlot [seen] runs the single parachutist slot in every era except era 4, where it returns at once. A free slot is handed to spawnAtEdgeAhead [seen]. That routine refuses while MOTHER_SHIP_ARMED is set and otherwise acts on odd ticks only, counting the slot's +0x0E delay down. When the delay runs out it places the parachutist at an edge position that the player's heading selects from a 16-sector table (EDGE_SPAWN_COORD_TABLE, 0x488D), and marks it live. While live it drifts along its stored velocity, animating off FRAME_TICK, and is retired into a cooldown if it reaches a retire line.

Collection is the parachutist's touch in markObjectsTouchingPlayer. Its state becomes 0xF0, and on its next turn showParachutistAward [seen] re-stamps it to 0x3B, requests the award sound, and shows the award shape chosen by PARACHUTIST_RUNG (0xA8F7) [seen], which is the record's +7 byte. The count then runs down one per pass. At 0x10, postNextParachutistBonus [seen] reads the rung, steps it, and posts command 4 with PARACHUTIST_BONUS_ARG_TABLE (0x484F) entry `rung` for the first four rungs: indices 10, 12, 13 and 14, which are **1,000, 2,000, 3,000 and 4,000**. For every rung after that it posts index 15, **5,000**. The rung keeps climbing past the table, so the award stays at 5,000. At zero the slot is retired into its cooldown. The rung is zeroed by resetPlayfieldForLifeStart [seen], the reset that also puts a fresh ship in place, and nothing else in this section resets it. No shot sweep includes the parachutist slot, so a parachutist cannot be shot. The one way to lose one is to let it reach a retire line. The Mother-Ship's sweep pays for it instead of losing it.

### Formations and the 2,000 bonus

In eras 0-3, driveEnemyWaveForLifePhase [seen] builds a formation inline across the craft band. Its row comes from WAVE_DESCRIPTOR_TABLE (0x397B), one of two rows per era picked by a random bit. Each member's spawn position is a pair from WAVE_EDGE_POSITION_TABLE (0x38E9), whose pairs trace the screen edge: the index is the member's descriptor byte plus an offset WAVE_HEADING_BIAS_TABLE (0x38D9) gives for PLAYER_HEADING rounded to sixteen directions, so where on the edge the formation appears shifts with the player's heading. The builder fills whichever of the first CRAFT_SPAWN_SLOT_COUNT (0xACC1) [seen] craft slots are free, or of the first five once the quota is spent. For each member it copies a delay from the descriptor into the record's +0x0E byte. Every one of the first seven entries in each ROM row has a non-zero delay, so every member starts **held** at 0xFE. The builder tallies the members into WAVE_KILL_COUNTDOWN (0xA811) [seen] and loads WAVE_CLAIM_TIMER (0xA812) [seen] with 228, which the vertical-blank service counts down once a frame. If five or more members were placed, the tally stands as the countdown and the formation sound is requested (requestEnemyWaveSound [seen]). Otherwise the countdown is overwritten with CRAFT_SPAWN_SLOT_COUNT, and the sound plays only if the tally reaches that count. releaseHeldObject lets each member go when its delay runs out, and on release it reloads +0x0E with 128. That top bit is what marks the craft as a formation member.

countTheKillAndGrantTheSharedToken does the claim. It acts only when the dying craft's +0x0E top bit is set and WAVE_CLAIM_TIMER is still non-zero, and then it decrements WAVE_KILL_COUNTDOWN. The kill that brings the countdown to zero writes that craft's slot ordinal (its record's +0x0F), with the top bit set, into CLAIM_TOKEN (0xA821) [seen]. The payment comes from the wreck's own animation. When the death count falls below 10, driveObjectAppearanceByPhaseBand retires every wreck except the one CLAIM_TOKEN names. That one holds a fixed shape and tint, which is the bonus display. On most passes its count is bumped back up as fast as it steps down, so it lingers, and the count creeps down only on a pass that falls on a frame whose FRAME_TICK low three bits are zero. When the count sits at 1 it posts command 4 with index 12, **2,000 points**, and clears the token, and the wreck retires on its next step.

The practical conditions for the bonus, as the code stands, are these. Enough kills of formation-marked craft (+0x0E top bit set) must land before WAVE_CLAIM_TIMER runs out, 228 frames after the formation spawned, to bring WAVE_KILL_COUNTDOWN to zero. Kills after the timer expires do not count down. A rammed member is marked 0xF0 exactly as a shot one is, so its death counts; a member that retires off the edge never reaches the count, and then the claim fails unless some other marked kill makes up for it. A formation that placed fewer than five members, and fewer than CRAFT_SPAWN_SLOT_COUNT, is given a countdown larger than its own membership, so it needs marked kills beyond its own members; any that come have to be survivors of an earlier formation that still carry the 0x80 mark.

Era 4 gets its waves from spawnEnemyWaveIntoFreeSlots [seen] instead. That routine loads WAVE_CLAIM_TIMER but writes 0 into each craft's +0x0E and marks it live immediately, with no hold. So **an era-4 craft spawns without the formation mark**, and its kill cannot pass the claim guard unless a later write sets bit 7 of its +0x0E. §9 lists the writes in the image that could do that.

## §7 Score, and the ladder that ends

Time Pilot keeps its long-running tallies in two places. A player's **score** sits in its own fixed triple of bytes that the two-player machinery never copies. Everything else a player carries from turn to turn sits in a sixteen-byte context block that is swapped in and out on every turn: the **lives**, **round** and **era**, the **opening difficulty rung**, and the **life tick counter** (LIFE_TICKS_LOW 0xAD05 to LIFE_TICKS_HIGH 0xAD07 [seen]). That counter is a three-place base-sixty count of round-engine passes during the current life, and it drives the difficulty ladder, which climbs while the player stays alive and drops back when they die. This section follows those tallies from the award for a single hit to the moment the machine gives up on both players and returns to attract.

Everything a player earns in Time Pilot reaches the score the same way: nothing adds to a score at the moment of the hit. A hit *posts a request*, a (command, argument) pair dropped into the command ring, and the foreground drain later runs command 4, awardScoreToPlayer 0x0C90 [seen], with the argument as an award number. That indirection explains several things below. Two awards in one frame are paid one after the other on the drain's own time. A request posted while the ring slot under the write cursor is still full is simply lost. And because awardScoreToPlayer begins by checking PLAY_ACTIVE 0xAD30 [seen] and returns when it is clear, the attract demo can post as many awards as it likes and no score moves.

### The score itself

Each player's score is six decimal digits packed two to a byte, three bytes stored least significant first: PLAYER1_SCORE_LO 0xAD33 up to PLAYER1_SCORE_HI 0xAD35 for player one, and the same layout from PLAYER2_SCORE_LO 0xAD36 to PLAYER2_SCORE_HI 0xAD38 for player two [seen]. ACTIVE_PLAYER 0xAD32 [seen] picks which triple an award lands in. The award number indexes SCORE_AWARD_TABLE 0x0D27 [seen], three packed bytes per entry, in the same low-first order. Entry 0 is zero and entries 1 to 9 are 100 to 900. Entry 10 is 1,000; 11 is 1,500; 12 is 2,000; 13 is 3,000; 14 is 4,000; and 15 is 5,000. awardScoreToPlayer [seen] adds the entry into the active score as a decimal add from the low byte up, carrying between bytes. Every entry has a zero low byte, so a score always ends in 00. A carry out of the top byte is dropped, so the score rolls over from 999,900 to zero rather than saturating.

Straight after the add, the same routine checks the high score. The single displayed high score ends at HIGH_SCORE_HI 0xA98D [seen], its most significant byte. It is laid out the same way as the player scores, low byte first in 0xA98B–0xA98D, and the comparison walks both from the top byte down and stops at the first byte that differs. Only a score that is strictly greater gets copied over the high score and repainted through paintHighScoreReadout 0x0D6B [seen]. The high score therefore climbs live during play rather than waiting for game over. Last, the routine repaints whichever player score it changed: paintPlayerOneScoreReadout 0x0D57 [seen] or paintPlayerTwoScoreReadout 0x0D61 [seen].

All three readouts hand their own triple (source byte, first screen cell, colour) to one shared printer, paintSixDigitFieldSuppressingLeadingZeros 0x0D73 [seen]. Player one's digits start at PLAYER1_SCORE_READOUT_BASE 0xA781 and the high score's at HIGH_SCORE_READOUT_BASE 0xA641 [seen]. The printer reads the score from its top byte downward while the cursor moves right, so the digits appear most significant first. The first four digits share one leading-zero flag, so the field's leading zeros are blanked as a single run. The last two digits are always painted, which is why a fresh score shows "00".

Award number 0 is not an award. It asks awardScoreToPlayer to redraw the score labels. In a two-player game (TWO_PLAYER_GAME 0xAD31 [seen] set) it draws both labels and both scores. In a one-player game it draws the label whose index is stored at SOLO_SCORE_LABEL_INDEX 0x0B31 [seen], draws player one's score, erases the label indexed by ABSENT_SCORE_LABEL_INDEX 0x15C6 [seen], and blanks the six cells from PLAYER2_SCORE_READOUT_BASE 0xA501 [seen]. That is how the second player's score disappears in a one-player game. The credited-game set-up armNewGameThenStepSequence 0x27B1 [seen] zeroes both score triples and posts exactly this award-0 request.

### What pays, and how much

Most points come through one ladder. Whenever the collision pass destroys something worth points it calls postChainedHitScore 0x51DE [seen]. That covers a player shot hitting a craft or a shootable weapon, a shot landing on the Mother-Ship, and the player's ship ramming something. The ladder runs on two cells. CHAIN_WINDOW 0xA99D [seen] says whether a chain is still running, and CHAIN_STEP 0xA99E [seen] is the rung reached so far.

When a hit arrives with the window already closed, the routine posts award 1 (100 points) and leaves the step alone. When it arrives with the window still open, it adds one to the step and posts award (step mod 8) + 1. Hits in close succession therefore pay 100, 200, … 800 and then wrap back to 100; the ladder does not stop at 800. Both paths reload the window to 30. The step cell itself is stored unmasked, and only the posted award is folded into the range 1 to 8.

The other half of the chain is expireHitChain 0x5205 [seen], which sits in the round engine's bookkeeping. On each pass of the round engine it takes one off a non-zero window. Once the window reads zero, it clears the step, and it repeats that clear on every idle pass. The poster never resets the step itself, so expireHitChain is the only thing that ends a chain. The window is measured in round-engine passes, not in frames.

The remaining awards are fixed, and each is posted by the subsystem that owns the target. The era-1 bomber pays award 11 (1,500) when its hit-soaking death plays out, from advanceHitSoakingObjectThenAnimateDeath 0x3B94 [seen]. A wiped-out formation pays award 12 (2,000) through a token. The kill that empties the wave's WAVE_KILL_COUNTDOWN 0xA811 [seen], while WAVE_CLAIM_TIMER 0xA812 [seen] is still open, writes its slot ordinal, with the top bit set, into CLAIM_TOKEN 0xA821 [seen]. Both the countdown and the token are kept by countTheKillAndGrantTheSharedToken 0x2BBA [seen]. The wreck that token names then lingers and posts the award once, from driveObjectAppearanceByPhaseBand 0x2C31 [seen]. The Mother-Ship pays twice over, both times from its own state machine loc_43f0 0x43F0 [seen]. When its death begins, its sweep of the field gives every live record a dying code and posts award 2 (200) for each one. At the 0xB4 step of its wreck countdown it posts award 13 (3,000).

The parachutist pays on its own ladder. A rescued parachutist's record runs a countdown. At its top, showParachutistAward 0x4809 [seen] swaps the sprite for an award glyph chosen by PARACHUTIST_RUNG 0xA8F7 [seen]: entries of PARACHUTIST_AWARD_SHAPE_TABLE 0x482D [seen] for rungs 0 to 3, and one fixed glyph from rung 4 on. When the countdown reaches 0x10, postNextParachutistBonus 0x4831 [seen] reads the same rung, adds one to it, and posts the payment. Rungs 0 to 3 take their award number from PARACHUTIST_BONUS_ARG_TABLE 0x484F [seen], which holds awards 10, 12, 13 and 14. From rung 4 on the routine posts award 15. A life's rescues therefore pay 1,000, 2,000, 3,000, 4,000, and then 5,000 for every one after that. The glyph on screen and the payment both read the rung before it is stepped, so they always agree. resetPlayfieldForLifeStart 0x19F0 [seen] zeroes PARACHUTIST_RUNG at every life start, and a new round is also a life start, so the ladder begins again at 1,000 both after a death and after a round is won.

### Bonus lives at score marks

awardBonusLifeAtScoreMark 0x4DDE [seen] runs once per round-engine pass and does nothing unless PLAY_ACTIVE is set. It looks only at the active player's top score byte, PLAYER1_SCORE_HI or PLAYER2_SCORE_HI [seen], the hundred-thousands and ten-thousands digits. It searches a mark list for an exact match. Bit 0 of BONUS_LIFE_SETTING 0xA9C3 [seen] selects the list. With the bit clear it is BONUS_LIFE_MARK_TABLE_BIT0_CLEAR 0x4E1B [seen], which holds 10,000 and then every 50,000 up to 960,000. With the bit set it is BONUS_LIFE_MARK_TABLE_BIT0_SET 0x4E30 [seen], which holds 20,000 and then every 60,000 up to 980,000.

The top byte keeps the mark's value for as long as the score sits in that band, so the routine needs a latch to pay only once. Bit 0 of BONUS_LIFE_LATCH 0xAD03 [seen] is that latch. A match with the bit already set does nothing, and the first pass on which the top byte matches no mark clears the bit again. A paying match sets the latch, adds one to LIVES_REMAINING 0xAD00 [seen], posts command 5 (the reserve-ship emblem strip) with the count from *before* the increment, and asks for the fanfare through requestBonusLifeSound 0x5805 [seen]. The value posted is the one the strip should show. The ship in play is never drawn in reserve, so the strip always shows lives less one, and after the increment that is exactly the old count.

No single award is larger than 5,000, so one award can never carry the score over a whole ten-thousand band. A band could be skipped only if more than 10,000 points were paid between two passes of the test. The lists end at 960,000 and 980,000, so no ship is awarded between the last mark and the rollover. The score rolls over to zero past 999,900 and the test looks only at the top byte, so a player on a second lap of the score earns the same marks over again. The latch sits inside the per-player context block (described below), so each player has their own.

### The kill meter

The bar along the bottom of the screen is the kill quota. KILLS_REMAINING 0xAD02 [seen] counts the craft still to destroy before the Mother-Ship may appear. Every round fills it from KILL_QUOTA 0xA9CD [seen]. That cell is written once at boot and never again [seen], and it is not keyed to the era, the loop or the difficulty, so every round asks for the same 56.

The count moves in exactly one place. A craft's death begins in stepDyingObjectState 0x2B93 [seen], which only the per-era craft services reach. It calls countTheKillAndGrantTheSharedToken [seen], which requests the death sounds and subtracts one from KILLS_REMAINING, stopping at zero rather than wrapping. Only the seven craft slots reach that step. Objects in the other banks never pass through it, and that includes the parachutist and the era-1 bomber on its hit-soaking path, so they do not count toward the quota.

drawKillMeter 0x0809 [seen] turns the count into glyphs. It runs in the bookkeeping at the end of every round-engine pass, and again from the life-start arm each time a life opens. ERA_INDEX 0xAD04 [seen] picks a ten-byte row of KILL_METER_GLYPH_ROW_TABLE 0x087C [seen], so each era builds its bar from its own pieces. The row's first two bytes are the bar glyphs and the other eight are end-caps. The routine lays (count ÷ 4) bar cells, kept to five bits, from KILL_METER_BAR_START_CELL 0xA79F [seen], alternating the two bar glyphs. Each cell is 32 addresses lower than the last, one cell along the bar on the rotated screen. After the bar comes the end-cap that the count's low three bits select, then one blank glyph. The bar loses a whole cell every four kills while the end-cap slides with it and shows the remainder. The single trailing blank wipes the cell the end-cap held a moment ago. Only the glyph plane is written.

Once KILLS_REMAINING is zero, armMotherShipOrStep 0x43B7 [seen] arms the Mother-Ship. It does this on its one-frame-in-eight beat, and only when the Mother-Ship's two-slot record bank is empty. It raises MOTHER_SHIP_ARMED 0xAD0D [seen] and seeds MOTHER_SHIP_HITS_TO_ABSORB 0xA8A4 [seen] with 7. The Mother-Ship's own life is covered elsewhere. What matters here is how it ends. The sweep of the field that opens its death raises ROUND_TRANSITION_HOLD 0xACC6 [seen] to 0xFE, and its last wreck step sets it to 0xFF and frees its record. From the sweep on, the round counts as won. The round engine still ends it only once the field is empty, and that cannot happen while the wreck's own record is busy.

### Ending a round and advancing the era

Each pass of the round engine, serviceRoundThenResolvePlayerState 0x1199 [seen], ends by reading PLAYER_STATE 0xA800 [seen]. If the ship is alive (0xFF), the pass goes to advanceRoundWhenFieldCleared 0x1271 [seen]. That routine ends the round only when three things hold together. KILLS_REMAINING must be zero, ROUND_TRANSITION_HOLD must be non-zero, and every one of the fifteen object records from ACTOR_RECORD_SLOT0 0xA810 [seen] must be free, so that nothing is still dying or flying off.

Most passes return at the first test. When all three hold, the routine queues the transition sound stops. In the attract demo (PLAY_ACTIVE clear) it then reloads the hold from ROUND_TRANSITION_HOLD_SEED 0x07D1 [seen], which reads 0, hides the sprites, and returns the machine to the attract phase (ATTRACT_SEQUENCE_START_PHASE 0x16D3 [seen]). A demo never advances an era.

In a credited game the routine parks the non-player sprites and calls startNextRound 0x2DB8 [seen]. That routine first adds one to ROUND_NUMBER 0xAD01 [seen]. This is the round ordinal the HUD shows, and it keeps climbing across loops rather than wrapping with the eras. ERA_INDEX goes up by one too, but wraps from 4 back to 0, so the sixth round replays the first era. Because ERA_INDEX never passes 4, the era-indexed word tables are never read past their fifth entry. Two of the three readers mask the era to three bits first; the MOTHER_SHIP_SHOT_VELOCITY_ARM_BY_ERA_TABLE reader uses it unmasked. Those tables are ERA_SLOT_DISPATCH_TABLE 0x2914 [seen], the Mother-Ship's velocity-arm table at 0x46C4 and MOTHER_SHIP_SHOT_VELOCITY_ARM_BY_ERA_TABLE 0x478B [seen]. Their sixth and seventh words are bytes of the code that follows, and their eighth points at 0x1323, 0x0D73 and 0x0B72. What makes the second lap harder than the first, even though it replays the same eras, is START_RUNG 0xAD0A [seen], the difficulty rung the round opens on. The routine reloads it from one of three cells by round bracket: START_RUNG_ROUNDS_1_5 0xA9D3 below round 6, START_RUNG_ROUNDS_6_10 0xA9D4 for rounds 6 to 10, and START_RUNG_ROUNDS_11_UP 0xA9D5 [seen] after that. The brackets fall exactly on the first pass through the five eras, the second pass, and every pass after that, so the ladder has three steps and then stops. All three, together with the rung period, were copied out of DIFFICULTY_RECORD_TABLE 0x186A [seen] when the game began, by the record the cabinet's DIFFICULTY_SETTING 0xA9C4 [seen] selects. Last, the routine refills KILLS_REMAINING from KILL_QUOTA, clears MOTHER_SHIP_ARMED and ROUND_TRANSITION_HOLD, and raises ROUND_INTRO_PENDING 0xAD0E [seen] to 0xFF.

advanceRoundWhenFieldCleared then copies the live sixteen-byte context from LIVES_REMAINING 0xAD00 into the active player's saved block. It reseats SEQUENCE_SUBSTEP 0xA9AC [seen] from NEXT_ROUND_START_SUBSTEP 0x4A35 [seen], which reads 0x0D. The ACTIVE_PLAYER cell is left alone: winning a round never passes the turn, and a player keeps playing until they die.

Sub-step 13, armRoundWonBandAnimationThenStepSequence 0x4A0F [seen], sets up the between-eras band animation, and stepRoundWonBandAnimation 0x1323 [seen] plays it, acting only on calls that find FRAME_TICK bit 1 clear. When the animation finishes, it loads the active player's context, posts the HUD, and sends the sequence back to sub-step 3 (INTRO_SUBSTEP_RELOAD 0x2750 [seen]), whose arm loads the context again; a won round therefore restores the block and posts the HUD twice. The round-start arms then run as they do for any life: postLifeStartCaptionsAndResetPlayfield 0x0774 [seen] repaints the kill meter at full and calls resetPlayfieldForLifeStart [seen].

That reset restarts the difficulty for the new life. It reloads ERA_RUNG_TIMER 0xA9D7 from ERA_RUNG_PERIOD 0xA9D6 [seen], seats ERA_RUNG 0xACC0 [seen] from START_RUNG, and applies the tuning row for that era and rung. During the life, escalateDifficultyRungOnCounterWrap 0x4D3A [seen] climbs the rung by one, stopping at 15, each time ERA_RUNG_TIMER runs out. That timer loses one each time the life counter's low place wraps from 59 to 0, which is once every sixty round-engine passes, and it is reloaded from the period each time it fires. Other subsystems read the same counter as a phase: reaimEnemyCraftByFlightScriptOnPhaseTick keys off its low place, and driveEnemyWaveForLifePhase [seen] keys its wave behaviour off the units digit of the middle place, a cycle of ten low-place wraps. Each life, and so each new round, therefore starts back at the bracket's opening rung.

ROUND_INTRO_PENDING marks a round's *first* life. While it is set, the life-start arm posts command 7, drawRoundNumberCaption 0x0EAC [seen], which prints ROUND_NUMBER in decimal inside its caption frame, dropping a leading zero, and prints nothing at 100 or above. The intro also flashes the era year. On a restart after a death, ROUND_INTRO_PENDING has been cleared (flyLifeStartHoldThenEraseLifeStartCaptions 0x16AF [seen] clears it when its hold expires), so the arm shows " READY " instead. ROUND_NUMBER is a single byte that nothing caps: a round won at 0xFF wraps it to 0, the next round's intro reads STAGE 0, and the round falls back into the first rung bracket.

The round number also appears as the tally strip. loadActivePlayerContextAndPostRoundHud 0x4C75 [seen] posts it as command 6, and drawCountAsPictogramStrip 0x0DD7 [seen] draws it clamped to 99 as blocks of thirty, ten and five plus single glyphs.

### Losing a life, and whose turn it is

Each player's progress lives in a sixteen-byte context block. The live copy starts at LIVES_REMAINING 0xAD00 [seen], player one's saved copy at PLAYER_ONE_LIVES 0xAD10 [seen], and player two's at PLAYER_TWO_LIVES 0xAD20 [seen]. The block carries the lives count, ROUND_NUMBER, KILLS_REMAINING, the bonus-life latch, ERA_INDEX, the life counter, START_RUNG, the caption pen, MOTHER_SHIP_ARMED and ROUND_INTRO_PENDING. The scores sit outside it, in their own per-player triples. The block's three remaining bytes, 0xAD08, 0xAD09 and 0xAD0F, ride along unnamed: only the power-on wipe of work RAM, the two block saves and the block restore touch them, and they hold zero.

At the start of a turn, loadActivePlayerContextAndPostRoundHud copies the saved block that ACTIVE_PLAYER selects over the live one. In credited play it then posts the round tally (command 6) and the reserve emblems (command 5, lives less one). Kill-meter progress is part of the block, so it survives a death: a player who dies with twenty kills still owed comes back owing twenty.

When the ship's dying sequence has run out, PLAYER_STATE reads 0 and the round engine falls into loseLifeAndHandOver 0x11ED [seen]. The routine first hides the sprites. If ROUND_TRANSITION_HOLD is already up, it calls startNextRound itself. That is the case where the Mother-Ship was destroyed and the player died before the field cleared, and the round is still banked, so the next life opens in the next era. The routine then queues the transition sound stops, subtracts one from LIVES_REMAINING, and copies the whole live block out to the active player's saved block, so the saved copy carries the new count.

If the count has reached zero, the routine hands off to postGameOverBanner 0x1253 [seen]. Otherwise it checks the *other* player's saved lives, and a non-zero value flips ACTIVE_PLAYER. In a one-player game, startOnePlayerGame 0x3215 [seen] zeroed PLAYER_TWO_LIVES, so the flip can never happen. In a two-player game, startTwoPlayerGame 0x189E [seen] loaded both players' lives from STARTING_LIVES 0xA9C1 [seen], so the players alternate on every death until one of them runs out, and the survivor then plays every life. Either way SEQUENCE_DELAY 0xA9EB [seen] is set to 90, the count for the life-start hold that comes after the arms, and SEQUENCE_SUBSTEP is reseated from NEXT_LIFE_SUBSTEP_SEED 0x4B52 [seen], which reads 1. The machine then re-runs the life-start arms from sub-step 1 for whichever player is now up. Sub-step 4 posts "PLAYER 1" or "PLAYER 2" according to ACTIVE_PLAYER.

### Game over

postGameOverBanner [seen] posts the PLAYER-n caption (caption 9, plus one when player two is up) and the GAME OVER caption. It holds them by setting SEQUENCE_DELAY to 180 and steps the sequence to sub-step 8. The routine also has an arm for PLAY_ACTIVE being clear, which goes straight to restartAttractSequence 0x12FB [seen].

Sub-step 8, fileScoreAfterGameOverHoldElsePassTurn 0x330B [seen], counts that hold down and then tries to file the finished score with fileScoreIntoHighScoreTable 0x4CC3 [seen]. That routine walks the five-record high-score table top-down and uses isScoreBelow 0x4D2B [seen] as its comparison (the table and initials entry have their own section).

If the score ranks, the step asks for the filed-score sound and sets the pen to colour 0 (its glyph stays the blank 0xF1). Sub-step 9 then traces the pen route in colour 0, which erases it, and opens initials entry, which sub-step 10 runs. When entry finishes, the sequence steps to sub-step 11, holdThenPassTurnToOtherPlayerIfLivesElseStepSequence 0x12E2 [seen], which waits out SEQUENCE_DELAY. If the score ranks nowhere, the step erases the two captions and reseats the sub-step from SKIP_INITIALS_SUBSTEP_SEED 0x0843 [seen], which reads 0x0B, the same hold sub-step. It then goes straight to the decision.

Both paths end at passTurnToOtherPlayerIfLivesElseStepSequence 0x12E7 [seen]. If the other player's saved lives are non-zero, handPlayOverToOtherPlayer 0x1226 [seen] flips ACTIVE_PLAYER, sets the delay to 90 and reseats sub-step 1. The surviving player then carries on from their own saved block: their own era, round, unfinished kill meter and score. If the other player has no lives, the sequence steps on to sub-step 12, restartAttractSequence [seen]. That clears PLAY_ACTIVE and ACTIVE_PLAYER, puts SEQUENCE_PHASE 0xA9AB [seen] back to the attract phase, and sets SEQUENCE_SUBSTEP from an image fold that lands on zero for the genuine program. This is the only place the ladder ends. The game has no final era and no win, and it is over only when both context blocks are out of lives.

A new game can also start from inside initials entry, without the sequence returning to attract. stepHighScoreInitialsEntry 0x18C3 [seen] can call startOnePlayerGame or startTwoPlayerGame directly, or startGameOnFreePlay [seen] on a free-play cabinet.

## §8 The character plane: text, the meter, and routines nothing reaches

### The two planes and the cursor that walks them

Everything in Time Pilot that is not a sprite is a tile in the character plane: the captions, the three score readouts, the kill meter, the strip of reserve-ship emblems and round pictograms, and the copyright line. The plane is two parallel blocks of video RAM. The glyph block runs from 0xA400 to 0xA7FF and the colour block sits 0x400 below it, cell for cell, so one address bit (bit 10) selects between a cell's glyph and its colour. The painters that write a cell's glyph and its colour one cell at a time use that bit the same way. drawTextRun, the digit painters, the one- and two-glyph slot painters and the line wipe each write the glyph, clear bit 10 to write the colour, and then *set* the bit again rather than restoring it. A cursor that arrives on the colour side therefore leaves on the glyph side. On a correct call this changes nothing, but it is why those painters' returned cursors always point at a glyph cell. The two-by-two painters, stampTwoByTwoTileBlock [seen] and paintQuadTile [seen], reach the colour plane by subtracting 0x400 instead, and eraseTextRunByIndex never touches the colour plane. The shot-cell painter works the other way round: it starts from a colour-plane address and sets bit 10 to reach the glyph.

The attribute byte does more than set colour. Its low five bits choose one of 32 palettes. Bit 4 is part of that palette number and also puts the cell in the category the board draws *over* the sprites rather than under them. Bit 5 selects the second 256-tile bank, and bits 6 and 7 mirror the tile along the plane's native axes. On the rotated glass, bit 6 flips it top to bottom and bit 7 left to right. Only native rows 2 to 29 of the plane are visible, so row 0 (0xA400–0xA41F) can hold data that is never seen; the between-eras band uses it that way (below).

The plane is laid out in rows of thirty-two cells, and the monitor is mounted rotated. The cell that follows the current one along a line of text on the glass is therefore thirty-two addresses *lower* in video RAM, not one address higher. Two one-byte restart vectors carry that step for many of the drawers; others step with their own add of ±0x20. advanceCharCursor (RST 0x20, 0x0020) subtracts 0x20 and moves one character on [seen]. retreatCharCursor (RST 0x28, 0x0028) adds 0x20 and moves one character back [seen]. The neighbour one address away (cell − 1) is the cell beside the cursor in the other direction, so a painter that writes at P and P − 1 lays a two-cell-tall mark. The emblems, the pictograms and the one-glyph slots are all built that way.

### The command ring: draw later, outside the interrupt

The frame interrupt decides what should appear on the screen, but it does almost none of the drawing. It posts requests instead. postCommand (RST 0x38, 0x0038) [seen] takes a command byte and an argument byte and appends them to COMMAND_RING 0xAC00 [seen], a 64-cell ring holding thirty-two two-byte requests. The free test is the high bit. Initialisation fills the ring with 0xFF, and a consumed pair is put back to 0xFF, so a cell with bit 7 set is empty. postCommand looks at the cell COMMAND_WRITE_CURSOR 0xA9B2 [seen] names. If that cell's high bit is clear, the reader has not caught up yet, and the pair is **dropped**: there is no retry and no signal. Otherwise the command goes into that cell, the argument into the next one, and the cursor steps two cells on, wrapped to 64. Because every score award also travels through this ring (below), a ring that is full at the moment of a hit loses that hit's points.

The consumer is the machine's foreground. Once enableInterruptAndEnterForegroundLoop [seen] has entered it, the CPU spends every moment outside the frame interrupt in runCommandRingDrainLoop (0x0B93) [seen]. That loop builds the cell address from COMMAND_READ_CURSOR 0xA9B3 [seen] and tests the high bit there. While the cell is empty it waits and looks again. The loop has no exit of its own. When the cell is occupied, the loop takes the command and the argument and writes 0xFF back over **both** cells *before* the handler runs, so a handler that posts a request of its own can land it in the slot it just came from. The loop then advances the read cursor past the pair, again wrapped to 64. It takes the command's low nibble, uses it to index the sixteen-word COMMAND_HANDLER_TABLE 0x0BBC [seen], and jumps to the handler with the argument byte in hand. Each handler is entered with 0x0B90 as its return address. enterCommandRingDrain (0x0B90) [seen] is just a `jp 0x0B93`, the loop's own back edge, so a handler that finishes comes straight back to look at the ring again.

This split is what lets the interrupt stay short. A caption of a dozen glyphs, a score award with its six-digit repaint, or a strip of emblems is queued in two bytes inside the vertical blank and drawn in the slack time after it, in the order it was posted.

### The sixteen handlers

The table at 0x0BBC holds sixteen words, and most of them name the work the game asks for. Command 1 is drawTextRunByIndex (0x0BF2) [seen], which paints a caption in the colour its own record carries. Command 2, drawCaptionInPenColour (0x0C0F) [seen], paints a caption in the shared pen colour. Commands 10 and 11, drawCaptionFivePastSharedColour (0x3421) [seen] and drawCaptionTenPastSharedColour (0x0C23) [seen], paint one in the pen colour plus 5 and plus 10. Command 3, eraseTextRunByIndex (0x0C39) [seen], blanks a caption. Command 4 is the scoring command, awardScoreToPlayer (0x0C90) [seen]. Commands 5 and 6 draw the two counted strips: the reserve ships through drawEmblemStripThenGuardImage (0x4D72) [seen] and the round pictograms through drawCountAsPictogramStrip (0x0DD7) [seen]. Command 7 draws the round-number caption through drawRoundNumberCaption (0x0EAC) [seen]. Every handler the ring reaches draws text or HUD, or adds score; sound requests travel through a separate queue (§2).

That leaves slot 0 and slots 8, 9 and 12 through 15. Slot 0 names drawCaptionGlyphsKeepingColour (0x0BDD) [code]. It looks up a caption record exactly as the others do, steps over the colour byte, and copies the glyph run into the glyph plane one cell at a time with advanceCharCursor, leaving every colour cell as it found it. It is the colourless twin of slot 1, and the drawing twin of slot 3's eraser. The other six slots all hold one address, loc_0bdc (0x0BDC) [code]. That is a lone `ret`, so taking such a command just frees the pair and returns to the top of the loop.

None of these seven slots is ever used. Every poster in the image loads its command byte from an immediate value or from a fixed program word, and the only commands loaded are 1 through 7, 10 and 11. Nothing posts command 0 or any of 8, 9 and 12 to 15. Both handlers are therefore unreached on a genuine image and are accounted for in `grounding-debt.txt` as dead code (0x0bdc, 0x0bdd). The bytes of the unused slot-0 handler are still read, though not as code: when its pen run finishes, blankKillMeterThenAdvancePenRunStep [seen] XOR-folds a span starting at IMAGE_GUARD_BLOCK_0BDD_BASE 0x0BDD [seen] as one of the game's image guards. A patched dead handler would still be noticed.

### Captions

A caption is a record in a table of record addresses, CAPTION_RECORD_TABLE 0x0C50 [seen], which the handlers index through fetchWideTableWord (0x018C) [seen]. A record opens with a two-byte destination, the glyph-plane cell where the caption starts. One colour byte follows, and then the glyph run itself, ended by the code 0xB9.

The painter is drawTextRun (0x0BFF) [seen]. It tests each byte for 0xB9 *before* writing anything, so an empty run paints nothing and the terminator is never drawn. For every other byte it writes the glyph to the cursor's cell, writes the colour to that cell's twin in the colour plane, and steps the cursor one character on. It hands back the cursor one place past the last glyph, so a caller can carry on writing after the caption.

The four drawing handlers differ only in where the colour comes from. drawTextRunByIndex [seen] unpacks the record's own colour byte and falls straight into drawTextRun. It is the one member of the family that uses that byte. The other three step over the byte unread and colour the caption from PEN_COLOUR 0xAD0C [seen] instead. drawCaptionInPenColour [seen] uses the pen value's low nibble, drawCaptionFivePastSharedColour [seen] adds 5 first, and drawCaptionTenPastSharedColour [seen] adds 10 first.

All three keep four bits, so a caption drawn through them takes a colour that follows the pen and never the one stored in its record. None of the three cycles colour by itself. A caption flashes because something posts it through all three in turn. flyLifeStartHoldThenEraseLifeStartCaptions [seen] does exactly that with the era's year caption (record 0x1A plus ERA_INDEX 0xAD04 [seen]). While ROUND_INTRO_PENDING 0xAD0E [seen] is set, it posts command 2, 10 or 11 when the low nibble of FRAME_TICK 0xA980 [seen] is 0, 5 or 10, so the year repaints in three related colours on a sixteen-frame beat.

The copyright line flashes by a different route. Records 0 and 31 share one destination (0xA6BC) and carry identical glyph runs, at 0x086E and 0x4903, but different colour bytes, 0x10 and 0x05. flashCopyrightLine [seen] posts command 1 with record 0 on odd frames and, through enqueueFixedCommandOnRing (0x0B46) [seen], command 1 with record 31 on even ones. The glyphs stay put and only the colour alternates.

eraseTextRunByIndex [seen] is the inverse of drawing. It walks the same record from the same cell for the same length, testing each byte only against 0xB9, and writes the blank glyph 0xF1 in its place. It never touches the colour plane, so a blanked caption keeps its old colour under the blank. Because the run's length comes from the record, erasing caption n removes exactly the cells that drawing caption n wrote, and the screens use it that way. It also blanks any other record of the same length at the same cell. The life-start hold erases records 9, 0x0E and 0x1A together when its delay runs out; record 0x1A blanks whichever era year is showing, because all five years share a cell and a length. The game-over filing step erases records 9 and 0x0B when the score takes no place on the high-score table, and the attract copyright hold erases records 3 and 4.

Glyph codes are not ASCII, and the records are not stored together: their addresses are scattered through the program image. The letters decode consistently across every record, and the records seen on screen read exactly as decoded. Record 0 is the copyright line, "© KONAMI 1982", in colour 0x10, and record 31 is the same line in colour 0x05. The attract and credit texts are "PLAY", "READY", "PLEASE DEPOSIT COIN" / "AND TRY THIS GAME", "HI-SCORE", "1-UP", "2-UP", "CREDIT", "FREE PLAY", "PUSH START BUTTON", "ONE PLAYER ONLY" and "ONE OR TWO PLAYERS". Two bonus-life caption pairs, "1ST BONUS 10000 PTS." / "AND EVERY 50000 PTS." and the 20000/60000 pair, are chosen by postPushStartScreenCaptions [seen] from BONUS_LIFE_SETTING 0xA9C3 [seen]. The play texts are "PLAYER 1", "PLAYER 2", "GAME OVER", "INPUT YOUR INITIALS" (its trailing glyph draws blank), "SCORE RANKING TABLE" and "STAGE" followed by three blanks. Records 26–30 are the five era years, each seven cells long and starting at the same cell 0xA673. Records 20 and 21 are drawn in colour 0x32, whose bit 5 sends their codes to the second tile bank: they are the two halves of the TIME PILOT title logo. Record 24 starts with its terminator, so it draws nothing, and nothing in the program posts it.

Record 2 is READY, records 9 and 10 are PLAYER 1 and PLAYER 2, record 11 is GAME OVER, and 0x0E is the stage frame that drawRoundNumberCaption fills in. postLifeStartCaptionsAndResetPlayfield [seen] posts these at each life start: in the demo, READY alone in pen colour. In a game it posts PLAYER n (record 9, plus one for the second player). It then posts READY again while ROUND_INTRO_PENDING is clear, or command 7 while it is set. postGameOverBanner [seen] posts PLAYER n through command 2 and GAME OVER through command 10.

The copyright line holds a further surprise. COPYRIGHT_CAPTION_RECORD 0x086B [seen] is also data for other parts of the machine: its "M" glyph, 0x38 at 0x0874, is DEFAULT_KILL_QUOTA, which seedGameConfigFromDipSwitches copies into KILL_QUOTA 0xA9CD [seen] as the 56 kills every round demands.

Several of these records sit where code also runs or lands. Record 9's bytes live at 0x0167, record 2's at 0x307F, record 7's at 0x2509, record 8's at 0x15CA with record 5 just after it, record 4's at 0x49FA and record 17's at 0x459B. Each of those addresses is also a landing point of a tamper derail or a misaligned entry (see the last part of this section). The caption table and the program image overlap, which is why a byte in one of those runs can be both a letter and an instruction.

### Pens: the colour of the era

PEN_COLOUR 0xAD0C [seen] and PEN_GLYPH 0xAD0B [seen] are the pen pair in the active player's context. Each player keeps a saved copy: PLAYER_ONE_PEN_GLYPH 0xAD1B [seen] / PLAYER_ONE_PEN_COLOUR 0xAD1C [seen], and PLAYER_TWO_PEN_GLYPH 0xAD2B [seen] / PLAYER_TWO_PEN_COLOUR 0xAD2C [seen].

Both setSavedPenFromEra [seen] and seatCaptionPenFromEraFoldingTamperIntoPhase [seen] load the pair from ERA_PEN_TABLE 0x0F8D, two bytes per era, indexed by the player's era. The first five entries are glyph 0xF1 with colours 1, 2, 3, 4 and 5, so the pen colour is simply the era number plus one. The seat routine writes the live pen as well as the saved copy.

So any caption drawn "in pen colour" changes colour from era to era. Those captions are PLAYER n at each life start of a game, READY in the demo and on a restart after a death (a round's first life posts the round-number caption, command 7, in READY's place), the STAGE frame of the round-number caption, PLAYER n and GAME OVER at game over, and the flashing era year. Masking to the low nibble also clears bit 4, so pen-coloured captions always sit in the under-sprite category. Most record colours (0x10, 0x11, 0x13, 0x14, and 0x32 for records 20/21) have bit 4 set and draw over the sprites. Record 31, the copyright line's flash partner, is colour 0x05, so it sits under them.

The same pair drives the attract pen plotter: plotPenCell [seen] stamps PEN_GLYPH into a video cell and PEN_COLOUR into its colour cell. Every era's pen glyph is already the blank 0xF1, so the plotter always lays blank tiles and what it changes is their colour. armPenRouteInColour5ThenAdvanceStep [seen] re-arms the pen with glyph 0xF1 and colour 5, and the high-score filing step with 0xF1 and colour 0, so the same route repaints the playfield in a fixed colour instead of the era's.

### Digits: the three score readouts

A score is three bytes of packed decimal, two digits per byte, stored with its low byte at the lowest address. Player one's runs from PLAYER1_SCORE_LO 0xAD33 [seen] up to PLAYER1_SCORE_HI 0xAD35 [seen], and player two's from PLAYER2_SCORE_LO 0xAD36 [seen] up to PLAYER2_SCORE_HI 0xAD38 [seen]. The high score is laid out the same way in 0xA98B–0xA98D and is named by its top byte, HIGH_SCORE_HI 0xA98D [seen]. Three entries put the readouts on screen. Each hands one shared painter the top byte of a score, a start cell and the colour 0x10. paintPlayerOneScoreReadout (0x0D57) [seen] paints player one's score from PLAYER1_SCORE_READOUT_BASE 0xA781 [seen], paintPlayerTwoScoreReadout (0x0D61) [seen] paints player two's from PLAYER2_SCORE_READOUT_BASE 0xA501 [seen], and paintHighScoreReadout (0x0D6B) [seen] paints the high score from HIGH_SCORE_READOUT_BASE 0xA641 [seen].

That painter is paintSixDigitFieldSuppressingLeadingZeros (0x0D73) [seen]. It reads its three bytes from the most significant one downward. The first two bytes go through paintTwoSuppressedDigitsFromByte (0x0DA0) [seen], which paints the high nibble and then the low nibble, each through paintSuppressedDigit (0x0DAF) [seen] with a cursor step after each. A flag starts clear and is stepped up by the first non-zero digit. While the flag is clear, a zero is a leading zero. It looks up the table index held at LEADING_ZERO_BLANK_GLYPH_INDEX 0x3246 [seen], and that entry of DIGIT_GLYPH_TABLE 0x0DCC [seen] is the blank glyph 0xF1. Once the flag is set, a zero indexes entry 0 and draws as '0'. The last byte goes through paintTwoUnsuppressedDigitsFromByte (0x0D81) [seen] and paintUnsuppressedDigit (0x0D90) [seen], which always draw both digits. A score therefore always shows at least two digits, and an empty score reads "00".

A blanked leading zero still takes up its cell, so all six digit positions stay fixed and the number is right-aligned. The glyph codes in the table are not in digit order, because the tile ROM does not keep its digits together. That is why every digit goes through a lookup, fetchTableByte (RST 0x08) [seen].

### Digits: the round number

drawRoundNumberCaption (0x0EAC) [seen] uses a second digit routine with a different rule. It ignores the ring argument and reads ROUND_NUMBER 0xAD01 [seen]. A value of 100 or more draws nothing. Otherwise it paints caption 0x0E through drawCaptionInPenColour, steps the returned cursor back two cells with retreatCharCursor, and paints tens and then ones there in the pen colour through paintDigitDroppingLeadingZero (0x0EEB) [seen]. That routine indexes a separate glyph table, DIGIT_GLYPH_TABLE_2 0x0F06 [seen], and handles a leading zero by *dropping* it.

The tens digit is painted with an allowance of one. If the tens digit is zero, the routine paints nothing, spends the allowance and steps the cursor back one cell. The caller's next forward step cancels that, so the ones digit lands in the tens position. Any digit that is painted zeroes the allowance, and the ones digit is always painted with no allowance left. A single-digit round therefore shifts one cell rather than leaving a gap, and round 0 still shows a lone '0'.

After painting, the routine sums sixteen program bytes onto a seed of 0x8C. A genuine image sums to zero. A mismatch jumps to 0x2509 and runs caption record 7's bytes as code (below). The command-7 request comes only from the life-start arm, while ROUND_INTRO_PENDING is set.

### The scoring command

awardScoreToPlayer (0x0C90) [seen] is the only routine that adds to a score, and it is reached only through the ring. Apart from the power-on wipe of work RAM, the scores are otherwise only zeroed, when a credited game opens. It does nothing at all unless PLAY_ACTIVE 0xAD30 [seen] is set, so the attract demo can post awards freely without ever touching a score.

Argument 0 is not an award but a request to redraw the score area. armNewGameThenStepSequence [seen] posts it when a credited game opens, right after zeroing both scores. In a two-player game (TWO_PLAYER_GAME 0xAD31 [seen] set), it draws caption 6 and the player-one readout, then caption 7 and the player-two readout. These are the two score labels, "1-UP" and "2-UP". In a one-player game it draws the caption whose number sits in SOLO_SCORE_LABEL_INDEX 0x0B31 [seen] and the player-one readout. It then erases the caption named by ABSENT_SCORE_LABEL_INDEX 0x15C6 [seen] and writes six blank glyphs over the second readout. Those two program bytes hold 6 and 7, so the one-player screen keeps the first label and takes down the second.

Any other argument selects an entry of SCORE_AWARD_TABLE 0x0D27 [seen], three packed-decimal bytes per entry. Read from the image, entries 1 to 10 are 100 to 1,000 in hundreds, then 11 to 15 are 1,500, 2,000, 3,000, 4,000 and 5,000. The routine picks the active player's score by ACTIVE_PLAYER 0xAD32 [seen] and adds the award a byte at a time with a decimal carry. A carry out of the top byte is dropped, so the score rolls over from 999,900 to zero.

The routine then compares the new score with the high score, most significant byte first. Only a score that is strictly greater replaces it, and that is followed by a high-score repaint. Finally the routine repaints the active player's readout.

The posters show which award is which. postChainedHitScore [seen] posts entries 1 to 8 as a hit chain climbs and wraps, and re-opens CHAIN_WINDOW 0xA99D [seen] each time. postNextParachutistBonus [seen] posts its rung from PARACHUTIST_BONUS_ARG_TABLE 0x484F [seen], and entry 15 (5,000) once the rungs run past the table. advanceHitSoakingObjectThenAnimateDeath [seen] posts 11 (1,500) and driveObjectAppearanceByPhaseBand [seen] posts 12 (2,000). loc_43f0 [seen] posts 2 for each live record its Mother-Ship field sweep catches, and 13 (3,000) at the wreck's 0xB4 step.

### The kill meter

drawKillMeter (0x0809) [seen] runs on every pass of the round engine, called from serviceRoundThenResolvePlayerState [seen], and once more from the life-start arm. It draws how many kills remain before the Mother-Ship.

It picks the era's ten-byte row of KILL_METER_GLYPH_ROW_TABLE 0x087C [seen] by ERA_INDEX × 10, so every era draws its meter in its own pieces. The row's first two bytes are the bar glyphs. Its other eight are end glyphs, indexed by the low three bits of KILLS_REMAINING 0xAD02 [seen]. The bar is KILLS_REMAINING ÷ 4 cells, laid from KILL_METER_BAR_START_CELL 0xA79F [seen] one character at a time, alternating the two bar glyphs. One end glyph caps it, and one blank 0xF1 follows. That single trailing blank is all the erasing the meter needs, because the count drops by one kill at a time and the end can move back by at most one cell.

The bytes of each row show what the end glyph is. Entries 0 and 4 are both the blank, and entries 1–3 and 5–7 are distinct glyphs. Bit 2 of the count is also the parity of the cell the end glyph lands in. The end glyph is therefore the partly filled version of whichever bar piece comes next, showing the remaining one to three kills of the current four-kill cell. KILLS_REMAINING is loaded from KILL_QUOTA 0xA9CD [seen] by startNextRound [seen] and counted down by countTheKillAndGrantTheSharedToken [seen], so the meter shortens as the player shoots. With the quota of 56 the bar starts fourteen cells long and shrinks toward its start cell, the "progress bar" of gameplay.md. The bar length takes bits 2 to 6 of the count, so it is at most 31 cells and a count of 128 or more would wrap. drawKillMeter writes glyphs only. The meter's colour comes from blankFourteenCharCells [seen], which both the pen-route arm and loadActivePlayerContextAndPostRoundHud [seen] run first: fourteen 0xF1 cells in colour 0x16 from the same start cell.

### The strip of emblems and pictograms

The other two counted displays share one two-cell-tall strip and meet at EMBLEM_STRIP_FLOOR 0xA623 [seen].

**Reserve-ship emblems (command 5).** drawEmblemStripThenGuardImage [seen] does nothing outside credited play, not even its guard. In play it starts at EMBLEM_STRIP_TOP 0xA783 [seen] and stamps one 2×2 emblem per reserve ship, at most six (so the 0xFF lives setting shows six), through stampTwoByTwoTileBlock [seen]. Each emblem is tiles 9 to 12 in colour 0x18, and the cursor moves two characters on. It then blanks forward one two-cell slot at a time through paintGlyphOverBlankInColourThenStepCursor [seen] (blank glyph 0xF1, colour 0x10) until the cursor passes the floor. A shorter strip therefore clears what a longer one drew.

The count it receives is the number of ships in reserve. loadActivePlayerContextAndPostRoundHud [seen] posts LIVES_REMAINING 0xAD00 [seen] minus one at the start of a turn. awardBonusLifeAtScoreMark [seen] posts the count before the increment when a bonus mark pays, which is the same thing one ship later. After stamping, the handler XOR-folds the 256 program bytes from IMAGE_GUARD_BLOCK_0711_BASE 0x0711 [seen]. It requires the fold plus 0x19 to be zero. Otherwise it jumps into DEFAULT_HIGH_SCORE_TABLE 0x4BB1 [seen], table data run as code.

**Round pictograms (command 6).** drawCountAsPictogramStrip [seen] takes a count, clamps it to 99, and splits it greedily into thirties, tens, fives and ones. It then paints from COUNT_PICTOGRAM_STRIP_START 0xA463 [seen], smallest denomination first. Each one is a single glyph beside a blank, laid by drawSlotWithOneGlyph [seen]. Each five is a two-tile block from paintDoubleTile [seen], and each ten and each thirty is a four-tile block from paintQuadTile [seen], with a different base tile and colour for the two.

Every painter hands its cursor on to the next, and blank slots fill the rest of the strip up to the floor. The turn-start post sends ROUND_NUMBER, and the attract screen sends 1. After painting, the routine adds three program words (IMAGE_CHECKSUM_WORD_009D 0x009D, IMAGE_CHECKSUM_WORD_00A0 0x00A0, IMAGE_CHECKSUM_WORD_00A3 0x00A3, all [seen]) and folds the sum's two bytes together. If the result is not 0x69, it jumps to the reset vector, and the machine restarts from power-on.

The two strips step in opposite directions: emblems with advanceCharCursor, pictograms with retreatCharCursor. That is how they grow toward each other from the two ends without overlapping.

### Wipes

armLineWipeFromFifthLine [seen] seats BLANK_LINE_CURSOR 0xA989 [seen] at BLANK_LINE_START_CELL 0xA404 (native column 4 of row 0). It loads BLANK_LINES_LEFT 0xA988 [seen] from the ROM byte BLANK_LINES_COUNT 0x0CCD, which is 27.

Each call of blankNextLine [seen] blanks one whole line: 32 cells stepping +32 through every native row, glyph 0xF1 in colour 0x10. It then moves the cursor one cell over (not 32) to the next line and counts down, returning true only when the count reaches zero. Its callers return early until then (armAttractScreenShowingHighScore [seen] is one), so a wipe costs one line per call and is spread over successive calls.

### The scripted band between eras

When a round is won, armRoundWonBandAnimationThenStepSequence [seen] stocks the nine-byte control block at ROUND_WON_ANIMATION_STEP 0xA9F0 [seen] (0xA9F0–0xA9F8), leaving 0xA9F5 untouched:
- step 0, read from ROUND_WON_ANIMATION_STEP_SEED 0x3213 [seen];
- PLAYER_FLASH_TICK 0xA9F1 [seen] = 0;
- BAND_TO2_PASS_COUNTDOWN 0xA9F2 [seen] = 0xFF;
- SPRITE_COLOUR_CYCLE_COUNTDOWN 0xA9F3 [seen] = 4;
- BAND_TO4_PASS_COUNTDOWN 0xA9F4 [seen] = 0xFF;
- COLOUR_FLOOD_COUNTDOWN 0xA9F6 [seen] = 8;
- BAND_SCRIPT_CURSOR 0xA9F7 [seen] = BAND_SCRIPT_START 0x56F1.

It then does two things to the character plane.

First, it fills the invisible row 0 at CHAR_PLANE_BASE with a 32-byte saved picture: thirteen 0x14 glyphs, two 0x00, thirteen more 0x14, and four 0x0E.

Second, it colours the cells that picture belongs to. The 28 visible cells of native column 0x11, from CHAR_PLANE_COLUMN_BASE 0xA451 (row 2) to CHAR_PLANE_LEFT_RUN_OUTER 0xA7B1 (row 29), form a line across the screen. names.js gives the on-glass mapping as display_y = native_x. The line is made of three parts:
- a right-hand run of thirteen (native rows 2-14), ending at its inner cell CHAR_PLANE_RIGHT_RUN_INNER 0xA5D1;
- two centre cells, CHAR_PLANE_COLUMN_MID_RIGHT 0xA5F1 and CHAR_PLANE_COLUMN_MID_LEFT 0xA611;
- a left-hand run of thirteen (native rows 17-29), starting at its inner cell CHAR_PLANE_LEFT_RUN_INNER 0xA631.

Beside the centre sit four stub cells, in native columns 0x10 and 0x12 of rows 15 and 16. On the glass the line is the horizontal streak through the centre of the screen at display_y 136-143, where the player's jet sits, and the four stubs are the corners of a diamond-shaped bulge on that streak around the jet: CHAR_PLANE_STUB_UPPER_RIGHT 0xA5F0 [seen] above the streak and right of centre, CHAR_PLANE_STUB_UPPER_LEFT 0xA610 [seen] above it and left, CHAR_PLANE_STUB_LOWER_RIGHT 0xA5F2 [seen] below it and right, and CHAR_PLANE_STUB_LOWER_LEFT 0xA612 [seen] below it and left. So native column 0x10 is the row of tiles above the streak and column 0x12 the row below it, while native row 15 is the right-hand tile of each pair and row 16 the left. The band always gives all four the same glyph, and their colour bytes differ only in the two top bits, so the one tile shape is drawn mirrored into the four corners.

The colouring uses fillCellRun [seen], which fills thirteen cells stepping −32. The right-hand run takes 0x20 plus the pen colour and the left-hand run 0xA0 plus the pen, both in the second tile bank. Bit 7 is the difference, so the left-hand run is the right-hand run's tiles mirrored left to right. The column-0x10 stubs and the centre pair take 0xA0 or 0x20 plus the pen in the same way. The column-0x12 stubs take 0xE0 or 0x60 plus the pen, whose bit 6 mirrors the tiles below the streak top to bottom.

The second half of this work, from the fifteenth row-0 byte (the second 0x00) onward, is also a separate entry at 0x4A42, paintRoundWonBandTailThenStepSequence [seen]. Starting one cell past the caller's cursor, it writes a caller-supplied head byte, thirteen caller-supplied body bytes and the four 0x0E bytes, and then does all of the colouring. On a genuine image it runs only as this routine's fall-through. The saved pen is then refreshed from the era.

**The dispatcher.** stepRoundWonBandAnimation [seen] runs only on frames where FRAME_TICK bit 1 is clear. It dispatches on ROUND_WON_ANIMATION_STEP:
- 0: the player flash;
- 1: the flash plus advanceScriptedCharPlaneBandTo2 [seen];
- 2: the sprite colour cycle plus advanceScriptedCharPlaneBandTo4 [seen];
- 3: band-to-4 alone;
- 4: floodColourPlaneWithSavedPlayerColour [seen];
- 5: sets the sequence delay, hides the sprites, reloads the player context and posts the HUD (above), and reloads the sub-step.

**The band drawers.** Both drawers alternate on bit 0 of their pass countdown.

On an even count they blank both thirteen-cell runs, the two centre cells and the four stubs to 0xF1, so the band blinks.

On an odd count they make a drawing pass:
1. restoreColumnFromSavedRun [seen] copies row 0's saved picture back onto the column and the four stubs.
2. They edit it under the script. Where a script byte is non-zero, stepThirteenScriptedGlyphCells [seen] steps that cell's glyph code by one, up or down, walking thirteen cells one native row on or back each, with the script cursor moving forward or back.
3. gatherCharColumnIntoBackingRun [seen] saves the edited picture back into row 0.

Band-to-2 moves forward and adds one per flag. Each pass it reads a stub bit (all four stubs step together), a centre bit (both centre cells), then thirteen flags applied outward from the centre along the right-hand run. It rewinds the cursor thirteen and applies the same thirteen flags outward along the left-hand run. The two halves therefore change as mirror images, from the centre toward both ends.

The script at 0x56F1 is 255 bytes of 0 and 1 between 0xFF sentinels at 0x56F0 and 0x57F0. Band-to-2 uses fifteen bytes per pass, so it makes exactly seventeen drawing passes. It then hits the upper sentinel, zeroes its countdown, sets step 2 and backs the cursor up one.

Band-to-4 replays the same bytes in reverse and subtracts one per flag. The glyphs walk back to where they started. It stops on any byte that is neither 0 nor 1, which is the lower sentinel. It then sets step 4 and asks for requestDestructionOrRoundEndSoundPair [seen].

The colour cycle (cyclePlayerSpriteColourThenAdvanceStepAtZero [seen]) runs alongside band-to-4 and sets step 3 when its own countdown ends. The flood then paints a 27×28 rectangle of the colour plane from COLOUR_FLOOD_FIRST_CELL 0xA044 in the active player's saved pen colour. It walks the rectangle backwards when SCREEN_UNFLIPPED 0xA987 [seen] is zero.

On the glass the band is a streak across the screen through the ship, swelling into the bulge around it and thinning away again.

### Routines nothing reaches

The character plane is also the game's tamper witness. Routines in this section and around it read a glyph or colour back off the screen, or fold a run of program bytes, and compare the result with what a genuine image produces. On a mismatch they do not report anything. guardBlockOrBlankDisplay [seen] switches the picture off and seeds a witness pair. Others, holdCopyrightThenVerifyGlyphAndSeatWitnessOrDerail [seen] and paintReadoutsThenSampleWitnessOrDerail [seen] among them, jump into bytes that were never written as code (table data, caption records, the middle of another routine) and let the CPU lose its way. On a genuine image those comparisons always pass, so the landing points never execute and a run on a good ROM cannot ground them. Each one named as a routine is accounted for in `grounding-debt.txt` with the reason it is unreachable.

Program tables are among the landing points. The velocity table at loc_08fa (0x08FA) [code] runs as instructions on the failure arm of the 256-byte sum in armPenRouteInColour5ThenAdvanceStep [seen] and of the 24-byte XOR fold in buildCopyrightScreenThenVerifyImage [seen]. The era pen table at loc_0f8d (0x0F8D) [code] runs as code when advanceSequenceUnlessImageTampered [seen] finds that its fold misses 0x67. advancePlayerAnimationStrip [seen] diverts into the stick-heading table at loc_1f2e (0x1F2E) [code] when TAMPER_GLYPH_STRIP 0xABFE [seen] or TAMPER_COLOUR_STRIP 0xABFF [seen] stops holding its planted glyph and colour, and loc_1f99 (0x1F99) [code] is reachable only from inside that table-as-code. A second demo-autopilot script, loc_2251 (0x2251) [code], runs as code when seedDemoAutopilotScript [seen] finds its readback witness wrong. loc_315b (0x315B) [code] is where setSceneryAttributesThenRunEraScenery [seen] goes when TAMPER_GLYPH_KONAMI 0xACC7 [seen] no longer holds the KONAMI glyph and colour copied off the copyright line. The emblem strip's guard lands in data as well, in DEFAULT_HIGH_SCORE_TABLE 0x4BB1 [seen].

Caption records are landing points too, which is why a patched text or pen table changes code and a patched routine changes text. Record 9, at loc_0167 (0x0167) [code], runs as code when the image total of armWholePlaneWipeThenDerailOnATamperedImage [seen] misses. seedSceneryEntriesThenRunScenery [seen] takes trampolineToLoc_307f (0x3114) [code], a bare `jp 0x307F`, when TAMPER_WITNESS 0xAD39 [seen] is wrong. Its target, loc_307f (0x307F) [code], is record 2's bytes run as code: they store E through the guard's pointer and hand the slot to the straight placer at 0x3074 while the counter in B holds. Their last-slot arm pops a word it never pushed, and the one way in never takes it, because it arrives with B = 0. Record 7, "2-UP", at 0x2509 is where drawRoundNumberCaption [seen] jumps when its sixteen-byte sum is not zero. Record 4, "AND TRY THIS GAME", at 0x49FA is where checkTheCopyrightLineColoursOrDerail [seen] derails. Its own bytes end in a `jr c` to the band-colouring entry 0x4A42 that cannot fire, because the preceding `and l` clears carry. Record 8, "CREDIT", at 0x15CA is where holdCopyrightThenVerifyGlyphAndSeatWitnessOrDerail lands when the copyright line's N is not glyph 0x3B, and it runs straight on into record 5. Record 5 holds the only call to spinRemainingSpriteMultiplexSlots (0x10FD) [seen], a second entry into the sprite-19 block of the multiplex pass. Its body is shared with multiplexSpriteSlots [seen], which passes through those bytes each time it is called, but nothing on a genuine image calls the entry itself.

Record 17 at 0x459B is also an entry into real code. derailIntoMotherShipWreckCountdown (0x459B) [code] is a misaligned entry into the Mother-Ship's dying countdown, whose first instructions pop the caller's frame out of step. paintReadoutsThenSampleWitnessOrDerail derails into it when TAMPER_GLYPH_SOURCE_CELL 0xA67C [seen] is not 0x7C, and so does the retire arm of loc_43f0 when TAMPER_GLYPH_COPY 0xAB43 [seen] is wrong.

Cells can sit on such a failed arm too. guardBlockOrBlankDisplay folds the copyright-strip code. Only when that fold fails, which never happens on a genuine image, does it read DISPLAY_OFF_VALUE 0x4C89 [code], the ROM zero it writes to VIDEO_ENABLE_LATCH 0xC308 [seen] to blank the picture, and TAMPER_WITNESS_SAMPLE_CELL 0xA65C [code], the copyright-line cell it copies into the witness pair.

Some code is dead for another reason: nothing could ever select it, even on a patched image. The ring handlers already described, loc_0bdc and drawCaptionGlyphsKeepingColour, belong to commands no poster loads. loc_15b5 (0x15B5) [code] is a lone `ret` in slot 15 of the phase-3 sub-step table that dispatchSequenceSubStepArm [seen] indexes. SEQUENCE_SUBSTEP 0xA9AC [seen] reaches 15 only for an instant: arm 14 steps it there and overwrites it with 3 in the same interrupt, so no dispatch ever reads the 15. The debt file records these as dead code rather than anti-tamper.

## §9 What is still open

These are the questions the code and the runs so far leave open. Each says what would close it, where that is known.

### Paths only a patched image runs

The anti-tamper arms below are guarded by checks that pass on the genuine image, so no run of the real ROM reaches them.

- Where does control end after TAMPER_IMAGE_SIGNATURE's mismatch transfer (`jp nz,0x2530` at 0x2735) lands in the 281-peak velocity table and runs it as code? A run with a patched signature, tracing the program counter after 0x2530, would settle it.
- What exactly does the acting arm of checkTamperGlyphCopyElseRunAwardLabelStep do to the slot it stamps and the counter it touches? On every genuine two-player start both witness cells hold 0x7C, so it returns without acting.

### How things look on the glass

- Where on the glass does the wrapped pass of a scenery object show up, and which colours and flips do the scenery attribute bytes select (0xCC in eras 0–3, 0x28 in era 4)?
- What is the geometry of the sprite doubling: how does the trigger line (the raster counter at 0xC000 reaching 256 minus the hardware Y byte) relate to where the sprite's first appearance is scanned out, which screen direction does the +128 X / −128 Y move go, and which part of the screen do the eight doubled hardware sprites (0–2, 19–23) cover? A frame capture with a single scenery sprite raised would close it.
- Are the ballistic era weapons of era 0 the hand grenades, the homing era weapons of eras 2 and 3 the missiles, and the era weapon of era 4 the bending alien weapon that gameplay.md describes? The motions fit, but no run has matched them to their pictures on the glass.
- What do the four enemy-shot slots and the era-1 bomber's launched object look like in each era?
- What does the formation-bonus wreck look like while driveObjectAppearanceByPhaseBand holds it on screen?
- Do the caption records not yet seen on screen (FREE PLAY, PUSH START BUTTON, ONE PLAYER ONLY, ONE OR TWO PLAYERS, GAME OVER, PLAYER 2 and the two bonus-life pairs) read as decoded?

### Code paths still open

- retireSlotAndSubPixel zeroes the fractions (+3/+5) and retireSlot does not. Does any slot that retireSlot frees get relaunched by a spawner that writes neither fraction, so that the next object starts from the old sub-pixel position? A run that retires such a slot through retireSlot and relaunches it would show whether the next object's first positions carry the old fractions.
- Can an era-4 craft carry bit 7 of +0x0E when it dies? spawnEnemyWaveIntoFreeSlots seats +0x0E = 0. In the traced image, the stores that can leave bit 7 set are at 0x2B5B (releaseHeldObject, 0x80), 0x3C20 (retireObjectAndHold, 0x80), 0x3E01 (a byte from 0xA8F6) and 0x48B9 (0xF0). The descriptor delay that driveEnemyWaveForLifePhase stores at 0x3742 cannot: every delay byte in the eight descriptor rows an era can select (two per era for eras 0-3; era 4 leaves before the table is read) is 0x31 or less. The decrements at 0x2B52, 0x3C2B, 0x418E, 0x453C and 0x485E would set it if they ran on a zero byte. No absolute store targets a craft record's +0x0E. Does any of these reach a live era-4 craft before its kill is counted? If none does, era 4 pays no formation bonus.
- How many frames does one round-engine pass take, and how does that depend on the load each pass carries? The life tick counter, the hit-chain window and the explosion count are all counted in passes. The rate is seen to vary, and this map does not model it; a frame-by-frame capture under different loads would give it.
