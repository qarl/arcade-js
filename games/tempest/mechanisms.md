# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
object-record draw loop, the mathbox projection, sound, and the EAROM — down to the caller routines that
drive them and the computed-jump dispatchers (`loc_b84e`, `loc_b5d7`, `loc_9a88`); the frozen-oracle
remainder (the remaining dispatcher spine and a register-thread caller) is noted at the end. The machine
is a colour vector game: the 6502 builds a display list in AVG vector RAM (`0x2000-0x2FFF`) each frame and
the Analog Vector Generator draws it, with the vblank interrupt as the per-frame heartbeat and a
game-state index driving a computed-jump dispatch that selects the mode handler (attract, coin-in, play,
transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

A cluster of short handlers implements a small per-object bytecode interpreter — a "motion script" that choreographs how a slot's object behaves as it works along the tube. All of these routines are reached only as computed-jump targets: the driver loc_9b1e fetches successive script bytes from the `loc_a0f7` region and vectors each one through the RTS-trick dispatcher loc_9b98, repeating while the walk-continue flag `loc_10a` stays nonzero. The shared instruction pointer for the script is `loc_10b`, the branch/hold gate the conditional opcodes consult and set is `loc_10c`, and the per-object state the opcodes read and mutate lives in the `x`-indexed slot cells (`loc_298,x` for a general slot byte, `loc_2b9,x` for the object's segment/lane, `loc_2df,x` for its depth along that lane).

Two opcodes load an operand into the current object's slot. loc_9bd0 [seen] advances the pointer by one — `loc_10b = (loc_10b + 1) & 0xff` — and copies the script byte it now selects, `loc_a0f7[loc_10b]`, straight into `loc_298,x`; the immediate-load form. Its sibling loc_9bdd [seen] performs the same pointer bump but treats the selected script byte as a zero-page address: it reads the live variable at `loc_00 + ptr` and stores THAT into `loc_298,x`, an indirect load of a running value rather than a constant. Both were observed advancing the pointer and writing the low object slots (the captured writes landed in the `0x29b`–`0x29e` group), confirming several slots are driven this way.

Three opcodes give the script its control flow, all keyed on the gate `loc_10c`. loc_9bee [seen] is a conditional skip: when `loc_10c` is nonzero it does nothing, and otherwise it steps the pointer forward by two, jumping over a two-byte operand. loc_9bfa [seen] is a conditional goto: it first bumps `loc_10b` by one, then — only while `loc_10c` is zero — reloads the pointer from `loc_a0f7[loc_10b]`, i.e. jumps to the operand target; a nonzero gate lets it fall straight through. loc_9c17 [seen], heavily exercised, is the unconditional goto: it uses the current pointer as an index into `loc_a0f8` (the byte immediately following the current position, since `loc_a0f8 = loc_a0f7 + 1`) and writes that value back as the new `loc_10b`. loc_9bca [seen], reached on essentially every walk, is the terminator: it clears `loc_10a` to zero, ending the driver loc_9b1e's inner loop over the script for this pass.

loc_9c0c [seen] is the timer opcode and the one place a slot cell is used as a countdown rather than as loaded state. It decrements the slot's timer at `loc_298 + x`; while that byte remains nonzero it tail-delegates to loc_9c17 to take the table-driven goto step, and only when the timer reaches zero does it instead bump the shared counter `loc_10b` by one, letting the script move past the wait.

The two TEST opcodes set the gate `loc_10c` but were not reached in the capture, so both carry the [code] tag. loc_9c21 [code] compares the object against its lane geometry: it reads the slot's segment from `loc_2b9,x`, looks up that segment's boundary in `loc_3ac[segment]` (a zero entry is read as `0xff`, the maximum), and writes `loc_10c = 1` when that boundary is at or beyond the slot's depth `loc_2df,x`, else `0` — a position-versus-boundary test consistent with an object reaching the end of its lane, though its store to `loc_10c` at `0x9c3a` is absent from the trace (the gate was produced elsewhere in the captured window). loc_9c3b [code] derives the gate from the phase accumulator pair instead, computing `loc_10c = ((((loc_147 << 2) + loc_148) & loc_148 & 0x80) ^ 0x80)`, all wrapping to a byte, so the result is `0x00` when that combined high bit is set and `0x80` when it is clear; `loc_148` is the signed phase value the driver's tail advances by `loc_147`. It too was not reached in the capture.

Finally, loc_96c7 [code] is a register-only cursor skip used to step over a packed record in a list without reading it. Entered at `loc_96c7` it advances the list cursor `Y` by one and delegates to its inner entry `loc_96c8`, which adds a further two, for a net skip of three; entered directly at `loc_96c8` the skip is two. It owns no memory writes — there is nothing to observe, hence [code] — and it is reached only through the `loc_969d` computed-dispatch table off loc_9683.

## Vector coordinate lists and the display cursor

Tempest draws its tube, ships, enemies and text as a list of vector words that the AVG hardware sweeps out of RAM at 0x2000 and up. Two machines meet in this subsystem: on the read side a *coordinate list* — a packed table of bytes reached through the zero-page indirect pointer loc_2c/loc_2d — that the walkers step through to recover successive coordinates, and on the write side the *display-list cursor* loc_74/loc_75 that the emitters push finished vector words into. The setup family points the reader at the right table; the walkers turn packed deltas back into positions; the emitters lay the words down and advance the cursor.

### Selecting a coordinate list to read

Before anything can walk a list, its pointer pair must be planted in loc_2c (low) / loc_2d (high), with the chosen table index remembered in loc_2b and the working value reloaded into loc_29. loc_9aee [seen] is the base of that setup: indexed by Y it copies the low byte from the ROM table loc_9b02+Y into loc_2c and the high byte from loc_9afd+Y into loc_2d, writes Y through to loc_2b as the selected index, and returns with A reloaded from loc_29 (the write-tap catches all three stores, e.g. loc_2d taking 0x07 and loc_2b changing). Sitting one entry later, loc_9af1 [seen] is the same tail but entered with the low pointer already in A from the caller, so it skips the loc_9b02 lookup, stores A straight into loc_2c, still takes the high byte from loc_9afd+Y, stashes Y in loc_2b and reloads A from loc_29 — the variant used when the caller has already computed a low pointer rather than picking one from the fixed table.

The choice among the several setup flavours is made by loc_9a88 [seen], a computed-jump dispatcher that takes an incoming index in A and runs one of five list-setup entries — for A = 0..4 they are loc_9a9d, loc_9aa9, loc_9abb, loc_9ab7, loc_9ab3 (loc_9abb belongs to a neighbouring subsystem). It performs no memory write of its own; only A = 0 is exercised in the capture, so the other four arms are reached only through it. loc_9a9d [code] is that A = 0 arm: it seeds the pointer pair for a fixed list, taking the low byte from the first table slot loc_9b02, forcing the index loc_2b to zero, taking the high byte not from loc_9afd but from the held source cell loc_15d, and reloading A from loc_29; its stores do fire in the capture but hold constant values, so the role rests on the code rather than on an observed change. The remaining arms are code-only. loc_9aa9 [code] (A = 1) folds two held bytes together — loc_9b03 OR loc_16d — into the low-pointer value and then runs the loc_9af1 setup preset at index 1; loc_9ab7 [code] (A = 3) and loc_9ab3 [code] (A = 4) simply preset the index (3 and 4 respectively) and run the loc_9aee setup. None of loc_9aa9, loc_9ab7, loc_9ab3 is reached in the capture.

### Walking the packed coordinate list

Once loc_2c/loc_2d points at a list, several helpers step through it, each recovering a value and a fresh cursor position. loc_96cb [seen] reads two adjacent entries — the byte at the cursor list[ptr+Y] and its predecessor list[ptr+(Y-1)] — stores their difference (an inter-entry step observed running 0x01..0x0f) into the delta cell loc_29, and returns the cursor advanced by that delta: it computes A = Y + delta and hands back Y = A + 2, so the list pointer moves forward by delta + 2 for the next entry. loc_96db [code] resolves a single list entry to an absolute coordinate: it reads list[ptr+Y] and adds the base value in loc_160, returning the sum in A masked to a byte. It writes nothing, so its reach through the computed-jump table that targets it cannot be confirmed from the write-tap, and it stays [code].

loc_96ab [seen] is the coordinate helper the display generator consumes. It first stashes the incoming cursor Y into loc_29, then forms a value from the delta two entries back: A = A - list[ptr+(Y-2)], A = A + loc_29 (adding the saved Y), and finally re-indexes, returning the entry list[ptr+A] with Y = A so the caller resumes at the new position. Its front loc_96ab feeds A = ((loc_2b - 1) & 0x0f) + 1 (a counter-derived value wrapped into 1..0x10), while the sibling entries feed the raw index loc_2b (loc_96b7) or simply return list[ptr+Y] with no arithmetic (loc_96c4). The only own write in this body is the loc_29 scratch, which the tap catches, grounding it as a reached compute helper whose output the vector-coordinate generator downstream consumes.

Two arithmetic helpers over the same list are code-only. loc_96f4 [code] records the cursor Y into loc_29 and returns (loc_2b - list[ptr+(Y-2)]) & 0xff — the running index in loc_2b minus a table byte two slots back — the same subtraction loc_96ab performs, delivered here as a bare count. loc_96e2 [code] uses it as a repeat count: it calls loc_96f4 to get the count, loads the first entry list[ptr+Y] as the running sum, steps Y once, and then folds that many additional copies of the next entry into a one-byte total. Both were auto-derived from own-cell changes; the roles above are re-derived from the code and neither is confirmed reached, so both stay [code].

### The display-list cursor and the emitters

Everything written toward the vector display list moves through loc_74/loc_75, the little-endian 16-bit write cursor into vector RAM at 0x2000. loc_df5f [seen] is the shared advance: it adds Y + 1 to loc_74 (the carry is forced set before the add, so the true stride is the argument plus one) and carries into loc_75 on overflow. It is exercised on essentially every emit — the tap shows loc_74 pulsing across the full byte range and loc_75 stepping through the 0x22..0x2a page window as the cursor sweeps the display list.

The lowest emitters lay down raw vector words. loc_df57 stores the pair {A, X} at the cursor's first two bytes (offset 0 and 1) and then advances by two via loc_df5f — the shared vector-word tail. loc_df53 [seen] rides that tail with a fixed load, emitting the {0x40, 0x80} header word at the cursor (the tap sees the 0x40/0x80 store pair land in vector RAM). loc_df59 [seen] is the general form: it stores {A, X} at the cursor offsets Y and Y+1 and advances the cursor past them, and is the core emit that lays real vector data — coordinate and opcode bytes across the whole 0x2000 page — into the list.

A second pair of emitters pull their word from the ROM table loc_31e4 by a nibble-derived index. loc_df19 [seen] takes the low nibble of A and forms the index — 0 when the carry is set and that nibble is zero, otherwise nibble + 1 — doubles it, and copies the two bytes of loc_31e4[index] into the cursor, then advances two. loc_df1f [seen] is a thinner front that always forms the index as (A & 0x0f) + 1 and shares loc_df19's copy-and-advance tail; its own arm is pure computation and leaves no write of its own, grounded [seen] as an index helper reached through that shared emit.

The record-style emitters build a header-plus-body entry. loc_df0d [code] emits the {0x40, 0x80} header via loc_df53 and then stores a fixed body byte 0x20 at the cursor origin through loc_df12 before continuing into the shared record tail; it is not reached in the capture. loc_df12 [code] is that body-byte entry on its own — it stores its input byte at the cursor origin and continues the record tail; it is reached through a neighbouring path that presets the byte, but the value observed holds constant, so the role rests on the code.

Two higher-level producers assemble complete objects. loc_aef8 [seen] emits text: it walks character codes from the 0x0606 message buffer (indexed by loc_38, which counts down from the incoming value plus two, with loc_39 counting three passes), replaces any code 0x1e or above with 0x1a (an out-of-range guard, leaving codes 0x00–0x1d unchanged), doubles it to index the glyph word table loc_31fa, and copies each glyph's two-byte word into the cursor — the glyph high byte carrying the vector-draw opcode — advancing the cursor past the three words written. loc_c772 [seen] emits an object's position: entered with the cursor offset at zero, it lays a fixed {0x40, 0x80} header, then two absolute coordinate words drawn from two zero-page pairs indexed by X — the X coordinate from the loc_2/loc_3 pair and the Y coordinate from the loc_00/loc_1 pair, each high byte masked to its low five bits — while caching the four raw bytes into loc_6a..loc_6d as the "previous point" that later stroke code subtracts against, then advances the cursor past the six emitted bytes. It is heavily exercised as a producer into the vector list.

## Draw-pointer setup and vector emission

Tempest paints the screen by filling a vector display list in the AVG RAM at 0x2000-0x2FFF, then handing that list to the vector generator. This subsystem is the machinery that decides *where* the list is written (the draw pointers) and *what bytes* go into it (the vector-word emitters). Almost everything here revolves around one shared 16-bit write cursor kept in the zero-page pair loc_74/loc_75, a running byte offset in loc_a9, and a family of small routines that append two- and four-byte vector words and then step the cursor forward.

### The per-frame frame builder

loc_b230 ([seen]) is the top of the whole display pass: it draws one complete frame. It walks the render subsystems in a fixed order, and around each one it runs a setup/teardown pair keyed to that subsystem's layer id — loc_b2be with the layer id to arm the draw pointer, the subsystem body, then loc_b2fe to close it out. The order is layer 0x07 (loc_b586), 0x04 (loc_b75b), 0x03 (loc_b5ad), 0x06 (loc_b79a), 0x05 (loc_b498), 0x00 (loc_a8b4), then 0x01 (loc_c5c2) and 0x08 (loc_c54d); loc_b367 runs just after the layer-0x00 teardown, outside its brackets. Inside the layer-0x00 brackets, and only when loc_5's sign bit is clear, it sums a 0x28-byte block: the pointer is taken from loc_b6/loc_b7, the accumulator is seeded with 0xf2, and bytes at offsets 0x27 down to 0 are added with a carry chain, the final total landing in loc_11b (a running checksum/status cell, not a coordinate). Having drawn every layer, it clears the change counter loc_114 and then latches the two ROM header constants into the very front of the display list, copying loc_cec2 into loc_2000 and loc_cec3 into loc_2001 — the list-header words the vector generator reads first, refreshed every frame.

### Arming the draw pointer

loc_b2be ([seen]) is the setup half of each subsystem bracket. From the incoming index it forms a two-byte stride 2*index and picks a 16-bit pointer out of one of two ROM tables: table loc_ce68 when the per-index flag loc_415+index is nonzero, otherwise table loc_ce7a. It publishes the low byte into loc_74 and the high byte into loc_75 — the shared write cursor — and clears the byte-offset cell loc_a9 so the next emitter starts at the head of that layer's slice.

loc_b2de ([seen]) is the same idea aimed at a *different* cursor pair, loc_3b/loc_3c, and with the table selection reversed: nonzero loc_415+index chooses loc_ce7a, zero chooses loc_ce68. It too clears loc_a9. loc_91b5 ([seen]) sets up yet another working pointer, loc_2a/loc_2b: it doubles its selector into a word index, clears the paired flag byte loc_29, and copies the little-endian pointer from the in-ROM table at loc_91c6/loc_91c7 into loc_2a/loc_2b.

loc_b332 ([seen]) is a guarded link-record emitter used to keep the list coherent across frame changes. If the source byte loc_cec4 differs from the checkpoint stored at loc_2000, it latches the new value into loc_2000 and reports "changed" (carry set) so the caller can restart. Otherwise it clears loc_16e, copies a two-byte word from loc_ce9e (at slot 0x08 when loc_415 is nonzero, else slot 0x02) out through the loc_74/loc_75 cursor, and then reloads that cursor from the matching loc_ce68 entry, chaining the write pointer to the next record.

Two more pointer utilities belong to the object-draw loop loc_b8ba, which was not reached in this capture, so both read [code]: loc_b944 ([code]) swaps the pointer pair loc_74/loc_75 with loc_76/loc_77 (retargeting the shared cursor at the other structure), and loc_b967 ([code]) selects one of two ROM pointer-table entries by the RAM flag loc_415 — returning (loc_ce87, loc_ce86) when the flag is zero and (loc_ce6f, loc_ce6e) when it is nonzero. The flag loc_415 itself is exercised elsewhere, but neither of these bodies ran.

### The dispatch group at loc_b84e

loc_b84e ([code]) is a computed-jump dispatcher: the caller passes a byte offset (0, 2, 4, or 6), and loc_b84e halves it to select one of four draw targets — loc_b85f, loc_b875, loc_b888, or loc_b896 — and tail-returns that target's result. It has no writes of its own; it only routes. Its target loc_b896 ([code]) is the vector-RAM tail record: it stores the 16-bit cursor loc_139 (low, raw) and loc_13a (high, ORed with 0x70) into the list tail at loc_2ffc/loc_2ffd, drops the terminator 0xc0 into loc_2fff, then steps the cursor down by 0x20 with a 16-bit borrow (decrementing loc_13a only when the low subtraction underflows) and masks loc_139 to 0x7f. loc_b896 is reached only through loc_b84e; it was not exercised in this capture.

### The shared cursor emitters

At the bottom of nearly every emit path is a tiny set of primitives that write through the loc_74/loc_75 cursor and then advance it. loc_df57 (helper) stores a two-byte word — first byte, then second byte — at the cursor origin and steps forward by one word. loc_df59 ([seen] as the core pair emitter) stores a {A, X} pair at cursor offsets Y and Y+1. Both finish through loc_df5f, which advances the little-endian cursor loc_74/loc_75 by its stride argument plus one, carrying into loc_75 on overflow. loc_b56a ([seen]) is the four-byte variant: it writes 0, 0, 0, A at the cursor and bumps loc_74 by four (carrying into loc_75) — the plain "append one entry" call.

Several one-liner fronts feed loc_df57 with fixed or tagged bytes. loc_ab0d ([code]) emits the fixed pair {0x20, 0x80}. loc_df4c ([code]) emits {Y, A|0x60} and loc_df6c ([code]) emits {Y, A|0x70} — the 0x60/0x70 being vector-opcode header bits forced into the second byte. loc_df4a ([code], not reached in the capture) emits {loc_73, A|0x60} (the table byte loc_73 as the first byte), and loc_df6a ([code]) emits {0x00, A|0x70}. loc_df09 ([code]) stores the fixed body byte 0xc0 at the cursor origin (via loc_df12) and runs the shared record tail. loc_df39 ([code]) builds a coordinate word: the high byte is the input's upper bits ((A>>1)&0x0f) ORed with the 0xa0 opcode tag, the low byte is A's bit0 rotated up to bit7 combined with X>>1; it writes the high byte at offset 1 and the low byte at offset 0, then advances (or, on wrap, falls through to loc_df4c with loc_73).

### Scaled-coordinate records

loc_df92 ([seen]) emits a four-byte coordinate record from four zero-page slots addressed off an index: byte 0 from loc_2+x, byte 1 from loc_3+x masked to five bits, byte 2 from loc_0+x, and a fourth "last" byte that is key-folded — ((loc_1+x XOR loc_73) & 0x1f) XOR loc_73, where loc_73 is the fold key — before the shared tail (loc_dfac) writes it and advances. loc_df75 ([seen]) is the usual front for it: it widens two input bytes by four with sign extension (low = value<<2, high = sign-fill combined with value's top bit) into the adjacent pairs loc_6e/loc_6f and loc_70/loc_71, then emits the record they anchor. loc_df73 ([code]) simply stashes its index byte into the fold key loc_73 first, then defers to loc_df75.

loc_d8a9 ([code]) stashes A into loc_29, scales its Y/X coordinates through loc_df75, then emits loc_29 as a single-byte nibble run. loc_dd2b ([code]) scales its A/X coordinates through loc_df75, then shifts the byte in loc_35 out MSB-first across eight passes (loc_37 counting 0x07 down through 0), emitting one vector digit per bit. Its fixed-operand fronts loc_dd29 ([code]) and loc_dd27 ([code]) preset the coordinate operands, not the bit source: loc_dd27 calls loc_dd29 with 0xd0, which calls loc_dd2b with 0xd0 and 0xf8 — so 0xd0 and 0xf8 are the two coordinate deltas that get scaled by four into loc_6e-loc_71, while the eight emitted bit-digits come from the caller's live-in value in loc_35.

loc_dd41 ([code]) is a binary-to-BCD digit renderer. It first forms a packed-decimal sum: it doubles the little-endian pair loc_40f/loc_410 (carrying the high bit) and adds loc_40c/loc_40d, writing the operands to the math-box registers loc_6095/loc_6096 and forcing the result to a minimum of one if it comes out zero; it seeds loc_608d from loc_409 and runs a divide (loc_dce6) whose quotient and remainder land in loc_412/loc_413. Then, across five passes (loc_37 counting 0x04 down through 0), it loads three source bytes into loc_56/loc_57/loc_58 from the pointer loc_3b/loc_3c and runs a double-dabble: 0x17 shift rounds that roll the three bytes left one bit at a time while conditionally decimal-adjusting the four accumulator digits at loc_31..loc_31+3. Each pass then emits the converted four-digit run through loc_dfb1 and appends a scaled record through loc_df75 (0xd0, 0xf8). It is a true double-dabble decimal conversion, not a bit-run.

### The math-box normalized appender and its callers

loc_bd3e ([seen]) appends a (mantissa, exponent) pair to the list. For a small input (loc_57 below 0x10) it uses the trivial pair (A=1, Y=0). Otherwise it drives the math coprocessor: it forms the 16-bit difference loc_57-loc_5f/loc_5b into the operand registers loc_6095/loc_6096, issues the compute through loc_608c/loc_608e/loc_6094, spins until loc_6040's bit 7 clears, reads the result out of loc_6060/loc_6070 into loc_79/loc_7a, then normalizes loc_79 by rotating left until a 1 rolls out of the top — the rotate count becomes the mantissa-shift written to loc_78 and the derived value becomes the exponent. It writes the pair through the cursor and returns its exit offset (loc_a9 + 2), which the callers thread into their own following stores.

Four routines drive that appender. loc_b69b ([code]) builds a screen position for a slot: it loads the slot coordinate loc_2df+x and the segment-indexed base pair loc_3ce/loc_3de, and when the phase byte loc_2cc+x is negative it interpolates the pair toward the next segment (index+1 & 0x0f) by scaling the delta through the fraction helper loc_b6fa. It folds the live deltas (loc_c098), lays the fixed header (loc_c765 at offset 0x61), zeroes loc_a9, appends the pair via loc_bd3e, then reloads the entry template from the word table loc_cec8/loc_cec9 (indexed by the frame's low bits) and emits through loc_df59. loc_bd09 ([seen]) is the same folding-and-appending shape but for a colour/intensity nibble: after loc_bd3e it clamps loc_78 XOR 0x07 (shifted, floored at 0x0a) into the high nibble of a byte, writes that byte and a 0x60 tag at the threaded cursor, reloads the template from loc_cec8/loc_cec9 by loc_55, and tails into loc_df59. loc_bcfd ([seen]) is its front: it stashes the value byte into loc_55, seats two indexed entries loc_435+y/loc_445+y into loc_56/loc_58, then calls loc_bd09. loc_c6c7 ([seen]) emits an enemy slot's entry: for an inactive slot (loc_3ac+x zero) it writes four blank+0x71 pairs; for an active slot it seats the scratch inputs, runs the clamp (loc_c453), the math-box delta (loc_c098), and the delta emit (loc_c73c), then either appends a randomized table word (chosen by loc_60ca's bit 1 into loc_cec8/loc_cec9, after driving loc_bd3e) or a fixed marker word ending in loc_3db2/loc_3db3, advancing loc_a9 in each case.

loc_b60f ([code]), loc_b622 ([code]) and loc_b69b are the shape-emit handlers reached through the spine computed-jump dispatcher loc_b5d7 (which selects a handler by A>>1); none of them reads Y. loc_b60f picks a jump-mode byte from loc_b61e by the slot's low two mode bits (loc_28a+x & 0x03) — loc_28a being the slot's flag/arm byte, not a coordinate — pairs it with the slot target loc_2b9+x, and passes both to loc_bcfd. loc_b622 picks the slot's table index loc_2b9+x, adds a four-phase animation offset ((loc_3 & 0x03)<<1)+0x12, and hands the pair to loc_bcfd. loc_b75b ([seen]) walks twelve slots high-to-low (loc_37 from 0x0b down, ending on wrap): for each non-empty loc_2d3+x it seats loc_57/loc_2f, reads loc_2ad+x, and computes a value that differs for near versus far slots (a phase-derived value for x>=0x08, the constant 0x08 otherwise) before calling loc_bcfd; when the walk finishes it latches a level byte into loc_808 chosen by the stage value loc_135 (0x04 below stage 6, 0x0b below 8, else 0x0c).

### Delta records and midpoints

loc_c3ba ([seen]) computes two 16-bit differences (current minus previous) from the loc_61/loc_62 and loc_63/loc_64 pairs against loc_6a/loc_6b and loc_6c/loc_6d, stores them into loc_6e-loc_71, emits the record through loc_df92, then latches current back into previous and sets the ready flag loc_73 to 0xc0. loc_c423 ([seen]) is its front for object slots: it reads the slot index loc_37 and snapshots four indexed table cells (loc_32a/loc_31a/loc_34a/loc_33a) into loc_61-loc_64 before emitting. loc_c73c ([seen]) emits two 16-bit differences directly through the cursor at loc_a9: the first is loc_63:loc_64 minus loc_6c:loc_6d (high byte masked to five bits) and the second is loc_61:loc_62 minus loc_6a:loc_6b (high byte masked to five bits and ORed with the 0xa0 opcode tag), advancing the offset by four. loc_c66d ([seen]) forms tube midpoints: it round-up averages slot loc_38's two coordinate pairs (loc_36a/loc_35a and loc_38a/loc_37a) with its wrap-around neighbour (loc_38+1 & 0x0f), stores the two midpoints into loc_61/loc_62 and loc_63/loc_64, appends the four midpoint bytes through the loc_74 pointer at offset loc_a9 (high bytes masked to 0x1f), and mirrors all four into loc_6a-loc_6d.

## Enemy spawning and lane selection

This subsystem decides which tube lane a new enemy is born into, allocates it a slot in the per-enemy parallel arrays, seeds the random tags that colour a wave, steps enemies around the rim and down the well toward their target segment, and runs the separate eight-slot "timed object" table through which spawns, hits and retirements are staged. Two coordinates recur throughout: a slot's **segment** around the rim (`loc_2b9`,x plus its successor `loc_2cc`,x, both kept mod-16) and its **depth** down the tube (`loc_2df`,x, large = far end, small = at the rim). A slot's flag/arm byte is `loc_283`,x (bit7 = live, bit6 = a per-slot toggle, low three bits = a segment sub-index) with a second flag byte `loc_28a`,x (bit6 = armed, bit7 = sign); neither is a coordinate.

**Slot allocation.** `loc_994d` [seen] is the core allocator. It saves the caller's Y into `loc_36`, then scans the depth table `loc_2df` downward from the index in `loc_11c`, decrementing until it finds an entry reading zero (a free slot); if the index walks past zero (goes negative, i.e. bit7 set) it reports 0x00 for "no slot free". On a hit it seeds the slot's parallel fields: the depth `loc_2df`,y is written from the scratch seed `loc_29` (observed entering deep, e.g. 0xf0, at the far end of the tube), and the segment `loc_2b9`,y is taken from `loc_2a` — except that when `loc_2a` reads 0x0f and the global gate `loc_111` has bit7 set, the segment is instead drawn from POKEY random `loc_60ca & 0x0e` (a random even segment). The successor `loc_2cc`,y is that segment plus one mod-16, the timer `loc_2a6`,y is cleared, the flag/arm byte `loc_28a`,y is seeded from `loc_2c` and its high companion `loc_291`,y from `loc_2d`, the active count `loc_108` is bumped, and the flag byte `loc_283`,y is seeded from `loc_2b`. **Per-wave random tagging.** `loc_9246` [seen] reseeds the wave's randomised slot tags. ## Enemy motion and the pursuit AI

Tempest's enemies live in a bank of parallel per-slot arrays indexed by a slot number: `loc_2df` holds each slot's depth along the tube (how far it has climbed toward the near rim, with 0 marking an empty slot), `loc_2b9` its lane/segment around the rim, `loc_2cc` a phase/animation counter, and `loc_283` a packed control byte whose low three bits name the slot's kind/state, bit 6 records which rotational way it travels, and bit 7 marks it live. A second flag byte `loc_28a` carries a separate arm bit (bit 6) and sign bit (bit 7) — it is a flag byte, not a coordinate. The routines below move those slots up the tube, walk them around the rim toward the player, and steer the blaster (both under manual control and under the attract-mode auto-aim).

### The shared "which way around the rim" primitive

Every pursuit decision rests on `loc_a7a6` [seen], which computes a signed rim distance: it forms `A - Y` and stashes it at `loc_2a`, then, when the level flag `loc_111`'s bit 7 is set, returns the full signed byte, otherwise masks to the low four bits and sign-extends bit 3 into a small signed nibble. That nibble is the difference in lane count between two segments folded onto the ring, so its sign tells a caller which direction is shorter. It is exercised on essentially every pursuit pass.

Two routines turn that difference into the travel-direction bit of a slot. `loc_9d67` [code] reads slot x's segment `loc_2b9,x`, diffs it against the shared player/reference segment `loc_200` through `loc_a7a6`, and then records the answer in bit 6 of the slot's control byte `loc_283,x` — clearing bit 6 when the difference is negative (top bit set) and setting it otherwise, i.e. stamping which rotational side the target lies on so the slot walks that way. `loc_9c4f` [seen] simply toggles that same bit 6 of `loc_283,x` in place (`^0x40`) and returns the new byte; its bit-6 flip is observed changing in the capture, which is why it grounds as [seen]. Together they let a walking enemy re-aim (`loc_9d67`) and reverse (`loc_9c4f`) as it chases the blaster.

### Flippers walking and reversing around the rim

The flip step has three co-entries sharing one tail. `loc_9f81` [code] re-derives the slot's side bit through `loc_9d67`, toggles it with `loc_9c4f`, then falls into the shared tail; `loc_9f8a` instead reseeds bit 6 of `loc_283,x` from a fresh POKEY-random bit (`loc_60ca` bit 6) — a randomized rather than aimed heading — before the same tail. The shared tail (beginning at `loc_9f99`) runs only while the board is live (`loc_111 != 0`): it flips bit 6 of `loc_283,x` when the slot's segment `loc_2b9,x` hits a rim extreme — reaching 0 while bit 6 is set, or reaching 0x0f while it is clear — so a flipper reverses direction at the ends of the lane range; it then reseeds the motion-script pointer `loc_10b = 0x66` and hands to the shared per-slot segment-step body `loc_9e5f`.

Which of those two entries runs is chosen by the fire gate `loc_9f5f` [code], a per-slot arming test: it returns immediately unless the slot's fire bit — bit 5 (`0x20`) of `loc_2df,x` — is set AND a fresh POKEY-random draw `loc_60da` is at least the threshold `loc_15f`; only then does it dispatch, picking `loc_9f8a` when the target flag `loc_159` bit 6 is clear or the slot index is even, and `loc_9f81` (the aimed rim-walk step) for odd slots. `loc_9f5f` itself writes nothing of its own and is not reached in the capture.

`loc_9d82` [seen] drives the turn animation between lanes. It first steps the phase counter `loc_2cc,x` one increment — down when `loc_283,x` bit 6 is set, up otherwise — keeps its low nibble and forces bit 7. If the slot's state (low three bits of `loc_283,x`) is not 4 it re-derives the target ring direction through the lookup `loc_9ed7` (fed `loc_283,x ^ 0x40` and the segment `loc_2b9,x`) and acts only when that direction equals the current phase: it drops bit 7 of the control byte and steps the lane by one — advancing `loc_2b9,x` when bit 6 is set, or copying the old segment into `loc_2cc,x` and decrementing `loc_2b9,x` otherwise. If the state IS 4 (a settling turn) and the phase has reached a step boundary (low three bits zero), it rotates the segment when phase bit 3 is set, clears bit 7, reseeds `loc_2cc,x = 0x20`, toggles bit 7 of the arm byte `loc_28a,x`, and — while `loc_3ab` is zero — either kicks the next flip step via `loc_9f81` when the slot's depth `loc_2df,x` has reached the shared target `loc_202`, or else isolates the sign bit of `loc_28a,x` (`&0x80`). Every exit publishes the control byte's bit 7 into the shared branch flag `loc_10c`.

`loc_9d06` [seen] is the per-slot settle/step invoked when a slot's tube-depth reaches the shared target `loc_202`. It stashes that shared byte into `loc_2df,x`, then branches on the slot's kind: a kind-1 slot with the gate `loc_3ab` nonzero merely flips bit 7 of its arm byte `loc_28a,x` and stops; a slot flagged negative in `loc_283,x` just bumps its stashed depth by one and stops. Otherwise it decrements `loc_108`, and when `loc_109 == 1` it scans slots 6..0 for a non-empty, non-self entry whose stashed depth matches the shared one and copies that neighbour's bit 6 (inverted) into `loc_283,x` (the loser index leaks through when none matches) — a cross-slot direction handoff; when `loc_109` is anything else it re-aims through `loc_9d67`. It closes by setting the script pointer `loc_10b = 0x41` and incrementing `loc_109`.

### Steering the blaster and the attract auto-aim

`loc_97c5` [seen] is the auto-aim scan: it walks the depth table `loc_2df` from index `loc_11c` down through 0, keeping the smallest nonzero depth in `loc_29` and its slot index in `loc_2a` (the nearest climbing enemy). `loc_9749` (no grounding-tag line is on record for this routine; role read from code; it executes as the tail of the [seen], reached routines below) is the rim-rotation update. ### Free-flying enemy physics

The free-motion enemies (as opposed to lane-locked flippers) carry three independent motion axes, each a velocity-low / velocity-whole / coordinate-fraction / coordinate-whole quartet. `loc_a6a9` [code] integrates all three for slot x: per axis it adds the velocity-low (`loc_2e3` / `loc_2c3` / `loc_303,x`) into the coordinate fraction (`loc_223` / `loc_203` / `loc_243,x`, keeping carry), then folds that carry plus the sign-tested velocity-whole (`loc_343` / `loc_323` / `loc_363,x`) into the whole coordinate, wrapping it back inside the tube ring — a rising axis (velocity-whole non-negative) resets when the whole reaches `0xf0`, a falling one (negative) when it drops below `0x10`. Axis 0's whole lands in the shared cell `loc_283,x` only at the very end, and is forced to 0 if axis 1 or axis 2 overflowed; axis 1's whole goes to `loc_263,x` and axis 2's to `loc_2a3,x`.

Velocities decay toward rest. `loc_a75d` [code] steps one signed 16-bit velocity a fixed increment `loc_a788` (`0x20`) toward zero — adding when the whole (Y) is negative, subtracting otherwise — and on crossing zero snaps low (`loc_2a`) and whole to 0 and bumps the saturation counter `loc_29`; it makes no own write and is not reached in the capture. `loc_a721` [code] drives that for one slot's three axes: it seeds `loc_29 = 0xfd`, steps each axis pair (`loc_2c3/loc_323`, `loc_2e3/loc_343`, `loc_303/loc_363,x`) back into place, and only when all three saturated (the counter climbs `0xfd → 0x00`) zeroes the slot's whole coordinate `loc_283,x`.

## The per-slot object-record draw loop

This subsystem turns the game's per-slot object records into entries in the vector display list. Two paths coexist. One is a dedicated slot sweep, `loc_b8ba`, that walks a fixed bank of object slots from the top down and emits a record for each live one. The other is a family of record builders — `loc_ab3b` and its two setup fronts `loc_ab14` and `loc_ab17` — that are driven instead by the per-frame frame-draw chain (`loc_a8b4`/`loc_a8e7` → `loc_aaa8`) and the mode-selecting prep entries `loc_aa62`/`loc_aa69`/`loc_aa6f`/`loc_aa79`/`loc_aa5a`. In the capture the frame-draw path is the one that ran: `loc_ab14`, `loc_ab17`, `loc_ab3b`, `loc_aaa8`, `loc_a8b4`, and `loc_a8e7` are all [seen], while the dedicated `loc_b8ba` sweep and the mode-prep entries never executed and remain [code], read from the source and not observed.

### The dedicated slot sweep

`loc_b8ba` [code], not reached in the capture, is the per-slot object-record draw loop proper. It opens by emitting a framing vector word and clearing its working state: the four accumulator bytes loc_6a/loc_6b/loc_6c/loc_6d go to zero, as do loc_202, loc_68 and loc_69, while loc_5f is seeded to 0xe0 and loc_5b to 0xff. It then caches a base draw-struct pointer pair by asking `loc_b967` for one of two ROM pointer-table entries selected by the RAM flag loc_415 — flag clear yields the pair at loc_ce86/loc_ce87, flag set the pair at loc_ce6e/loc_ce6f — and stores the returned high byte into loc_77 and low byte into loc_76.

The slot counter loc_37 is loaded with 0x0f and the loop runs downward. On each pass it reads the slot's control byte from loc_283 indexed by loc_37; a zero there means the slot is inactive and the body is skipped. For a live slot it caches that control byte into loc_57 and pulls the slot's two companion attributes from loc_263 and loc_2a3 (same index) into loc_56 and loc_58. It then integrates the slot's deltas through `loc_c098`, clears loc_73, and performs a pointer-pair exchange via `loc_b944` (which swaps the 16-bit cursor loc_74/loc_75 with loc_76/loc_77) so that the following emitters write against the alternate buffer; after `loc_c3ba` and `loc_b56a` run it swaps the pair back with a second `loc_b944`. It emits the slot's record body through `loc_c772`, then takes the constant pair A=0x02, Y=0x00 from the register leaf `loc_b955` and emits it with `loc_df6c`. A per-slot phase is computed as loc_37 & 0x07, with the value 0x07 folded down to 0x00; that phase is latched into loc_9e and emitted as a tagged record by `loc_df4c` (which lays the raw phase byte first, followed by the fixed 0x08 payload OR'd with the 0x60 header, i.e. 0x68), and `loc_df4a` closes it. A fresh `loc_b967` selection is then emitted as a header word. The counter is decremented with 8-bit wraparound and the loop terminates when the decrement underflows below zero (the result's bit 7 becomes set) — so the sweep covers slots 0x0f down through 0x00. After the loop it swaps pointers a final time, emits a closing word via `loc_df6a`, runs `loc_df09`, and returns through one last `loc_b944`.

### The shared record builder

`loc_ab3b` [seen] is the core that actually copies an object's outline into the vector buffer. It seeds a per-record header (loc_73 cleared, loc_72 set to 0x01, and that 0x01 emitted through `loc_df6a` as a 0x70-tagged word), then hands loc_2a and loc_2b to `loc_df75`, which widens each of the two values by four with sign extension — low byte `(v << 2) & 0xff`, high byte carrying the sign into the adjacent little-endian pair loc_6e/loc_6f and loc_70/loc_71 — and emits the anchoring vector record. ## Object-record projection and emission helpers

### The tube-segment spread builder (loc_bda0 / loc_bdcb)

## The mathbox: projection and level tables

Tempest draws its perspective tube by feeding coordinate deltas through the cabinet's math coprocessor — a hardware unit that lives behind the register block at loc_6080..loc_6096, signals "busy" through bit 7 of loc_6040, and hands its result back through loc_6060 (low) and loc_6070 (high). Around that coprocessor sits a family of routines that (a) unpack the per-level shape and colour tables out of packed ROM, (b) build the raw per-lane tube geometry, and (c) project that geometry into the signed screen offsets the display list consumes. This section describes that machine.

### The coprocessor driver — loc_c098 `[seen]`

loc_c098 is the projection primitive, and it is heavily exercised: essentially every point that has to be projected passes through it. It first forms a 16-bit delta from the coordinate operands the caller has staged. The low byte is `loc_57 - loc_5f`, stored to loc_6095, and the carry/borrow of that subtraction feeds the high byte `(0 - loc_5b - (1 - borrow)) & 0xff`, stored to loc_6096. If that high byte comes out negative (bit 7 set) the delta is clamped up toward +1 — loc_6096 is forced to 0x00 and loc_6095 to 0x01 — so the routine never presents the coprocessor a negative composite here.

It then computes the two absolute magnitudes it needs. From loc_58 and loc_60 it forms |dx| (writing it to both loc_608e and loc_6094, the coprocessor's magnitude inputs) and records the sign of that subtraction in loc_33 (0xff when loc_58 < loc_60, else 0x00). From loc_56 and loc_5e it forms |dy|, keeping the magnitude in loc_32 and the sign in loc_34. A spin-wait on `loc_6040 & 0x80` then blocks until the coprocessor has finished the first multiply/divide.

Once the coprocessor reports ready, loc_c098 reads the result out of loc_6060/loc_6070 into the pair loc_63:loc_64, re-arms the coprocessor with the dy magnitude out of loc_32 (into loc_608e/loc_6094), and folds a stored offset pair (loc_68:loc_69) into loc_63:loc_64. The direction of that fold is chosen by the dx sign in loc_33: bit 7 set means a 16-bit subtract with negative saturation (on overflow the pair is pinned to loc_63=0x00, loc_64=0x80); bit 7 clear means a 16-bit add with positive saturation (pinned to loc_63=0xff, loc_64=0x7f). A second spin-wait, then the same treatment for the other axis: the fresh coprocessor result lands in loc_61:loc_62, the offset pair loc_66:loc_67 is folded in, and this time the dy sign in loc_34 selects add versus subtract with the identical saturation clamps. The two saturating 16-bit accumulators loc_63:loc_64 and loc_61:loc_62 are the projected point the callers read back.

### Priming the coprocessor — loc_c1c3 `[seen]`

loc_c1c3 is the reset that clears the working state before a projection run. It zeroes a set of zero-page scratch cells (loc_81, loc_91, loc_80, loc_78, loc_90, loc_88) and then clears the coprocessor's input block: loc_6080, loc_6081, loc_6083, loc_6084, loc_6085, loc_6086, loc_6087, loc_6089, loc_608d, loc_608e, loc_608f, loc_6090 all to zero, finishing by writing the control register loc_608c to 0x0f (the function select). Notably it leaves loc_6082, loc_6088, loc_608a and loc_608b untouched — they are not part of the block it resets. It is reached on essentially every pass; the caveat carried from grounding is that every observed transition here was a constant one (0→0, and loc_608c 0xf→0xf), because the target cells already held zero in the capture, so the zeroing is real code but was never seen to actually change a value.

### Unpacking the per-level nibble tables — loc_c196 `[seen]`

loc_c196 turns one packed ROM run into the current level's four small nibble tables. It takes the level/geometry selector loc_9f, masks it to `& 0x70`, clamps that to at most 0x5f, and forms the ROM index `x = (sel >> 1) | 0x07`. Walking `y` from 7 down to 0, it reads the packed byte at loc_c1fd+x and splits it: the low nibble goes to both loc_19+y (zero-page) and loc_800+y (the colour-RAM mirror), and the high nibble goes to both loc_21+y and loc_808+y. Each pass steps `x` down one, so eight packed bytes fill four eight-entry tables in a single sweep. This is the routine that installs a level's shape/colour nibbles into the working tables and their display mirror.

### Building the tube's lane geometry — loc_c235 `[seen]`

loc_c235 is the once-per-level-setup routine that lays out the current tube's per-lane vertex geometry. It first reduces the active slot selector: it reads loc_46 indexed by loc_3d, runs it through the packer loc_c2e8, and keeps the returned packed value as the walk `seed`; loc_c2e8 leaves the table entry it looked up in loc_112, which loc_c235 reads back as the index `y` into the level-parameter tables.

Using `y`, it derives the span scalars: `neg = -mem[loc_bc8c+y]` is written to both loc_5f and loc_5d, its complement `0x10 - neg` to loc_a0, the guard loc_5b is set to 0xff, loc_60 takes `mem[loc_bc9c+y]`, and loc_111 takes `mem[loc_bccc+y]`. The offset pair is then established one of two ways depending on the game-mode byte loc_2: when loc_2 == 0x1e the pair loc_68:loc_69 is copied straight from `mem[loc_bcac+y]`:`mem[loc_bcbc+y]`; otherwise it takes the signed 16-bit difference `{bcbc:bcac} - {loc_69:loc_68}` and shifts it right four bits (four one-bit rotations carrying the high byte into the low byte), landing the low byte in loc_121, the level geometry scale. It also clears loc_66, loc_67, loc_10f, loc_110 and sets loc_113 to 0x2c.

It then seeds six per-column arrays top-down, walking a neighbour index `ny` down from `seed`: each column x (0x0f down to 0) receives its base X coordinate from loc_b97c+ny into loc_3ce+x, its base Y from loc_ba7c+ny into loc_3de+x, a third geometry byte from loc_bb7c+ny into loc_3ee+x, and zeroes into loc_31a+x, loc_33a+x and loc_39a+x (the projected-output slots, cleared for the projection pass to fill). Finally it computes two rounded neighbour-midpoint tables: for each column x it averages that column with its next wrapping neighbour `(x+1)&0x0f`, writing loc_435+x from the loc_3ce pair and loc_445+x from the loc_3de pair. The average is `(a + b + 1)` rotated right one bit with the ninth (carry) bit rotated into bit 7 — a rounding mean that wraps. The result is a full set of symmetric tube-vertex coordinates plus their between-lane midpoints.

### Projecting the lanes to slot coordinates — loc_c473 `[seen]`

loc_c473 is the projection sweep that consumes the geometry loc_c235 built and produces the signed slot-coordinate tables. It takes an incoming reference value into loc_57 and an output base index into loc_38, zeroes the clamp tally loc_59, and sets the loop counter loc_37 to 0x0f. For each of the sixteen lanes (loc_37 counting 0x0f down to 0, ending when the decrement wraps past zero into bit 7 set) it loads that lane's base coordinates — loc_3ce+col into loc_56 and loc_3de+col into loc_58 — and calls the coprocessor driver loc_c098 against the reference operands the level setup left in loc_5e/loc_5f/loc_60.

Each returned pair is then saturated into a small signed window before storage. The clamp treats a value with bit 7 set as negative: below 0xfc it is pinned to 0xfc with sign 0x01; a non-negative value 0x04 or greater is pinned to 0x03 with sign 0xff; anything inside is passed through with its own sign and counts as no clamp — i.e. the window is [-4..+3]. The first projected pair (loc_62 value, loc_61 sign) is written to loc_31a+out (value) and loc_32a+out (sign); the second pair (loc_64 value, loc_63 sign) to loc_33a+out (value) and loc_34a+out (sign), indexed by loc_38. Every clamp that actually fired bumps loc_59, the output base loc_38 decrements each pass, and the accumulated clamp count in loc_59 is handed back. This fills the four per-slot coordinate arrays the display list draws from.

### The value packer — loc_c2e8 `[seen]`

loc_c2e8 packs an arbitrary input byte into the table-entry form the geometry code expects. If the incoming value is 0x62 or greater it is discarded in favour of a masked hardware byte `mem[loc_60ca] & 0x5f` (a random/timer fallback). It then splits the value into a quotient `v >> 4` and remainder `v & 0x0f`, uses the remainder to index the ROM table at loc_bc7c, stores that looked-up entry to loc_112, and returns the entry shifted into the high nibble with the low nibble forced to 0x0f (the packed byte), handing back the quotient in X and the remainder in Y. loc_112 — the stored entry — is exactly the shape/level-parameter index that loc_c235 and loc_c4e1 read back to index their ROM tables.

### Snapping a coordinate up to reference — loc_c453 `[seen]`

loc_c453 is a small guarded adjustment on the same coordinate operands the coprocessor consumes. If the guard loc_5b is non-zero it returns untouched; if loc_57 already sits at least 0x0c above the reference loc_5f it also returns; otherwise it snaps loc_57 up to `loc_5f + 0x0f`, capped at a ceiling of 0xf0. In the capture loc_57 was observed making a large upward jump under this rule, and it independently pulses across a wide range, so it is grounded as seen.

### The mode-flag/scale producer — loc_ca48 `[code]`

loc_ca48 sets a mode flag bit and its paired scale byte from two gate cells. It defaults the pair to `(a, y) = (0x00, 0x10)` and switches to `(0x04, 0x08)` only when both loc_117 and loc_3d are non-zero. It then copies bit 2 of the chosen `a` into loc_a1 while preserving that byte's other bits (`((a ^ cur) & 0x04) ^ cur`) and stores `y` to loc_b4. Although the routine is reached, only the default branch runs in the capture, so both writes land constant values that never change their cells — loc_a1's bit 2 stays clear and loc_b4 takes 0x10 — a constant no-op, which is why it grounds as `[code]` rather than seen; the alternate `a = 0x04` branch that would actually set the flag bit and write the 0x08 scale is not exercised.

### The vector-shape emitter — loc_c4e1 `[seen]`

loc_c4e1 walks the shape vertex tables to draw one tube/shape outline into the vector display list. It packs its input byte through loc_c2e8, keeping the reduced value in loc_36 and the quotient in loc_35, and clears loc_73 before opening the record by driving loc_df6a with 0x05. It selects a header from loc_c22d indexed by `loc_35 & 0x07`, stashes it in loc_9e, and drives loc_df4c with that header. It reads the shape index the packer left in loc_112, takes an initial walk seed from loc_36, and — when the shape's loc_bccc entry is zero — backs the seed off by 0x0f. The first vertex is loaded from the shape tables (loc_ba7c+seed as Y into loc_57, loc_b97c+seed as X into loc_56) and emitted as an absolute move with both coordinates XORed by 0x80 through loc_df75.

It then sets loc_73 to 0xc0 and the segment counter loc_38 to 0x0f and runs sixteen segments: each pass reads the next vertex from loc_b97c/loc_ba7c indexed by loc_36, forms the delta from the running loc_56/loc_57 cursor, advances that cursor to the new vertex, emits the delta segment through loc_df75, and steps loc_36 down; the loop ends when the counter wrapping past zero sets bit 7. ### The two setup fronts — loc_b888 `[code]`, loc_c16e `[seen]`

## Sound, POKEY and the interrupt heartbeat

Tempest's audio and its per-interrupt bookkeeping both live on the `$60xx` hardware page, which carries two POKEY sound chips (POKEY1 at loc_60c0–loc_60cf, POKEY2 at loc_60d0–loc_60df) alongside the math coprocessor and the option switches. Two routines fire on essentially every interrupt from the CPU's IRQ entry — first loc_cf24, then the voice stepper loc_cd0a — and it is that pair that gives the machine its steady heartbeat: one advances the input/counter lanes, the other pushes the current sound state out to the POKEY registers.

### The per-interrupt lane stepper — loc_cf24 [seen]

loc_cf24 runs three parallel lanes indexed by X counting down 2→0, each gated by a distinct bit of the control byte loc_8: lane X=2 tests bit0, lane X=1 tests bit1, lane X=0 tests bit2 (the byte is shifted into carry by one, two, or three positions respectively, so the shifted-out bit routes the lane). The code is a dense branch web, so it is walked as an explicit block-by-block state machine with a running `carry`. For each lane it maintains a position cell in loc_d/loc_e/loc_f (read masked to its low five bits and wrapped modulo 0x20: the advance path adds 0x20 and, on saturation, clamps to 0x1f), a timer cell in the loc_10 triple (reloaded to 0x78 and counted down), and a counter cell in the loc_13 triple. A gate cell loc_c is armed to 0xf0 whenever loc_8 bit3 is clear and, while it drains, forces that lane's position and timer back to zero — a periodic reset of the lane.

When a lane's carry gate is set it takes the advance branch and, on the pass where its counter expires, contributes a small increment `sv` into a shared multi-byte accumulator. The per-lane contribution is deliberately small and the loc_9 input byte's bits *gate* which lanes contribute rather than supplying the value: lane 0 contributes 0; lane 1 contributes 0x01 only when loc_9 bit4 is set; lane 2 contributes `((loc_9 & 0x0c) >> 2) + 2 + carry` (and only when that masked field is nonzero). Each contribution is folded (with a +1) into both loc_16 and loc_17, and the lane's loc_13 counter is bumped.

After the three lanes the tail performs a threshold debit: the top three bits of loc_9 index the ROM table loc_cfd9, whose entry is subtracted from the loc_16 accumulator; when that does not underflow the result is kept and loc_18 is bumped (twice, when the index is 0x03). A second stage keyed on the low two bits of loc_9 does a parallel signed adjust of loc_17/loc_18 and conditionally bumps loc_6 once or twice. The path that would run off the end of this logic into the embedded data table is guarded as unreachable in any valid state.

The routine finishes with two clamp passes over the loc_13 lane triple, both skipped entirely when loc_7 bit0 is set. The two passes subtract *different* constants: the first pass subtracts 0x10 from each loc_13 lane that is at least 0x10 (gated `>= 0x10`), and if any lane was clamped it stops there; only when no lane qualified does the second pass run, subtracting 0x11 from each nonzero lane (gated nonzero) and stopping at the first that goes negative.

### The voice stepper — loc_cd0a [seen]

Immediately after loc_cf24, loc_cd0a walks the sixteen voice slots (X = 0x0f down to 0). A slot is skipped when its frame byte loc_c0,x is zero (idle) or when X equals the reserved-slot index held in loc_bf. For a live slot it counts down a fast timer loc_e0,x and, when that reaches zero, a slow timer loc_f0,x. If only the fast timer expired it takes a single envelope step: the frame byte's sign bit selects between the two parallel ROM envelope tables based at loc_cbcb and loc_cccb (indexed by the doubled frame value), reloading loc_e0,x from the table's +1 entry and taking a new level increment from the +2 entry, which is added into the level cell loc_d0,x — and for odd slots the prior high nibble of the level byte is preserved across that add. If both timers expired it instead walks the frame counter loc_c0,x forward (by two) through the tables until a nonzero frame lands, refreshing loc_d0,x from the +0 entry and reloading the slow timer loc_f0,x from the +3 entry. Finally the slot's level byte loc_d0,x is published to its POKEY audio register: slots 0–7 write loc_60c0+x (POKEY1), slots 8–15 write loc_60c8+x, which lands in POKEY2's audio registers loc_60d0–loc_60d7. So the sixteen slots map one-to-one onto the two chips' sixteen audio registers.

### Registering a sound — loc_ccc7 [seen] and the enable gate loc_ccc3 [code]

A sound is requested by its id in A. loc_ccc7 saves the caller's X/Y into loc_31/loc_32, then reads a descending run of bytes from the ROM row table loc_cb01 (loc_cb01+id, decrementing id with each of the sixteen slots). Every nonzero byte claims that hardware slot: it stores the byte as the slot's starting frame loc_c0,x, arms both timers loc_e0,x = 1 and loc_f0,x = 1, and brackets the write by setting loc_bf to the slot index and then back to the 0xff sentinel. So a single sound id activates up to sixteen voices from one ROM row.

Almost every request first passes through loc_ccc3 [code], the enable gate: it tests loc_5 and, when bit7 is clear, drops the request outright (returns without registering); only when the global sound-enable bit is set does it fall into loc_ccc7. Its own body writes nothing, so the gate's vectoring itself is not attributable in this capture, but its handler loc_ccc7 is heavily exercised.

### The fixed-id sound triggers

A family of thin trampolines each loads one fixed sound id and hands it to the gate, threading the caller's X/Y through. Through the enable gate loc_ccc3 go: loc_ccb5 [code] (id 0x0f), loc_ccc1 [code] (0x1f), loc_ccea [code] (0x2f), loc_cd02 [code] (0x3f), loc_ccb9 [code] (0x4f), loc_ccb0 [code] (0x5f), loc_ccee [code] (0x6f), loc_ccf2 [code] (0x7f), loc_ccbd [code] (0x8f), loc_ccf6 [code] (0x9f), loc_ccfe [code] (0xbf), and loc_cd06 [code] (0xcf). ### POKEY reset and random self-test — loc_cd95 [seen]

### Option switches and the selector nibble — loc_d6bb [seen] and loc_dbe0 [code]

In this capture every observed store is a constant (loc_60cb and loc_37 stay 0, loc_60db holds 0xd0), so the packing role rests on the code → [code].

### A math-coprocessor probe on the same page — loc_dce6 [code]

loc_dce6 is not sound at all; it shares the `$60xx` page as a math-coprocessor helper. It clears loc_73/loc_414/loc_6090, loads its two operands from A and X into loc_608e/loc_608f, sets the step count in loc_608c and loc_6094 to 0x10, then counts X down through a sixteen-slot window scanning loc_6040 for the first slot whose ready flag (bit7) is clear, handing back that slot's low/high result pair from loc_6060/loc_6070 (or exiting with the counter run past the end). It is not reached in the capture → [code], accounted "not exercised in this capture".

### Per-tick record queue and slot service — loc_ac3f [seen], loc_ad6e [code], loc_c800 [seen]

Three routines ride the same tick to keep a small record queue in order and drain it. loc_ac3f clears bit6 of loc_5, optionally pre-clears the scratch block through loc_ca62 (when loc_9 & 0x43 == 0x40), queues a request via loc_ddfb, and zeroes loc_601. loc_ad6e [code] is the per-frame service of the active slot, not exercised in this capture. ## The EAROM high-score store

The cabinet keeps its high-score table (and the initials entered against it) in an ER-2055 EAROM that survives power-off, and this subsystem is the whole path between "some code decided the table should be saved or reloaded" and the bit-serial handshake that actually moves bytes across the non-volatile part. The interface between the two halves is a three-cell request queue in page one — `loc_1c6`, `loc_1c7`, and `loc_1c8` — that a family of small setter fronts populate and that the transfer driver `loc_de1b` drains one block at a time.

The setters all funnel through one shared merge tail. That tail stores its index/mode argument into `loc_1c6`, then *ORs* its mask argument into both `loc_1c7` (the set of blocks whose transfer is still pending) and `loc_1c8` (the direction bits: a set bit here later means "write this block out", a clear bit means "read it back in"). Because both merges are bitwise-OR, requests accumulate rather than overwrite, so several callers can pile blocks onto the queue before the driver next runs. Two thin wrappers sit in front of the tail: one zeroes the index byte and forwards a caller-supplied mask, and one further hard-codes that mask to `0x04` before the zeroed-index entry — the plain "queue block `0x04` for a read-back at index 0" request (`loc_ddfb`, `[seen]`, whose `0x04` write into `loc_1c7`/`loc_1c8` is the one merge-tail value the capture actually exercised). The remaining fronts are fixed-operand variants of the same tail: `loc_ddf3` (`[code]`) forces the index byte to `0xff` and merges the live-in mask; `loc_ddf7` (`[code]`) supplies mask `0x03` (blocks 0 and 1) through the zeroed-index entry; and `loc_dde9` (`[code]`) runs the `0xff`-index path with a fixed mask of `0x04`. None of these last three merge values (`0x03`, or the `0xff` index) were seen at the merge point in the capture, so they rest on the code alone.

`loc_ddf1` (`[code]`) is the "save the whole table" front: it stamps `0xff` into `loc_1c6` and ORs `0x07` into both `loc_1c7` and `loc_1c8`, i.e. all three blocks, all in write direction, with the blank/index byte set. That specific blank-plus-mask-7 stamp was never observed on the write-tap, so it stays `[code]` rather than `[seen]`. Its mirror-image is `loc_de11` (`[seen]`), the load path, which does *not* merge but hard-*sets* `loc_1c7 = 0x07` and `loc_1c8 = 0x00` — all three blocks requested, every direction bit clear, i.e. read-back — and then immediately falls straight into the driver so the reload happens on the same pass. Both of `loc_de11`'s writes (`loc_1c7 = 7`, `loc_1c8 = 0`) are confirmed on the tap, which is what makes this the observed boot-time reload of the score table.

The engine is `loc_de1b` (`[seen]`), reached on essentially every service pass and the only cell writer of the whole group. When it finds no row in progress but a pending mask waiting (`loc_1ca == 0` and `loc_1c7 != 0`), it opens a fresh block: it clears the byte cursor `loc_1cb`, the running checksum accumulator `loc_1cf`, and the walking mask `loc_1ce`, then rebuilds `loc_1ce` into a single set bit by rotating `loc_1c7` (seeding a `1` at bit 7 and shifting until a set request bit rotates out), which both isolates one pending request and, through the countdown of its loop index, yields the row number. The direction is decided right there: the mode byte `loc_1ca` becomes `0x80` when that isolated bit also appears in `loc_1c8` (a write row) and `0x20` otherwise (a read row). The serviced bit is then cleared from the pending set via `loc_1c7 ^= loc_1ce`, and the doubled index picks that block's descriptor out of four parallel ROM tables — `loc_dddd` supplies the starting byte counter `loc_1cc`, `loc_ddde` the byte-limit `loc_1cd`, and `loc_dde3`/`loc_dde4` the low/high halves of the RAM pointer `loc_bd`:`loc_be` that addresses the block's source or destination bytes.

From there the common block runs one byte per re-entry. It first pulses the control port `loc_6040 = 0`, and if the mode byte has been retired to zero it simply returns. Otherwise it latches the byte cursor and counter, shifts the mode byte left, and branches on the resulting bits. On a write step it reads a byte through the `loc_bd`:`loc_be` pointer — first zeroing that source cell when the blank flag `loc_1c6` is non-zero, which is how the "erase" mode blanks the table as it writes — and once the cursor passes the byte-limit `loc_1cd` it instead emits the accumulated checksum from `loc_1cf` as the block's final byte, driving that byte out to `loc_6000 + x`. A read step performs the ER-2055 read handshake directly on the ports — asserting `loc_6040 = 0x08`, writing `0x08` to `loc_6000 + x`, clocking `loc_6040` through `0x09` back to `0x08`, and reading the data byte from `loc_6050` — then either stores that byte back through the row pointer, or, once past the limit, XORs it against the running checksum in `loc_1cf`: a zero result retires the row cleanly, while any mismatch walks the pointer back down zeroing the whole block and records the failed request bit into `loc_1c9` (the completed/failed-block accumulator). Each surviving byte is folded into `loc_1cf` and both cursors `loc_1cb`/`loc_1cc` advance; the pass ends by strobing the control port with the step's status code and either returning (non-zero strobe) or looping straight into the next byte or next queued block (zero strobe). The net effect is a checksum-protected save/reload of the score table across as many blocks as the request mask named, one block and one byte at a time.

The remaining routines grouped here — `loc_db22`, `loc_db84`, `loc_db88`, `loc_db7e`, `loc_db6f`, and `loc_db9a`, all `[code]` — do **not**, by their code, participate in the EAROM store: none touch the `loc_1c6`–`loc_1cf` queue or the ER-2055 read/clock handshake. They belong to the display/vector side. `loc_db22` broadly resets the `0x60xx` hardware register bank (zeroing `loc_60e0`, `loc_6080`, `loc_60c0`, `loc_60d0`, `loc_6000`, and `loc_6040`), takes four settling reads (`loc_6040`, `loc_6060`, `loc_6070`, `loc_6050`), sets `loc_60e0 = 0x08`, and then marches a single set bit across the 32-slot table at `loc_6080 + x` for `x = 0x1f` down to 0 (rotating the bit through carry) before emitting one framing record via `loc_df39(0x34, 0xa6)`. `loc_db84`, `loc_db88`, `loc_db7e`, and `loc_db6f` are variations on "emit a header/framing word through `loc_df39` (or `loc_df4c`), then blank the four even-indexed slots (`x = 6,4,2,0`) of `loc_60c1 + x` and `loc_60d1 + x`" — `loc_db88` takes the value/index pair live, `loc_db7e` primes it with `0x32`/`0xb6`, and `loc_db6f` first emits `loc_df4c(0x68, loc_50 >> 1)` from a halved slot count and then blanks via `loc_db88(0x33, 0x4e)`. `loc_db9a` advances a phase counter `loc_39` (skipped while `loc_3 & 0x3f` is non-zero), takes `idx = loc_39 & 0x07`, and uses that to index the parallel tables `loc_dbd5`/`loc_dbd6`/`loc_dfdc` to seed a pair of output cells (`loc_60c1 + slotA = 0`, `loc_60c0 + slotB = loc_dfdc[idx]`, `loc_60c1 + slotB = 0xa8`) before emitting three framing words through `loc_df39`/`loc_df6c`. Their roles rest on the code and stay `[code]`; the operative point for this section is that they drive the `0x60xx` I/O banks and the vector framing stream, not the EAROM high-score store.

## State-reset, init and per-frame update chains

This subsystem is the machine's scaffolding: the straight-line seeders that lay down starting constants at a cold start or a state change, the master reset that walks a fleet of blanking leaves before a wave begins, the wave-setup that measures the tube and drains a spawn queue, the once-per-frame ager that expires climbing objects and steps a countdown, the option/geometry rebuild guard, and the score-accumulate callers that ride the per-frame collision path.

### Fixed-constant seeders

Several leaves do nothing but stamp a small block of zero-page work cells with literal startup values, each landing at a different state entry and overlapping on the shared `loc_0`–`loc_4` config quartet. `loc_921b` [seen] seeds five cells with a fixed set — `loc_200`=0x0e, `loc_51`=0xf0, `loc_106`=0x00, `loc_201`=0x0f, `loc_202`=0x10 — and because `loc_200` and `loc_51` carry real varying state elsewhere, this is a genuine reseed rather than a no-op; it is reached through the init chain that falls into `loc_902b`. `loc_b0e7` [seen] writes six startup constants straight through — `loc_0`=0x0a, `loc_2`=0x00, `loc_4`=0xdf, `loc_1`=0x12, `loc_14e`=0x19, `loc_14d`=0x18 — every write observed at its own instruction. `loc_c97b` [seen] is a smaller state-entry seeder covering the same quartet from a different mode (`loc_2`=0x04, `loc_1`=0x00, `loc_0`=0x0a, `loc_4`=0x14). `loc_ca18` [seen] first masks `loc_5` down to its low six bits (clearing its top two flag bits) and then seeds a fixed block: `loc_3e`=0x00, `loc_2`=0x1a, `loc_0`=0x0a, `loc_4`=0xa0, `loc_16b`=0x01, `loc_1`=0x0a. The three seeders that touch `loc_0`/`loc_1`/`loc_2`/`loc_4` are mutually exclusive entry points that establish that config quartet differently depending on which state the machine is entering.

### The master reset chain

`loc_902b` is the init sequencer, tagged [code]; it drives six subsystem-reset leaves in order — `loc_928f`, `loc_926f`, `loc_9246`, `loc_929f`, `loc_92ad`, and `loc_c16e` — then closes by writing `loc_124`=0xff, `loc_148`=0xff and `loc_123`=0x00. Each of the resets it calls is itself [seen] and is reached through this chain; the three closing writes are constant seeds and rest on the code. The resets it calls each blank one region and its associated flags. `loc_928f` [seen] zeroes the twelve-byte array `loc_2d3`..`loc_2de` top-down and then clears `loc_135` and `loc_a6`; because the array head, `loc_135` and `loc_a6` all vary elsewhere this is a real state reset. `loc_926f` [seen] zeroes the seven-byte block `loc_2df`..`loc_2e5` (index 6 down to 0) and then clears seven scattered flag cells — `loc_108`, `loc_109`, `loc_145`, `loc_142`, `loc_144`, `loc_143`, `loc_146` — several of which (`loc_108`, `loc_142`) hold non-zero values elsewhere, so the reset is meaningful. `loc_929f` [seen] zeroes the eight-byte table `loc_30a`..`loc_311` and then clears the trailing flag `loc_116`. `loc_92ad` [seen] makes a single meaningful write, clearing `loc_50` to zero — a cell that ranges widely elsewhere — as the init-time reset of that byte; it is also invoked from other reset paths.

A second family of init leaves sits outside the six-reset chain but performs the same kind of blanking-then-seeding. `loc_9234` [seen] builds a seventeen-byte parameter block for the per-lane geometry: it copies the header source `loc_15b` into `loc_3ab`, then fills the sixteen body cells `loc_3ac`..`loc_3bb` (index 0x0f down to 0) with the second source byte `loc_15a`; in the capture `loc_15a` was 0 so the `loc_3ac` array stayed zero, while `loc_3ab` is a real changing header (it drains 0xf→0x0 elsewhere). ### Wave setup and spawn-queue drain

`loc_a5cb` [seen] initialises the wave: it sets `loc_0`=0x20, ORs bit7 into `loc_106`, clears `loc_104`/`loc_107`/`loc_5c`/`loc_123`, sets `loc_105`=0x02, and then tallies how many of the sixteen `loc_3ac` per-lane entries are non-zero, accumulating that count into `loc_123` (observed climbing to a count of occupied/spiked segments). If any segment is live and the level `loc_9f` is below 0x07, it loads an intro parameter block — `loc_4`=0x1e, `loc_0`=0x0a, `loc_2`=0x20 — and overwrites `loc_123` with 0x80; in all cases it finishes by raising the block-ready latch `loc_125`=0xff.

`loc_ad22` [seen] drains the packed spawn-request word `loc_603` two bits at a time. Each pass, if `loc_603` is exhausted it writes the idle exit status `loc_0`=0x14 and returns (the arm exercised in the capture, with `loc_603` observed draining to zero and `loc_0` reaching 0x14). Otherwise it takes the low two bits minus one as the slot index into `loc_3d`, shifts them out of `loc_603`, and reads that slot's byte from `loc_600`+index; a slot byte of zero or 0x09-and-above is skipped. For a byte `n` in 1..8 it scales it into the paired value by doubling `n`, adding `n` again (giving 3·n), XOR-ing with 0xff, and subtracting 0xe5, storing the result in `loc_602`; it then calls `loc_ca48`, seeds `loc_605`=0x60, `loc_4e`=0x00, `loc_50`=0x00 and `loc_604`=0x02, calls the slot-table reset `loc_a789`, writes the armed exit status `loc_0`=0x24, and returns.

### The per-frame ager and clock

`loc_a504` [seen] is the once-per-frame update, split by the sign of the control byte `loc_201`. The negative arm is the one exercised. It bails immediately if any of `loc_135`, `loc_a6` or `loc_116` is set; otherwise it ages every live entry of the depth table `loc_2df` — walking down from `loc_11c`, adding 0x0f to each non-zero cell and snapping it to 0x00 once the sum reaches the 0xf0 ceiling, so objects that have climbed to the far end expire. It then advances one of two counters selected by `loc_48`+`loc_3d`: when that slot byte is not 0x01 it steps `loc_202` up by 0x0f and proceeds once it crosses 0xf0; when it is 0x01 it clears `loc_10f`, sets `loc_114`=0x01, and steps the sixteen-bit countdown `loc_5b`:`loc_5f` down by 0x20 (subtracting from the low byte `loc_5f`, borrowing into the high byte `loc_5b`), proceeding when the high byte reaches the marker 0xfa. On proceeding it writes `loc_0`=0x06, calls `loc_928f`, and folds a running total: it sums `loc_108`+`loc_109`+`loc_3ab` and stores it back into `loc_3ab`, clamped at 0x3f. The positive arm (present in the code, not the one grounded here) instead bumps a per-slot timer at `loc_00`+`loc_40` when the `loc_455`/`loc_11b` gate is live and `loc_42` exceeds 0x17, and — gated on `loc_106`, `loc_3ab`/`loc_116`, and a scan of `loc_2df` for any entry that has grown to 0x11 or beyond — conditionally re-runs the wave setup `loc_a5cb` (with `loc_928f`) or, behind the `loc_4d`&0x60 / `loc_5`&0x80 / `loc_9`&0x43==0x40 gates, runs `loc_a5cb` alone.

### Option/geometry rebuild guard

A cluster of callers keeps the two control-block regions in sync with the live option-switch/geometry state, requesting a rebuild only when that state has drifted from a cached snapshot. `loc_ac20` [code] refreshes the snapshot through `loc_d6bb` and then compares `loc_a`&0xf8 against the cached `loc_71e` and `loc_16a`&0x03 against the cached `loc_71f`; on a match it falls to the shared no-op return `loc_ac3e`, and on a mismatch it hands off to `loc_ac36` (which ORs 0x03 into the request word `loc_1c9`). In the capture only the matching, no-op-return path fired, so it stays [code]. `loc_aba2` [code] refreshes through `loc_ac20` and then branches on the low two request bits of `loc_1c9`: idle takes the no-op tail `loc_ac07`, otherwise it runs the rebuild path `loc_abac`. `loc_d7e1` [code] arms two mode bytes (`loc_5`=0x00, `loc_1`=0x02) and then performs the rebuild only while the machine is idle, enabled and unbusy: it returns early if `loc_1ca` is non-zero or if `loc_c00`&0x10 is clear, otherwise clears `loc_0` and, if a request bit in `loc_1c9` is pending, delegates to `loc_abac`.

`loc_abac` [seen] is where the rebuild fires. After refreshing through `loc_ac20` it writes `loc_100`=0x08 and, when all three of `loc_71b`/`loc_71c`/`loc_71d` are idle, forces both request bits via `loc_ac36`. It then reads the request flags from `loc_1c9`: request bit0 selects a copy top of 0x17 (else 0x0e) and copies that many-plus-one bytes of the template `loc_ac08` down into `loc_606`; request bit1 selects a fill top of 0x17 (else 0x0e) and fills that run of `loc_706` with 0x01. ### Score-accumulate callers on the collision path

The bonus-life award that follows the threshold test against `loc_156` — bumping the per-slot counter `loc_48`+index while it is still under six, firing the `loc_ccc3` chime, and latching `loc_124`=0x20 — is code-only.

## Utilities and shared tails

This section gathers the small, widely-shared helpers of the Tempest ROM: the binary-to-BCD packer that feeds score and counter display, a couple of byte-partition helpers, two table-maintenance routines, the rebuild-request flag setter, and the several bare `rts` leaves that serve as shared return tails and do-nothing dispatch slots.

**Binary-to-BCD packing — `loc_aaf5` ([seen]).** This is the classic double-dabble converter and one of the heavily-exercised leaves in the machine. It takes the binary byte in A and folds it into a packed-BCD accumulator over eight passes: each pass shifts the top bit out of the source (an arithmetic left shift, high bit becoming the carry) and, in decimal arithmetic, doubles the running accumulator while adding that carry back in. The decimal double is done digit-wise — the low nibble is doubled with the incoming carry and given the +6 BCD correction when it exceeds 9, then the high nibble is doubled and given the +0x60 correction when the whole thing crosses 0xa0 — so the eight passes leave a valid packed-BCD representation of the original value. The finished byte is stored to **both** `loc_29` and `loc_2c`; the two cells receive the identical packed value, spanning the full 0x00..0x99 packed-BCD range as inputs vary, and A is left holding the same result. Its caller `loc_af77` runs it and then emits the freshly-packed `loc_29` byte as display nibbles.

**Clamp-and-emit — `loc_af71` ([code]).** A thin display front-end: it clamps the incoming byte to a maximum of 0x63, then hands that clamped value to `loc_af77`, which packs it to BCD through `loc_aaf5` (writing `loc_29`/`loc_2c`) and immediately emits it. The emit path runs `loc_dfb1` with a start index of `loc_29` and a length of one, so exactly that one zeropage byte is streamed out as its high nibble followed by its low nibble into the vector cursor cells (`loc_ae` the running count, `loc_af` the byte index, reading through the `loc_0` base). It has no own role-defining write; its work is entirely the clamp plus the delegated pack-and-emit, which is why it rests on `[code]`.

**Byte partition into a value and an index — `loc_93e0` ([seen]).** Reached exclusively through the three call sites of `loc_92c5`, this helper splits the byte in A into two independent pieces. It walks A's top three bits, MSB first, folding each one into the low bits of a seed that starts at 0xff; the seed therefore ends as 0xf8 with those three ejected high bits packed into its low three positions. That seed is stashed to `loc_29` (the observed own-cell write, seen taking values around 0xff/0xfe as the fold runs) and also returned in Y. Meanwhile A itself is shifted left three times, so it ends holding the input's low five bits promoted upward (its top three bits shifted away) — the "fine value" half of the split. X is derived from the seed's complement as `((seed ^ 0xff) + 0x0d) >> 1`, giving the coarse index half. All three register live-outs (the shifted A, the derived X, the seed in Y) ride out of the routine so its callers see each of them; the only memory it touches is the `loc_29` scratch, which is what grounds it as a reached compute helper.

**Constant-pair leaf — `loc_b955` ([code]).** This routine reads `loc_57`, right-shifts it, and spins a small increment/shift/branch loop that looks for all the world like a bit-count or log-of-`loc_57`, but the loop's result is thrown away: the tail clears the accumulator, adds 2, and zeroes Y, so it *always* returns the fixed pair A = 0x02, Y = 0x00 no matter what `loc_57` held. It writes no memory. A blind reading would mis-name it a bit-count of `loc_57`; the code settles it as a constant-pair return leaf, and with no own write it stays `[code]`.

**Parallel-table swap — `loc_92b2` ([code]).** A straight table-maintenance routine that swaps two parallel 18-entry tables slot-for-slot: for each index x from 0x11 down to 0, it exchanges the byte at `loc_3aa + x` with the byte at `loc_3bc + x`, so afterward each slot in one table holds what its sibling held. The exchange stores never fire in this capture, so the routine is not reached; both tables appear in the trace only as constant zeros written from unrelated points, leaving it `[code]`.

**Triple-entry array seed — `loc_b85f` ([code]).** A straight-line initializer for two paired three-entry arrays. It writes the fixed values 0x00, 0x04, 0x0c into the `loc_22`/`loc_23`/`loc_24` slots and the identical 0x00, 0x04, 0x0c into the parallel `loc_809`/`loc_80a`/`loc_80b` slots, so the two arrays come up mirroring each other with that fixed ramp, and returns with A = 0. None of its stores are observed — the routine is not reached across attract, coin, start, or play in the capture — so although its body is fully readable it remains `[code]`.

**Rebuild request — `loc_ac36` ([seen]).** This is the flag-setter that arms the geometry-rebuild machinery: it ORs 0x03 into `loc_1c9`, setting the two low pending-rebuild request bits, stores the merged value back, and returns it. The own-body write to `loc_1c9` is observed (value 0x07, showing both request bits present alongside an already-set higher bit), which grounds it `[seen]`. It falls straight through into the shared return tail at `loc_ac3e`. Its callers reach it when a rebuild is needed — `loc_ac20` on a live-geometry state mismatch and `loc_abac` on its own trigger — and the request bits it sets are later consumed by the rebuild path (bit 0 driving one block copy, bit 1 the other).

**Shared return tails and do-nothing slots ([code]).** Several bare `rts` leaves exist purely as branch targets that let a caller unwind cleanly on a "nothing to do" path, and none of them can be grounded by a write-tap because none of them write:

- `loc_ac3e` is the shared return tail that `loc_ac36` falls into and that `loc_ac20` branches to directly when the live geometry state already matches its latch — the `loc_a` high bits against `loc_71e` and the low two bits of `loc_16a` against `loc_71f` — so no rebuild is requested.
- `loc_ac07` is the matching "nothing to rebuild" leaf that `loc_aba2` tail-branches to when the low two bits of `loc_1c9` are clear.
- `loc_af6e` is the exposed `rts` tail of the `loc_af3f` draw routine; `loc_af26` tail-branches here when `loc_600 | loc_601` is zero, i.e. both draw slots are empty and there is nothing to draw.
- `loc_9bcf` is a do-nothing handler occupying a slot in a computed-dispatch table: it returns immediately, letting the caller's own return unwind, so a selecting index that lands on it produces no effect.

All four are `[code]`: they are readable no-op leaves with no side effect for a write-tap to confirm.
