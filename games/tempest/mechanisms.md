# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
object-record draw loop, the mathbox projection, sound, and the EAROM — down to the caller routines that
drive them and the computed-jump dispatchers (`loc_b84e`, `loc_b5d7`, `loc_9a88`); the frozen-oracle
remainder (the remaining dispatcher spine and the deferred register-thread callers) is noted at the end.
The machine is a colour vector game: the 6502 builds a display list in AVG vector RAM (`0x2000-0x2FFF`)
each frame and the Analog Vector Generator draws it, with the vblank interrupt as the per-frame heartbeat
and a game-state index driving a computed-jump dispatch that selects the mode handler (attract, coin-in,
play, transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

Each moving object is driven by a small byte-script rather than by open-coded logic. The script bytes live in the table `loc_a0f7`, a rolling cursor `loc_10b` names the current position within it, a branch flag `loc_10c` records the outcome of the most recent test, and a walk-continuation flag `loc_10a` keeps the driving walk alive. The routines here are the opcode handlers: the script-walker `loc_9b1e` fetches a script byte and hands control to one of them, so each is reached through the walker's computed dispatch rather than by a fixed caller. Together they form a tiny instruction set — load, jump, test, and time — that steers an object's per-slot cells.

**Loading operands into a slot.** The two store opcodes both begin by stepping the cursor forward and then deposit a value into the acting object's cell `loc_298,x`. `loc_9bd0` [seen] does the immediate form: it advances `loc_10b` by one (wrapping to a byte) and copies the script byte it now points at, `loc_a0f7[loc_10b]`, straight into `loc_298,x` — the operand written verbatim into the slot. `loc_9bdd` [seen] is the indirect form: after the same one-step advance it treats the fetched script byte `loc_a0f7[loc_10b]` as a zero-page address and copies the *live variable* found at `loc_00 + ptr` into `loc_298,x`, so the slot receives a runtime value chosen by pointer rather than a constant baked into the script. Both are confirmed by the cursor-advance write and by the slot writes landing across `loc_298,x`'s object cells.

**Control flow.** Three opcodes move the cursor conditionally or unconditionally. `loc_9bee` [seen] is the conditional skip: if the branch flag `loc_10c` is nonzero it does nothing, and otherwise it advances `loc_10b` by two, stepping the cursor past a two-byte operand — the two increments were both observed. `loc_9bfa` [seen] is the conditional jump: it first advances `loc_10b` by one, then, only while `loc_10c` is zero, replaces the cursor entirely with the operand target `loc_a0f7[loc_10b]`, reloading the program counter to jump; a nonzero flag lets execution fall through past the operand. `loc_9c17` [seen] is the unconditional goto, and it is exercised heavily: it uses the current cursor value to index the *parallel* table `loc_a0f8` and writes `loc_a0f8[loc_10b]` back as the new cursor, following the operand chained after the current opcode. This same tail is shared as the continuation of the timer opcode below.

**Tests that set the branch flag.** Two opcodes compute `loc_10c` for the conditional skip and jump to consume. `loc_9c21` [code] tests position against a segment boundary: it reads the slot's segment `loc_2b9,x`, looks up that segment's boundary in `loc_3ac` (an entry of zero reads as the maximum `0xff`), and sets `loc_10c` to 1 when the boundary is at or beyond the slot's depth `loc_2df,x`, else 0 — a "have we crossed the edge" test. Its store to `loc_10c` was not reached in the capture (the flag was produced elsewhere during the captured window), so it stands [code]. `loc_9c3b` [code] tests a phase accumulator instead: it forms `((loc_147 << 2) + loc_148) & loc_148 & 0x80`, then exclusive-ORs that against `0x80`, so `loc_10c` becomes `0x00` when the resulting high bit is set and `0x80` when it is clear — a sign/phase probe on the `loc_147`/`loc_148` accumulator pair. All arithmetic wraps to a byte. Its store to `loc_10c` was likewise not reached in the capture, hence [code].

**Timing.** `loc_9c0c` [seen] is the dwell opcode. It decrements the acting slot's timer `loc_298,x`; while that timer remains nonzero it delegates to `loc_9c17`, running the `loc_a0f8`-driven goto step so the object keeps cycling through its current state; only when the timer reaches zero does it bump the shared cursor `loc_10b`, releasing the script to advance to the next instruction. This is the mechanism by which a scripted object holds a pose for a fixed number of frames before moving on.

**Housekeeping.** `loc_9bca` [seen] is a one-line leaf that clears the walk-continuation flag by writing `loc_10a = 0`; it is reached often, ending the walker's inner loop over script entries so the per-object pass terminates. `loc_96c7` [code] is a cursor-skip helper that advances the list cursor by a fixed run to step over a packed record without reading it — its first entry moves the cursor forward by three (it bumps by one and falls into the second entry) and its second entry moves it by two. It touches only the cursor register and writes no memory, so there is nothing observable to lift it past [code].

## Vector coordinate lists and the display cursor

Two zero-page pointers govern this subsystem: `loc_2c`/`loc_2d` names the current *coordinate list* being walked, and `loc_74`/`loc_75` is the *display cursor* — the write head that lays vector words into the AVG display RAM at `$2000`-`$2fff`. One family of routines seats and walks the coordinate-list pointer; another family emits words through the display cursor and steps it forward.

### Seating the coordinate-list pointer

`loc_9aee` [seen] is the pointer-seating core. Indexed by the incoming Y, it reads the low byte of a list pointer from the ROM table at `loc_9b02`+Y into `loc_2c` and the high byte from `loc_9afd`+Y into `loc_2d`, records the chosen index at `loc_2b`, and reloads the accumulator from its holding cell `loc_29`. `loc_9af1` [seen] is the same setup entered one step in: the caller has already computed the low pointer byte, so it stores that directly into `loc_2c`, still pulls the high byte from `loc_9afd`+Y, still stashes the index at `loc_2b`, and still reloads `loc_29`. The effect either way is a 16-bit pointer parked at `loc_2c`/`loc_2d` aimed at a packed coordinate list, with the index that selected it remembered at `loc_2b`.

`loc_9a88` [seen] is a computed-jump dispatcher: the incoming value picks one of five list-setup entries — `loc_9a9d`, `loc_9aa9`, `loc_9abb`, `loc_9ab7`, `loc_9ab3` — and runs it (any of these being a computed-jump target, it is reached through this dispatcher, never callerless). Each entry front-loads a specific index or low-byte source and falls into the shared `loc_9aee`/`loc_9af1` seating. Only index 0, `loc_9a9d`, is exercised in the capture; the rest are [code], not reached. `loc_9a9d` [code] seeds the low pointer from the fixed table byte `loc_9b02`, marks the index zero at `loc_2b`, takes the high pointer from the held source cell `loc_15d`, and reloads `loc_29`. `loc_9aa9` [code] (index 1) folds two held bytes into the low pointer by OR-ing `loc_9b03` with `loc_16d`, presets index 1, and runs the `loc_9af1` seating. `loc_9ab7` [code] (index 3) presets index 3 and runs the `loc_9aee` seating; `loc_9ab3` [code] (index 4) presets index 4 and does likewise. (Index 2, `loc_9abb`, is a sibling entry belonging to another subsystem.)

### Walking the coordinate list

With the pointer seated, several helpers read the packed list. `loc_96cb` [seen] steps the cursor by an inter-entry delta: through the `loc_2c`/`loc_2d` pointer it reads the entry at Y and its predecessor at Y-1, stores their difference (`cur - prev`) at `loc_29` as the step delta, and advances Y by that delta plus two. Observed deltas run 1..0x0f, the genuine inter-entry strides of the list reached through the coordinate dispatch. `loc_96db` [code] resolves one list entry to an absolute coordinate: it reads the byte at the pointer offset by Y and adds the base value in `loc_160`, returning the 8-bit sum — a pure compute helper with no memory write, so its role rests on the code.

`loc_96ab` [seen] is the coordinate helper the computed-jump coordinate generator consumes. Its own write is only the scratch at `loc_29`, where it stashes the incoming Y; it then combines an index value with the list entry two positions back — reading the byte at pointer+(Y-2), subtracting it from the index value and adding back the saved Y — re-indexes the pointer by that result, and loads the entry it lands on, returning both that entry and the new index. The `loc_96ab` entry derives its index value as `((loc_2b - 1) & 0x0f) + 1` (a counter-derived value wrapped into 1..0x10); the sibling `loc_96b7` entry uses the raw `loc_2b`, and `loc_96c4` is the bare form that just reads pointer+Y. `loc_96f4` [code] is the front half of that same arithmetic exposed alone: it records Y at `loc_29` and returns `loc_2b` minus the pointed byte two slots back (pointer+(Y-2)); as a leaf whose result is only consumed downstream, its role rests on the code. `loc_96e2` [code] uses `loc_96f4` as a repeat count, loads the first entry it selects from the pointer at Y, then folds that many further consecutive entries into a single wrapped one-byte total.

### The display cursor and the vector emitters

`loc_df5f` [seen] is the display-cursor advance and the hinge every emitter turns on. It adds Y+1 to the low byte `loc_74` (the carry is forced set, so the stride is `loc_74 + Y + 1`), stores it back, and on overflow bumps the high byte `loc_75`; the returned accumulator is the new low byte. Under load the cursor sweeps continuously across `$2000`-`$2fff`, which is what makes it the display-list write head.

The primitive word emitter is `loc_df57` [seen]: it stores the pair {A, X} — A at the cursor origin `(loc_74)`+0, X at +1 — then advances the cursor by two via `loc_df5f`. `loc_df53` [seen] rides that tail with the fixed pair preset, emitting the `{0x40, 0x80}` header word (0x40 then 0x80 into the vector RAM) before the same advance. `loc_df59` [seen] is the indexed form of the core emitter: it stores {A, X} at cursor offset Y and Y+1 and advances the cursor past them (by (Y+1)+1); its stores lay real vector data (for example a `0x3c` low byte against a `0x72` high byte) across a wide value range, which grounds it as a role-defining emit.

`loc_df19` [seen] emits a table-selected word: from the accumulator's low nibble it forms a word-table index — 0 when the carry is set and the nibble is zero, otherwise nibble+1 — doubles it, copies the two bytes of `loc_31e4`[index] into the display list at the cursor, and advances two. `loc_df1f` [seen] is the thin index wrapper: it forms the index as `(A & 0x0f) + 1` and shares the same `loc_31e4` copy-and-advance emit tail; its own index arm is pure compute, [seen] by reaching that shared emit.

`loc_df0d` [code] builds a two-byte-header record: it emits the `{0x40, 0x80}` header via `loc_df53`, then stores a fixed body byte 0x20 at the cursor origin through `loc_df12` and runs the shared record tail; it is not reached in the capture. `loc_df12` [code] is the shared body-byte entry — it stores its input byte at the cursor origin `(loc_74)` and continues into the shared record tail; it is reached along a path that presets the body byte to a constant, so its emit is observed but never varies and its role rests on the code.

Two producers assemble complete on-screen objects through the cursor. `loc_aef8` [seen] renders text: it walks three character codes from the `loc_606` buffer (tracking the source position at `loc_38` and a two-count at `loc_39`), clamps each code to at most 0x1a (any value 0x1e or above folds to 0x1a), doubles it to index the glyph word table `loc_31fa`, and copies each 2-byte glyph word into the display list at the cursor; after the copies it advances the cursor past everything written. `loc_c772` [seen] emits an object's position vector: starting the cursor offset at zero, it writes the fixed `{0x40, 0x80}` header, then an X word taken from the zero-page pair `loc_2`/`loc_3` indexed by X and a Y word from the pair `loc_00`/`loc_1`, each word's high byte masked to five bits (`& 0x1f`). As it writes it caches the raw coordinate bytes as the "previous point" — the low/high X at `loc_6c`/`loc_6d` and the low/high Y at `loc_6a`/`loc_6b` — which later stroke-delta drawing subtracts from, then advances the cursor past the six emitted bytes.

## Draw-pointer setup and vector emission

Every frame is assembled into the AVG vector RAM at 0x2000-0x2fff, where each two-byte word carries drawing data in its low byte and a generator opcode in the high nibble. The routines here fall into four bands: the frame sequencer that walks the display layers, the pointer-setup helpers that aim the working cursor at each layer's slice of RAM, a family of tiny tail-emitters that lay one vector word at a time, and the object builders that turn tube-slot and enemy coordinates into vector records.

### The frame sequencer and its layer brackets

loc_b230 (b230, [seen]) drives one whole frame. It calls each drawing subsystem in a fixed order — the score/status draw (loc_b586), the twelve-slot shape draw (loc_b75b), then loc_b5ad, loc_b79a, loc_b498, the marker-row builder (loc_a8b4), loc_b367, the enemy-list builder (loc_c5c2), and loc_c54d — and brackets every one with a setup call loc_b2be and a matching teardown loc_b2fe keyed to that layer's id (0x07, 0x04, 0x03, 0x06, 0x05, 0x00, 0x01, 0x08). Inside the player-layer bracket, when the sign flag loc_5 bit7 is clear, it sums a forty-byte block (0x28 bytes) reached through the pointer loc_b6/loc_b7 — carry-chained from a seed of 0xf2, walking index 0x27 down to 0 — and leaves the running total in the status cell loc_11b. After the layers it zeroes the change counter loc_114 and latches the two ROM constants loc_cec2 and loc_cec3 into the first two vector words loc_2000 and loc_2001, which head the display list every frame.

loc_b2be (b2be, [seen]) is the per-subsystem draw-pointer setup: from the layer index A it forms the two-byte stride 2*A and, choosing table loc_ce68 when the per-index flag loc_415+A is non-zero (else loc_ce7a), copies that table's 16-bit pointer into the indirect draw cursor loc_74/loc_75, then clears the status cell loc_a9 so the cursor offset restarts at zero for the layer. loc_b2de (b2de, [seen]) is the same selector aimed at the alternate working pointer loc_3b/loc_3c, with the table sense reversed (loc_ce7a when the flag is set, else loc_ce68), again clearing loc_a9. loc_91b5 (91b5, [seen]) is the in-page variant: it doubles the selector A into a word index, clears the paired flag byte loc_29, and copies the little-endian pointer at the ROM table loc_91c6/loc_91c7 into the working pointer loc_2a/loc_2b.

loc_b332 (b332, [seen]) emits a link record between draw lists but first guards against a mid-frame change: if the source byte loc_cec4 differs from the checkpoint loc_2000 it latches the new value into loc_2000 and returns carry set, signalling the caller to redo the frame. Otherwise it copies a two-byte word from loc_ce9e (at offset 8 when loc_415 is non-zero, else 2) out through the draw cursor loc_74, clears loc_16e, then reloads the cursor loc_74/loc_75 from loc_ce68 at that same offset and returns carry clear.

loc_b84e (b84e, [code]) is a computed-jump dispatcher: the caller's Y is a byte offset (0,2,4,6) selecting one of four draw-pointer targets loc_b85f, loc_b875, loc_b888, loc_b896. loc_b896 (b896, [code], reached only via that dispatcher) writes the 16-bit cursor loc_139/loc_13a into the vector-RAM tail — loc_2ffc gets the low byte, loc_2ffd the high byte tagged 0x70, loc_2fff the 0xc0 terminator — then steps the cursor down by 0x20 with a 16-bit borrow into loc_13a and masks the low byte to 0x7f; it is not reached in the capture. loc_b944 (b944, [code]) swaps the two 16-bit pointers loc_74/loc_75 and loc_76/loc_77 so the shared cursor addresses the other structure, and loc_b967 (b967, [code]) picks one of two ROM pointer pairs by the flag loc_415 (zero selects loc_ce87/loc_ce86, non-zero loc_ce6f/loc_ce6e); neither is reached in the capture.

### The shared vector-word tail-emitters

A cluster of small routines each lay exactly one vector word through the draw cursor loc_74 and step past it, differing only in the header nibble and the payload source. loc_ab0d (ab0d, [code]) emits the fixed pair (0x20, 0x80). loc_df4c ([code]) stores Y as the first byte and A tagged with 0x60 as the second; loc_df6c ([code]) is the same with the 0x70 tag. loc_df4a (df4a, [code]) drives loc_df4c with the low table byte loc_73 as its data, and loc_df6a (df6a, [code]) drives loc_df6c with a zero data byte. loc_df09 (df09, [code]) stores the fixed body byte 0xc0 at the cursor origin (loc_df12) and continues the shared record tail. loc_df39 (df39, [code]) emits a coordinate word: the high byte is A's upper nibble tagged 0xa0, the low byte is X shifted right with A's carry bit rotated into bit7; it writes the high byte at cursor+1 and the low byte at cursor+0, then either advances (loc_df5f) or, if the offset wrapped to zero, falls through to loc_df4c with the tag byte loc_73.

loc_df92 (df92, [seen]) emits a four-byte coordinate record from four zeropage slots indexed off X: the raw byte loc_2+x, the packed loc_3+x masked to five bits, loc_0+x, and a key-folded five-bit last byte built by XOR-folding loc_1+x with the key loc_73 — the last byte handed to loc_dfac, which stores it at the next cursor slot and either advances the cursor or, on wrap to zero, runs the terminating nibble run. loc_df75 (df75, [seen]) widens two input values by four with sign extension — each value shifted left two with its high bit propagated into the adjacent byte — into the little-endian delta pairs loc_6e/loc_6f and loc_70/loc_71, then emits the record they anchor through loc_df92. loc_df73 (df73, [code]) merely stashes the index byte into loc_73 before scaling the two coordinates through loc_df75.

loc_dfb1 (dfb1, [seen], reached extensively) draws a run of Y zeropage bytes from the top index A+Y-1 downward: for each byte it emits the high nibble then the low nibble through loc_df19 (which looks up a glyph word-pair from table loc_31e4 at 2*nibble and writes it through the cursor loc_74), chaining carry so that only the final low nibble sees carry cleared — the run's terminator marker. loc_aa9e (aa9e, [code]) increments the slot index, publishes it into loc_61, and emits that single byte via loc_dfb1. loc_af77 (af77, [code]) packs the incoming byte to BCD (loc_aaf5, which writes the same packed digits into loc_29) then emits that one zeropage byte as nibbles; loc_b0c6 (b0c6, [code]) seats a table pointer by index through loc_91b5 then emits the three-byte run at loc_29 as nibbles.

loc_b56a (b56a, [seen]) appends a blank-plus-value record: it stores 0, 0, 0, A at the draw cursor loc_74 and advances the cursor by four, carrying into loc_75.

### Glyph strings and per-digit runs

loc_a9fc (a9fc, [seen]) maps A's low nibble to a stroke word for the text buffer: the beq/clc/bcs carry dance yields y = nibble+1, or 0 for a zero nibble with carry in, and it reads a **single byte** from ROM table loc_31e4 at offset 2*y (not a word), stores it at the buffer cursor loc_2f60+x, and advances x by two. loc_a9d7 (a9d7, [seen], reached heavily) walks three source bytes backward — pass counter in loc_2a, source pointer in loc_3b/loc_3c — emitting each byte's high then low nibble through loc_a9fc, threading the carry so only the last low nibble on the final pass sees it forced clear. loc_a97f (a97f, [seen]) builds a marker-row vector list: it lays a header byte (A OR 0x70, zeroed only when the row index Y equals the marker loc_3d and loc_5 bit7 is set) at loc_2f60, fills seven glyph entries from loc_3284/loc_3286 (the alternate glyph used once the row passes the count in loc_48), then — unless it is state 4 away from the marker — seeds the glyph pointer loc_3b/loc_3c and hands off to loc_a9d7.

loc_dd41 (dd41, [code]) is the large packed-decimal digit builder: it doubles the first little-endian input pair (loc_40f/loc_410, its high bit carried) and adds the second (loc_40c/loc_40d) into the math-box operands loc_6095/loc_6096, forcing a minimum of one, seeds a divide through loc_dce6 into loc_412/loc_413, then emits a header via loc_df39. ## Enemy motion and the pursuit AI

Enemies live in a bank of slots indexed by `x`. Each slot carries a whole-coordinate cell `loc_283,x` (nonzero while the slot is alive, also serving as a per-slot flag byte), a segment/lane number `loc_2b9,x`, a phase counter `loc_2cc,x`, a direction/state byte `loc_28a,x`, and a depth pair `loc_2df,x` (high) / `loc_29f,x` (low). Two distinct locomotion styles run over these slots: a free-flight three-axis integrator used at spawn time, and the lane-by-lane climb that carries the pursuit logic. Both are stepped once per frame by the slot walk.

### The per-frame slot walk and spawning

`loc_a618` [code] drives the frame. It first copies the spawn budget `loc_10e` into the frame-active flag `loc_10d`, then walks the sixteen slots from `0x0f` down to `0`. A slot whose `loc_283,x` is nonzero is live: it is integrated by `loc_a6a9` and then decayed by `loc_a721`, and it forces `loc_10d = 0xff` to mark the frame active. A free slot (`loc_283,x == 0`) is refilled by `loc_a65b` as long as the budget `loc_10e` remains nonzero. The decay step leaves its last axis's whole byte in a register, and `loc_a618` carries that register value forward so each subsequent spawn stamps it in; after the walk it settles the slot counter `loc_37 = 0xff`. On even frames (`loc_3` bit0 clear) with budget remaining it ticks `loc_10e` down by one, and if the walk found nothing live or spawned (`loc_10d` still zero) it raises the mode-request byte `loc_0 = 0x12`.

`loc_a65b` [code] populates a free slot. It marks the slot active by writing `0x80` to `loc_263,x`, `loc_283,x`, and `loc_2a3,x`, then seeds three velocity/coordinate pairs from the POKEY random draws `loc_60da`/`loc_60ca`. For each axis the raw draw becomes the low byte (`loc_2c3,x`, `loc_2e3,x`, `loc_303,x`) and a signed nudge from `loc_a69b` becomes the whole byte (`loc_323,x`, `loc_343,x`, `loc_363,x`); the middle axis's nudge is forced non-positive (negated when it comes out positive). It closes by cueing a sound (`loc_ccc1`). `loc_a69b` [code] is the leaf that produces that nudge: it reads a 3-bit magnitude (`loc_60da & 0x07`, so 0..7) and negates it when the caller's incoming value has bit0 set, giving a signed step in [-7, +7]. It makes no own write and is not reached in the capture (its effect would land only through `loc_a65b`, which also did not run in the capture).

### Free-flight integration and decay

`loc_a6a9` [code] integrates the live slot's three motion axes. Each axis adds its low velocity into a position fraction (axis 0: `loc_223,x += loc_2e3,x`; axis 1: `loc_203,x += loc_2c3,x`; axis 2: `loc_243,x += loc_303,x`), then folds that fraction's carry together with the signed whole velocity (`loc_343,x`, `loc_323,x`, `loc_363,x`) into a whole coordinate. The whole is tested against the tube ring [0x10, 0xf0): a rising axis (velocity sign bit clear) overflows when the whole reaches `0xf0` or more, a falling axis (sign bit set) overflows when it drops below `0x10`. Axis 1's whole commits to `loc_263,x`, axis 2's to `loc_2a3,x`, and axis 0's whole commits to the shared cell `loc_283,x` — but any axis overflowing forces that committed value to `0`, which retires the slot. 

`loc_a721` [code] is the companion decay. It seeds a saturation counter `loc_29 = 0xfd`, then steps each of the three velocity pairs (`loc_2c3,x`/`loc_323,x`, `loc_2e3,x`/`loc_343,x`, `loc_303,x`/`loc_363,x`) one increment toward zero through `loc_a75d`, writing the stepped low/whole back. `loc_a75d` bumps `loc_29` on each axis that reaches zero, so the counter climbs from `0xfd` to `0` only when all three axes saturate in the same frame; in that case `loc_a721` clears the slot's whole coordinate `loc_283,x`. `loc_a75d` [code] steps one signed 16-bit velocity toward zero by the fixed increment `loc_a788` (0x20): it stashes the whole into `loc_2b`, adds when the whole is negative and subtracts otherwise, and on crossing zero snaps the low byte `loc_2a = 0` and increments `loc_29`. ## The per-slot object-record draw loop

Every frame the machine turns a compact per-slot object record into a run of
vector-generator words appended to the display list at the write cursor
`loc_74`/`loc_75`. Three near-identical builders — `loc_ab14` [seen],
`loc_ab17` [seen], and the shared tail `loc_ab3b` [seen] — do the expansion, and
a family of small drivers calls them once per fixed slot to compose the frame.

### The shared record builder

`loc_ab14`, `loc_ab17`, and `loc_ab3b` share one body; they differ only in how
much of the record they seed before the common work begins. `loc_ab14` is the
primary entry: given a slot index `x`, it latches the slot into `loc_35`, takes
that slot's header/colour seed from the ROM byte at `loc_d122 + x` into `loc_2b`,
and loads the slot's 16-bit shape-list pointer from the pointer table based at
`(loc_ac)` — the entry at `(loc_ac) + x` becomes `loc_3b` and the next byte
`loc_3c`. When the slot is the marker slot `0x2c` it snapshots the current cursor
into `loc_b6`/`loc_b7`, remembering where in the display list that record began.
It then reads the first byte of the shape list (`(loc_3b)` indirect) into `loc_2a`
as a position seed and lays down the fixed positioning word `0x20`/`0x80` through
`loc_ab0d`. `loc_ab17` is the same routine but takes its `loc_2b` header seed as a
direct argument `a` instead of reading `loc_d122`; `loc_ab98` [code] is a thinner
front that seats `loc_35 = x`, `loc_2a = a`, and a zero header `loc_2b = 0x00`
before falling into `loc_ab3b`.

`loc_ab3b` is the common tail all three converge on, and it is where the record is
actually built. It clears `loc_73`, sets `loc_72 = 0x01`, and emits an intensity
header word (`loc_df6a` with `0x01`). It positions the object by widening the two
seeds `loc_2a` and `loc_2b` by four with sign extension into little-endian
coordinate pairs and emitting that beam-position record (`loc_df75`, whose
`scale4` shifts each value left by two and sign-extends the high byte). It reloads
the shape-list pointer from `(loc_ac)` keyed by `loc_35`, then reads the slot's
scale key from the ROM byte at `loc_d121 + loc_35` and splits it into two scale
settings: the high nibble drives `loc_b0d1` (which latches `loc_9e` and re-emits
only when it changes) and the low nibble drives `loc_b0dd` (which latches `loc_72`
the same way). Finally it walks the shape list: with the output offset `loc_2a`
reset to zero and the read index `loc_2c` starting at one, each list entry is
fetched from `(loc_3b) + listIdx`, its low seven bits `entry & 0x7f` used as a
point offset `src`, and the byte pair at `loc_31e4 + src` and `loc_31e5 + src`
(the two consecutive bytes of a packed vector word in the point table at
`loc_31e4`) is copied into the display list at `(loc_74) + outOff`, advancing the
output offset by two each time. The loop runs until an entry with its high bit set
(`entry & 0x80`) terminates the list, after which `loc_df5f` advances the cursor
past everything written (`loc_2a - 1` plus one). The effect is that a slot's shape
is stored as a short list of point indices and expanded here into a stream of
coordinate words, scaled and positioned per slot.

### The 16-slot moving-object cascade

`loc_b8ba` [code] is the eponymous loop over the object slots, and it is not
reached in the capture. It resets its running accumulators (`loc_6a` through
`loc_6d`, plus `loc_202`, `loc_68`, `loc_69`, all cleared, with `loc_5f` seeded to

## The mathbox: projection and level tables

Tempest draws its tube in perspective through a hardware math coprocessor — the "Math Box" — mapped into the register block at loc_6080 through loc_6096, with its busy signal in the high bit of loc_6040 and its two-byte result read back from loc_6060 (low) and loc_6070 (high). ## Sound, POKEY and the interrupt heartbeat

Tempest carries two POKEY chips, mapped side by side: the first occupies the eight audio registers `loc_60c0`..`loc_60c7` with its control register `loc_60c8`, its random-number register `loc_60ca`, and its serial-control register `loc_60cf`; the second mirrors that layout at `loc_60d0`..`loc_60d7`, `loc_60d8`, `loc_60da`, and `loc_60df`. A software voice engine sits above them, translating abstract sound requests into per-frame register writes, and a short chain of counters riding on the CPU interrupt keeps the game's timebase and running tallies moving.

### The interrupt heartbeat

`loc_cf24` [seen] runs on every interrupt, immediately ahead of the voice stepper, and it is the busiest routine in this group. It walks three parallel lanes indexed 2, 1, 0, each lane gated by its own bit of the control byte `loc_8`: lane 2 by bit 0, lane 1 by bit 1, lane 0 by bit 2 (the code shifts `loc_8` right once for lane 2, twice for lane 1, three times for lane 0, landing the chosen bit in carry — the first shift tests bit 0, so lane order runs opposite to bit order). For each enabled lane it advances a wrapped position held in the `loc_d`/`loc_e`/`loc_f` triple, keeping it masked to five bits (0x1f) and folding it around the 0x20 boundary — a value climbing past 0x1f wraps back low, and the descending branch adds 0x20 then re-clamps to 0x1f. Alongside the position it runs the per-lane down-timer `loc_10`,x: when that timer hits zero it reloads it to 0x78 and raises the carry that drives the accumulator step. That step folds a small per-lane increment into the running pair `loc_16`/`loc_17` (a low/high accumulator advanced with a carry link) and bumps the per-lane counter `loc_13`,x. The increment itself is tiny and lane-specific: lane 0 contributes 0, lane 1 contributes 0x01 only when bit 4 of `loc_9` is set, and lane 2 derives its value from `(loc_9 & 0x0c) >> 2` with a `+2+carry` adjustment — in every case the masked bits act as a gate on whether the contribution lands, not as its magnitude.

After the three-lane sweep, `loc_cf24` reduces the high accumulator `loc_16` by a table amount indexed from the top bits of `loc_9` (the lookup `loc_cfd9`), advancing the overflow tally `loc_18` when the subtraction stays non-negative, and it may nudge `loc_6` from the low two bits of `loc_9` before finally storing `loc_17`. The masks throughout gate which lanes and which steps apply; they are not themselves the stepped values.

`loc_c800` [seen] is the guarded delay that promotes a pending mode. While the guard formed by `loc_3 & loc_16b` is set it does nothing but hand off. Otherwise it runs the delay counter `loc_4` down, and on the frame that counter reaches zero it arms the live mode `loc_0` from the pending mode `loc_2` and clears the guard `loc_16b` back to zero. ### The voice engine and the request path

`loc_cd0a` [seen] is the per-frame sound engine. It scans all sixteen voice slots from 0x0f down to 0, skipping any slot whose value byte `loc_c0`,x is zero (idle) and the one slot currently reserved by the sentinel in `loc_bf`. For a live slot it decrements the fast timer `loc_e0`,x; only when that reaches zero does it decrement the slow timer `loc_f0`,x. If the fast timer expired but the slow one is still running, it takes a single animation step: the slot's frame byte selects a table pair (the `loc_cbcc`/`loc_cbcd` pair, or the `loc_cccc`/`loc_cccd` pair when the frame's high bit is set), reloads the fast timer from one entry, and folds the other into the slot's level byte `loc_d0`,x — with odd-numbered slots preserving the prior high nibble of that level. When both timers have expired it instead walks the frame forward (in steps of two) through the `loc_cbcb`/`loc_cbce` (or `loc_cccb`/`loc_ccce`) tables until it lands on a non-zero frame, reloading both timers and the level as it goes. Whatever the path, the slot's final level byte `loc_d0`,x is published to a POKEY audio register: slots below 8 write into `loc_60c0`,x on the first chip, the upper slots into `loc_60c8`,x. In front of `loc_ccc7` sits the enable gate `loc_ccc3` [code]: it tests the high bit of the enable flag `loc_5` and, only when that bit is set, falls through to register the id in A; with sound disabled it simply returns. Its own vectoring was not witnessed in the capture, though its handler is [seen].

A family of one-line trampolines each carry a fixed sound id into that gate, all threading the caller's X/Y through to the loader, and each is [code] because it makes no cell write of its own — the audible effect is entirely the loader's: `loc_ccb5` id 0x0f, `loc_ccc1` id 0x1f, `loc_ccea` id 0x2f, `loc_cd02` id 0x3f, `loc_ccb9` id 0x4f, `loc_ccb0` id 0x5f, `loc_ccee` id 0x6f, `loc_ccf2` id 0x7f, `loc_ccbd` id 0x8f, `loc_ccf6` id 0x9f, `loc_ccfe` id 0xbf, and `loc_cd06` id 0xcf. `loc_ccfa` [code] is the one exception in shape: it loads id 0xaf but jumps straight into the loader `loc_ccc7`, bypassing the enable gate; which in-game event 0xaf denotes is not settled from the code alone.

## The EAROM high-score store

Persistent settings and high scores live in a small serial NVRAM (an ER-2055-class EAROM) reached through the $6000 hardware block: a data window at `loc_6000` (indexed by a cursor), a control/strobe port at `loc_6040`, and a read-back port at `loc_6050`. Nothing touches that hardware directly on demand; instead callers post a request into three zero-page flag cells and let a single step-driver drain it one entry at a time.

### Posting a request

The request is held in three cells. `loc_1c7` carries the region-pending bits (up to three independent regions, one per low bit); `loc_1c8` carries the matching direction bits (a set bit means write that region out, a clear bit means read it back in); and `loc_1c6` is the blank flag — when nonzero, the write path zeros each source cell as it goes, erasing a region rather than saving it. A family of small front doors seats these cells:

`loc_ddfb` ([seen]) is the general entry: it forces the direction/value pair (mask `0x04`, index `0x00`) and folds them through its shared tail, which stores the index byte into `loc_1c6` and ORs the mask into both `loc_1c7` and `loc_1c8` — a plain, non-blanked write of the region carried by bit `0x04`. `loc_ddf1` ([code]) is the all-regions erase entry: it stamps `loc_1c6` to `0xff` and ORs `0x07` into both `loc_1c7` and `loc_1c8`, requesting a blanked write of all three regions; its specific operands were not observed in the capture (the shared tail those stores live in ran with another entry's values). `loc_ddf3` ([code]) forces the index byte to `0xff` (blank mode) and then merges whatever mask it is handed, so it requests a blanked write of the caller's regions. `loc_ddf7` ([code]) supplies the fixed mask `0x03` to the zeroed-index (non-blank) merge, requesting a write of the two low regions; that particular mask is not reached in the capture. `loc_dde9` ([code]) is a trampoline that feeds mask `0x04` into `loc_ddf3`, i.e. a blanked write of the single region on bit `0x04`.

`loc_de11` ([seen]) stands apart from the OR-in family: it *sets* `loc_1c7` to `0x07` and clears `loc_1c8` to `0x00`, then immediately drives the step-machine. With every direction bit clear this arms a read-back of all three regions — the path that reloads saved state at power-up. Its two direct writes to `loc_1c7`/`loc_1c8` are observed, which is what grounds it.

### Draining the queue

`loc_de1b` ([seen]) is the step-driver, reached often. When the mode byte `loc_1ca` is idle and `loc_1c7` shows a pending region, it opens a fresh region: it clears the pass counter `loc_1cb`, the running accumulator `loc_1cf`, and the mask cell `loc_1ce`, then isolates a single requested region into `loc_1ce` by rotating `loc_1c7` rightward through carry across eight positions until one set bit falls out, counting `x` down from `0x08`. The surviving pass count, doubled, indexes four packed ROM rows: `loc_dddd` gives the starting cursor stored into `loc_1cc`, `loc_ddde` the limit into `loc_1cd`, and `loc_dde3`/`loc_dde4` the low/high halves of a zero-page row pointer in `loc_bd`/`loc_be` that walks the region's RAM copy. The direction is decided here: `loc_1ca` is armed to `0x80` when this region's bit is also set in `loc_1c8` (a write), otherwise `0x20` (a read), and the serviced bit is cleared from `loc_1c7` by XOR with `loc_1ce`.

Each subsequent pass handles one entry and returns, resetting `loc_6040` to `0` on the way in and bailing once `loc_1ca` reaches `0`. On a write, the next RAM byte is fetched through the `loc_bd`/`loc_be` pointer — or forced to zero first when the blank flag `loc_1c6` is set — folded into the running sum `loc_1cf`, and pushed to `loc_6000+cursor`; when the cursor reaches the limit `loc_1cd`, the accumulated sum in `loc_1cf` is written out as a trailing checksum and the mode retires. On a read, the entry strobes the control port through its `0x08`/`0x09`/`0x08` handshake, takes the byte from `loc_6050`, and stores it through the row pointer while folding it into `loc_1cf`; at the limit the freshly read checksum byte is XOR-compared against `loc_1cf`, and a mismatch walks the row pointer back down zeroing every cell and records this region's bit into the result-status cell `loc_1c9`. The pass counter `loc_1cb` and cursor `loc_1cc` advance together, and the final control write to `loc_6040` (values `0x0e`, `0x0c`, or `0`) both clocks the hardware and signals whether to re-enter or stop. The result flags left in `loc_1c9` are what a caller reads back to learn which regions were serviced or failed their checksum.

## State-reset, init and per-frame update chains

This subsystem is the machinery that wipes and re-seeds the game's working RAM at every state transition, and the small handful of per-frame housekeeping passes that age timers, drain a request queue, and fold score. The routines fall into four families: the reset orchestrator and its leaves, the fixed-constant seeders, the control-block rebuild chain, and the per-frame agers.

## Utilities and shared tails

This subsystem gathers the small format-and-scratch helpers that other routines lean on, the fixed-array seeders, and the bare return leaves that terminate several branch chains.

**Binary-to-BCD conversion.** loc_aaf5 [seen] turns the byte handed to it into packed binary-coded decimal by the classic double-dabble method: it walks eight passes, each pass shifting the top bit out of the source and doubling a BCD accumulator with that bit folded back in as a decimal-mode add-with-carry. The digit-bearing writes are observed inside the body — the packed BCD result lands in loc_29 (up to 0x99) and the SAME byte is written a second time to loc_2c (also up to 0x99); both cells receive the identical result, they are not two different digits. (loc_29 is also written earlier in the body with the raw input byte before the conversion, so its stash value ranges lower.) This is the shared numeric-formatting primitive: whenever a raw count needs to be shown as decimal digits, it passes through here first.

**Clamped two-digit readout.** loc_af71 [code] is the front of that display path. It clamps the incoming byte to a maximum of 0x63 (99 decimal), then routes it into the pack-and-emit helper: the clamped value is converted to BCD via loc_aaf5, which seats it in loc_29, and that single zero-page byte is then spilled out as its two decimal digits. The clamp fixes the field at two digits, so the effect is a bounded two-digit on-screen readout. No role-defining own-cell write lives in loc_af71 itself; its work is the clamp and the hand-off.

**Byte-splitter for a fine value plus a coarse index.** loc_93e0 [seen] partitions one input byte three ways. It folds the input's top three bits, MSB first, into the low bits of a 0xff seed, producing a seed of the form 0xf8-with-those-three-bits, which it both stashes in loc_29 and carries out as the seed live-out. The input itself is left shifted up by three positions, giving a fine value carrying the low five bits in the high part of the byte. From the seed's complement it derives a small coarse index as ((seed ^ 0xff) + 0x0d) >> 1. It is reached, exclusively through loc_92c5's three entry points, and its only memory write is the loc_29 scratch, marking it a pure compute helper: one byte in, a fine value / coarse index / seed triple out.

**Rebuild-request flag.** loc_ac36 [seen] sets the two low request bits of the working flags cell loc_1c9, ORing 0x03 into it and returning the merged value; the resulting byte with bits 0 and 1 present is observed written at the body's store. This is the "both blocks need rebuilding" request — callers that detect a geometry-state change (including the mismatch path into loc_ac20) mark the pending work here, and the two bits are later consumed where the actual block copies are performed. It flows straight into the shared no-op return at loc_ac3e.

**Fixed-array seeders.** Two routines lay down constant seed values into paired tables. loc_92b2 [code] swaps two parallel eighteen-entry tables slot for slot: for each index from 0x11 down to 0, the entry in loc_3aa and the entry in loc_3bc trade places, so each table ends holding what its sibling held. loc_b85f [code] seeds two paired three-entry arrays with the fixed values 0, 4, and 0x0c — writing 0 to loc_22 and loc_809, 4 to loc_23 and loc_80a, and 0x0c to loc_24 and loc_80b. Neither routine's role-defining writes are exercised in the capture, so both are grounded [code] / not reached in the capture; their bodies are readable and unambiguous, they simply are not entered along the paths the capture covered.

**A constant-returning leaf that reads like a computation.** loc_b955 [code] appears to count bits: it reads loc_57, shifts it right four, and runs an iny/lsr/bne loop over the remaining bits. But the loop's result is discarded — a clc followed by adc #2 leaves the accumulator at 0+2, and a ldy #0 resets the second register to 0 — so the routine ALWAYS returns the constant pair (2, 0) regardless of what loc_57 holds. It is a fixed-constant leaf, not a population-count of loc_57; the read of loc_57 has no effect on the output.

**Bare return leaves.** The remaining routines are do-nothing terminators, each grounded [code] with no write to ground. loc_9bcf is a no-op dispatch stub: a single bare return occupying a slot in a computed-dispatch set, so selecting it simply falls straight back to the caller. loc_ac07 is the nothing-to-rebuild leaf, tail-branched to when the rebuild-request bits in loc_1c9 are clear. loc_ac3e is the shared return tail reached when the live geometry snapshot ((loc_a & 0xf8) against the latch loc_71e, and (loc_16a & 3) against loc_71f) already matches and no rebuild is needed. loc_af6e is the exposed return tail of the loc_af3f draw routine, branched to when both draw slots (loc_600 and loc_601) are empty and there is nothing to draw. Each is a genuine control-flow terminator whose only job is to unwind.
