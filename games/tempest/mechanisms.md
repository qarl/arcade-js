# Tempest — mechanisms

A code-grounded model of how Tempest actually runs, built from the translated 6502 lift and the idiomatic
rewrite and confirmed against the real ROM under MAME. It covers the subsystems reached by the idiomatic
decompile so far — the motion-script engine, the vector pipeline, enemy spawning and the pursuit AI, the
object-record draw loop, the mathbox projection, sound, and the EAROM — down to the caller routines that
drive them and the computed-jump dispatchers (`loc_b84e`, `loc_b5d7`); the frozen-oracle remainder (the
remaining dispatcher spine and two register-thread callers) is noted at the end. The machine is a colour
vector game: the 6502 builds a display list in AVG vector RAM (`0x2000-0x2FFF`) each frame and the Analog
Vector Generator draws it, with the vblank interrupt as the per-frame heartbeat and a game-state index
driving a computed-jump dispatch that selects the mode handler (attract, coin-in, play, transitions).

**Confidence tags.** `[seen]` — a role-defining observation on the real ROM under MAME (a watched write, a
value change, confirmed reachability). `[code]` — derived from the faithful lift's behaviour, mechanically
exact but the role is inference. `[guess]` — plausible, unverified. A `[code]` routine is real code whose
game-purpose is not yet pinned; where the purpose is genuinely open the identifier stays `loc_<addr>`.

## The object motion-script engine

Each moving object on the tube is driven by a tiny byte-coded script rather than by hand-written per-object motion. The script text lives in ROM at `loc_a0f7` (with `loc_a0f8` its one-byte-later neighbor), and a single instruction pointer, `loc_10b`, walks it. The per-object driver arms a walk by setting the continuation flag `loc_10a` to 1 and then, for each script byte it fetches, hands control to one of the opcode handlers below through a computed-jump (RTS-trick) dispatch, looping while `loc_10a` stays nonzero. The handlers read and rewrite `loc_10b` to move through the script, park results in the current object's per-slot cell `loc_298,x`, and consult or set the single branch flag `loc_10c` that ties conditionals together. The whole family is a small interpreter: fetch/advance/store opcodes, two flavors of test that produce the branch flag, conditional and unconditional gotos that consume it, a per-slot countdown, and a terminator.

**Terminating the walk.** `loc_9bca` [seen] is the leaf that ends the current object's pass: it stores 0 into `loc_10a` and returns. Because the driver loops only while `loc_10a` is nonzero, this is the opcode a script uses to say "done with this object for now." It is exercised on essentially every walk.

**Store opcodes (write into the object's slot).** `loc_9bd0` [seen] is the immediate store: it bumps the instruction pointer `loc_10b` by one (wrapping to a byte), then copies the script byte now selected — `mem8[loc_a0f7 + loc_10b]` — straight into the object's slot `loc_298,x`. The advance and the slot write are both observed, the slot writes landing across the active object slots (`0x29b`–`0x29e`). `loc_9bdd` [seen] is its indirect sibling: it likewise advances `loc_10b`, but treats the selected script byte `mem8[loc_a0f7 + loc_10b]` as a zero-page address and copies the *pointed-at* live variable `mem8[loc_00 + ptr]` into `loc_298,x`. So `loc_9bd0` plants a constant from the script while `loc_9bdd` plants whatever a chosen zero-page variable currently holds — a constant load versus a live-variable load into the same slot cell.

**Test opcodes (produce the branch flag `loc_10c`).** `loc_9c21` [code] is the boundary test: it reads the slot's segment index `loc_2b9,x`, looks up that segment's boundary value in the per-segment table `loc_3ac` (a table entry of 0 is treated as the maximum, `0xff`), and sets `loc_10c` to 1 when that boundary is at or beyond the slot's depth `loc_2df,x`, else 0 — i.e. the flag reports whether the object is still within its allowed reach along the lane. Its store to `loc_10c` is not reached in the capture (the flag seen during the window was produced elsewhere), so it carries the [code] tag. `loc_9c3b` [code] is the accumulator-phase test: it forms `(((loc_147 << 2) + loc_148) & loc_148 & 0x80) ^ 0x80` as a byte and writes the result to `loc_10c` — the value is `0x00` when that combined high bit is set and `0x80` when it is clear (the neighboring phase logic advances the `loc_148` accumulator by the `loc_147` step, though this handler only reads the pair). Because the branch flag is elsewhere tested only for nonzero, `0x80` reads as "set." Its store at the tail is likewise absent from the capture, so [code].

**Branch opcodes (consume the branch flag).** `loc_9bee` [seen] is the two-byte skip: if `loc_10c` is nonzero it does nothing, otherwise it advances `loc_10b` by two, stepping the pointer past a two-byte operand. `loc_9bfa` [seen] is the conditional goto: it first advances `loc_10b` by one, then — only while `loc_10c` is zero — reloads `loc_10b` from the operand it now points at, `mem8[loc_a0f7 + loc_10b]`, redirecting the walk to that target. Both the ordinary advance and the target reload are observed. `loc_9c17` [seen] is the unconditional goto and doubles as a loop-back tail: it reloads `loc_10b` from `mem8[loc_a0f8 + loc_10b]` — the byte following the current opcode in the script — with no flag consulted. It is heavily exercised, its pointer reload pulsing across a range of low values.

**Per-slot timing.** `loc_9c0c` [seen] is the countdown opcode: it decrements the slot cell `loc_298,x`; while that cell stays nonzero it delegates to `loc_9c17` to take the table-driven pointer step (holding the object in its current scripted state as the timer runs), and only when the cell reaches zero does it instead bump the shared counter `loc_10b` to move the script forward. It is one of the most heavily run handlers in the family, since it fires while an object simply waits out a timed state.

**List-cursor skip (separate dispatch).** `loc_96c7` [code] belongs to a sibling computed-dispatch path — reached through `loc_9683`'s `$969d` table (an RTS-style select on `loc_15e`) rather than the `loc_a0f7` script walk. It is register-only and advances the packed-list cursor `Y` to step over a record without reading it: entry `loc_96c7` bumps `Y` by one and falls into `loc_96c8`, which adds two more, so the first entry skips a three-byte record and the second (`loc_96c8`) a two-byte one. It has no memory writes of its own — nothing to observe — and is not reached in the capture, so [code].

## Vector coordinate lists and the display cursor

Every shape Tempest paints reaches the AVG (Atari analog vector generator) display list as a stream of two-byte words, and this subsystem is the machinery that packs those words and keeps the write position moving. The write position is a single little-endian 16-bit pointer held in `loc_74`/`loc_75`, and `loc_df5f` [seen] is the one primitive that advances it: it forms `loc_74 + Y + 1` (the addition runs with carry already set, so the stride is always `Y + 1`, not `Y`), stores the low byte back into `loc_74`, and on overflow past `0xff` bumps `loc_75`. This routine sits at the tail of essentially every emitter below and is exercised on essentially every pass; the pointer it drives sweeps the `$2000`–`$2fff` vector-RAM window as the display list is rebuilt each frame.

The lowest-level emitters all store a word and then hand `loc_df5f` the stride to skip past it. `loc_df57` [seen] is the shared vector-word tail: it writes the accumulator byte at the cursor origin `(loc_74)+0`, the X byte at `+1`, and then advances the cursor by two (it calls the advance with stride 1, which becomes `Y+1 = 2`). `loc_df53` [seen] is a fixed-header front for that tail — it enters with `A=0x40, X=0x80`, emitting the `{0x40,0x80}` header word that marks the start of an absolute-position record. `loc_df59` [seen] is the offset-relative sibling: it stores the pair `{A,X}` at `(loc_74)+Y` and `(loc_74)+(Y+1)`, then advances by `Y+2`, so a caller that has already laid down `Y` bytes can append a word without recomputing the base. These three are the core word-store paths and their writes into `$2xxx` carry real vector data across wide value ranges.

Two more emitters translate a nibble into a table-driven word. `loc_df19` [seen] takes the low nibble of A and picks a word-table index — index 0 only when the carry is set *and* the nibble is exactly zero, otherwise `nibble + 1` — doubles it, and copies the two bytes of the ROM word table at `loc_31e4[idx]` into the list at the cursor before advancing one word. `loc_df1f` [seen] is the thinner front of the same idea: it forces the index to `(A & 0x0f) + 1` (no carry-zero special case) and shares the emit tail, copying `loc_31e4[idx]`'s two bytes through the cursor. Both leave the geometry choice to that `loc_31e4` word table and only the index arithmetic distinguishes them.

The coordinate lists that feed the walkers are addressed through the zero-page pointer pair `loc_2c` (low) / `loc_2d` (high), with `loc_2b` holding the currently selected list index. `loc_9aee` [seen] installs that pointer: indexed by Y it loads `loc_2c` from the ROM table at `loc_9b02` and `loc_2d` from the table at `loc_9afd`, stashes Y into `loc_2b` as the chosen index, and reloads A from `loc_29`. `loc_9a9d` [code] is the fixed-seed variant used for the attract/demo list — it takes `loc_2c` from the very first entry `loc_9b02[0]`, forces the index `loc_2b = 0`, draws the high byte `loc_2d` from the held source cell `loc_15d`, and likewise reloads A from `loc_29`; its one observed own write is constant, so its role rests on the code.

With the pointer set, several helpers step through the packed list. `loc_96cb` [seen] reads the entry at the cursor and its predecessor, stores their difference (observed running across the real inter-entry steps `1`–`0xf`) into the step-delta scratch `loc_29`, and advances the cursor by that delta plus two — the walker that turns a list of stops into successive draw positions. `loc_96db` [code] resolves a single list entry to an absolute coordinate: it reads the byte at `(loc_2c)+Y` and adds the base value in `loc_160`, returning the sum in A; it is a pure compute helper reached only through a computed dispatch, so no own write can confirm it. `loc_96ab` [seen] is a re-indexing coordinate helper: it stashes the incoming cursor into `loc_29`, forms a starting value of `((loc_2b - 1) & 0x0f) + 1`, subtracts the list byte two entries back at `(loc_2c)+(Y-2)`, adds `loc_29` again, then re-indexes by that result to load the entry it lands on (its sibling entry `loc_96b7` does the same with the raw `loc_2b`, and `loc_96c4` is the bare fetch at `(loc_2c)+Y`); its only own write is the `loc_29` scratch.

`loc_96f4` [code] and `loc_96e2` [code] read the same list to produce a fold rather than a coordinate. `loc_96f4` records the cursor index into `loc_29` and returns `(loc_2b - list-byte-two-slots-back) & 0xff`, i.e. the base index minus the operand at `(loc_2c)+(Y-2)`. `loc_96e2` uses that as a repeat count: it loads the first entry at `(loc_2c)+Y`, advances Y once, and if the count is non-zero folds that many additional copies of the entry at the advanced position into a single one-byte total (the loop re-adds the same entry `count` times, wrapping at `0xff`). Both are auto-derived callers grounded only at the code level here.

Two producers assemble full display records rather than single words. `loc_c772` [seen] (entering with the cursor offset at zero via `loc_c774`) emits an absolute object-position record: first the `{0x40,0x80}` header, then an X word whose low byte comes from `(loc_2 + X)` and high byte from `(loc_3 + X)` with the high byte masked to five bits, then a Y word from `(loc_00 + X)` low and `(loc_1 + X)` high, again masked to five bits. As it goes it caches the four raw bytes into `loc_6a`–`loc_6d` as the "previous point" that later stroke-delta code subtracts from, then advances the cursor past the six emitted bytes; it is a heavily reached producer. `loc_aef8` [seen] emits text: it sets a source index `loc_38 = A + 2` and a count `loc_39 = 0x02`, then loops three times copying two-byte glyph words. Each pass reads a character code from the `loc_606` buffer at `loc_38`, clamps any code `>= 0x1e` down to `0x1a`, doubles it into the glyph word table at `loc_31fa`, and copies both bytes through the cursor (the high byte being the AVG draw opcode); it decrements `loc_38` and `loc_39` each pass and continues while `loc_39` stays non-negative, wrapping the count from `0` to `0xff` to break after the third glyph, then advances the cursor past what was written.

Finally, `loc_df0d` [code] and `loc_df12` [code] build a variable-length record with a header. `loc_df0d` emits the `{0x40,0x80}` header via `loc_df53` and then stores a fixed body byte `0x20` at the cursor origin through `loc_df12`; it is not reached in the capture. `loc_df12` stores its input byte at the cursor origin `(loc_74)` and continues into the shared record tail at `loc_dfac`, which appends further bytes and either advances the cursor or, when the slot index wraps to zero, runs the terminating packed-nibble byte run. `loc_df12` itself is reached through a different front that presets the body byte to `0xc0`, but its emitted value is constant there, so both routines are held at the code level.

## Draw-pointer setup and vector emission

Tempest paints its picture into the AVG vector RAM at $2000–$2FFF, and almost every routine that builds a frame writes there through one shared indirect cursor held in `loc_74`/`loc_75` (low/high). This family is the plumbing under that cursor: the routines that *publish* a draw pointer into the cursor cells, the small primitives that *store* a word and *step* the cursor, and the larger builders that turn coordinates, glyphs, and packed digits into the vector-generator opcodes the hardware chews on. Two cells thread through the whole family: `loc_74`/`loc_75` is the byte-address the next write lands under, and `loc_a9` is the running cursor *offset* several builders add on top of that base while they lay a multi-word record.

### The store/advance primitives

The lowest layer is `loc_df5f` [seen], which advances the little-endian cursor `loc_74`/`loc_75` by its argument plus one (the 6502 `sec;adc` forces the extra count), carrying into `loc_75` on overflow; it is exercised on essentially every emit. Sitting on top of it, `loc_df59` [seen] is the core two-byte emitter: it stores the pair {A, X} at `(loc_74)+Y` and `(loc_74)+(Y+1)` then advances the cursor past them, and it is the tail that the math-box appenders below jump into. `loc_df57` [seen] is the sibling that always writes at the cursor *origin* — A at `(loc_74)+0`, X at `+1` — and steps the cursor by two; `loc_df53` presets it with the fixed `{0x40,0x80}` header pair. Three thin fronts feed `loc_df57` with constant headers: `loc_ab0d` [code] emits the `{0x20,0x80}` word, `loc_df4c` [code] emits `{Y, A|0x60}` (the mid-header tag), and `loc_df6c` [code] emits `{Y, A|0x70}` (the upper-header tag); above those, `loc_df4a` [code] calls `loc_df4c` with the table byte `loc_73` as its second operand, and `loc_df6a` [code] calls `loc_df6c` with a zero data byte. Of these, `loc_ab0d`, `loc_df4c`, `loc_df6c` and `loc_df6a` are reached in the capture as dispatched emit-callers (none leaves a role-defining own write); `loc_df4a` is not reached. Their roles rest on the code.

### Publishing a draw pointer

Several routines choose a 16-bit pointer out of a ROM table and publish it so the emitters that follow write into the right buffer. `loc_b2be` [seen] is the per-subsystem setup: from selector A it reads the per-index flag `loc_415`[A] and picks table `loc_ce68` when that flag is non-zero or `loc_ce7a` when it is zero, takes the two-byte pointer at stride `2*A`, publishes it into `loc_74`/`loc_75`, and clears the offset cell `loc_a9`. Its twin `loc_b2de` [seen] does the same selection but with the two tables *swapped* — non-zero flag picks `loc_ce7a`, zero picks `loc_ce68` — and publishes into the *other* pointer pair `loc_3b`/`loc_3c` (the glyph/text pointer), again clearing `loc_a9`. `loc_91b5` [seen] doubles its selector into a word index, clears the paired flag byte `loc_29`, and copies the little-endian pointer at ROM table `loc_91c6`+`2*A` into the working pointer `loc_2a`/`loc_2b`. `loc_b967` [code] selects an (A, X) pair by the flag `loc_415`: zero yields (`loc_ce87`, `loc_ce86`), non-zero yields (`loc_ce6f`, `loc_ce6e`); its consumer stores those as a draw-struct pointer, but `loc_b967` itself was not reached in the capture. `loc_b944` [code] swaps the two pointers `loc_74`/`loc_75` and `loc_76`/`loc_77` so the shared cursor addresses the other structure; it too was not reached in the capture (its only caller never ran).

`loc_b56a` [seen] appends a bare four-byte record — 0, 0, 0, A — at the current `loc_74`/`loc_75` and advances that pointer by four, and it is heavily exercised across the whole vector buffer. `loc_b332` [seen] is a frame-guard emitter: it compares `loc_cec4` against the checkpoint byte at `loc_2000`, and if they differ it latches the new value into `loc_2000` and returns carry set to signal "frame changed, redo"; otherwise it emits a two-byte word from `loc_ce9e`[x] through the `loc_74` cursor, clears `loc_16e`, and reloads the cursor from `loc_ce68`[x], where the record slot x is 8 when `loc_415` is non-zero and 2 otherwise.

### The computed draw dispatch

`loc_b84e` [code] is a computed dispatch: the caller passes Y as a byte offset (0,2,4,6) into a four-entry table, and it hands off to whichever of `loc_b85f`, `loc_b875`, `loc_b888`, `loc_b896` the index `Y>>1` selects — so its four targets are reached only through `loc_b84e`, never callerless. `loc_b84e` itself was not reached in the capture. One of its targets, `loc_b896` [code], writes the 16-bit cursor `loc_139`/`loc_13a` into the vector-RAM tail — `loc_2ffc` gets the low byte, `loc_2ffd` the high byte tagged with `0x70`, and `loc_2fff` the `0xc0` terminator — then steps the cursor down by 0x20 with a 16-bit borrow (decrementing `loc_13a` on underflow) and masks the low byte to `0x7f`; it was not reached in the capture, so those five target cells rest on the code.

### Glyph and packed-digit emission

A whole sub-family turns nibbles into vector words out of the ROM word-table at `loc_31e4`. The two-byte version is `loc_df19` [seen]: it turns the low nibble of A into a table index (0 when carry is set and the nibble is zero, otherwise nibble+1), copies *both* bytes of `loc_31e4`[index] into the `loc_74` list, and advances the cursor; `loc_df1f` [seen] is the same emit with the index forced to nibble+1. Contrast this with `loc_a9fc` [seen], the glyph-buffer version, which is *not* a word emit: it maps A's low nibble to y (nibble+1, or 0 for a zero nibble with carry set) and stores the **single** byte at `loc_31e4`+`2*y` into the `loc_2f60` buffer at cursor X, then advances X by two — so it leaves the odd slot `loc_2f60`+X+1 untouched.

`loc_df19` is driven by `loc_dfb1` [seen], the packed-digit run driver, which is exercised extensively: given a start it walks a run of Y zeropage bytes from source index `A+Y-1` downward (tracking the count in `loc_ae` and the index in `loc_af`), emitting each byte's high nibble then its low nibble through `loc_df19`, chaining the carry so that only the final low nibble sees it cleared (the terminator marker). Three fronts feed `loc_dfb1`: `loc_aa9e` [code] bumps a slot index, publishes it through `loc_61`, and emits that one-byte run; `loc_af77` [code] packs its input to BCD (via the double-dabble in `loc_aaf5`, whose result lands identically in both `loc_29` and `loc_2c`, each ranging 0x00–0x99) then emits the single byte at `loc_29`; and `loc_b0c6` [code] selects a pointer through `loc_91b5` then emits a three-byte run starting at `loc_29`. All three fronts are reached in the capture (loc_aa9e publishes its loc_61 write; loc_af77 and loc_b0c6 run as callers), though their game-role certs still rest on the code.

The glyph-string path mirrors this over `loc_a9fc`. `loc_a9d7` [seen], heavily reached, seeds a three-pass counter in `loc_2a` and walks the packed glyph string backward through `loc_3b`/`loc_3c`, emitting each source byte's high then low nibble via `loc_a9fc`, carrying the same "only the last nibble clears" convention and decrementing `loc_3b` after each byte. Above it, `loc_a97f` [seen] builds a seven-entry marker row into the `loc_2f60` buffer: it saves the row index into `loc_2b`, computes a head value (A | 0x70, zeroed only when Y hits the marker index `loc_3d` and `loc_5` bit7 is set), reads the row count from `loc_48`[Y] into `loc_38` (one short at the marker), then fills rows using the alternate glyph `loc_3286` past the count and the main glyph `loc_3284` within it; unless the state cell `loc_00` is 4 away from the marker (an early out), it seeds the glyph pointer `loc_3b`/`loc_3c` from `loc_a97d`[Y] and hands off to `loc_a9d7`.

### Coordinate-record emission (the scaled-delta path)

A second builder family emits four-byte coordinate records through the same cursor. The record layout is written by `loc_df92` [seen]: at the cursor origin it lays byte0 = `loc_2`+X, byte1 = (`loc_3`+X) masked to 5 bits, byte2 = `loc_0`+X, and a fourth byte computed by folding `loc_1`+X against the key `loc_73` as `((in ^ key) & 0x1f) ^ key`; the tail `loc_dfac` stores that last byte at the next cursor slot and either advances (via `loc_df5f`) or, if the slot index wrapped to zero, runs the terminating byte run. `loc_df75` [seen] preloads the delta slots for it: it widens two input values by four with sign extension — low = `v<<2`, high carries the sign and bit 6 of v — into the little-endian pairs `loc_6e`/`loc_6f` and `loc_70`/`loc_71`, then emits through `loc_df92`. `loc_df73` [code] stashes its index byte into the key cell `loc_73` before scaling via `loc_df75`, and was not reached in the capture.

`loc_c3ba` [seen] computes the record as two 16-bit differences of "current minus previous" — (`loc_61`/`loc_62`)−(`loc_6a`/`loc_6b`) into `loc_6e`/`loc_6f`, and (`loc_63`/`loc_64`)−(`loc_6c`/`loc_6d`) into `loc_70`/`loc_71` — emits it through `loc_df92`, then latches current into previous (copying `loc_61`–`loc_64` into `loc_6a`–`loc_6d`) and flags the key cell `loc_73` = 0xc0 for the next pass. `loc_c423` [seen] snapshots four indexed table cells (`loc_32a`/`loc_31a`/`loc_34a`/`loc_33a` at index `loc_37`) into the record header `loc_61`–`loc_64` and then emits via `loc_c3ba`. `loc_c36e` [seen] is the gated record-draw loop: it returns immediately when its gate byte A is non-zero; otherwise it seats the four header fields from the same indexed tables, emits a fixed header word plus two coordinate words through `loc_c772`, caches the resulting cursor into `loc_b0`/`loc_b1`, sets the run length to 0x0e or 0x0f depending on `loc_111`, and draws one record per pass via `loc_c423`, decrementing the slot index `loc_37` and bumping it by 0x10 whenever its low nibble saturates to 0x0f.

`loc_df39` [code] emits a single coordinate word: the high byte is bits 4..1 of A tagged with `0xa0` (`((A>>1)&0x0f)|0xa0`, not the upper nibble) and the low byte is X rotated right with A's LSB shifted into bit 7; it stores those two, and if the cursor index did not wrap it advances, otherwise it falls into `loc_df4c`. It is reached in the capture — its emit path stores coordinate words into vector RAM. `loc_d8a9` [code] stashes A into `loc_29`, scales two coordinates via `loc_df75`, and emits that one stashed byte as a single-entry run; `loc_dd2b` [code] scales two coordinates via `loc_df75` (the fixed operands `0xd0`/`0xf8` are coordinate deltas widened x4 into `loc_6e`–`loc_71`) then shifts the caller's live-in byte `loc_35` out MSB-first, emitting each of its eight bits as one vector digit through `loc_df1f`; its two fronts `loc_dd29` [code] (index preset `0xf8`) and `loc_dd27` [code] (value preset `0xd0`, feeding `loc_dd29`) are fixed-operand wrappers. None of `loc_d8a9`, `loc_dd2b`, `loc_dd29`, or `loc_dd27` was reached in the capture.

`loc_dd41` [code] is the score/digit builder that folds all of these together and was not reached in the capture. It first does a packed-decimal add of two little-endian input pairs — the first (`loc_40f`/`loc_410`) doubled into `loc_29`/`loc_2a`, added to `loc_40c`/`loc_40d` into the coprocessor operands `loc_6095`/`loc_6096`, forced to a minimum of one when the result is zero — issues a divide through `loc_dce6` (results into `loc_412`/`loc_413`), lays a leading word via `loc_df39`, then over five outer passes (index `loc_37` = 4 down) walks the three-byte source the pointer `loc_3b`/`loc_3c` reads, running a binary-to-BCD double-dabble (23-plus-iteration inner loop shifting `loc_56`/`loc_57`/`loc_58` into the four-digit BCD accumulator at `loc_31`) and emitting each pass's converted digits through `loc_dfb1` followed by a scaled record via `loc_df75`.

### Math-box projected pairs

The perspective work goes through the math coprocessor and lands as a (mantissa, exponent) pair in the vector list. `loc_bd3e` [seen] is that appender: for a small input (`loc_57` < 0x10) it emits the trivial pair (mantissa 1, exponent 0); otherwise it forms the 16-bit difference `loc_57`−`loc_5f`/`loc_5b` into the operand registers `loc_6095`/`loc_6096`, issues the compute through `loc_608c`/`loc_608e`/`loc_6094`, spins on `loc_6040` bit 7 until done, reads the results `loc_6060`/`loc_6070` into `loc_79`/`loc_7a`, then normalizes `loc_79` into a mantissa shift count while rolling the exponent, storing the shift into `loc_78`. It writes the exponent byte and the `mantissa|0x70` byte at `(loc_74)+loc_a9`, and returns the exit cursor `loc_a9`+2 for the caller to thread onward.

## Enemy spawning and lane selection

This subsystem decides which segments of the tube new enemies appear in, allocates them into the per-slot enemy arrays, feeds a separate short-lived "timed object" table, and steps each active enemy toward the lane it is aiming for. Throughout, a slot is one enemy tracked in a bundle of parallel arrays indexed by the same `x`/`y`: `loc_2df` holds the slot's depth down the tube, `loc_2b9` its current segment (0..0x0f around the 16-segment rim), `loc_2cc` the neighbouring segment it will flip toward, `loc_283` and `loc_28a` its two flag bytes, and `loc_2a6` a per-slot countdown timer.

### Allocating a new enemy slot

`loc_994d` [seen] is the enemy-slot allocator. On a free slot it seeds the whole parallel bundle for that `y`: the depth `loc_2df,y` takes the staged value from `loc_29`; the segment value comes from `loc_2a`, except that when `loc_2a` is exactly `0x0f` and the global gate `loc_111` has bit7 set it is instead drawn fresh as `loc_60ca & 0x0e` (an even POKEY-random segment), and that value is written to `loc_2b9,y` while its successor `(value+1) & 0x0f` goes to `loc_2cc,y`. The slot's timer `loc_2a6,y` is cleared to 0, its flag bytes are seeded from the staging cells (`loc_28a,y` from `loc_2c`, `loc_291,y` from `loc_2d`, and `loc_283,y` from `loc_2b`), the global active count `loc_108` is bumped by one, and the per-lane counter `loc_142` is incremented at the lane index `loc_2b & 0x07` taken from the low three bits of the seeded flag. ### Choosing which lanes are eligible

`loc_9246` [seen] refills the per-slot tag tables that the lane logic reads. ### Selecting an enemy's target segment

## Enemy motion and the pursuit AI

Each enemy on the tube occupies one of sixteen slots, and the state for a slot lives in a spread of parallel zero-page/RAM tables indexed by the slot number in `x`. The governing byte is `loc_283`,x: a nonzero value marks the slot live, its low three bits carry the enemy's kind/turn-state, bit 6 is the rim travel-direction flag, and bit 7 is the sign/active bit. Alongside it each slot carries a segment index `loc_2b9`,x (which lane of the tube the enemy sits in, 0..0x0f), a tube-depth byte `loc_2df`,x, and a phase/animation counter `loc_2cc`,x.

### The per-frame slot walk

`loc_a618` (tag [code]) is the frame driver for the enemy slots. It first copies the spawn budget `loc_10e` into the frame-active flag `loc_10d`, then walks the sixteen slots from 0x0f down to 0. The step routine leaves its last axis's whole byte in a register, and `loc_a618` threads that register forward so the next spawn stamps it — the last live slot's stepped value rides into each subsequent spawn. After the walk it settles the slot cursor `loc_37` to 0xff, ticks the spawn countdown `loc_10e` toward zero on even frames only (`loc_3` bit 0 clear), and, if nothing was live or spawned (`loc_10d` still zero), raises the mode-request byte `loc_0` to 0x12. ### Motion integration

`loc_a6a9` (tag [code]) integrates a slot's three motion axes. ### Rim direction and the pursuit AI

The pursuit logic turns on the signed segment difference computed by `loc_a7a6` (tag [seen]). It forms A minus Y and stashes it in `loc_2a`, then either keeps the full byte (when the geometry flag `loc_111` has bit 7 set) or masks to the low four bits and sign-extends bit 3 into a signed byte (the 16-segment wrap case). `loc_9d06` (tag [seen]) is the per-slot pursuit step. It first stashes the shared depth byte `loc_202` into the slot's depth `loc_2df`,x. `loc_9d82` (tag [seen]) advances a turning enemy's animation. ## The per-slot object-record draw loop

This subsystem turns the game's active on-tube objects into vector display-list
words. Two pieces cooperate: a shared list-copy engine that expands one object's
stored point list into buffer words, and the per-frame drivers that call it in a
fixed order to lay out every object, panel and readout for a frame. Everything is
emitted through the little-endian write cursor `loc_74`/`loc_75`; the source point
lists are reached through the draw-list pointer `loc_ac`; and the raw point
coordinates come from the ROM tables at `loc_31e4` (low) and `loc_31e5` (its
paired next byte).

### The shared list-copy engine — loc_ab14 / loc_ab17 / loc_ab3b / loc_ab98

`loc_ab14` [seen] is the object-render entry keyed by slot index. Given a slot in
X it reads that slot's scale/type byte from the ROM table `loc_d122 + x` into
`loc_2b`, stashes the slot number in `loc_35`, and fetches the object's 16-bit
point-list pointer into `loc_3b`/`loc_3c` from the draw-list table addressed by
`loc_ac` (two consecutive bytes at `(loc_ac) + x` and `+ x+1`). When the slot is
the marker slot `0x2c` it caches the current write cursor into `loc_b6`/`loc_b7`
for later use. It takes the list's first byte `[(loc_3b)]` as the anchor value in
`loc_2a`, emits the fixed lead word `{0x20,0x80}` through `loc_ab0d`, primes the
scale byte `loc_72 = 0x01` and emits a header word, then hands `loc_2a`/`loc_2b`
to `loc_df75`, which sign-extends each ×4 into the `loc_6e..loc_71` deltas and
lays down the anchor vector record. It then re-reads the list pointer, splits the
per-slot key at `loc_d121 + loc_35` into its two nibbles and pushes them through
`loc_b0d1` (high nibble → scale tag in `loc_9e`) and `loc_b0dd` (low nibble →
header in `loc_72`). The copy loop follows: starting at list index 1 it reads each
entry, masks off the terminator bit to form `src = entry & 0x7f`, and writes the
two consecutive coordinate bytes `loc_31e4 + src` and `loc_31e5 + src` into the
buffer at `(loc_74) + loc_2a`, bumping `loc_2a` by two each entry and tracking the
running list index in `loc_2c`; it stops after the entry whose bit 7 is set (the
list terminator), then advances the cursor by `loc_2a - 1` (plus one) through
`loc_df5f`.

`loc_ab17` [seen] is the same engine with the scale byte supplied directly: it
takes both A and X, storing A straight into `loc_2b` instead of looking it up in
`loc_d122`, and is otherwise identical (slot in `loc_35`, the `0x2c` cursor
cache, the anchor emit, the nibble keys, the terminator-bounded copy loop). This
lets a caller draw a list with a chosen scale rather than the table's default.

`loc_ab3b` [seen] is the bare record builder that expects `loc_35`, `loc_2a` and
`loc_2b` already seated by its caller: it skips the `{0x20,0x80}` lead word and the
`0x2c` cursor cache, going straight to the header emit, the `loc_df75` anchor
record, the `loc_d121` nibble keys and the same terminator-bounded copy loop into
`(loc_74)`. `loc_ab98` [code] is the thin front that seats those inputs —
`loc_35 = x`, `loc_2a = a`, `loc_2b = 0x00` — before running `loc_ab3b`; it holds
no distinctive own write of its own, so it reads code-only here.

### The per-frame draw drivers

`loc_aaa8` [seen] is the object-and-readout driver. It first draws a tube-face
variant slot chosen by phase — `loc_ab14(loc_a8b0 + (loc_9 & 0x03))`, the low two
bits of `loc_9` indexing the ROM table `loc_a8b0` — then decrements the counter
`loc_16e`. When the phase gate `loc_a & 0x01` is set and the mode bit `loc_3 &
0x20` is clear it draws the alternate slot `0x32`, otherwise it defers to
`loc_aeca`. It then draws the two fixed slots `0x2c` and `0x2e`, clamps `loc_6`
down to a ceiling of `0x28`, packs that value to BCD and emits it as nibbles
through `loc_af77`, and finally, only when `loc_17` is nonzero, posts one more
coordinate word via `loc_df39(loc_aaf4, loc_aaf3)`. Its own `loc_16e`
counter tick is observed decrementing in the capture, and it drives the observed
render setups, so it is grounded [seen].

`loc_a8b4` [seen] and `loc_a8e7` [seen] are the two near-identical per-frame
overlay setups. `loc_a8b4` opens with the preamble the tail lacks: it seats
`loc_72 = 0x01`, emits its header, and forces scale tag `loc_b0d1(0x05)`. Unless
the freeze bit `loc_5 & 0x80` is set it then picks a marker slot — `0x00` when
`loc_3 & 0x20`, else `0x22` when `loc_6 == 0` or the sign bit `loc_a2 & 0x80` is
set, else `0x06` — draws it with `loc_ab14`, snapshots `loc_31e4` into both mirror
cells `loc_2fa6` and `loc_2fa8`, and runs `loc_aaa8`. Both routines then emit the
base marker list through `loc_a97f(0x01,0x00)`, and emit a second list through
`loc_a97f(0x01,0x01)` only when the flag source is nonzero — that source is
`loc_3e` under the freeze bit, otherwise the OR of `loc_43 | loc_44 | loc_45`.
When the state byte `loc_0` is not `0x04` they rebuild a small fixed structure:
seed `loc_3b`/`loc_3c` to `0x1d`/`0x07`, run `loc_a9d7(loc_cde4)`, fold the eleven
bytes at `loc_aace + 0x0a .. loc_aace` into a checksum seeded at `0xa7` stored to
`loc_16c`, then copy three doubled-index entries `loc_31fa + (loc_61b[c] << 1)`
into the strided mirror at `loc_2f60` starting from `loc_cde5` (stride two). Here
the two diverge only in bookkeeping: `loc_a8b4` runs the copy as a fixed
three-iteration count and closes with `loc_38 = 0xff`, while `loc_a8e7` drives it
with `loc_38` counting down from `0x02` and breaking when it goes negative. Both
then emit the framing word `loc_df39(0x2f,0x60)`, draw slot `0x36` when
`loc_123 & 0x80`, and — only when `loc_0 == 0x18` and the freeze bit `loc_5 &
0x80` is set — draw the indexed pair `loc_ab14(0x30)` plus `loc_b0c6` when
`loc_102 + loc_3d` is nonzero, followed by the two trailing markers `0x3a` and
`0x38`. `loc_a8e7` is the tail entry that skips `loc_a8b4`'s leading overlay
preamble and starts at `loc_aaa8`.

The remaining routines are thin ordering fronts, each with no distinctive own
write and so all [code]. `loc_aa92` draws the fixed slot `loc_ab14(0x02)` then
falls into `loc_aa97`, which publishes a zero header via `loc_b0dd(0x00)` and emits
the run for the slot named in `loc_3d` through `loc_aa9e`. `loc_aa5a` draws slot
`loc_ab14(0x08)` then runs `loc_aa69`, which runs `loc_aa92` and dispatches
`loc_a8e7`. `loc_aa62` primes a list with `loc_ab17(0x30, 0x00)`, runs `loc_aa92`,

### The per-slot object-record draw loop proper — loc_b8ba

`loc_b8ba` [code] is the record-emitting loop that walks the object slot arrays
from the top down; it was not reached in the capture (no write program-counter
appears anywhere in its region, and its own seed cells are driven only from other
code paths), so its role is read from the code. It opens by emitting a header word
`loc_df39(0x3f, 0xf2)` and clearing the delta history and accumulators — the
"previous" delta cells `loc_6a`/`loc_6b`/`loc_6c`/`loc_6d`, `loc_202`, and
`loc_68`/`loc_69` all to zero, with `loc_5f = 0xe0` and `loc_5b = 0xff` as the
starting limits. It selects the base draw-struct pointer through `loc_b967` (one
of two ROM pointer-table pairs chosen by the RAM flag `loc_415`) and stores it into
`loc_77`/`loc_76`. Then, with the slot counter `loc_37` starting at `0x0f`, it
loops downward, breaking once the decrement carries below zero (bit 7 of the next
value set).

For each slot it reads the activity byte `loc_283 + x`; a zero skips the slot. When
active, it copies that byte into `loc_57` and the slot's two companion bytes
`loc_263 + x` and `loc_2a3 + x` into `loc_56` and `loc_58`, then integrates the
frame's motion through `loc_c098`, which clamps signed X/Y deltas into the math
coprocessor and folds them into the 16-bit accumulators `loc_61..loc_64`. It clears
`loc_73`, swaps the working and shadow cursors with `loc_b944`, lays a difference
record through `loc_c3ba`, writes the four-byte block `{0,0,0,0xa0}` with
`loc_b56a`, swaps the cursors back, and emits the object's coordinate words from
those accumulators via `loc_c772(0x61)` (whose zeropage index `0x61` reaches
exactly the `loc_61..loc_64` pairs). It takes the constant pair from `loc_b955`
(A = 0x02, Y = 0x00) into a `loc_df6c` emit, computes the phase `loc_37 & 0x07`
(remapping `0x07` to `0x00`) into `loc_9e`, emits the tagged pair through
`loc_df4c(0x08, phase)` and `loc_df4a(0x00)`, and re-selects the base pointer with
`loc_b967` for a closing `loc_df39`. After the last slot it swaps cursors once more
with `loc_b944`, emits `loc_df6a(0x01)`, writes the fixed body byte `0xc0` at the
cursor origin through `loc_df09`, and returns after a final `loc_b944` cursor swap.

## Object-record projection and emission helpers

These routines turn game-object state and per-lane tube geometry into the stream of four-byte draw records that fills the AVG vector display RAM (0x2000-0x2FFF). Nearly every one writes through the shared draw cursor held in `loc_74`/`loc_75` (with the running byte offset kept in `loc_a9`), leans on the math-box projection driver `loc_c098` to turn world coordinates into on-screen deltas, and hands the actual word writes to a family of vector-word emitters: `loc_df4c`/`loc_df6c` (emit one word whose second byte is OR-tagged with the 0x60 / 0x70 header bits), `loc_df39` (a coordinate word with the high nibble tagged 0xa0 and the low byte rotated), `loc_df75` (widen two bytes ×4 with sign extension into `loc_6e`-`loc_71` then emit), `loc_df57`/`loc_df5f` (store a word at the cursor and step it two bytes forward), `loc_df6a` (a 0x70-tagged word with a zero data byte), and `loc_df09` (drop the fixed 0xc0 body byte at the cursor origin). The header primitive `loc_c765` lays the fixed {0x00,0x71} word ahead of a draw, and the object-render helpers `loc_ab14`/`loc_ab17`/`loc_ab0d`/`loc_a8b4` copy indexed stroke-point pairs out of the glyph/shape table at 0x31e4 into the buffer. The draw color/mode index for a record is staged in `loc_9e` and the per-record header/color byte in `loc_73`.

### The tube-wall segment builder — loc_bda0 / loc_bdcb

`loc_bda0` [seen] is the full entry for drawing one tube-wall segment between two adjacent lane corners. It stashes the caller's record count in `loc_36`, reads the source corner's rim-vertex coordinates from the per-lane geometry tables `loc_3ce` (X) and `loc_3de` (Y) at index `y` into `loc_56`/`loc_58`, copies the working depth `loc_57` into `loc_2f`, then reads the next corner `(y+1)&0x0f` into `loc_2e`/`loc_30`; it seeds the run counters `loc_59`=0x00 / `loc_5a`=0x04 and falls into the shared builder `loc_bdcb` with the corner index from `loc_36`. `loc_bdcb` (also entered directly by the enemy-slot targets below) first gates: unless the active flag `loc_5b` bit7 is set it bails when the working depth `loc_57` is nearer than the reference depth `loc_5f`. It then reads the segment's record count into `loc_99` and a starting table index into `loc_38` from ROM tables `loc_bfb6`/`loc_bfc4` indexed by the corner, projects both endpoints through `loc_c098` (once per endpoint, framing each with `loc_df4c`/`loc_c765` and copying `loc_2e`/`loc_2f`/`loc_30` into `loc_56`/`loc_57`/`loc_58` between the two projections, closing with `loc_df6c`). From the two projected points it forms two clamped signed 16-bit deltas — `loc_61`-`loc_6a` into magnitude `loc_79` with sign high byte `loc_9b`, and `loc_63`-`loc_6c` into `loc_89`/`loc_9d`, each magnitude pinned to 0xff when the high byte is nonzero (and, when the high byte is exactly 0xff, taken as the two's-complement magnitude). It then expands those two deltas into two parallel multi-byte accumulator chains (`loc_82`-`loc_87` from `loc_79`, `loc_92`-`loc_97` from `loc_89`) that hold successive shifted multiples of each delta — the "fivefold spread" used to distribute the segment's stroke across its records. Finally it emits `loc_99` four-byte records: each iteration reads a header byte from `loc_bfd3[loc_38]` (a value of 1 promoted to 0xc0) into `loc_73` and a packed corner byte from `loc_bfd2[loc_38]` into `loc_2d`, advances `loc_38` by two, doubles the packed byte to split out a low index (`packed & 0x07`) and a high index (`(dbl>>4) & 0x07`), and combines the spread offsets `loc_78`/`loc_80`/`loc_88`/`loc_90` — negating each contribution according to the XOR of the packed sign bit with `loc_9b` / `loc_9d` — into a rotated point pair (`loc_61`/`loc_62`, `loc_63`/`loc_64`). Each record writes those two coordinate words (high bytes masked to 0x1f, the fourth byte OR'd with the record header `loc_73`) at the cursor base `loc_74`+`loc_a9`, and the run ends with `loc_df5f` advancing the cursor past the whole block.

### The enemy-slot draw dispatcher — loc_b5d7 / loc_b5eb / loc_b71b

`loc_b5d7` [code] is the spine computed-jump dispatcher: the caller passes A as a byte offset (0,2,4,6,8) and it indexes `TABLE[A>>1]` over `[loc_b5eb, loc_b71b, loc_b60f, loc_b622, loc_b69b]` (ROM table at 0xb5e1), tail-returning the selected draw handler's result. ## The mathbox: projection and level tables

This subsystem turns the abstract level geometry — a selector into a bank of ROM shape tables — into the concrete per-lane screen coordinates the vector generator draws, using the board's hardware math coprocessor (the "mathbox") mapped into the `0x6080`-`0x6096` register block with its busy/status flag at `loc_6040` and its result ports at `loc_6060`/`loc_6070`. The flow runs outside-in: a level index selects packed ROM tables, those tables seed a set of per-lane base-coordinate arrays, and every lane vertex is then pushed through the coprocessor to be projected down the perspective tube.

**Priming the coprocessor.** `loc_c1c3` [seen] is the reset that a projection pass starts from. It zeroes a handful of zero-page scratch cells (`loc_78`, `loc_80`, `loc_81`, `loc_88`, `loc_90`, `loc_91`) and clears the mathbox input block: `loc_6080`, `loc_6081`, `loc_6083`, `loc_6084`, `loc_6085`, `loc_6086`, `loc_6087`, `loc_6089`, `loc_608d`, `loc_608e`, `loc_608f`, `loc_6090`, and finally writes the control byte `loc_608c = 0x0f`. It deliberately leaves `loc_6082`, `loc_6088`, `loc_608a`, and `loc_608b` untouched. In this capture every observed transition through the routine was a constant one (each target cell already held zero, and `loc_608c` went `0x0f`->`0x0f`), so the tag rests on the writes firing at their sites rather than on any value actually changing.

**The projection driver.** `loc_c098` [seen] is the per-point workhorse that feeds one coordinate through the coprocessor and folds its two 16-bit results into a pair of saturating accumulators. It first forms a 16-bit signed difference: the low byte `loc_57 - loc_5f` goes to `loc_6095`, and the high byte `(0 - loc_5b - (1 - carry))` to `loc_6096`; when that high byte comes out negative (bit 7 set) the whole delta is clamped up to `+1` by forcing `loc_6096 = 0x00`, `loc_6095 = 0x01`. It then computes the two magnitudes the mathbox needs: `|loc_58 - loc_60|` written to both input ports `loc_608e` and `loc_6094` with its sign recorded in `loc_33`, and `|loc_56 - loc_5e|` stashed in `loc_32` with its sign in `loc_34`. It spins on `loc_6040 & 0x80` until the coprocessor drops its busy bit, then reads the first result pair `loc_6060 -> loc_63` and `loc_6070 -> loc_64`. It re-issues the `loc_32` magnitude to `loc_608e`/`loc_6094`, and — gated on the `loc_33` sign flag — either subtracts or adds the `{loc_68, loc_69}` offset pair into the `{loc_63, loc_64}` accumulator, saturating a subtract underflow to `0x8000` (`loc_63 = 0x00`, `loc_64 = 0x80` — the signed 16-bit minimum) and an add overflow to `0x7fff` (`loc_63 = 0xff`, `loc_64 = 0x7f`). After a second busy-wait it reads `loc_6060 -> loc_61`, `loc_6070 -> loc_62`, and gated on the `loc_34` sign folds the `{loc_66, loc_67}` pair into `{loc_61, loc_62}` with the same saturation. The net effect is two projected signed 16-bit accumulators — `loc_61:loc_62` and `loc_63:loc_64` — one per axis of the projected vertex.

**Snapping an operand to reference.** `loc_c453` [seen] is a small guard that conditions one of the mathbox coordinate operands before projection. If the guard `loc_5b` is nonzero it returns untouched; if `loc_57` already sits `0x0c` or more above the reference `loc_5f` it also returns; otherwise it snaps `loc_57` up to `loc_5f + 0x0f`, capped at a ceiling of `0xf0`. Because `loc_57`, `loc_5b`, and `loc_5f` are exactly the coordinate operands `loc_c098` differences, this nudge pulls a lagging coordinate up close to its reference before the projection reads it.

**Projecting a whole level's lanes.** `loc_c473` [seen] drives `loc_c098` across all sixteen lanes to fill the per-lane screen-coordinate tables. It takes the incoming `a` into `loc_57` and `x` into `loc_38`, zeroes a clamp tally in `loc_59`, and counts the loop down from `loc_37 = 0x0f`. On each pass it loads the lane's base coordinates from the geometry tables — `loc_3ce + loc_37` into `loc_56` and `loc_3de + loc_37` into `loc_58` — projects them through `loc_c098`, then clamps each of the two projected results (the accumulator high byte `loc_62` with companion `loc_61`, and `loc_64` with `loc_63`) into the signed window `[-4..+3]`, i.e. `0xfc..0x03`: a negative value below `0xfc` snaps to `0xfc` (sign byte `0x01`), a value at or above `0x04` snaps to `0x03` (sign byte `0xff`), and anything inside passes through with its own sign byte. Each clamp bumps `loc_59`. The clamped value/sign pairs are written into the four slot-coordinate tables indexed by `loc_38`: `loc_31a` and `loc_32a` from the first pair, `loc_33a` and `loc_34a` from the second. `loc_38` counts down alongside `loc_37`, the loop ends when `loc_37` wraps past zero, and the clamp count in `loc_59` is handed back — these four tables are the near-rim lane vertices the rest of the renderer consumes.

**Packing a table index.** `loc_c2e8` [seen] is a shared reducer that turns a raw value into a packed table byte. It closes by inlining the same nibble-unpack that `loc_c196` performs: clamp `loc_9f & 0x70` to `0x5f`, halve and force the low bits to `(sel >> 1) | 0x07`, then walk eight entries down from `loc_c1fd`, splitting each packed byte's low nibble into `loc_19 + y`/`loc_800 + y` and high nibble into `loc_21 + y`/`loc_808 + y`.

**Emitting the tube outline.** `loc_c4e1` [seen] turns the geometry tables into the actual vector segments drawn on screen for one tube shape. It reduces its input through `loc_c2e8`, keeping the reduced byte in `loc_36` and the quotient in `loc_35`, clears `loc_73` and emits a framing record via the vector emitter with header `0x05`. From `loc_35 & 0x07` it indexes the ROM header table `loc_c22d`, stores that header in `loc_9e`, and emits it (tagged `0x08`). Taking the shape index `loc_112`, it seeds a walk over the vertex tables at `loc_b97c` (X) and `loc_ba7c` (Y) — the same tables `loc_c235` seeds its base coordinates from — decrementing the seed by `0x0f` when `bccc[shape]` is zero. It reads the first vertex `firstX = b97c[seed]` into `loc_56` and `firstY = ba7c[seed]` into `loc_57` and emits it with both coordinates XOR'd by `0x80` (recentered) as the pen-move to the start. It then raises `loc_73 = 0xc0`, sets the step count `loc_38 = 0x0f`, and loops: each pass reads the next vertex from `b97c[loc_36]`/`ba7c[loc_36]`, computes the delta from the previous position (`dx`, `dy`), updates `loc_56`/`loc_57`, and emits that segment; `loc_36` and `loc_38` count down and the loop ends when `loc_38` wraps past zero (>= `0x80`). A final framing record with header `0x01` closes the shape. This is the routine that actually draws the tube's perimeter as a chain of relative vector moves.

**A mode-flag/scale side helper.** `loc_ca48` [code] sits at the edge of this subsystem, setting a flag bit and a paired count from two zero-page gates. It defaults to `(a, y) = (0x00, 0x10)` and only when both `loc_117 != 0` and `loc_3d != 0` selects the alternate `(0x04, 0x08)`. It then copies bit 2 of the chosen `a` into `loc_a1` while preserving the byte's other bits (`loc_a1 = ((a ^ loc_a1) & 0x04) ^ loc_a1`) and stores `y` into `loc_b4`. In the capture only the default branch ran, so both writes landed as constant no-ops (`loc_a1` `0x03`->`0x03` with bit 2 staying clear, `loc_b4` `0x10`->`0x10`) and the alternate `a = 0x04` path was never exercised — hence the code tag despite the writes firing.

## Sound, POKEY and the interrupt heartbeat

The audio machine runs on two hardware POKEYs, mapped into the register banks at `loc_60c0` (POKEY 1) and `loc_60d0` (POKEY 2), and is driven from the frame interrupt. On every interrupt the handler reads the raw control port `loc_0c00` into `loc_8`, then immediately runs the counter stepper `loc_cf24` followed by the voice engine `loc_cd0a` — so the two routines below beat once per frame, back to back, as the game's heartbeat.

### The gated counters — loc_cf24

`loc_cf24` [seen] is entered from the interrupt path each frame. It walks three parallel lanes with the index `x` running `2 -> 0`, and each lane is armed by a distinct bit of the control byte `loc_8`: the lane at `x=2` tests bit 0, the lane at `x=1` tests bit 1, and the lane at `x=0` tests bit 2 (the routine shifts `loc_8` right a different number of times per lane to land the tested bit into carry). Each lane owns a position cell in the `loc_d`/`loc_e`/`loc_f` triple, a timer in the `loc_10` triple, and an event counter in the `loc_13` triple. When a lane's control bit is clear it advances the position (`loc_d + x`, masked to its low five bits) either downward through the small-step path or upward by `0x20`, wrapping and clamping so the value stays inside `0x00..0x1f` — the write at `0x20 -> 0x1f` is the observed wrap. A shared reload cell `loc_c` is preset to `0xf0` whenever `loc_8` bit 3 is clear; while it is still counting down (nonzero) it blanks that lane's position (`loc_d + x`) and timer (`loc_10 + x`) on every frame, and the blanking stops once it reaches zero. When a lane's timer `loc_10 + x` runs out it raises a carry that lets the lane contribute to the running accumulators.

That contribution is small and gated by `loc_9`: lane 0 contributes `0`; lane 1 contributes `0x01` only when `loc_9` bit 4 is set; lane 2 contributes `((loc_9 & 0x0c) >> 2) + 2 + carry`, where the `loc_9` bits merely *gate and index* the term rather than being added directly, and `carry` here is bit 2 of `loc_9`. Whatever the lane yields is folded into the position/score accumulators `loc_16` and `loc_17` (each with a `+1`), and the lane's event counter `loc_13 + x` is bumped. After all three lanes, the routine indexes a ROM table at `loc_cfd9` by `loc_9 >> 5`, subtracts that entry from `loc_16`, and on certain outcomes steps the carry counters `loc_18` and `loc_6`. It closes with two clamp passes over the `loc_13` lane triple that subtract *different* constants: the first pass subtracts `0x10` and only touches lanes whose value is already `>= 0x10`, while the second pass subtracts `0x11` and only touches lanes whose value is nonzero. The dense branch web of the lane update is walked block by block, tracking the running carry explicitly.

### The sound-request path — trampolines, the enable gate, and the registrar

A sound is requested by loading a fixed id and passing it through a gate into a shared registrar. The gate is `loc_ccc3` [code]: it tests bit 7 of the enable flag `loc_5` and, only when that high bit is set, forwards the id (with the caller's `X`/`Y`) into the registrar `loc_ccc7`; when the bit is clear it simply returns and the sound is suppressed. A family of one-line fronts each pins a specific id and routes through that gate, carrying the caller's `X`/`Y` so the registrar can restore them: `loc_ccb5` (`0x0f`) [code], `loc_ccc1` (`0x1f`) [code], `loc_ccea` (`0x2f`) [code], `loc_cd02` (`0x3f`) [code], `loc_ccb9` (`0x4f`) [code], `loc_ccb0` (`0x5f`) [code], `loc_ccee` (`0x6f`) [code], `loc_ccf2` (`0x7f`) [code], `loc_ccbd` (`0x8f`) [code], `loc_ccf6` (`0x9f`) [code], `loc_ccfe` (`0xbf`) [code], and `loc_cd06` (`0xcf`) [code]. Every id shares the low nibble `0xf`, so the high nibble is what selects the sound. `loc_ccfa` (`0xaf`) [code] is the odd one out: it skips the enable gate and jumps straight into the registrar. All of these carry the `[code]` tag because their own bodies write no cell — the effect is entirely the registrar's, and a write-only trace cannot attribute a specific trampoline's reach; their shared consumer `loc_ccc7`, however, is `[seen]`.

`loc_ccc7` [seen] is the registrar that turns an id into claimed voice slots. It first saves the caller's `X`/`Y` into `loc_31`/`loc_32`, then sweeps sixteen slots with the index running `0x0f -> 0`, decrementing the id each step so it reads a descending column of the sound table at `loc_cb01`. For every nonzero table byte it claims that slot: it writes the slot index into the scratch `loc_bf`, stores the table byte as the slot's frame value at `loc_c0 + slot`, arms both of the slot's timers by writing `0x01` to `loc_e0 + slot` and `loc_f0 + slot`, and then restores `loc_bf` to the `0xff` sentinel. Those armed slots are what the per-frame engine picks up next.

### The per-frame voice engine — loc_cd0a

`loc_cd0a` [seen] runs immediately after `loc_cf24` on each interrupt and advances all sixteen voice slots, index `0x0f -> 0`. It skips any slot whose frame value `loc_c0 + x` is zero (idle) and skips the slot currently reserved in `loc_bf`. For a live slot it counts down the fast timer `loc_e0 + x`; while that is still running it moves on. When the fast timer expires it counts down the slow timer `loc_f0 + x`. If only the fast timer expired, it takes a single animation step: the high bit of the frame value chooses between the ROM table pair at `loc_cbcc`/`loc_cbcd` and the pair at `loc_cccc`/`loc_cccd`, indexed by the frame value doubled; it reloads the fast timer from the table and adds the table's amplitude byte to the running level `loc_d0 + x`, with odd slots preserving the previous high nibble of that level byte. If both timers expire together, it walks the frame forward two at a time — reading from `loc_cbcb`/`loc_cbce`/`loc_cbcc` or `loc_cccb`/`loc_ccce`/`loc_cccc` by the same high-bit selector — until a nonzero frame lands. Finally it publishes the slot's level `loc_d0 + x` to hardware: slots `x < 0x08` write POKEY 1 at `loc_60c0 + x`, and slots `0x08..0x0f` write POKEY 2 at `loc_60c8 + x` (i.e. `loc_60d0..loc_60d7`). So the sixteen software slots map one-to-one onto the two POKEYs' audio registers.

### POKEY reset and the RANDOM self-test — loc_cd95

`loc_cd95` [seen] is the textbook dual-POKEY reset. It first zeroes both SKCTL registers (`loc_60cf`, `loc_60df`) and clears the flag `loc_720`. It then samples both POKEYs' RANDOM registers, `loc_60ca` and `loc_60da`, once and re-reads them across a five-pass poll (`x = 4 -> 0`); if either RANDOM register has changed value it latches the first sample into `loc_720` and stops — a working-random self-test. Next it writes the canonical init value `7` into both SKCTL registers, then sweeps `x = 7 -> 0` zeroing the paired audio arrays `loc_60c0 + x`/`loc_60d0 + x` alongside the software frame/level arrays `loc_c0 + x`/`loc_d0 + x`. It closes by clearing both AUDCTL registers, `loc_60c8` and `loc_60d8`, to zero.

### POKEY-port packing and configuration decode — loc_dbe0, loc_d6bb

`loc_dbe0` [code] is a small bit-packer that reads the POKEY input side. It stores its incoming byte into `loc_60db`, takes the low three bits of `loc_60d8`, mirrors *only* those three bits into the scratch `loc_37` and into `loc_60cb`, and returns those three bits merged with one relocated bit — bit 5 of `loc_60c8` shifted down to bit 3 (`(loc_60c8 & 0x20) >> 2`). It is reached, but every observed write is a constant (`loc_60cb = 0`, `loc_37 = 0`, `loc_60db = 0xd0`), so the packing role itself was never witnessed varying — hence `[code]`.

`loc_d6bb` [seen] is the configuration decoder that feeds that packer. It reads the option-switch port `loc_e00` into `loc_a`, then slices it three ways through ROM tables: the port's bits 5-3 index `loc_d6f7` into `loc_156`, its bits 7-6 index `loc_d6ff` into `loc_158`, and its bits 2-1 (as an even offset `a0 & 0x06`) index the paired tables `loc_d6b3`/`loc_d6b4` into `loc_ac`/`loc_ad`. It also writes `loc_9 = loc_d00 ^ 0x02`, folding the coin/switch port through an inversion — and this is the same `loc_9` that `loc_cf24` later reads to shape its lane accumulators. Finally it hands the `loc_d6b4` result through `loc_dbe0` and records the packed nibble in `loc_16a`.

### The math-box result fetch — loc_dce6

`loc_dce6` [code] is not part of the audio chain and was not reached in the capture (no PC in its body appears in the trace). It primes a hardware coprocessor's operand and count registers — clearing `loc_73` and `loc_414`, storing its `A` operand into `loc_608e` and its `X` operand into `loc_608f`, zeroing `loc_6090`, and loading the count `0x10` into both `loc_608c` and `loc_6094` — then scans a sixteen-step window (`x` from `0x10` downward) over the slot table at `loc_6040`, skipping any slot whose high bit marks it still busy, and hands back the first ready slot's low byte from `loc_6060` and high byte from `loc_6070`. If the counter runs past the end it exits with `x` gone negative. Because it never executed here, its result-fetch role rests on the code, not on any observed write.

### Record sort and active-slot tick — loc_ac3f, loc_ad6e

`loc_ac3f` [seen] is the per-pass record sort. It clears bit 6 of the shared flag `loc_5` (the same byte whose bit 7 the sound gate reads), optionally pre-clears a scratch block, and then for each of two record banks (channel `0` or `3`, chosen from `loc_3e`) bubble-sorts the key triple held in `loc_620`/`loc_61f`/`loc_61e` — comparing lexicographically against the working triple in `loc_2c`/`loc_2d`/`loc_2e`, carrying the parallel payload in the `loc_520` row when the cursor is high enough, and stepping the row cursor down by two (or three while still above `0x55`). It counts the passes each bank takes to settle into `loc_605`, records that per-bank count into `loc_600`, and nudges the running total `loc_601` upward when it has caught up and is still below `0x63`. From the flag byte `loc_3d` it derives a packed request byte into `loc_603` (`(((flag ^ 0x01) << 2) | flag) + 0x05 + bit6-of-flag`), then hands off to the request walker `loc_ad22`.

`loc_ad6e` [code] is the active-slot tick and was not exercised in this capture (no PC in its body appears in the write trace). By the code it sets `loc_1 = 0x06`, and while the frame countdown `loc_3` (low five bits) is idle it expires the `loc_605` counter, resetting `loc_00` to `0x14` when it reaches zero. Otherwise it clamps the active slot's value at `loc_606 + slot` (via `loc_adce`) into the `0x00..0x1a` rail, gates on bits 3-4 of `loc_4e` (clearing them to `loc_4e & 0x67`), and — when the gate is set — steps the two counters `loc_602` and `loc_604`, re-arming through `loc_ddf7`/`loc_ad22` when the step goes negative (and only when `loc_600` for the current `loc_3d` index is below `0x04`), or else blanking the retired slot at `loc_606 + (slot - 1)`.

## The EAROM high-score store

The cabinet keeps its high-score table in non-volatile EAROM, and a small family of routines drives the serial read/write protocol against it. The persistent surface is a three-cell request queue plus a block of scratch registers: `loc_1c7` holds one pending-region bit per storage block, `loc_1c8` holds the matching per-region direction (a set bit means *write out*, a clear bit means *read back*), and `loc_1c6` is a blank-mode/index byte that, when non-zero, tells the transfer engine to zero each source RAM cell as it is written out. Everything downstream of those three cells is bookkeeping for the walk: `loc_1ca` the live mode byte, `loc_1ce` the single walking-bit selector, `loc_1cb`/`loc_1cc` the pass and byte cursors, `loc_1cd` the per-region end index, `loc_1cf` the running checksum, and `loc_1c9` a per-region failure latch.

Requests are lodged by a small cluster of setters that all funnel into one shared tail. That tail (reached through `loc_ddfb`'s `loc_ddff` body) writes the supplied index byte into `loc_1c6` and OR-folds a region mask into both `loc_1c7` and `loc_1c8`, so a single call arms a region *and* declares its direction as write. `loc_ddfb` [seen] is the fixed mask-4 entry (region bit 2, index 0); `loc_ddfd` lets a caller pass its own mask with a zeroed index; `loc_ddf7` [code] supplies the constant mask 0x03 (regions 0 and 1) through that zeroed-index path; `loc_ddf3` [code] runs the same merge but forces the index byte to 0xff, i.e. requests a write-out in blank mode; and `loc_dde9` [code] is the fixed front that asks for region bit 2 in that blank write mode. `loc_ddf1` [code] is the whole-table commit: it loads mask 0x07 and index 0xff and branches into the shared setter tail, arming all three blocks for a blanked write-out at once — the "save the high-score table and clear the working copy" request. Its own operands are not distinctly observed in the capture (the shared tail PCs carried another entry's mask, not ddf1's 0x07/0xff), so the role rests on the code.

The two directions of the transfer are opened from opposite ends. `loc_de11` [seen] is the load side: it *sets* (not merges) `loc_1c7` = 0x07 and clears `loc_1c8` = 0x00 — all three regions pending, every direction bit clear, i.e. read all three blocks back from EAROM — then falls straight into the state machine to run the read. This is the distinct "SET, all-read" initiator, separate from the OR-merge family above.

`loc_de1b` [seen] is the state machine itself, and it is heavily exercised. On each entry, if the mode byte `loc_1ca` is idle and `loc_1c7` still carries a pending bit, it opens a fresh region: it clears the pass counter `loc_1cb`, the checksum `loc_1cf`, and the selector `loc_1ce`, then rebuilds `loc_1ce` as a single walking bit. That rebuild rotates the request mask `loc_1c7` *left* through carry while rotating `loc_1ce` right, breaking on the first bit shifted out of the top — so it isolates the **highest** set request bit, never the lowest, and leaves a running bit-position count in `x`. The mode byte `loc_1ca` is then seeded to 0x80 when that same bit is set in the direction mask `loc_1c8` (a write) or 0x20 otherwise (a read), the selected bit is cleared from the pending mask (`loc_1c7 ^= loc_1ce`), and the doubled bit-position indexes the packed ROM tables at `loc_dddd`, `loc_ddde`, `loc_dde3`, `loc_dde4` to load the byte cursor `loc_1cc`, the end index `loc_1cd`, and the 16-bit RAM pointer `loc_bd`/`loc_be` for that region's working copy.

Each pass then services one entry against the memory-mapped EAROM port block. It resets the control port `loc_6040` to 0 and, if the live mode byte `loc_1ca` has gone idle, returns. Otherwise it rotates `loc_1ca` left and branches three ways. When a bit rotates out of the top, that is the address-strobe pass: the rotated mode is written to `loc_6000` + cursor, `loc_1ca` becomes 0x40, and 0x0e is queued to the control port. On a write pass (top bit of the rotated mode set), it reads the source cell through the region pointer — first zeroing that cell when `loc_1c6` blank-mode is armed — and, once the byte cursor reaches the end index `loc_1cd`, closes the region (`loc_1ca` = 0) and substitutes the accumulated checksum `loc_1cf` as the final byte, driving the result out on `loc_6000` + cursor. On a read pass it performs the EAROM read handshake by pulsing `loc_6040` through 0x08 / and strobing `loc_6000` + cursor and reading the data back from `loc_6050`; ordinary bytes are stored through the region pointer, but the final byte is XOR-checked against `loc_1cf`, and a non-zero mismatch walks the region's cells back to zero and OR-marks the failure into `loc_1c9`. Every serviced entry folds its byte into the running checksum `loc_1cf`, bumps both cursors, and writes the queued control value to `loc_6040`; a non-zero control value pauses the machine until the next entry, and a zero value loops it straight into the next pass. The net effect is a byte-serial ER-2055 read/write cycle over the three high-score blocks, with a trailing checksum that both stamps written data and invalidates a block whose read-back does not verify.

The remaining routines grouped here — `loc_db22`, `loc_db84`, `loc_db88`, `loc_db9a`, `loc_db7e`, `loc_db6f`, all [code] — share the `loc_6000`-page I/O but are not part of high-score persistence; they are vector-list and hardware-register machinery, and the code carries no EAROM read/write logic in any of them. `loc_db22` is the broadest overlap: it performs a cold clear of a bank of hardware ports, zeroing `loc_60e0`, `loc_6080`, `loc_60c0`, `loc_60d0`, and incidentally the EAROM data line `loc_6000` and control port `loc_6040`, takes four settling reads (`loc_6040`, `loc_6060`, `loc_6070`, `loc_6050`), re-arms `loc_60e0` = 0x08, then marches a single set bit through the 32-byte table at `loc_6080` before emitting one framing word via `loc_df39` (with header 0x34, 0xa6). The rest are pure display-list emitters that push coordinate/framing words through the vector cursor and blank output tables: `loc_db84` emits a header (0x33, 0x0a) then clears the four even slots of `loc_60c1` and `loc_60d1`; `loc_db88` does the same clear after emitting a caller-supplied header word, with `loc_db7e` priming it (0x32, 0xb6) and `loc_db6f` priming it (0x33, 0x4e) after first emitting a header derived from `loc_50` halved; and `loc_db9a` advances a phase counter `loc_39` (skipped while the frame gate in `loc_3` bits 0–5 is set), indexes the parallel tables `loc_dbd5`/`loc_dbd6`/`loc_dfdc` to seed two `loc_60c0`/`loc_60c1` output cells, and emits three framing words. Their only relationship to the EAROM store is the shared memory-mapped I/O page, and their [code] tags stand — none of these paths were observed carrying a high-score transfer.

## State-reset, init and per-frame update chains

This subsystem is the machine's plumbing for wiping working state to a known baseline, seeding the small parameter block the rest of the game reads, draining the spawn queue into a fresh slot, and then folding per-frame ageing, scoring and control-block maintenance on every pass. The routines split into cold reset leaves, constant seeders, one composite reset cascade, the per-frame update arm, the control-block rebuild chain, and the scoring folds.

### The reset cascade and its leaves

`loc_902b` **[code]** is the composite reset entry: it runs six subsystem clears back to back — `loc_928f`, `loc_926f`, `loc_9246`, `loc_929f`, `loc_92ad`, and `loc_c16e` — and then seeds two bytes high and one clear, writing `loc_124 = 0xff`, `loc_148 = 0xff`, and `loc_123 = 0x00`. Its own role rests on that structure rather than an independently grounded own-write narrative, so it carries [code]; the individual leaves it drives are each separately grounded [seen].

Four of those leaves live in this section. `loc_926f` **[seen]** zeroes the seven-byte array at `loc_2df..loc_2df+6` top-down and then clears seven scattered flag cells — `loc_108`, `loc_109`, `loc_145`, `loc_142`, `loc_144`, `loc_143`, `loc_146` — several of which (`loc_108`, `loc_142`) hold real non-zero values elsewhere, making this a meaningful baseline wipe rather than a no-op. `loc_928f` **[seen]** zeroes the twelve-byte array `loc_2d3..loc_2d3+0x0b` and clears the two flag cells `loc_135` and `loc_a6`. `loc_929f` **[seen]** blanks the eight-byte table `loc_30a..loc_30a+7` and clears the trailing flag `loc_116`. `loc_92ad` **[seen]** is the smallest of the set: a single write of `loc_50 = 0x00`, a genuine reset of a cell that ranges widely elsewhere. `loc_928f` in particular is reused outside the cascade — both the per-frame update arm and the wave-init pull it in to re-clear the twelve-byte block on demand.

### Parameter-block seeders

`loc_921b` **[seen]** seeds five fixed init constants in one straight-line pass: `loc_200 = 0x0e`, `loc_51 = 0xf0`, `loc_106 = 0x00`, `loc_201 = 0x0f`, and `loc_202 = 0x10`. Both `loc_200` and `loc_51` vary elsewhere, so these are real state cells being primed, and `loc_201` here is the same control byte whose sign the per-frame update arm later branches on.

`loc_9234` **[seen]** builds a seventeen-cell block from two source bytes: the header `loc_3ab` takes `loc_15b`, then the sixteen body cells `loc_3ac..loc_3ac+0x0f` are all filled top-down with the single value read from `loc_15a`. In the capture the header source varied (observed draining `0xf` toward `0xc`) while `loc_15a` read zero, so the sixteen-entry body stayed all-zero on those passes; `loc_3ab` is a live cell that is drained toward `0x0` elsewhere. That `loc_3ac` array is exactly the sixteen per-segment table the wave-init and the scoring fold below both read back.

### Per-slot table and scalar resets

Several leaves reset the object/slot tables and re-seed scalars for a fresh mode or spawn. `loc_a7bd` **[seen]** zeroes the eight-byte table `loc_3fe..loc_405`, then overwrites its last slot `loc_405 = 0xf0` and arms the flag `loc_115 = 0xff`; its caller steps the descending spike/pulsar object and runs this once that object crosses a threshold while `loc_115` is still clear. `loc_a831` **[seen]** clears the pair `loc_3aa = 0x00` and `loc_125 = 0x00` — the latter being a latch that other routines raise to `0xff`, so the clear here is role-defining. `loc_ca62` **[seen]** zeroes the six-byte scratch block `loc_40..loc_45`, run as an optional pre-clear by callers that then stage three-byte entries into that block.

`loc_a789` **[code]** is the slot-state reset that the spawn path hands off to: it zeroes the sixteen-byte per-slot table `loc_283..loc_283+0x0f`, then re-seeds `loc_10e = 0x20`, `loc_10d = 0x20`, `loc_1 = 0x04`, and the pair `loc_68 = loc_69 = 0x00`. It was **not reached in the capture** — the `loc_283` cells were only touched elsewhere — so its role rests on the code.

### State-entry constant seeders

Three leaves seed the small zero-page working block `loc_0..loc_4` (plus a few neighbours), each configuring it differently for the state it introduces. `loc_b0e7` **[seen]** writes `loc_0 = 0x0a`, `loc_2 = 0x00`, `loc_4 = 0xdf`, `loc_1 = 0x12`, and the pair `loc_14e = 0x19`, `loc_14d = 0x18`. `loc_c97b` **[seen]** seeds `loc_2 = 0x04`, `loc_1 = 0x00`, `loc_0 = 0x0a`, `loc_4 = 0x14`. `loc_ca18` **[seen]** first masks `loc_5 &= 0x3f` (dropping the top two flag bits) and then seeds `loc_3e = 0x00`, `loc_2 = 0x1a`, `loc_0 = 0x0a`, `loc_4 = 0xa0`, `loc_16b = 0x01`, `loc_1 = 0x0a`. Each is a computed-dispatch target with no static caller; together they show `loc_0..loc_4` acting as a shared step/mode parameter block that whichever state is entering rewrites to its own constants.

### Wave-init and slot-spawn drain

`loc_a5cb` **[seen]** initialises wave state and tallies the occupied segments. It sets `loc_0 = 0x20`, ORs bit 7 into `loc_106`, clears `loc_104`, `loc_107`, `loc_5c` and `loc_123`, and sets `loc_105 = 0x02`. It then walks the sixteen-entry `loc_3ac` table and counts how many entries are nonzero into `loc_123` (grounded rising `0x0` toward `0x6` — six spiked/occupied segments). If any are occupied and the level cell `loc_9f` is below `0x07`, it loads an intro/param block — `loc_4 = 0x1e`, `loc_0 = 0x0a`, `loc_2 = 0x20`, `loc_123 = 0x80` — and finally always marks the block ready with `loc_125 = 0xff`.

### The per-frame update arm

## Utilities and shared tails

This subsystem gathers the small register-and-memory helpers the larger machinery leans on: a binary-to-BCD converter that feeds the on-screen number display, a request-flag setter for the geometry-rebuild bookkeeping, a couple of table-shuffling seeders, a byte-splitter used by the tube-position math, a constant-return leaf, and the several bare return leaves and dispatch stubs that other routines branch into as shared tails.

**loc_aaf5** *[seen]* is the machine's binary-to-decimal converter, driving the numeric readouts (scores, counters) that are ultimately drawn as vector digits. It runs the classic double-dabble over the incoming byte in A: eight passes, each shifting the top bit out of the source (`shifted << 1`, carrying bit 7) and doubling a decimal-mode BCD accumulator with that bit folded in (the `bcdDouble` helper handles the low-nibble +6 and high-nibble +0x60 decimal corrections). The finished packed-BCD value is stored to **loc_29** *and* to **loc_2c** — the same byte lands in both, so both cells range 0x00..0x99. Its role writes to loc_29 and loc_2c are observed in the capture. It is reached through **loc_af77**, which runs the conversion and then walks the single zeropage byte out as nibbles via loc_dfb1.

**loc_af71** *[code]* is the front the display path calls to bound a value before showing it: it clamps its input to a maximum of 0x63 (`min(a, 0x63)`) and hands the clamped byte straight to loc_af77, which packs it through loc_aaf5 and emits it. The clamp is the only work of its own; no cell write grounds it, hence the [code] tag.

**loc_ac36** *[seen]* raises both pending geometry-rebuild requests. It ORs 0x03 into the request-flags cell **loc_1c9** (setting bits 0 and 1) and returns the merged value; the write to loc_1c9 is observed, carrying value 0x7 where a third flag bit was already present. It sits at the mismatch tail of the snapshot-check path — loc_ac20 falls into it when the live control-panel geometry state no longer matches its cached latch, and loc_abac reaches it likewise — after which the rebuild consumers act on bit 0 and bit 1 to rebuild the two control-block regions. On the no-change side those same callers instead fall through to the shared empty return at loc_ac3e.

**loc_ac3e** *[code]* is that shared return leaf: a lone RTS with no memory effect. loc_ac20 branches here when its two comparisons (`loc_0a & 0xf8` vs cached loc_71e, and `loc_16a & 3` vs cached loc_71f) both already match the latch and no rebuild is needed. Nothing writes, so it stays [code].

**loc_ac07** *[code]* is a sibling no-op return leaf. loc_aba2 tail-branches into it when `loc_1c9 & 3 == 0` — the request-flags are clear, so there is nothing to rebuild and the routine simply unwinds. No role-defining write exists to ground it.

**loc_af6e** *[code]* is the exposed RTS tail of the draw routine loc_af3f. Its caller loc_af26 branches here when `loc_600 | loc_601 == 0` — both draw slots empty, nothing to draw — so control returns without touching memory. [code], no write to ground.

**loc_9bcf** *[code]* is a do-nothing dispatch slot: a single bare RTS occupying an entry in a computed-jump table. Selecting it lets the caller's own return unwind immediately, i.e. it is the "this index does nothing" handler. Being a pure return with no side effect, it produces no write and cannot be confirmed reached from a write-tap.

**loc_b955** *[code]* is a register-only leaf that always returns the constant pair A = 2, Y = 0, touching no memory. It reads no state that survives — a naive reading of the underlying code (which reads loc_57, shifts, and runs a bit-counting loop) looks like a log2/popcount of loc_57, but the loop's result is discarded: the tail clears A and adds 2, and reloads Y with 0, so the output is fixed regardless of loc_57. It is a constant-return helper, not a bit-count.

**loc_93e0** *[seen]* splits a byte into a fine value and a coarse table index for the tube-position math, and is driven exclusively from loc_92c5's three call sites. It folds A's top three bits (MSB first) into the low bits of a 0xff seed across three left-shift passes: the seed accumulator ends as `0xf8 | (top-three-bit value)` and is stored to **loc_29** — its one observed role write (the 0xff seed set, then rotated). Only loc_29 is a memory write; A/X/Y are register outputs, so grounding rests on the loc_29 write plus the reach through loc_92c5.

Its two swap-store PCs never fire in the capture, so the routine was not reached; loc_3aa/loc_3bc appear in the trace only as constant 0 at unrelated points. **loc_b85f** *[code]* seeds two paired three-entry arrays with the fixed constants 0, 4, and 12: it writes 0x0c to loc_80b and loc_24, 0x04 to loc_80a and loc_23, and 0x00 to loc_809 and loc_22, then returns.
